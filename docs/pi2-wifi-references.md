# RTL8188CU USB Wi-Fi port references

Research for USB `0bda:8176` (Realtek RTL8188CU 1x1 dongle), focused on a Raspberry Pi 2B bare-metal port.

## Recommended driver base

Use OpenBSD `urtwn` as the behavioral reference and port the RTL8192C/RTL8188C path into gabix's USB and network abstractions. OpenBSD documents RTL8188CU support, infrastructure association, WPA2-PSK, and its firmware dependencies in [`urtwn(4)`](https://man.openbsd.org/urtwn). Its shared `rtwn` core and USB transport are [permissively licensed](https://raw.githubusercontent.com/openbsd/src/master/sys/dev/ic/rtwn.c) and [permissively licensed](https://raw.githubusercontent.com/openbsd/src/master/sys/dev/usb/if_urtwn.c) with ISC-style terms in their source headers. Preserve each file's copyright and license notice when porting.

The current OpenBSD USB table supports many RTL8188CU OEM IDs, although its `if_urtwn.c` table does not list Realtek `0bda:8176` directly. Add this ID using the existing 8192C/8188C chip flags after confirming the target adapter's descriptors. Linux's primary `rtl8192cu` source explicitly maps `0x0bda:0x8176` as an 8188CU 1x1 dongle in [`sw.c`](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/realtek/rtlwifi/rtl8192cu/sw.c).

The OpenBSD transport's porting seams are especially useful: it opens one bulk-IN endpoint and one to three bulk-OUT endpoints, routes register reads/writes and firmware-page writes through bus callbacks, then connects the transport to a bus-independent `rtwn` core ([`if_urtwn.c`](https://raw.githubusercontent.com/openbsd/src/master/sys/dev/usb/if_urtwn.c), especially attach and endpoint setup). In the shared core, initialization order is allocate buffers → power on → DMA → MAC/BB/RF setup → calibrations; it loads 8051 microcode after DMA and the preceding MAC queue/beacon setup, immediately before MAC/BB/RF initialization ([`rtwn_init`](https://raw.githubusercontent.com/openbsd/src/master/sys/dev/ic/rtwn.c)). The RTL8192C path selects `urtwn-rtl8192cT` or `urtwn-rtl8192cU` for UMC A-cut and writes firmware pages through the MCU firmware window ([firmware selection and download](https://raw.githubusercontent.com/openbsd/src/master/sys/dev/usb/if_urtwn.c)). The matching OpenBSD manual names the firmware files and says WPA2-PSK is supported.

For comparison, Linux `rtl8192cu` also supports the exact USB ID and chooses among `rtl8192cufw_A.bin`, `_B.bin`, or `_TMSC.bin` by chip cut ([`sw.c`](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/realtek/rtlwifi/rtl8192cu/sw.c)). That driver is GPL-2.0, so it is useful as a register/firmware cross-check but is a less suitable code base for gabix's permissive-source goal.

## WPA2 and reusable code

`urtwn(4)` handles the WPA2-PSK association/key path with OpenBSD's 802.11 stack; its manual says WPA-Enterprise needs `wpa_supplicant`. In gabix, expect to implement a small station-mode control path: scan/beacon parsing, open-system authentication, association, EAPOL-Key four-way handshake, pairwise/group key installation, then Ethernet/IP handoff. WPA2-PSK requires PBKDF2-HMAC-SHA1 to derive the PMK, the EAPOL-Key state machine/PTK derivation, and CCMP AES-CCM data protection. The driver and supplicant responsibilities must meet at a clear raw 802.11/EAPOL and key-install interface.

Circle's [`addon/wlan`](https://github.com/rsta2/circle/tree/master/addon/wlan) is useful as a bare-metal integration example: Circle says it uses a Plan 9 WLAN driver and `wpa_supplicant`, and its changelog records a port of `wpa_supplicant` v2.11. Its wireless hardware path targets Raspberry Pi's built-in Broadcom WLAN, not this USB Realtek adapter ([Circle overview](https://github.com/rsta2/circle), [addon listing](https://github.com/rsta2/circle/blob/master/addon/README)). The supplicant can inform the EAPOL/WPA state machine integration, but its C and platform glue require a substantial adaptation for gabix.

There is no verified drop-in Rust `no_std` WPA2 station supplicant in these references. The Rust crate [`supplicant-rs`](https://docs.rs/supplicant-rs/latest/supplicant_rs/) advertises WPA2, but its architecture uses Linux `nl80211` netlink and is therefore not directly usable on bare metal. `no_std` Rust cryptographic primitives can supply pieces; for WPA2-PSK the needed set includes SHA-1, HMAC, PBKDF2, AES-CCM, and AES key wrapping where required. Gabix still needs its own 802.11/EAPOL state machine and hardware key handoff.

## Suggested implementation order

1. Add USB match for `0bda:8176`; enumerate interfaces/endpoints and validate control-register transfers.
2. Read chip identity, efuse/MAC/calibration data, power on, load the RTL8192C firmware, initialize LLT/DMA and MAC/baseband/RF, then receive/transmit raw frames.
3. Add passive scan and open-network association; capture/replay known-good 802.11 management and data frames.
4. Add WPA2-PSK EAPOL four-way handshake and CCMP/key programming; only then connect the station interface to DHCP/IP.

Keep firmware provenance separate from driver licensing. OpenBSD's manual identifies firmware names, while Linux requests firmware files under `rtlwifi/`; confirm redistribution and provenance for any binary copied into gabix before checking one in.

## DWC2 control-transfer reliability references

### FIFO partition on the BCM2836

For the observed `GHWCFG3=0x0ff000e8`, Linux's `GHWCFG3_DFIFO_DEPTH` field is bits 31:16, so the implemented shared FIFO RAM is `0x0ff0` = 4080 32-bit words. Decode `GRXFSIZ` as RX depth in its low 16 bits; decode `GNPTXFSIZ` and `HPTXFSIZ` as depth in bits 31:16 and start offset in bits 15:0. The old values `GRXFSIZ=0x1000`, `GNPTXFSIZ=0x01001000`, `HPTXFSIZ=0x02002000` allocate RX depth 4096 at zero, NPTX depth 256 starting at 4096, and PTX depth 512 starting at 8192. RX alone exceeds the reported total; both TX ranges also begin beyond it. Linux's host FIFO sizing uses exactly these depth/start fields and derives `total_fifo_size` from `GHWCFG3.DFIFO_DEPTH` ([`params.c`](https://github.com/torvalds/linux/blob/master/drivers/usb/dwc2/params.c), [`hw.h`](https://github.com/torvalds/linux/blob/master/drivers/usb/dwc2/hw.h)).

Circle's current bare-metal DWC2 host driver explicitly reprograms RX, non-periodic TX, and periodic TX to 1024 words each. It sets starts at 0, 1024, and 2048 respectively, flushes all TX FIFOs and RX after writing the partitions, and then powers the root port ([`dwhcidevice.cpp`](https://raw.githubusercontent.com/rsta2/circle/master/lib/usb/dwhcidevice.cpp), `InitHost`, lines 37–40 and 553–568; register offsets and `GHWCFG3.DFIFO_DEPTH` decoding in [`dwhci.h`](https://raw.githubusercontent.com/rsta2/circle/master/include/circle/usb/dwhci.h), lines 86–109 and 126). Circle is GPL-3.0-or-later; use its implementation as a behavioral reference. The proposed 1024/1024/1024 partition occupies 3072 words, below the observed 4080-word capacity, with contiguous non-overlapping regions.

Linux DWC2 host source clarifies NAK behavior in DMA mode. For non-split control/bulk IN, Linux treats NAK as a notification for error-count reset; the controller continues the transfer. NAKs on control/bulk OUT are different: Linux accounts for transferred bytes, saves the DPID toggle from `HCTSIZ`, halts, and resumes from the correct point ([`hcd_intr.c`](https://github.com/torvalds/linux/blob/master/drivers/usb/dwc2/hcd_intr.c), `dwc2_hc_nak_intr`, `dwc2_update_urb_state_abn`, `dwc2_hcd_save_data_toggle`). This makes the current gabix retry strategy risky for multi-packet control OUT: on a NAK or transaction error, `transfer()` retries the original full buffer with the original PID. Firmware register writes use up to 196-byte control data phases, which can span four 64-byte packets. A mid-transfer retry can replay packets already ACKed by the adapter with a stale DATA toggle. A small first fix is to split control OUT data into one USB packet per DWC2 transfer; the complete implementation should resume from packet count and current PID.

For DMA control/bulk IN, wait for channel completion/halt and preserve the NAK bit as diagnostic state; do not request a halt merely because NAK is set while the channel remains active. The same Linux NAK handler documents that the core continues control/bulk IN after NAK in DMA mode. An IN status containing both `XFERCOMP` and `NAK` should still be interpreted as complete. Linux computes normal-completion IN length from `HCTSIZ.XFERSIZE`, but uses `HCTSIZ.PKTCNT` for transfers halted early because XFERSIZE tracks AHB byte movement rather than USB-ACKed packets ([`hcd_intr.c`](https://github.com/torvalds/linux/blob/master/drivers/usb/dwc2/hcd_intr.c), `dwc2_get_actual_xfer_length`).

Check HCINT bit definitions when interpreting traces: DWC2 has XFERCOMP bit 0, CHHLTD bit 1, STALL bit 3, NAK bit 4, ACK bit 5. Therefore `HCINT=0x23` means XFERCOMP+CHHLTD+ACK; it does not contain NAK. The gabix constants use these standard positions in [`usb.rs`](../targets/armv7/src/raspi2b/usb.rs). Linux's channel completion path gives XFERCOMP precedence over other latched status bits ([`hcd_intr.c`](https://github.com/torvalds/linux/blob/master/drivers/usb/dwc2/hcd_intr.c), `dwc2_hc_chhltd_intr_dma`).

## First transmit setup: RTL8188CU IQK and CCK 1 Mbps

The current receiver setup performs LC calibration but omits IQ calibration and per-channel transmit-power programming. OpenBSD's 8188CU/8192CU sequence runs IQK after firmware, MAC/BB/RF setup, enables CCK/OFDM, enables security and hardware sequence numbering, then runs LC calibration; it subsequently sets default channel through `rtwn_set_chan`, which calls `rtwn_set_txpower` before RF channel programming ([`rtwn_init`](https://github.com/openbsd/src/blob/master/sys/dev/ic/rtwn.c#L3085), [`rtwn_set_chan`](https://github.com/openbsd/src/blob/master/sys/dev/ic/rtwn.c#L2264)). The source carries ISC-style permission terms.

For the single transmit chain, IQK in `rtwn_iq_calib_run` uses the RTL8192C ADDA pattern `0x0b1b25a0` for 0x85c and `0x0bdb25a0` for the other 15 ADDA registers (0xe6c–0xeec); it snapshots those registers plus TXPAUSE, beacon controls, GPIO mux, RF path/interface controls, antenna config, and CCK AFE before calibration. It pauses the queues, puts chain 0 into IQK mode, runs Tx/Rx calibration twice per run, accepts only stable adjacent-run results (each measured Tx/Rx component within 5), tries at most three runs, writes corrections only after a stable valid pair, and restores the saved state. Failed Tx/Rx measurements use sentinel `0xff` and are not programmed. The detailed sequence, comparison, result application, and loop are in [`rtwn_iq_calib_run` / `rtwn_iq_calib_chain` / `rtwn_iq_calib_write_results`](https://github.com/openbsd/src/blob/master/sys/dev/ic/rtwn.c#L2427) and [`rtwn_iq_calib`](https://github.com/openbsd/src/blob/master/sys/dev/ic/rtwn.c#L2709). Port the whole single-chain sequence or leave the factory/baseband correction untouched; a partial IQK sequence can leave RF/baseband state changed.

For channel 1, RTL8192C eFuse ROM group 0 covers channels 1–3. `struct r92c_rom` places `cck_tx_pwr[2][3]` at byte offset `0x5a`; chain A/group 0 is byte `0x5a`. OpenBSD combines that byte with its dongle baseline CCK rate power (chain 0, group 0, CCK1 baseline 0), then clamps to `R92C_MAX_TX_PWR=0x3f` ([ROM layout and max](https://github.com/openbsd/src/blob/master/sys/dev/ic/r92creg.h#L1152), [`rtwn_r92c_get_txpower`](https://github.com/openbsd/src/blob/master/sys/dev/ic/rtwn.c#L2045)). The CCK1 power byte occupies bits 8–15 of BB register `0xe08` (`R92C_TXAGC_A_CCK1_MCS32`); preserve other bits with a mask `0x0000ff00` ([register fields](https://github.com/openbsd/src/blob/master/sys/dev/ic/r92creg.h#L762)). On channel change, write that programmed power before RF CHNLBW; OpenBSD sets USB's initial response-rate bitmap to CCK 1 Mbps and initializes ACK timeout at `0x40` ([initial rate/ACK setup](https://github.com/openbsd/src/blob/master/sys/dev/ic/rtwn.c#L3026)). The TX descriptor must also select CCK1 for each management frame; RRSR's response bitmap alone does not select the outgoing descriptor rate.

**DMA address register diagnostics.** In buffer-DMA mode, `HCDMA` is the controller's current buffer pointer ([Infineon XMC4000 USB reference manual](https://community.infineon.com/gfawx74859/attachments/gfawx74859/XMC/16076/2/Infineon-ReferenceManual_XMC4700_XMC4800-UM-v01_03-EN.pdf)); it can advance while a transfer runs, so a completed 4-byte IN may leave it near the programmed address plus four bytes. It should not turn into an unrelated low address such as `0x00050044`. The Raspberry Pi peripheral manual says DMA engines use bus addresses, with RAM mapped at `0xC0000000`; the current `dma_address()` conversion follows that alias for identity-mapped RAM ([BCM2835 peripherals manual §1.2.3–1.2.4](https://www.raspberrypi.com/app/uploads/2012/02/BCM2835-ARM-Peripherals.pdf); Raspberry Pi identifies BCM2836 as architecturally based on BCM2835 in its [BCM2836 specification](https://pip-assets.raspberrypi.com/categories/506-raspberry-pi-2-model-b/documents/RP-008250-DS-1-bcm2836-peripherals.pdf)). Linux DWC2 initializes HCDMA with the transfer DMA address before enabling the host channel ([`hcd.c`](https://github.com/torvalds/linux/blob/master/drivers/usb/dwc2/hcd.c), `dwc2_hc_start_transfer`). A post-data-stage `HCTSIZ=0x8000003c` decodes as XFERSIZE 60, PKTCNT 0, PID 0, and DOPING 1; compare that readback with the exact pre-enable value, which for a 64-byte DATA1 IN is expected to encode XFERSIZE 64, PKTCNT 1, and PID DATA1 ([Linux DWC2 register definitions](https://github.com/torvalds/linux/blob/master/drivers/usb/dwc2/hw.h)). DWC2 channel register offsets are `HCCHAR=0x500+0x20*n` and `HCDMA=0x514+0x20*n`; channel 0 is at `0x500`, channel 1 at `0x520` (same Linux register definitions). I found no primary-source evidence that VideoCore reserves DWC2 host channel 0, so channel ownership remains unverified rather than an explanation for a corrupted pointer.

## Minimal WPA2-PSK/CCMP handshake notes

These notes scope a first WPA2-Personal station path to RSN, PSK AKM, CCMP-128 pairwise/group cipher, and the EAPOL-Key descriptor version 2 (HMAC-SHA1 + AES key wrap). The dual-licensed hostap supplicant code in [Espressif's upstream mirror](https://github.com/espressif/esp-idf/tree/master/components/wpa_supplicant/src) is a useful embedded implementation reference; the source headers permit BSD terms, with GPL-2.0 also offered. Preserve notices/terms for any reused source.

**Association RSN IE.** A minimal association request advertises the RSN IE (`element ID 48`) with version 1 LE16, group cipher selector `00:0f:ac:04` (CCMP), pairwise count 1 plus CCMP selector, AKM count 1 plus PSK selector `00:0f:ac:02`, then capabilities LE16 (zero is a valid minimal value absent optional features). Include the IE in the association request body and require the AP response to accept the requested suite. Parse the AP beacon/probe RSN IE with bounds checks and match the selected protocol, cipher, and AKM before associating. Selector constants and RSN IE parser are in [`wpa_common.h`](https://raw.githubusercontent.com/espressif/esp-idf/master/components/wpa_supplicant/src/common/wpa_common.h) and [`wpa_common.c`](https://raw.githubusercontent.com/espressif/esp-idf/master/components/wpa_supplicant/src/common/wpa_common.c).

**EAPOL-Key byte layout.** Ethernet ethertype is `0x888e`; the EAPOL header is version, packet type (`3` Key), big-endian body length. RSN descriptor body begins with descriptor type `2`, followed by the packed 95-byte key descriptor. Relative to descriptor start: `0` type; `1..2` Key Information BE16; `3..4` Key Length BE16; `5..12` Replay Counter; `13..44` Nonce; `45..60` IV; `61..68` RSC; `69..76` reserved Key ID; `77..92` MIC; `93..94` Key Data Length BE16; then Key Data. Add 4 bytes for offsets relative to EAPOL payload start. Hostap's struct confirms the field sequence and lengths ([`wpa_common.h`](https://raw.githubusercontent.com/espressif/esp-idf/master/components/wpa_supplicant/src/common/wpa_common.h)); EAPOL version/type/header are in [`eapol_common.h`](https://raw.githubusercontent.com/espressif/esp-idf/master/components/wpa_supplicant/src/common/eapol_common.h).

Key Information is BE16: bits 0–2 descriptor version (`2` for this path), bit 3 pairwise key type, bit 6 Install, bit 7 ACK, bit 8 MIC, bit 9 Secure, bit 10 Error, bit 11 Request, and bit 12 Encrypted Key Data. Hostap defines these masks in [`wpa_common.h`](https://raw.githubusercontent.com/espressif/esp-idf/master/components/wpa_supplicant/src/common/wpa_common.h). For M1 expect Pairwise+ACK, no MIC/Install, and a nonzero ANonce. Send M2 with Pairwise+MIC, a fresh SNonce, and the exact selected RSN IE in clear key data. M3 has Pairwise+Install+ACK+MIC+Secure+Encrypted-Key-Data, the AP's ANonce, and encrypted key data. Send M4 with Pairwise+MIC+Secure, zero nonce/key data, and M3's replay counter.

**Derive and verify keys.** For a passphrase, derive 32-byte PMK using PBKDF2-HMAC-SHA1(passphrase, SSID, 4096 iterations). PTK input is the 6-byte lexicographically smaller then larger of AP/STA MAC addresses, followed by the 32-byte smaller then larger of ANonce/SNonce. Apply WPA PRF-512 with PMK and label `Pairwise key expansion`; for CCMP-128 use first 16 PTK bytes as KCK, next 16 as KEK, final 16 as TK. Hostap documents and implements this sorted-input construction in [`wpa_pmk_to_ptk`](https://raw.githubusercontent.com/espressif/esp-idf/master/components/wpa_supplicant/src/common/wpa_common.c). To verify an EAPOL-Key MIC, copy the complete EAPOL packet, zero its 16-byte MIC field, compute HMAC-SHA1 with KCK and compare the first 16 bytes in constant time. Check M2 MIC before sending it onward; check M3 MIC before unwrapping or installing any key.

**M3 GTK and install.** AES-unwrap the M3 Key Data with KEK using RFC 3394 AES Key Wrap. Reject malformed wrapped lengths and unwrap integrity failure. Parse the plaintext as bounded 802.11 IEs/KDEs. GTK is vendor-specific KDE `dd`, OUI/type `00:0f:ac:01`, then KeyID/Tx/reserved octet, reserved octet, then GTK bytes (16 bytes for CCMP-128). `wpa_supplicant_pairwise_gtk` documents this layout and validates the cipher-specific length ([`wpa.c`](https://raw.githubusercontent.com/espressif/esp-idf/master/components/wpa_supplicant/src/rsn_supp/wpa.c)); AES unwrap path is in the same source. Install the pairwise TK for the AP/BSSID and group GTK at its KDE key index, then transmit M4. Keep M3's RSC as the initial receive packet number state where the hardware interface supports it.

**Replay and retransmission safety.** Track handshake state, ANonce/SNonce, and the last accepted 8-byte replay counter per association. M2 echoes M1's counter; accept M3 only for the current exchange, with its matching ANonce and a valid MIC. M4 echoes M3's counter. Drop stale counters and unexpected message/flag combinations. Retransmitted M1 should cause M2 to be retransmitted; a duplicate valid M3 should cause M4 retransmission, while cached PTK/GTK state prevents key installation and receive packet numbers from resetting. Do not treat an identical retransmission as a new handshake. Hostap's supplicant state machine and GTK/PTK install logic in [`wpa.c`](https://raw.githubusercontent.com/espressif/esp-idf/master/components/wpa_supplicant/src/rsn_supp/wpa.c) are the implementation reference for retry and duplicate behavior; its source also contains explicit GTK-in-use checks to prevent reinstallation.
