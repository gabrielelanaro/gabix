Kernel Stack

What the KernelStack region in our memory map actually is: the bytes that hold the kernel's function-call stack while it runs. Animated walkthrough of how each call and ret pushes and pops frames, with our actual QEMU memory map on the side.

1. What a "frame" is

Every time a function is called, the CPU appends a chunk of bytes to the top of the stack — that chunk is the function's frame. The frame holds everything the function needs while it runs:

  • Return address — where to jump back to when the function finishes.
  • Saved frame pointer — the previous function's anchor (more on this below).
  • Local variables — anything declared with let inside the function.
  • Saved registers — values the function promised not to clobber.

When the function returns, the entire frame is popped off — those bytes become "free" again, ready for the next function call to reuse them.

3. Where this all lives in our kernel

Two completely different regions of physical RAM are involved in a function call:

0x00400000 → 0x0043B000Kernel (code + .data + .bss)
0x00100000 → 0x0027E000KernelStack ← RSP points here
0x00019000 → 0x0009F000KernelStack (the other one)
0x0043B000 → 0x00443000PageTable
0x00443000 → 0x07FE0000Usable
…(other regions omitted)

The compiled instructions for _start, gdt::init, etc. live in the Kernel region — that's just bytes the bootloader copied from our kernel file. The CPU reads them via the instruction pointer (RIP), which wanders around inside that region.

When those instructions call functions, the CPU writes return addresses and locals into the KernelStack region — a completely separate set of addresses. RSP lives there.

Key separation: code (Kernel region) is read by the CPU as instructions. Stack (KernelStack region) is read/written by the CPU as data during function calls. They don't overlap — they're different parts of physical RAM.

4. Why are there TWO KernelStack regions?

Our memory map shows two of them, very different sizes:

RegionAddress rangeSizeUsed by
KernelStack (low)0x00019000 → 0x0009F000~540 KB?
KernelStack (high)0x00100000 → 0x0027E000~1.5 MB?

The honest answer: this is a bootloader = "0.9" implementation detail, and we'd have to read its source to know for sure. But the typical pattern in x86 kernels is to keep multiple stacks for safety:

  • Main kernel stack — what _start runs on. RSP points here during normal kernel code.
  • Double-fault stack — a separate stack the CPU switches to automatically if the kernel crashes while handling an exception. Without this, a stack overflow would cause an exception, which would try to push to the overflowed stack, which would overflow again, which would double-fault — the CPU needs a known-good stack to recover.
  • Interrupt stack — sometimes a separate stack for hardware interrupts, so an interrupt that arrives during a nearly-full stack doesn't overflow.

Linux does this too — see arch/x86/include/asm/stacktrace.h. The CPU picks which stack to use based on entries in the TSS (Task State Segment — same one we mentioned when we set up the GDT). We haven't configured any of that ourselves yet, so the bootloader's defaults are still in effect.

For the rest of M2 we don't need to care which stack is which — we just trust that RSP points somewhere reasonable, and that function calls work the way the animation above shows. When we get to user processes (M3), we'll set up our own per-task stacks and finally deal with this properly.

5. Recap

  • Stack frame = the chunk of bytes a function pushes onto the stack: return address, saved RBP, locals, saved registers.
  • RSP (stack pointer register) always points at the current top of the stack.
  • RBP (base pointer register) anchors the current frame — locals are accessed as [RBP - offset].
  • The stack lives in the KernelStack region, separate from kernel code in the Kernel region.
  • Stack grows downward: pushes subtract from RSP, pops add.
  • Multiple stack regions exist for safety (main, double-fault, interrupt) — bootloader 0.9 set them up for us.
