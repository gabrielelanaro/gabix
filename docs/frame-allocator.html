Frame Allocator

The first piece of memory management: a way to track which 4 KB chunks of physical RAM are free, hand them out on request, and take them back when returned. Without this, we can't allocate page tables, build a heap, or do anything else that needs fresh memory.

The job, in one sentence: given a list of physical memory regions (from the bootloader), maintain a fast lookup of "is frame N free?" and answer allocate() / deallocate() requests.

1. The hotel analogy

Think of physical RAM as a hotel with thousands of identical rooms. Each room is the same size (4 KB), each has a number, and at any moment each is either occupied or vacant. The front desk needs a system that can:

  • Check in a guest: find an empty room, mark it occupied, hand over the key.
  • Check out: take the key back, mark the room vacant.
  • Report vacancy: how many rooms are still free?

2. From rooms to bits

We don't need to track each room with a full byte — a single bit is enough (1 = occupied, 0 = vacant). String the bits together and you get a packed array: the bitmap.

Each frame above corresponds to one bit below. The bitmap is just num_frames / 8 bytes packed in memory — for 32 frames, that's 4 bytes.

Hover over a frame above to highlight its bit. The translation between frame numbers and physical addresses is trivial:

frame_number    = physical_address / 4096
physical_address = frame_number * 4096

That's it. No metadata, no header, no per-frame bookkeeping. The position of the bit IS the bookkeeping.

3. Bootstrapping the bitmap from the memory map

At boot we don't yet know which frames are free — but the bootloader just handed us a memory map that says, region by region, what kind each chunk of RAM is. The initialization is one loop: 

// Start: every bit = 1 (assume allocated). We'll clear bits for Usable regions.
for bit in bitmap.iter_mut(): bit = 1;

for region in memory_map:
    if region.kind == Usable:
        for frame in region.range:
            bitmap[frame.number] = 0;   // mark free
    // all other kinds stay 1 (Kernel, Reserved, PageTable, ...)

Visually, our QEMU memory map turns into a bitmap like this:

Bitmap bits after init. Green = bit 0 (frame is free, region was Usable). Other colors = bit 1 (frame is allocated, region was something else).

4. The chicken-and-egg: where does the bitmap itself live?

Puzzle: to allocate frames, we need a bitmap. To store the bitmap, we need a frame. Which comes first?

Answer: the bitmap is small enough that we can either reserve space for it statically (a fixed-size global buffer compiled into the kernel image), or grab the first few frames of the first Usable region before we start the normal allocator and use those as bitmap storage.

The math for our QEMU memory map:

num_frames ≈ (128 MB) / 4 KB ≈ 32,000 frames
bitmap_size = 32,000 bits / 8 = 4,000 bytes ≈ 1 frame

So the bitmap fits in ONE 4 KB frame.

For real machines with gigabytes of RAM, the bitmap gets proportionally bigger — 32 GB of RAM would need 1 MB of bitmap. Still small in absolute terms, but enough that Linux picks a different data structure (the buddy allocator) to avoid both the storage cost and the "scan a million bits to find a free one" cost.

5. Bitmap vs. buddy

BitmapBuddy (what Linux uses)
Data structureArray of bitsBinary tree of free lists, one per power-of-two size
Allocate one frameLinear scan for first 0 bitPop head of the order-0 free list — O(1)
Allocate N contiguous framesLinear scan for N consecutive 0 bitsWalk to the right order list, split if needed — O(log N)
Free a frameSet bit to 0 — O(1)Set bit, then try to merge with neighbor ("buddy") into a bigger block — O(log N)
Storage overhead1 bit per frame (≈ 0.003%)~10 bytes per frame for free list nodes (≈ 0.25%)
Implementation~50 lines~500 lines
Fragmentation behaviorDoesn't merge, but doesn't fragment eitherAggressively merges, but can fail on odd-sized requests
Why we pick bitmap for mini-os: simplicity. We have 32,000 frames — even a linear scan takes microseconds. Buddy's strengths (fast allocation, merging) only matter when you have millions of frames and many concurrent allocators. For learning the concept of physical-frame management, the bitmap is the right tool.

6. The interface we'll implement

pub struct FrameAllocator {
    bitmap: [u8; ...],   // 1 bit per frame
    num_frames: usize,
}

impl FrameAllocator {
    pub fn init(memory_map: &MemoryMap) -> Self;
    pub fn allocate(&mut self) -> Option<u64>;        // returns frame number, or None if out
    pub fn deallocate(&mut self, frame_number: u64);
    pub fn frames_free(&self) -> usize;
}

That's the whole API. allocate returns an Option because the day we run out of physical RAM, we want it to fail visibly, not silently corrupt memory.

7. Recap

  • Frame = 4 KB chunk of physical RAM. Page = the same chunk when seen through virtual memory. Same size, different perspective.
  • A bitmap allocator uses 1 bit per frame. 0 = free, 1 = allocated.
  • The bitmap is initialized from the bootloader's memory map — every Usable region's frames become 0, everything else stays 1.
  • Allocation = linear scan for the first 0 bit. Deallocation = flip the bit.
  • For ~128 MB of RAM (QEMU), the bitmap itself is ~4 KB — fits in one frame.
  • Linux uses a buddy allocator instead, because it scales better to gigabytes of RAM and supports merging adjacent free regions.
