The trick, in one sentence

There's no special "switch task" instruction. We just swap RSP (the stack pointer) and then do a normal function return — ret pops the new stack's top into RIP, which magically jumps to wherever the new task was paused.

Why a brand-new task's stack looks like this

Task B has never actually executed, so it has no "real" saved state. We fake it: when Task::new() creates B, it writes the saved registers (zeros) and the entry function's address onto B's stack as if B had been paused right before calling its entry function. That way, the same context-switch code works for both resuming an old task and starting a new one — the algorithm doesn't care which.

Why only 6 registers?

  • The x86-64 calling convention splits registers into two groups: caller-saved (RAX, RCX, RDX, RSI, RDI, R8-R11) and callee-saved (RBX, RBP, R12-R15).
  • The convention says: when you call a function, the caller assumes caller-saved registers might be clobbered. So the compiler already saves/restores them around the call as needed.
  • The context switch lives inside a function call (yield() → switch()), so the compiler does the caller-saved work for us. We only need to manually save/restore the callee-saved ones.
  • RIP isn't saved manually either — the call instruction pushes it, ret pops it. We just need to make sure the new task's stack has the right value on top.

Real Linux: task_struct → thread_struct → sp. Just one field. All other register state lives on the paused task's stack.
