exec, or: how to run a different program

fork + wait gave us process tree management. exec is the missing piece: it replaces the running program with a new one. Without exec, every child runs the same code as its parent. With exec, a shell can fork then immediately exec ls or grep or whatever.

01 What exec does, in one breath

Replace the current process's program with a new one. Same PID, same open files (one day), same parent — but the user code, user stack, and execution point are all gone. The process starts running the new program from its entry point.

fork clones

New task, new AS, both run the same code, diverge on RAX. Two processes after.

wait blocks

Parent yields until child exits. Same number of processes; just one is paused.

exec replaces

Same number of processes. Same PID. Different program. The old user code is gone.

The classic Unix pattern

A shell runs ls by combining all three: fork → exec → wait. The shell forks a child, the child immediately execs ls, the shell waits for the child to finish. This is what makes a shell a shell.

02 The hard problem: where does the program come from?

exec needs to load bytes into the process's address space. Linux reads them from a file on disk. We don't have a filesystem yet. Three options.

(a) Embed programs in the kernel image

Compile a few tiny test programs as &[u8] constants. A registry maps program_id → (bytes, entry_offset). exec(2) loads program #2 from this registry.

Smallest scope. No filesystem needed. Lets us prove the mechanism end-to-end. This is the path of least resistance for getting exec working.

(b) Minimal ramfs

Build a tiny in-memory filesystem (a flat list of files). Kernel reads from it. More Linux-like. But this is slice 4.4 / 4.5 — a whole milestone by itself.

Right thing to do eventually, but doing it before exec means two big lifts in sequence. Defer.

(c) Hand-coded test programs only

Just one fixed "after-exec" program baked into kernel code. exec ignores its argument and always loads that one.

Minimal but uninteresting. Reduces exec to a "demo mode" rather than a real syscall. Skip.

Recommendation: option (a)

A PROGRAMS constant — array of (name, bytes, entry) tuples — compiled into the kernel. exec(name) looks it up by name. Three or four programs ("hello", "goodbye", "counter") is enough to demonstrate the mechanism. Replace with ramfs later when we tackle 4.4 / 4.5.

03 Program format: skip ELF

Linux uses ELF (Executable and Linkable Format) — a structured format with sections, segments, dynamic linking info, debug symbols. Way too much for our purposes. We can use flat binary with a tiny header.

ELF what Linux parses

ELF header (52 bytes), program headers (one per segment), section headers, optional dynamic linking tables, relocations, symbols. Each segment has its own virtual address, file offset, memory size, and flags (R/W/X).

Required when programs are compiled separately and linked against libraries.

flat what we need

Raw bytes for the program. One fixed load address (e.g. 0x4000_0000). Entry = start of the bytes. No sections, no relocations, no symbols.

We control the compiler / assembler, so we can produce flat binaries directly.

Optionally, a tiny header at the front of each program: magic + size + entry offset. Lets exec validate it's loading a real program and not garbage. For the absolute simplest version, even skip the header — fixed conventions for load address and entry, bytes are bytes.

Unlike fork, exec doesn't create a new task — it just rewrites the current one's user-space identity. The task struct stays alive. Its kernel stack, syscall stack, and scheduler entry are all unchanged. Only the AS, the saved user state, and (for cosmetic reasons) the name change.

05 Reusing fork_trampoline for the jump

We already have the infrastructure to "set up registers and sysretq into user mode" — it's called fork_trampoline. With one small tweak, exec can reuse it.

fork_trampoline today

Naked asm that reads saved user RIP/RSP/RFLAGS from fixed kernel-stack offsets and sysretqs. Designed for the child's first switch-in. Sets RAX=0.

exec_trampoline proposed

Identical mechanism, just reads from different slots. exec fills those slots with the new program's entry (0x4000_0000), fresh user-stack top, and a clean RFLAGS (just the IF bit set). Sets RAX=0.

The two trampolines could even share code: parameterize on "where to find the saved state". But starting with copy-paste is fine — clearer, and easy to refactor later.

Or even simpler: just write the new state to the same slots fork_trampoline reads from, then call it. Same trampoline, different meaning. A bit hacky but works.

06 Suggested build order

Three sub-slices. Each one is independently testable. Together they add up to a working exec.

4.5.a

Program registry

Define PROGRAMS: &[(name, bytes, entry)] with two test programs. Compile them in (just like USER_PROGRAM today, but as a list).

4.5.b

sys_exec core

Look up by id, allocate fresh AS, copy program bytes to user code page, set up fresh user stack. Update Task struct. Switch CR3 immediately.

4.5.c

exec_trampoline

Naked-asm sibling of fork_trampoline. Reads the new entry/RSP/RFLAGS from the kernel stack and sysretqs into the new program.

test

End-to-end

USER_PROGRAM calls fork. Child execs a different program. Parent waits. Verify the second program's output appears and the parent's wait returns.

Sub-slice details

  1. 4.5.a — Program registry Add PROGRAMS: &[(name: &str, bytes: &[u8], entry: u64)] in a new file (or in user.rs). Start with two programs: "hello" (writes "hello from exec\n") and "goodbye" (writes "goodbye from exec\n"). Both compiled the same way as today's USER_PROGRAM — hand-assembled machine code.
  2. 4.5.b — sys_exec(program_id) Implement SYS_EXEC (Linux uses 59 for execve). Look up by id. Allocate a fresh AddressSpace via AddressSpace::new(). Map the program bytes at 0x4000_0000 with USER_ACCESSIBLE. Allocate fresh user stack pages at 0x7000_0000–0x7001_0000. Update current.address_space. Switch CR3 immediately (we're in the kernel; old AS can leak for now).
  3. 4.5.c — exec_trampoline Write to the current task's kernel stack at the same offsets fork_trampoline reads from (stack_top - 64/-72/-80) with the new entry/RSP/RFLAGS. Then either reuse fork_trampoline or write a sibling exec_trampoline. sysretq into the new program. Done.
  4. Test Update USER_PROGRAM: parent forks. Child immediately calls exec("hello"). Parent waits. Expected output: "hello from exec\n", then parent's normal output. Verify the child's PID didn't change (still 1) and the parent's wait reaped it.

07 What we'd reuse vs what's new

Most of exec is "do what fork did, but simpler". The infrastructure from 4.4.a–f carries over.

Piece Reuse from fork? Notes
AddressSpace type Yes — new() gives us a fresh kernel-mapped AS No changes needed. Just don't deep_clone_from_current — we want a blank user half.
Mapping user pages Yes — AddressSpace::map_to Map program bytes (read+execute) and stack (read+write). Same flags as today.
Trampoline mechanism Yes — naked asm reading saved state from kernel stack Copy fork_trampoline, change which slots it reads from (or which values are in those slots).
Per-task syscall stack Yes — already per-task, exec keeps the existing one No change. The kernel stack is per-task already; exec doesn't touch it.
Scheduler entry Yes — task stays in scheduler with same id No new task created. Just the AS and the saved user state change.
Program registry NEW Single new PROGRAMS constant. Trivial.
Cleanup of old AS NEW (but optional) Old AS leaks until cleanup lands. Same situation as fork's leaked Zombie stacks.

08 Ours vs Linux exec

Same idea, very different scope. We're a teaching kernel — Linux handles a lot of edge cases we can ignore.

Concern mini-os (proposed) Linux execve
Program source Embedded bytes in kernel (PROGRAMS registry) Path in filesystem, opened via VFS lookup
Format Flat binary, fixed load address, entry = start ELF (or scripts via shebang). Multi-segment, dynamic linker, the works
Arguments Just program_id. No argv/envp. argv, envp arrays passed via syscall, copied onto new user stack
Address space Allocate fresh, leak old Carefully tear down old AS (unmap user pages, free page tables, close file descriptors marked CLOEXEC)
Failure mode Panic if program not found Returns -ENOENT (or similar) to caller; old program keeps running
Threads N/A — single-threaded Kills all other threads in the process (with signaling)
File descriptors N/A — no FDs yet Inherited, except those marked CLOEXEC
setuid/setgid N/A Honored if executable has the bits set

09 Open questions to resolve before coding

Small design decisions that should be settled up front. None are blockers; all are easy to reverse later if we change our mind.

  1. How does the user identify which program to exec? Option A: integer id (exec(0), exec(1)). Option B: short name string (exec("hello")). Name is more readable, id is simpler. Recommend: name, matched against the PROGRAMS registry.
  2. What happens to the existing user state? Just overwrite it. The current AS gets replaced wholesale. No need to "save" anything — by definition, exec means we don't want to come back.
  3. What's the failure path? For now: panic if the program id is unknown. Real kernels return an error code. We can add error returns once we have a real syscall error convention.
  4. Does exec need a new TaskState? No. The task stays Running through exec — there's no scheduling event, just a CR3 swap and a register rewrite. Same task, different program.
  5. What if exec is called from kernel context (not via syscall)? For now: undefined. sys_exec only runs via the syscall path. Could add a kernel_exec helper later for things like running an init program from main.
