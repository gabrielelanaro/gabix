Heap Allocator

We can hand out 4 KB frames, but kernel code often needs 32-byte structs or growable buffers. The heap allocator subdivides a large virtual region into small chunks on demand, so Box::new, Vec, and String work in the kernel.

The job, in one sentence: given a request for N bytes aligned to M, return a pointer into a big region of pre-mapped memory; later, accept that pointer back and mark the chunk as free for reuse.

1. The problem we're solving

The frame allocator (slice 2.1) hands out 4 KB chunks. That's great for page tables — they're exactly 4 KB. But it's terrible for everyday allocations:

  • Box::new(5u32) needs 4 bytes — would burn 4 KB on it.
  • vec![1, 2, 3] needs 24 bytes — would burn 4 KB.
  • Worst case: thousands of small allocations, each in their own 4 KB page. The frame allocator would be empty in seconds.

We need a finer-grained layer on top. That layer is the heap.

2. Where the heap lives

The heap is just a virtual address range we set aside — say 0x_4444_4444_0000 for 100 KB. We use our page-table mapper (slice 2.2) to map that range to physical frames. Then the heap allocator subdivides the inside of that range.

virtual address space
0x4444_4444_0000 ┬───────────────────┬ ← heap start │ Box │ ~4 bytes │ Vec buffer │ ~64 bytes │ String header │ ~24 bytes │ ... │ │ (free) │ ← allocator's "next" pointer │ ... │ 0x4444_4444_0000 ┴───────────────────┴ ← heap end (100 KB later) + 0x20000
The heap is just a region. The allocator decides which bytes go to which allocation inside it.

3. Strategy 1: Bump allocator (the dumbest thing that works)

A bump allocator is one pointer (next) and a record of the heap's start and end. To allocate N bytes: return next, then move next forward by N. To free: do nothing. That's the whole allocator.

Try it. Notice that "free" is a no-op — once bytes are claimed, they're gone forever. Run out of space and the next allocation fails. This is why bump allocators are only useful for short-lived programs or for arenas that get wholesale-reset.

4. Strategy 2: Linked-list allocator (frees actually work)

A linked-list allocator keeps a list of free blocks. Each block has a header (size + "free"/"used" flag) and the free ones are linked together. To allocate N bytes: walk the list, find a free block that fits, split it if it's much bigger than N, mark the chosen block as used. To free: mark the block as free, optionally merge with adjacent free blocks.

5. Fragmentation

The long-term failure mode of any heap allocator. After many allocate/free cycles in random orders, the heap becomes Swiss cheese: lots of small free blocks scattered between used blocks. The total free bytes might be plenty, but no single block is big enough to satisfy a new allocation.

Three flavors of fragmentation:

  • External fragmentation: the picture above — free space is scattered, can't fit a big request.
  • Internal fragmentation: allocator rounds up to fit a block size. Asking for 17 bytes, getting a 32-byte block — 15 bytes wasted inside the block.
  • Slab decay: if you allocate/free the same size class repeatedly, then suddenly need a different size, the cached slabs for the first size don't help.

Allocators fight fragmentation with:

  • Coalescing: when you free a block, merge it with adjacent free neighbors.
  • Best-fit / first-fit / next-fit: different heuristics for picking which free block to use.
  • Slab allocation: pre-allocated pools per size class. Common objects (inodes, task_structs) get their own pool, eliminating fragmentation for them.
  • Compaction: move live objects to consolidate free space. Requires updating all pointers — feasible only with runtime support (GC). Not used in kernel allocators.

6. The Rust API: GlobalAlloc

Rust exposes a single trait with two methods. Implement it on a struct, mark that struct with #[global_allocator], and every Box/Vec/String in the kernel routes through your code. 

use core::alloc::{GlobalAlloc, Layout};

struct MyAllocator { /* ... */ }

unsafe impl GlobalAlloc for MyAllocator {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        // Return a pointer to `layout.size()` bytes, aligned to `layout.align()`.
        // Return null if you can't satisfy the request.
        todo!()
    }

    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout) {
        // Free the allocation previously returned by alloc().
        todo!()
    }
}

#[global_allocator]
static ALLOCATOR: MyAllocator = MyAllocator { /* ... */ };

After that, this just works: 

let x: Box<u32> = Box::new(42);              // calls ALLOCATOR.alloc(Layout::new::())
let v: Vec<u8> = vec![1, 2, 3, 4, 5];      // calls alloc(5-byte layout), then later dealloc
let s = String::from("hello");              // same pattern
drop(x);                                     // calls ALLOCATOR.dealloc(...)

8. Recap

  • The heap is a virtual region we subdivide for small allocations.
  • Bump allocator: one pointer, never frees. Simplest possible.
  • Linked-list allocator: free blocks linked, can free and reuse. Realistic.
  • Fragmentation is the long-term enemy; coalescing, slab pools, and good fit-heuristics fight it.
  • Rust's #[global_allocator] on a GlobalAlloc impl hooks our allocator into every Box/Vec/String in the kernel.
  • Linux uses the slab allocator (one flavor of it) for the same job; we'll start simpler.
