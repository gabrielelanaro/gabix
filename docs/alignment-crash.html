The Alignment Crash, in Pictures

Our breakpoint handler kept crashing. The reason: a chain of small alignment problems that ended with one instruction refusing to run. Here's the whole story, visually.

What "aligned" means (1-minute intro)

Memory addresses are just numbers. Sometimes an instruction demands that an address be a multiple of some power of 2 — like 16. We call that "16-byte aligned."

Address ends in…Aligned to 16?Why
...0✓ yes0 is divisible by 16
...8✗ no8 is not divisible by 16
...0✓ yes(e.g. 0x...40 = 64 = 16×4)
...8✗ no(e.g. 0x...78 = 120 = 16×7.5)

Quick check: if the last hex digit is 0, you're 16-aligned. If it's 8, you're almost aligned (8-aligned only). Anything else and you're not even 8-aligned.

Analogy: imagine a ruler with centimeter marks. "16-aligned" means your measurement lands exactly on a centimeter mark — not 7mm in, not 13mm in. Some instructions demand exact centimeter marks. If your measurement is "between marks," they refuse.

The story, in five steps

1Before int3 fires — stack is 16-aligned

The stack pointer (RSP) is at 0x...fe8 when our kernel calls int3. Wait, ...8 — that's 8-aligned, not 16-aligned! So actually we're starting misaligned.

(That's normal — the kernel's calling convention says "stack is 16-aligned at function call entry." int3 isn't a function call, so that rule didn't apply.)

2CPU pushes the interrupt frame — now it's 16-aligned

RSP = 0x...fc0 ✓ 16-aligned

The CPU pushed 5 things (40 bytes total). That's an even multiple of 8 but not of 16. So the alignment flipped from ...8 to ...0 — by luck, we're now 16-aligned.

This is the stack our handler sees when it starts running.

3Handler pushes 9 registers — misaligned again

The compiler-generated prologue saves 9 registers. Each push is 8 bytes, so each one flips the alignment (0 → 8 → 0 → 8 ...).

Nine pushes = odd number, so we ended on ...8. Now misaligned.

If the prologue had pushed an even number of registers, we'd be fine. But it didn't.

4Handler subtracts 0x130 — doesn't help

Stack after sub $0x130, %rsp
0x120 bytes of scratch space
(for saving more stuff)
↓
0x130 bytes total
RSP = 0x...e48 ✗ still 8-aligned

0x130 in decimal is 304. 304 ÷ 16 = 19. So 304 is a multiple of 16.

Subtracting a multiple of 16 preserves alignment. If we were misaligned at ...8, we stay at ...8.

The compiler should have subtracted 0x138 (304 + 8 = 312) to add the extra 8 bytes needed to realign. It didn't.

5The crash: movaps demands 16-alignment

The handler now wants to save 16-byte-wide registers (called xmm) to the scratch space it just reserved. It uses an instruction called movaps — but movaps has a strict rule:

movaps rule: the destination address must be 16-aligned. No exceptions. If it isn't, the CPU raises a General Protection Fault.
movaps %xmm15, 0x120(%rsp)
Destination: RSP + 0x120 = 0x...e48 + 0x120 = 0x...f68
Ends in 8 → NOT 16-aligned → FAULT

The instruction faults. The handler hasn't even done anything useful yet — the crash happens in the prologue, before our actual code runs.

The cascade — why a single misalignment became a reboot

One fault isn't a reboot. The CPU tries to handle the fault by calling another handler. But that handler isn't installed either, so it faults too. Eventually:

1. movaps faults → General Protection Fault (#GP)
↓ CPU tries to call GP handler, but we didn't register one
2. Double Fault (#DF) → "an exception happened while handling another exception"
↓ CPU tries to call double-fault handler, but we didn't register one either
3. Triple Fault → CPU gives up. The only thing it can do is reset.
↓ CPU resets → SeaBIOS → bootloader → our kernel → int3 → #1 again
4. Reboot loop. This is what you saw.
Key insight: a single fault is fine — the kernel handles it. A double fault is also fine — if you have a double-fault handler. A triple fault is unrecoverable: the CPU physically can't continue, so it resets the machine.

The fix we applied

We made the breakpoint handler empty:

extern "x86-interrupt" fn breakpoint_handler(_stack_frame: InterruptStackFrame) {
    // Empty for now
}

The compiler looks at this and says "function does nothing, doesn't use any wide registers." So it skips the entire prologue — no register saves, no movaps, no fault. The compiled handler is literally one instruction:

2066d0:  iretq   ← just return from the interrupt

No prologue, no problem. The handler runs, returns, execution continues. That's why "It did not crash!" shows up on screen.

The "real" fix (future)

The empty handler is a workaround. We'd like our handler to actually do something — like print the exception info. But any non-trivial work (especially formatting with {:#?}) triggers the compiler to save xmm registers, and we're back to the alignment problem.

Real fixes (pick one, eventually):

  1. Stack realignment stub. Write a small assembly wrapper that aligns the stack before calling the Rust handler. Most production Rust kernels do this.
  2. Wait for the Rust compiler. The extern "x86-interrupt" ABI is supposed to handle this automatically; it's a known bug.
  3. Disable SSE for handlers. Tell the compiler "don't use wide registers here." Tricky in current Rust — needs per-function target features.
  4. Use naked assembly. Write the entire handler in assembly. Maximum control, maximum tedium.

For now, the empty handler proves the IDT mechanism works end-to-end. The breakpoint fires, our handler is called, iretq returns, execution continues. That was the goal of this slice.

What we learned (mentally)

  • The CPU delivers interrupt handlers a stack that might be misaligned by 8.
  • Some instructions (like movaps) demand exact 16-byte alignment. No slack.
  • If an instruction can't run, the CPU raises a fault. Faults on faults on faults = triple fault = reboot.
  • The empty-handler trick sidesteps the issue by avoiding the prologue entirely.
  • Real kernels either realign the stack manually or wait for the compiler to do it right.
