Linker, Bootloader, and Where the Kernel Lives

We use the bootloader crate (Philipp Oppermann's, version 0.9) — not a hand-rolled bootloader. So "what does the linker do?" and "what does the bootloader do?" are two questions with concrete, separable answers. This page walks through both, using our actual addresses.

1. Who decides the kernel's virtual address?

Q: Since we use the bootloader crate, who actually decides that our kernel ends up at virtual address 0x200000?
A: Three players, in order:
  • The linker script — decides which virtual address each section (.text, .rodata, .data, .bss) wants to live at. The addresses get baked into the ELF (Executable and Linkable Format) file. We don't have a custom script — the bootloader crate brings its own default.
  • The bootloader crate — reads our kernel's ELF at boot time, sees the requested addresses, picks where in physical RAM to actually load each section, and sets up initial paging tables so that virtual → physical translation works as the ELF requested.
  • Our kernel code — takes over from there. Whenever we create a new address space (fork) or map new pages, we are responsible for keeping the kernel mappings intact. The bootloader handed us a working setup; from here it's ours.

The key point: the linker script makes the decision, the bootloader crate respects it. When we say "relink the kernel at high addresses," we mean: change the linker script so it asks for high addresses, and the bootloader crate will map us there instead.

Steps 1–3 happen at compile time on your machine — they produce a static ELF file sitting in target/x86_64-mini-os/debug/. Steps 4–5 happen at boot time inside QEMU.

Where the address decision happens: Step 3. The linker is the only step that decides "this function lives at virtual address X." Everything before just produces bytes; everything after just respects the decision.

3. What's actually inside the ELF binary

The ELF file is a container with two views: a section view (used by linkers and debuggers — "here's .text, here's .rodata") and a program header view (used by loaders — "load these byte ranges into memory at these virtual addresses"). The bootloader uses the program header view.

Here's roughly what our kernel ELF's program headers look like (concrete numbers from our current setup — verified by running readelf -l on the built binary):

Segment Virt address (where linker placed it) Contents PML4 (Page Map Level 4) entry
.text 0x200000 — 0x2xxxxx Kernel code (every function) entry 0
.rodata 0x2xxxxx — 0x2xxxxx String literals, constants entry 0
.data / .bss 0x2xxxxx — 0x2xxxxx Mutables, uninitialized globals entry 0

Plus what the bootloader crate adds at runtime, on top of the ELF:

Mapping Virt address Why PML4 entry
physical memory offset 0x180_0000_0000 So we can read/write any physical address from kernel code entry 96 (still low half)
VGA text buffer 0xb8000 Identity-mapped so we can write to screen directly entry 0
Compare with Linux: Linux's kernel ELF places .text at 0xFFFFFFFF81000000 — that's PML4 entry 511 (the top of the upper half). The program headers literally ask for high addresses, so the linker script makes the decision and everything downstream respects it.

4. What the bootloader crate does at runtime

When QEMU starts, the BIOS hands control to the bootloader crate (it's the first thing on the boot image). Here's what it does, step by step: 

// Inside the bootloader crate (not our code):

1.  Enter in 16-bit real mode (BIOS) or 64-bit long mode (UEFI)
2.  Switch to 32-bit protected mode, set up a basic GDT
3.  Switch to 64-bit long mode, set up identity-mapped 4-level paging
4.  // Read our kernel ELF from disk (already loaded into memory by GRUB/BIOS)
     for each program header in kernel.elf:
         allocate physical frames for the segment
         memcpy bytes from ELF on disk → those physical frames
5.  // Build the kernel's "real" page tables
     for each program header:
         map header.virt_addr → allocated_phys_addr
     // Plus: map all of physical RAM at physical_memory_offset
     map 0x180_0000_0000 ... 0x180_0000_0000 + RAM_size → 0 ... RAM_size
6.  Set CR3 = the new PML4's physical address (this activates the mappings)
7.  Allocate a kernel stack, set RSP to its top
8.  Jump to _start (the entry point in our main.rs)
     — passing a pointer to BootInfo in RDI, which contains physical_memory_offset
       and the memory map

// Now we're running our kernel, with paging already set up.
// Our memory::init() captures physical_memory_offset for later use.

The crucial part for understanding the wart: step 5. The bootloader crate builds the initial PML4 (Page Map Level 4) for our kernel. Every entry it puts in there corresponds to whatever virtual address the ELF asked for. Since our ELF asked for low addresses (0x200000), that's where the entries land — in PML4 entries 0–255.

The "sign extend" bits (47–63) decide whether you're in the lower half (PML4 entries 0–255) or upper half (entries 256–511). All-zero means lower; all-one means upper. The CPU enforces this — any address with mismatched bits 47–63 (a "non-canonical" address) faults.

PML4 entry 0 contains both the kernel's .text at 0x200000 and the user's program at 0x40000000. They're both inside entry 0 because they're both in the lower half of the address space. When you fork, the child needs the kernel half of entry 0 but a fresh copy of the user half — but there's no entry-level granularity below PML4. You'd have to walk the entire subtree.

That's why our deep_clone_from_current() walks all four paging levels:

// From src/memory.rs:
for pml4_entry in 0..512 {
    if entry is present {
        // Allocate a fresh PDPT frame for the child
        for pdpt_entry in 0..512 {
            if entry is present {
                // Allocate a fresh PD frame
                for pd_entry in 0..512 {
                    if entry is present {
                        // Allocate a fresh PT frame
                        for pt_entry in 0..512 {
                            if USER_ACCESSIBLE {
                                // User page — allocate fresh data frame, memcpy
                            } else {
                                // Kernel page — just copy the entry (share the frame)
                            }
                        }
                    }
                }
            }
        }
    }
}
// OUCH: 4 nested loops, frame allocation at every level, page-by-page decisions

Kernel lives only in entries 256–511, user only in 0–255. To fork: copy the top 256 entries verbatim (one frame, identical in every process), allocate a fresh PML4 for the bottom 256. No subtree walking needed.

8. What relinking to high addresses would change

Concrete steps, in order:

  1. Add a custom linker script (e.g., kernel.ld) that places .text at 0xFFFFFFFF80000000 instead of letting the default pick. About 20 lines of linker syntax. Reference it from .cargo/config.toml via rustflags = ["-C", "link-arg=kernel.ld"].
  2. Rebuild. The ELF now has high addresses in its program headers. Run readelf -l to confirm.
  3. The bootloader crate automatically respects the new addresses — that's the whole point of using it. It reads the ELF, sees the high virtual addresses, and maps them to whatever physical frames it allocated. We don't change any bootloader code.
  4. Update our address constants: change PHYS_OFFSET handling (no longer needed if the bootloader gives us a high-offset mapping), update VGA_BUFFER if we were using identity mapping (we can map it explicitly wherever we want now), change HEAP_START to a high address, etc.
  5. Simplify fork: replace deep_clone_from_current with the trivial version — copy PML4 entries 256–511 (kernel half), allocate a fresh PML4 with zeroed entries 0–255 (user half), walk only the user subtrees.
The payoff: Once the kernel is in the upper half, fork becomes a 20-line operation instead of 150. The kernel mappings are "shared" between processes automatically — every process's PML4 has the same upper 256 entries, pointing at the same kernel PDPT/PD/PT frames. No copying. No walking. The whole deep_clone_from_current machinery goes away.
Why we haven't done it yet: it's a 1–2 session detour with no user-facing payoff. Everything works today, just less elegantly. The workarounds (deep clone, sharing kernel frames) are well-understood and don't cause bugs. Better to do this as a "now that we understand why it matters" cleanup later, after VFS (Virtual File System) is in place.

Summary

  • Linker = the step that bakes virtual addresses into the ELF. Decision point for where the kernel "lives" virtually.
  • Bootloader crate = reads the ELF at boot, sets up paging to make those addresses actually work. We don't write this code; the crate does it for us.
  • Our wart = the default linker behavior placed us at low addresses (PML4 entries 0–255), where user memory also lives.
  • The wart's symptom = fork needs deep_clone_from_current because we can't separate "kernel entries" from "user entries" at the PML4 entry level.
  • The fix = write a custom linker script asking for high addresses. The bootloader crate honors it automatically. Then fork becomes trivial.
