Interrupts, in Pictures

An interrupt is just a way to make the CPU pause what it's doing, run some other code, then resume. The whole OS is built on this primitive. Let me show you.

1. The basic idea

Without interrupts, the CPU just runs your code top-to-bottom. If it wants to react to anything external (key press, timer tick, disk finishing), it has to keep checking "did it happen? did it happen?" — wasteful.

Interrupts flip this around. The CPU runs your code, and when something happens, the device pokes the CPU. The CPU stops, runs a handler, then resumes your code as if nothing happened.

Analogy: you're reading a book. Without interrupts, you'd have to check the door every 30 seconds "did the pizza arrive?" With a doorbell (an interrupt), the doorbell rings when the pizza arrives, you put a bookmark in, answer the door, come back, resume reading.

2. The three types of interrupts

⏰

Hardware interrupts

A device somewhere sent an electrical signal. CPU must respond.

  • Timer tick (every 10ms)
  • Key pressed on keyboard
  • Network packet arrived
  • Disk finished a read
💥

CPU exceptions

CPU tried to do something and couldn't. Must report it.

  • Divide by zero
  • Page fault (memory not mapped)
  • Invalid opcode
  • General protection fault
📞

Software interrupts (intentional)

Your code asked for one explicitly via int N.

  • int3 — breakpoint (debug)
  • int 0x80 — old Linux syscall
  • (Modern Linux uses syscall instruction instead)

All three go through the same IDT (Interrupt Descriptor Table). The CPU doesn't distinguish — interrupt N fires → look up IDT[N] → jump to handler.

The orange dot flowing left-to-right along the bar is the interrupt signal traveling from device to CPU. The colored step label cycles through the 7 stages:

  1. CPU running user code at instruction X
  2. Device fires — timer sends electrical signal
  3. PIC routes it — looks up which IRQ, maps to vector 32
  4. CPU notified — finishes current instruction, prepares to switch
  5. CPU saves state — pushes RIP, RSP, RFLAGS, CS, SS onto the kernel stack
  6. CPU looks up IDT[32] — gets handler address, jumps there
  7. Handler runs — does its work (e.g., print "tick"), sends EOI, runs iretq to resume

After iretq, the CPU pops the saved state and continues at instruction X+1. The interrupted code has no idea anything happened.

4. The PIC: why it exists

Modern CPUs have one interrupt pin. But you have many devices (timer, keyboard, mouse, disk, NIC, USB, ...). They can't all share one wire.

So the PIC (Programmable Interrupt Controller) sits between devices and the CPU. It has many input wires (one per device) and one output wire to the CPU. When any device fires, the PIC signals the CPU and tells it which device.

Modern reality: the 8259 PIC is from 1980s. Modern systems use APIC (Advanced PIC) — many more inputs, distributed across CPU cores. But the 8259 still works in QEMU and is much simpler to learn. We'll use it for mini-os.

5. The remap problem (and why we need to fix it)

The PIC maps its IRQs to CPU interrupt vectors. By default, it uses vectors 8-15. But the CPU already uses 0-31 for exceptions:

CPU vectorUsed for
0-7CPU exceptions (divide error, invalid opcode, etc.)
8-15⚠️ CONFLICT — CPU exceptions here (double fault, page fault, etc.) AND default PIC mapping
16-31More CPU exceptions (x87 error, machine check, etc.)
32-47✓ Free — where we remap the PIC

If we left the default, the timer (IRQ 0) would fire CPU vector 8 — which is double fault. The kernel would think the CPU is double-faulting every 10ms. Bad.

The fix is to "remap the PIC" by sending it initialization commands that say "use vectors 32-47 instead of 8-15." Then:

  • Timer IRQ 0 → vector 32
  • Keyboard IRQ 1 → vector 33
  • ...etc.

6. EOI: End Of Interrupt (the acknowledgement)

When an interrupt fires, the PIC marks that IRQ as "in progress" and won't deliver another from the same source until you tell it "I'm done."

This is the EOI (End Of Interrupt) signal. Our handler must send EOI to the PIC after handling the interrupt, or the PIC will sit silently forever waiting.

Common gotcha: forget EOI → timer fires once, then never again. You see one "tick" then nothing. Always send EOI at the end of every hardware interrupt handler.

7. Interrupt Flag (IF): the master switch

The CPU has a flag in RFLAGS called IF (Interrupt Flag). When it's 0, the CPU ignores all hardware interrupts (timer, keyboard, etc.). When it's 1, it handles them.

By default after boot, IF=0. So even with a perfect IDT, PIC, and timer set up, nothing will fire until we explicitly enable interrupts.

IF value Hardware interrupts CPU exceptions
IF = 0 (default after boot)IgnoredStill fire (you can't ignore a divide-by-zero)
IF = 1 (we enable in _start)Fire normallyStill fire

So the sequence is: set everything up first, then enable interrupts last. Otherwise you'd get an interrupt before the handler is ready → triple fault.

8. Real examples: how Linux uses interrupts

Same mechanism, scaled up. Concrete scenarios:

📋 Scenario 1: Pressing a key

1. Keyboard controller sends electrical signal on IRQ 1
2. PIC notifies CPU; CPU looks up IDT[33] (33 = 32 + 1, the remapped IRQ 1)
3. CPU jumps to Linux's i8042_interrupt handler in drivers/input/serio/i8042.c
4. Handler reads the scan code from keyboard port, decodes it
5. Passes it to input subsystem → tty layer → shell sees the character
6. Sends EOI to PIC, returns via iretq
7. Your terminal now shows the letter you typed

⏱️ Scenario 2: Timer tick (every ~1ms in Linux)

1. APIC timer (modern) or PIT (old) fires — IRQ 0 → vector 32
2. CPU jumps to smp_apic_timer_interrupt in arch/x86/kernel/apic/apic.c
3. Calls scheduler_tick() in kernel/sched/core.c
4. Scheduler checks: has the current task used up its time slice?
5. If yes, sets TIF_NEED_RESCHED flag
6. On return to user mode, kernel calls schedule() → switches to next task
7. This is how multitasking works — the timer forces periodic task switches

💾 Scenario 3: Disk read completes

1. Your program calls read() → kernel starts disk I/O → puts your process to sleep
2. Disk reads the data into kernel buffer
3. Disk controller fires interrupt when done
4. CPU jumps to disk driver's interrupt handler (e.g., NVMe IRQ handler)
5. Handler marks your process as "ready to run," wakes it up
6. Eventually scheduler picks your process, it resumes read() with the data
7. This is how blocking I/O works — the kernel sleeps you, an interrupt wakes you

📄 Scenario 4: Page fault (this is an exception, not a hardware interrupt)

1. Process accesses memory address that isn't currently mapped
2. CPU raises exception #14 → vector 14 → IDT[14]
3. CPU jumps to page_fault in arch/x86/entry/entry_64.S
4. Calls do_page_fault in arch/x86/mm/fault.c
5. Looks up the faulting address in process's VMAs (virtual memory areas)
6. If valid but not yet loaded: read from disk, map the page, resume → "demand paging"
7. If invalid: send SIGSEGV to process

9. Our mini-os plan for 1.6

Putting it all together, here's what we'll do:

  1. Remap the PIC — change IRQ vectors from 8-15 to 32-47. New src/pic.rs module.
  2. Add timer handler at IDT[32] — uses the naked wrapper pattern from slice 7. Prints "tick" + sends EOI.
  3. Configure the PIT — program the timer chip to fire at 100 Hz (every 10ms).
  4. Enable interrupts — set IF=1. Until this, hardware interrupts are ignored.

After step 4, the kernel will print "tick" 100 times per second. We'll see it scrolling on the screen.

Pattern recognition: notice that Linux's flow (device → PIC → IDT → handler → EOI → resume) is exactly what we're about to build. Same hardware, same mechanism, just smaller scale. Linux has thousands of interrupt handlers and a sophisticated scheduler; we'll have one handler that prints "tick." But the skeleton is identical.

10. Mental model summary

  • Interrupt = "pause and call this function." The CPU does it automatically when notified.
  • PIC routes device signals to the CPU's single interrupt pin.
  • Vector = IDT entry number. PIC maps IRQs to vectors (default 8-15, we remap to 32-47).
  • EOI tells the PIC "I'm done, send the next one." Forget it = no more interrupts from that device.
  • IF is the master switch. Off by default; we enable it as the last step.
  • Linux does the same thing — same primitives, same flow, scaled up to thousands of devices and handlers.
