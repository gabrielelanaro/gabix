The GDT, in Plain English

A small list that lives in RAM. The CPU reads it to know "what memory regions exist, and who is allowed to touch each one." Everything else in this document is just unpacking that one sentence.

Quick answers first

Is this a CPU feature?

Yes — it's hardware. The CPU chip itself has a tiny storage slot called GDTR (the "GDT Register") that holds the address where the GDT lives in RAM. On every relevant operation, the CPU walks over to that RAM address and reads entries.

What is a "memory segment"?

A named region of memory with rules attached. For example: "the bytes from address 0 to 0xFFFF are code, executable but not writable, only the kernel can touch them." That whole description is one "segment."

What are "permissions" here?

Three flavors of rule, all enforced by the CPU in hardware:

  • Access type — read? write? execute?
  • Privilege tier — kernel-only, or anyone (including user programs)?
  • Presence — is this entry even real, or just empty space?

Which permissions exist exactly?

The full list (each is one bit in a GDT entry):

Readable
CPU allows reads from this region. (Code segments can be marked non-readable in theory, but in practice code is always readable.)
Writable
CPU allows writes. Code is never writable; data is.
Executable
CPU will fetch instructions from this region. Only code is executable.
Privilege tier (DPL)
0 = kernel only. 3 = anyone. (1 and 2 exist but aren't used in practice.)
Present (P)
If 0, this entry is unused. CPU will fault if anyone tries to use it.
Accessed (A)
CPU sets this to 1 the first time the segment is used. OSes use it to track which segments are hot.
Type
Is this a code segment, a data segment, or a system segment (like a TSS)?
Direction / Conforming
Obscure bits that control how segments behave across privilege changes. We can ignore them.

The CPU's GDTR register points to where the GDT lives in RAM. The CPU reads entries from that location whenever it needs to check what a segment allows.
Analogy: imagine a building with a security desk. The desk has a binder (the GDT) listing every room and its rules: "Room 101 — staff only. Room 102 — public. Room 103 — storage, no entry." Every visitor (every memory access) is checked against the binder by the security guard (the CPU). The guard's location register (GDTR) just says which binder to use.

What's actually in a GDT? (our kernel's GDT)

#0null — required to be all zeros (CPU quirk)
#1kernel code: execute + read, ring 0
#2kernel data: read + write, ring 0
#3(unused for now)
#4user code: execute + read, ring 3 (later)
#5user data: read + write, ring 3 (later)
A GDT is just an array of these entries. Index times 8 = byte offset in the array. Entry #1 starts at byte 0x08, entry #2 at byte 0x10, etc.

What is a "segment register"? Why are there several?

The CPU has 6 tiny storage slots called segment registers. Each one is meant to point at a specific kind of memory access:

CS
Code — currently running instructions
DS
Data — default for memory reads/writes
SS
Stack — push/pop and stack pointer
ES
Extra (mostly unused today)
FS
Linux/Windows: per-CPU data
GS
thread-local / per-CPU data

The value inside each register is a 16-bit number that selects an entry in the GDT. So CS = 0x08 means "use GDT entry #1 for all code accesses."

What happens when you "load a segment register"?

Say the kernel runs this assembly instruction:

mov ds, 0x10   ; "load the value 0x10 into the DS register"

The CPU does much more than just store 0x10. Here's the full sequence:

Read the value being loaded: 0x10
Strip off the bottom 3 bits (they encode privilege + which table): 0x10 >> 3 = 2
Use 2 as an index into the GDT — read entry #2 (kernel data)
Check the entry's permissions against the current privilege level. If not allowed → general protection fault (CPU exception → kernel panic if unhandled)
Cache that entry's rules inside the CPU (in a hidden "descriptor cache"). From now on, every memory access via DS uses those rules automatically — without re-reading the GDT.
Store 0x10 in the visible part of DS so the next reload sees the same value
The key idea: loading a segment register isn't just "store this number." It's "look up this entry in the GDT, validate it, and from now on use its rules for this kind of memory access." The CPU caches the rules so it doesn't have to walk to RAM every time.

Putting it together — the whole loop

1. Kernel builds a GDT in RAM at some address (say 0xA000)
↓
2. Kernel runs lgdt instruction: "GDTR, point at 0xA000"
↓
3. Kernel runs mov cs, 0x08, mov ds, 0x10, etc.
↓
4. CPU reads GDT entries #1 and #2, caches their rules
↓
5. From now on, every code/data/stack access uses those rules automatically

Why do we even need this in 64-bit mode?

Short version: history. We're paying for a design choice made in 1982.

Back then, the 80286 needed a way to enforce memory protection. They invented segmentation: divide memory into named chunks, each with rules. The GDT held those rules.

In 1985, the 386 added paging, which is a much better way to do memory protection. Segmentation became redundant.

In 2000, AMD designed the 64-bit extension (AMD64 / x86-64) and basically said: "segmentation is broken, we're making all segments flat — base address 0, no size limit, just privilege bits and type."

So in 64-bit mode, the GDT's original job (memory layout) is gone. Paging does that. The GDT survives because:

  1. The CPU still requires segment registers to be loaded with valid GDT entries for code/data/stack — even if all segments are flat.
  2. Privilege levels (kernel vs user) are stored in GDT entries. You can't say "I'm in ring 0" without a GDT entry that says so.
  3. The TSS (Task State Segment), which we'll need for interrupt stack switching later, lives in the GDT.
Analogy: imagine a building from 1982 where every door had a keycard reader that checked a printed binder of rules. In 2000 they renovated: now there's a digital access system (paging). But the old binder (GDT) is still required at the front desk, mostly ignored except for "is this person staff or public." Removing it would break too much existing infrastructure.

What this means for our kernel

We need to:

  1. Add the x86_64 crate (a Rust wrapper for hardware data structures)
  2. Build a tiny GDT in memory: [null, kernel_code, kernel_data]
  3. Run the lgdt instruction to tell the CPU where it is
  4. Reload CS, DS, SS, etc. so the CPU picks up our new entries

That's it. The result is invisible — no change on screen. The kernel just keeps running. But now we own the GDT, which we need before interrupts (M1 continues), syscalls (M4), and user-mode (M4).

Recap in one breath

GDT = a small array of entries in RAM.
Each entry says "here's a memory region, here's what kind (code/data), here's its privilege tier, here's whether it's present."
The CPU has a register (GDTR) pointing at this array.
The CPU has 6 segment registers (CS, DS, SS, ES, FS, GS) that each pick an entry from the array.
When you load a segment register, the CPU fetches the entry, validates it, and caches its rules.
In 64-bit mode, segments are flat — the GDT exists mainly for privilege levels and as a place to find the TSS.
Our kernel needs its own GDT before it can do interrupts or syscalls.
