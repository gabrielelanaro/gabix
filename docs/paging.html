4-Level Paging

How the CPU translates a virtual address to a physical one — by walking a 4-level tree of tables in RAM, using slices of the address as indices at each level. This is the heart of M2: the frame allocator manages the physical RAM these tables point at; this slice builds the tables themselves.

1. The setup

We've established that every memory access goes through paging: the program writes a virtual address, the CPU translates it to a physical address, then talks to the RAM chips. The translation is done by looking up the virtual address in a tree of tables.

The CR3 register (which we mentioned earlier) holds the physical address of the top of this tree. On every memory access, the CPU starts at CR3 and walks down through 4 levels of tables, picking one entry at each level based on parts of the virtual address. The final entry contains the physical frame address.

One translation = four memory reads. Each level of the tree is a separate table in RAM. To translate one virtual address, the CPU does 4 memory reads (one per level). This sounds slow, but the CPU caches translations in a chip called the TLB (Translation Lookaside Buffer), so most accesses don't actually walk the tree.

2. Why 4 levels? Why 9 bits per level?

A virtual address on x86-64 is 48 bits (the top 16 bits must be 0 or all-1, but we ignore those for now). The CPU splits those 48 bits into chunks, using each chunk as an index into a different table:

PML4 index (9 bits)
PDPT index (9 bits)
PD index (9 bits)
PT index (9 bits)
Page offset (12 bits)
A 48-bit virtual address, split into five chunks. Each chunk (except the offset) is an index into a different level of the page table tree.

Each table has 512 entries because 9 bits gives you indices 0–511. Each entry is 8 bytes (it has to hold a physical address plus flags). 512 × 8 = 4096 bytes = exactly one frame. So each table in the tree fits perfectly in one physical frame — which is why the frame allocator is exactly what we need to grow the tree.

5. What's inside a page table entry?

Each entry is 64 bits. Most of those bits are the physical frame address (the target of this entry), and a few are flags that control permissions and behavior.

Flags (bits 0–11) Frame address bits (12–51) Available / ignored (52–63)

The most important flag bits (the low 12):

BitNameMeaning
0Present1 = this entry has a valid mapping. 0 = page fault if accessed.
1Writable1 = code can write to this page. 0 = read-only.
2User1 = user-mode code (ring 3) can access. 0 = kernel only.
3Write-throughCaching policy. We'll ignore.
4Cache-disableCaching policy. We'll ignore.
5AccessedCPU sets this when the page is read/written. OS can clear it.
6DirtyCPU sets this when the page is written.
7Huge pageIf set in PD or PDPT, this entry maps a 2 MB or 1 GB page directly (skipping lower levels).
8–11OS-defined3 bits the OS can use however it wants.

For the page we care about most — read+write kernel data — we set Present=1, Writable=1, User=0. The frame address goes in bits 12–51, leaving bits 0–11 free for those flags (because frame addresses are always 4 KB-aligned, the low 12 bits of the address are always 0 anyway — perfect place to pack flags).

6. Our kernel's current situation

When the bootloader handed control to _start, it had already built a page table tree and loaded its top into CR3. That tree implements identity mapping for the relevant range — meaning virtual address X maps to physical address X.

That's why all of these work today:

  • ptr::write_volatile(0xB8000, byte) — virtual 0xB8000 → physical 0xB8000 (VGA buffer).
  • The kernel's own code at virtual ~0x200000 → physical 0x400000-ish... wait, no — those should be equal under identity mapping. They are: bootloader identity-mapped the entire kernel region.
  • The frame allocator's bitmap at virtual ~0x201BB6 → physical ~0x201BB6.
Why this matters for 2.2: right now, virtual and physical are the same numbers. When we replace the bootloader's tree with our own, we have to be very careful: if we accidentally unmap the code we're currently executing, the CPU faults instantly and the kernel crashes (usually triple-faults and reboots). Page-table bugs are the worst to debug.

7. What "mapping a page" actually means (the API we'll build)

To create a new mapping — say, map virtual address 0xFFFFFFFF80000000 to physical frame 638 — we do three things:

  1. Walk the tree down to the level where the entry needs to go.
  2. If a mid-level table is missing, allocate a new frame from our frame allocator, zero it (so unused entries read "not present"), and install a pointer to it in the parent.
  3. Write the leaf entry: the physical frame address + the flag bits (Present + Writable + ...).

That's it — the CPU's hardware walker takes over from there. Next time anyone accesses that virtual address, the new mapping takes effect.

8. Recap

  • Virtual address translation = walking a 4-level tree of tables in RAM, one entry per level.
  • The 48-bit address is split into 9 + 9 + 9 + 9 + 12 bits: four 9-bit indices and a 12-byte page offset.
  • Each table is exactly 4 KB (512 entries × 8 bytes) — so it fits in one frame.
  • CR3 points to the top of the tree (the PML4).
  • Each entry is 64 bits: a frame address packed with permission flags.
  • Bootloader set up identity mapping for us; we'll replace it with our own in 2.2.
  • Adding a new mapping = walk down, allocate frames for missing mid-level tables, write the leaf entry.
