Debugging the Timer Interrupt

A walkthrough of how I found and fixed two real bugs that prevented timer interrupts from firing. Each bug needed a different debugging technique. Both techniques are reusable for any future kernel debugging.

The setup

After wiring up the PIC + PIT + IDT + handler for the timer interrupt, I expected to see tick #N printed once per second. Instead: black screen. No output, no ticks.

I had to figure out which of many possible failure modes was happening:

  • Did the kernel even boot?
  • Did it panic during init?
  • Are interrupts being delivered?
  • Is the handler running?
  • Is the screen rendering correctly?

Two bugs were stacked on top of each other. Here's how I found each one.

Bug #1: PIC mask (timer was masked)

1

Symptom: ticks don't fire after enable()

First hypothesis: I'd read the pic8259 source and saw this:

// in pic8259::initialize()
// Save our original interrupt masks, because I'm too lazy to
// figure out reasonable values. We'll restore these when we're done.
let saved_masks = self.read_masks();
// ... initialization sequence ...
self.write_masks(saved_masks[0], saved_masks[1])

The library saves whatever mask state the firmware left and restores it after init. In QEMU, the BIOS leaves everything masked. So initialize() was "done" but the timer was still masked → no interrupts delivered.

2

Fix: explicitly unmask IRQ 0

After initialize(), write the masks ourselves:

pub fn init() {
    unsafe {
        let mut pics = PICS.lock();
        pics.initialize();
        pics.write_masks(0xFE, 0xFF);
    }
}

0xFE in binary is 11111110. Bit 0 = 0 means "IRQ 0 (timer) UNMASKED." All other bits = 1 means "every other IRQ masked." Slave mask 0xFF = all masked.

Bug #2: panic in set_frequency(2)

After fixing the mask, still black screen. Time to actually look inside the running kernel.

3

Tool: QEMU monitor via Unix socket

Run QEMU with -display none and a monitor socket, then send commands via nc -U:

qemu-system-x86_64 -drive format=raw,file=.../mini-os.bin \
  -display none \
  -monitor unix:/tmp/qm.sock,server,nowait &

sleep 4  # let kernel boot

# Dump first 32 bytes of VGA memory
echo "xp /32bx 0xb8000" | nc -U /tmp/qm.sock

# Print CPU registers (look at RIP)
echo "info registers" | nc -U /tmp/qm.sock

The monitor doesn't need screen-recording permission (unlike macOS screencapture) and lets us inspect any memory or register directly.

4

Found: VGA buffer was all zeros

The xp /32bx 0xb8000 command returned:

000b8000: 0x00 0x00 0x00 0x00 0x00 0x00 0x00 0x00
000b8008: 0x00 0x00 0x00 0x00 0x00 0x00 0x00 0x00
...

Not even [boot] gdt... was printed. So the kernel was hanging or panicking before any println! actually wrote.

5

Found: RIP pointed at jmp -2 (infinite loop)

info registers showed:

RIP=0000000000206c15

Disassemble around that address:

0x00206c15:  eb fe    jmp      0x206c15   # jmp -2 = infinite loop on itself

Look up the symbol with nm:

$ nm mini-os | sort | awk '$1 <= "0000000000206c15" {last=$0} END {print last}'
0000000000206c10 t rust_begin_unwind

The kernel was panicking. The infinite loop is the default panic handler doing loop {}.

6

Walk the stack to find who panicked

Dump the kernel stack with x /20gx $rsp. The non-zero values are return addresses:

0x...1f80: ... 0x000000000020dc14   # panic fmt helper
0x...1f90: ... 0x000000000021b468
0x...1fa0: ... 0x00000000002017ee
0x...1fc0: ... 0x000000000020778e   # in pit::set_frequency
0x...1fe0: ... 0x0000000000206caa   # return addr from set_frequency call
0x...1ff0: 0x0000000000206c20       # _start

The call chain (top = innermost):

_start (0x206c20)
  ↓ calls at 0x206ca5
pit::set_frequency (0x207730)
  ↓ panics
rust_begin_unwind (0x206c15)
  ↓ loops forever
stuck

So pit::set_frequency was the source of the panic.

7

The panic: divisor overflow

Look at the source of set_frequency:

pub fn set_frequency(frequency_hz: u32) {
    let divisor = BASE_FREQUENCY_HZ / frequency_hz;
    assert!(divisor < 0x10000, "frequency too low — divisor doesn't fit in 16 bits");
    ...
}

For frequency_hz = 2: divisor = 1193182 / 2 = 596591. That's way bigger than 0x10000 (65535). Assert fails → panic.

Physical reason: the PIT divisor is a 16-bit register. Max value 65535. The PIT's base clock is ~1.193 MHz, so the minimum programmable frequency is 1193182 / 65535 ≈ 18.2 Hz. You literally cannot ask for 2 Hz.

8

Fix: 100 Hz + throttle the printing

Use a realistic frequency (100 Hz is Linux's default), then throttle the visible output:

// In _start:
pit::set_frequency(100);

// In interrupts.rs:
static TICKS: AtomicUsize = AtomicUsize::new(0);

extern "C" fn timer_inner(_sf: &InterruptStackFrame) {
    let count = TICKS.fetch_add(1, Ordering::SeqCst) + 1;
    if count % 100 == 0 {
        println!("tick #{}", count);
    }
    unsafe { crate::pic::PICS.lock().notify_end_of_interrupt(0x20); }
}

Result: timer fires 100×/sec (good for scheduling), but we only see tick #100, tick #200, etc. — once per second.

Bug #3 (gotcha): stale bootimage

After applying both fixes, the screen was STILL black. VGA dump showed all zeros.

The trap: cargo build rebuilds the kernel ELF, but the bootable disk image (bootimage-mini-os.bin) is built by the bootimage tool. If you only ran cargo build, QEMU is booting the old kernel.

Fix: always run cargo run (which triggers bootimage) or cargo bootimage explicitly after code changes. Don't trust cargo build alone when running in QEMU.

The debugging toolkit, summarized

echo "xp /Nbx ADDR" | nc -U /tmp/qm.sock
Dump N bytes of physical memory at ADDR. Use 0xb8000 for VGA, 0x21d7f0 for IDT, etc.
echo "info registers" | nc -U /tmp/qm.sock
Print all CPU registers. RIP tells you what's executing; RSP where the stack is.
echo "x /20i ADDR" | nc -U /tmp/qm.sock
Disassemble 20 instructions starting at ADDR. Lets you see what the CPU is actually running.
echo "x /20gx $rsp" | nc -U /tmp/qm.sock
Dump 20 8-byte values from the stack. Non-zero values are usually return addresses — walk them to get a backtrace.
nm mini-os | sort | awk '$1 <= ADDR {last=$0} END {print last}'
Look up which function contains a hex address. Walks sorted symbol table, returns the most recent function whose address ≤ target.
objdump -d mini-os | grep -A 20 "FN_NAME:"
Disassemble a specific function by name. Useful to verify what the compiler generated.
cargo bootimage
Rebuild the bootable disk image. Must run this (or cargo run) after code changes; cargo build alone leaves a stale .bin.
qemu ... -d int -D qemu.log
Log every interrupt/exception to a file. Useful for tracing fault cascades.

The mental flowchart

Kernel doesn't print what I expect
    ↓
Dump VGA at 0xb8000
    ├─> Has text?  → writer is fine, problem is elsewhere
    └─> All zeros? → kernel isn't writing
         ↓
         Check RIP via monitor
            ├─> RIP in real code? → kernel running, look at what it's doing
            └─> RIP at eb fe (jmp -2)? → stuck in panic handler
                 ↓
                 Walk stack (x /20gx $rsp)
                    ↓
                    Decode return addresses via nm
                       ↓
                       Find which function panicked
                          ↓
                          Read its source — usually obvious why

Lessons

  1. Read the source of your dependencies. The pic8259 mask behavior was a 4-line comment in its source. Saved hours of guessing.
  2. QEMU monitor is your GDB. It's available even when GDB isn't set up. Can inspect any memory or register, disassemble, walk stacks.
  3. Panic handler with loop {} is a black hole. It hides the panic. We had to read RIP and the stack to figure out it was a panic at all.
  4. Know your hardware's constraints. PIT max divisor 65535 isn't a software choice — it's a 16-bit register. The error message tells you only if you ask.
  5. Rebuild via the right tool. cargo build ≠ cargo bootimage. One of them gives you a stale binary.
  6. Debug method > guess-and-check. Five minutes of inspection (VGA dump, RIP, stack) saved an hour of trial-and-error.
