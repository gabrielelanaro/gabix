CPU Concurrency: How Tasks Sleep and the CPU Idles

A concrete swimlane trace of the echo server receiving one UDP packet — showing exactly when the process sleeps, when the CPU sleeps, and what wakes each one.

Four entities interact: the CPU core (the hardware), Task A (the echo server user process), the timer (PIT, firing every 10 ms), and the virtio-net device (the network card). Each has its own notion of "sleeping" and "waking." This trace shows how they relate.

The key distinction

Process sleep ≠ CPU sleep

Process sleep (Blocked state)
The task's state field is set to Blocked inside the scheduler's task table. The task struct stays in memory. The scheduler skips it when picking the next task. The task consumes zero CPU — it simply never gets picked.
CPU sleep (hlt instruction)
The physical CPU core stops executing instructions and enters a low-power halt state. It stays halted until a hardware interrupt arrives (timer, device, NMI). The CPU doesn't know about tasks — it just stops and waits for a signal.
Task switch (yield_now)
The scheduler saves the current task's registers, picks the next Ready task, loads its registers, and returns. The CPU never stops — it just switches from executing one stack to another.
Interrupt (ISR)
A hardware signal causes the CPU to stop whatever it's doing (including hlt), push a frame, and jump to a handler in the IDT. After iretq, the CPU resumes wherever it was — including inside hlt, which then finishes.

A process can sleep while the CPU runs a different process (multiplexing). A process can sleep and the CPU also sleeps (idle loop). Both happen in the trace below.

The scenario

The echo server (the only user task) calls recvfrom. The socket queue is empty, so it blocks. No other task exists. The CPU enters the idle loop and sleeps. 10 ms later the timer fires, the scheduler rescans, finds nothing, and sleeps again. At 17 ms the host sends a UDP packet. The device fires an interrupt. The ISR delivers the datagram, wakes the task, and returns. The scheduler resumes the echo server, which processes the packet and sends a reply. Then it blocks again.

What makes multiplexing work

In this trace there was only one task. With two tasks, the picture changes at step 3. When Task A blocks and yields, instead of entering the idle loop, the scheduler finds Task B is Ready and switches to it:

CPU runs Task B. The timer fires every 10 ms and the ISR calls yield_now(), but Task A is still Blocked, so the scheduler picks Task B again. Task B gets the full CPU. The timer is still firing — it's the heartbeat that gives the scheduler a chance to re-check whether Task A has been woken. When the packet arrives at T=17 ms, the RX ISR wakes Task A, and the next timer tick (or the idle-loop rescan) switches to it.

With two tasks, the CPU never sleeps — Task B keeps it busy. The idle loop only runs when every task is blocked. That's the difference between "CPU running another task" and "CPU sleeping." The scheduler handles both.

Summary: the four mechanisms

Task sleeps → CPU runs another task
Task A is Blocked. Task B is Ready. Scheduler switches to B. CPU keeps running. This is multiplexing.
All tasks sleep → CPU sleeps
Every task is Blocked. Scheduler enters idle loop. hlt. CPU physically halts. This is the idle path.
Hardware interrupt wakes the CPU
Timer fires (every 10 ms) or device fires (packet arrived). CPU wakes from hlt. ISR runs. If the ISR woke a task, the scheduler resumes it.
Timer is the multiplexing heartbeat
Without the timer, a sleeping CPU would never wake to check whether tasks are ready. The timer fires at 100 Hz, giving the scheduler 100 chances per second to switch tasks.
