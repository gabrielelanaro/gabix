Module 1 — The CPU

A program running on the CPU can, in principle, read or write any memory and run any instruction. The kernel has to stop user programs from doing that, and it has to give each program a controlled way back in when it needs the kernel to do something for it — read a file, send a packet, get the time. This module covers both: running a program with fewer privileges, and the door a program knocks on to call the kernel. x86 and ARM solve the same two problems differently; we read both.

  • 1.01 privilege and the syscall door
  • 1.02 interrupt entry — how a device or a timer grabs the CPU's attention

Module 2 — Memory

Every program must see its own memory and must not see another program's memory or the kernel's. The CPU enforces that with a table it checks on every memory access: the table says, for each range of addresses, where the bytes really live and whether this program is allowed to reach them. This module covers how that table is built and how the CPU is switched on to start using it. x86 gives each process its own table; the ARM port so far uses one shared table for everything.

  • 2.01 Two programs using the same address
  • 2.02 turning the table on — the sequence that makes the CPU start using it

Module 3 — Processes

To run more than one program, the kernel has to pause one, remember exactly where it was, and resume another later — without either program noticing. Starting a new program means reading its file off disk and laying its code out in memory. And one program has to be able to start a copy of itself, replace itself with a different program, and wait for a child to finish. This module covers all three, plus the small set of CPU registers the kernel must save and restore to switch between programs on x86 and on ARM.

Module 4 — Devices

The CPU has to find the devices wired to the board — a disk, a network card — and move bytes in and out of them. It also has to learn the moment a device finishes a job, instead of asking over and over. This module covers how the kernel discovers a device, how it hands the device a read or write request and learns the device is done, and how the device signals the CPU when there is news. x86 finds devices on a shared bus and is signaled by one interrupt controller; the ARM QEMU machine places devices at fixed memory addresses and is signaled by another. The request and response machinery is the same on both.

Module 5 — Storage

A file is not really a file to the hardware — it is a set of fixed-size sectors scattered across a disk. This module covers the three layers that turn those sectors into the open / read / write / close a program calls: the layer that reads one sector, the layer that gives every file the same interface regardless of where it lives, and the layer that knows where the ext2 filesystem keeps each file's data on the disk. None of this depends on the CPU; the x86 and ARM kernels share it.

Module 6 — Networking

To send bytes to another computer over a wire, the kernel has to wrap them in the frame the wire expects, find the other machine's address, hand the frame to the network card, and — when the bytes matter — make sure they arrive, in order, exactly once. This module walks that path one layer at a time, from the raw frame up to a reliable stream a program can read and write like a file. Each layer has a name you will meet inside. The code does not depend on the CPU, so the x86 lessons carry straight over to ARM. The open end is the layer that talks to a web server — the path to the LinkedIn goal.

Module 7 — Real hardware: the Raspberry Pi 2B

The ARM manual describes the CPU core. It does not describe the actual chips on a Raspberry Pi board — the SD card socket, the USB sockets, the Ethernet socket. Those chips are made by Broadcom, they have their own manual, and they have their own rules for how you talk to them. This module covers those chips: how the Pi reads the SD card, drives its USB port, and reaches Ethernet through a chip that bridges USB to Ethernet. This is the gap between "works in the emulator" and "works on the board you plug in Monday."
