Lesson 6 · M4 · Disk path — bring the device online

virtio Device Initialization

Read the capability list, do the virtio handshake. At the end the device is "live" — ready for virtqueues in Lesson 7.

Read time ~25 min Build time ~30–45 min Prereq Lesson 5

Lesson 5 found the virtio-blk device at PCI slot 00:04.0 and decoded its BARs — the modern transport region lives at 0xFE000000 in BAR4. But we can't read or write sectors yet. Before any I/O, the device has to be brought up through a specific handshake: reset, acknowledge, identify the driver, agree on features, ready. This lesson walks through how the virtio PCI modern transport exposes its registers via a capability list in PCI config space, and how the handshake works bit by bit.

Why virtio exists

A real hard disk has its own hardware controller that speaks a specific protocol over a specific bus (SATA, SCSI, NVMe). When QEMU wants to give a VM a disk, it has two choices:

  1. Emulate real hardware — QEMU pretends to be a real Intel SATA controller. The guest runs unmodified Intel SATA drivers. Works, but slow: every register access traps, and the emulation has to model hardware quirks.
  2. Paravirtualize — QEMU says "I'm a virtio device, designed for VMs." The guest runs a virtio driver that knows it's talking to a hypervisor. Communication is via shared-memory ring buffers — no per-register emulation, faster, simpler.

Virtio (originally by Rusty Russell at Red Hat, ~2007) standardized the paravirtual approach. The current spec is OASIS VIRTIO 1.2 — virtio-net, virtio-blk, virtio-scsi, virtio-gpu, virtio-console, virtio-rng, etc. all share the same transport layer. We're using virtio-blk.

Modern vs legacy vs transitional. Three transports exist. Legacy (the original) uses I/O ports — that's BAR0 in our 5.4 output. Modern (the current default since ~2017) uses memory-mapped I/O via the capability list. Transitional devices support both — that's what QEMU exposes. We're going modern: it's the cleaner interface and what Linux uses by default. We ignore the legacy BAR entirely.

The PCI capability list

The "PCI capability list" is a generic PCI mechanism (not virtio specific) for a device to advertise optional features. It's a linked list of capability records living in the upper half of config space (offsets 0x40–0xFF).

The list starts at the offset stored in the capabilities pointer field at offset 0x34 in the standard config header. Each capability record is:

offset+0 cap_id u8 — capability type (0x09 = vendor specific, 0x01 = Power Management, etc.) offset+1 next_ptr u8 — offset of next capability in config space, 0 = end of list offset+2 length u8 — total length of this capability (header + body) offset+3 data u8[..] — capability-specific body, length-3 bytes

To enumerate capabilities: read offset 0x34 to get the first capability's offset, read that capability, follow next_ptr to the next, repeat until next_ptr is 0.

What capability IDs exist?

Some standard ones we might see in QEMU's virtio-blk:

• 0x01 Power Management — standard PCI PM (sleep states, etc.)
• 0x05 MSI (Message Signaled Interrupts) — interrupt delivery without the legacy PIC
• 0x11 MSI-X — extended MSI, more vectors
• 0x09 Vendor Specific — the catch-all for vendor-defined capabilities. virtio uses this one.
• 0x10 PCI Express — for PCIe devices

For virtio, we ignore everything except 0x09. The vendor-specific body has a virtio-specific sub-header (see below).

The virtio vendor-specific capability

When cap_id == 0x09, the next bytes are vendor-defined. virtio defines a sub-header:

offset+0 cap_id u8 = 0x09 (vendor specific) offset+1 next_ptr u8 offset+2 length u8 offset+3 cfg_type u8 — virtio sub-type (see below) offset+4 bar u8 — which BAR (0-5) this region lives in offset+5 padding u8[3] offset+8 offset u32 — offset within the BAR (in bytes) offset+12 length u32 — length of the region (in bytes)

So each virtio cap says: "structure cfg_type lives at BAR N + offset M, for L bytes." We translate that into a virtual address (BAR base + offset) and access it via normal memory loads/stores.

The cfg_type values:

  • 1 — common config: device status, feature negotiation, queue_select. The bulk of the handshake.
  • 2 — notifications: where the guest writes to "kick" the device after submitting work.
  • 3 — ISR status: where the device writes to signal interrupt.
  • 4 — device-specific config: virtio-blk puts its disk size, sector size, etc. here.
  • 5 — PCI config alt access: an alternative way to read the common config (we won't use).

Memory-Mapped I/O (MMIO)

The caps point at regions inside the device's BARs. To access those regions, the kernel uses MMIO — Memory-Mapped I/O. The CPU executes a normal memory load/store, the address routes to the device's registers instead of RAM, and the device sees the access. To the instruction's perspective, RAM and device registers look identical; only the page tables know which physical address belongs to what.

MMIO is the foundation of every modern device driver on x86. Before diving into the common config layout, let's pin down how it works.

The address routing pipeline

When the CPU executes mov rax, [0x180FE000014], the request flows through several layers:

CPU executes mov rax, [0x180FE000014]
↓ virtual address
MMU walks page tables — finds virt 0x180FE000014 → phys 0xFE000014
↓ physical address on the memory bus
PCI host bridge decodes address — 0xFE000000 falls in BAR4's range
↓ routes to virtio-blk instead of RAM
virtio-blk device sees a read at offset 0x14 — returns device_status
↓ response flows back up
rax now holds the device_status byte
The CPU has no idea this isn't a RAM access. The MMU has no idea either — it just translates virt to phys via the page tables. The PCI host bridge is the first component that decides "this address belongs to a device, not RAM."

None of this is special to virtio. Every PCIe (Peripheral Component Interconnect Express) device on modern x86 uses MMIO for its registers — network cards, GPUs (Graphics Processing Units), NVMe (Non-Volatile Memory Express) drives, USB (Universal Serial Bus) controllers, all of them.

Two address spaces on x86

x86 has two separate address spaces, accessed by different CPU instructions:

Memory space mov / load / store — 64-bit address range. RAM and MMIO regions live here. I/O port space in / out — 16-bit address range (64K ports). Legacy. PCI config space at 0xCF8/0xCFC lives here.

We've already used both. PCI config space access in src/pci.rs uses Port<u32>::read/write (which wrap in/out) — that's I/O port space. virtio MMIO access in src/virtio.rs uses read_volatile(addr) (which compiles to a normal mov) — that's memory space.

Why does x86 have two address spaces at all?

History. The original IBM PC (1981, Intel 8088) had only the I/O port space — in/out instructions, 16-bit port addresses. Devices like the keyboard controller, serial port, and PIT (Programmable Interval Timer) lived at fixed port addresses (0x60, 0x3F8, 0x40, etc.). RAM was a separate physical thing accessed via memory loads.

The 80286 (1982) introduced protected mode with a 24-bit memory address space. The 80386 (1985) took it to 32-bit. Memory became huge, but the I/O port space stayed at 16 bits because of backward compatibility — existing software expected in/out to work the same way.

PCI (1992) inherited this split: configuration space used port I/O (0xCF8/0xCFC) and BARs used memory space (MMIO). PCIe (2004) tried to move everything to memory space with the ECAM (Enhanced Configuration Access Mechanism) — config space accessed via MMIO instead of ports — but the legacy port interface was kept for compatibility. Modern OSes use ECAM; we use the legacy port interface because it's simpler.

The long-term trend is everything-in-memory-space. I/O ports are kept for legacy hardware and configuration access. ARM, for comparison, never had this split — everything is memory-mapped there.

Same conceptual operation, two ways

Compare reading a register using port I/O vs MMIO:

— Port I/O: PCI config read (two-step protocol) 
// Reading vendor_id of device at 00:00.0 via port I/O
let address = (1 << 31) | (0 << 16) | (0 << 11) | (0 << 8) | (0x00 & 0xFC);
unsafe {
    let mut addr_port: Port<u32> = Port::new(0xCF8);
    let mut data_port: Port<u32> = Port::new(0xCFC);
    addr_port.write(address);    // out dx, eax  — sets the address
    data_port.read()             // in eax, dx   — reads the data
                                // (returns vendor_id | device_id packed)
}
— MMIO: virtio register read (one-step) 
// Reading device_status of virtio-blk via MMIO
let common_virt = 0x180FE000000;  // phys_offset + BAR4_base + common_cap.offset
let status = unsafe {
    read_volatile((common_virt + 0x14) as *const u8)
};                              // mov al, [0x180FE000014]  — one instruction

The MMIO version is one instruction. The port I/O version is two instructions, and in/out are serializing — the CPU flushes its pipeline before executing them. MMIO is significantly faster.

The page table mapping that makes MMIO work

MMIO doesn't work by magic. For the CPU's mov instruction to reach the device, the kernel's page tables need an entry mapping some virtual address to the device's physical BAR address. Without that entry, the MMU has no translation and the access page-faults.

That's what map_mmio(phys, size) in src/memory.rs does — explicitly create the page table entries for an MMIO region:

src/memory.rs — map_mmio: bridge the gap between device and CPU 
pub fn map_mmio(phys_start: u64, size: u64) -> u64 {
    let offset = phys_offset();                  // bootloader's direct-map base
    let virt_start = phys_start + offset;

    let aspace = AddressSpace::from_current();
    let flags = PageTableFlags::PRESENT
        | PageTableFlags::WRITABLE
        | PageTableFlags::NO_CACHE       // ← load-bearing for MMIO
        | PageTableFlags::NO_EXECUTE;

    for page in Page::range_inclusive(start_page, end_page) {
        if translate(page.start_address()).is_none() {
            unsafe { aspace.map_to(page.start_address(), current_phys, flags).unwrap(); }
        }
        current_phys += 4096;
    }
    virt_start
}

After map_mmio(0xFE000000, 0x1000) runs, the kernel page tables have entries like:

virt 0x180FE000000 → phys 0xFE000000 (NO_CACHE | WRITABLE | PRESENT) virt 0x180FE001000 → phys 0xFE001000 (next page in the BAR4 region) virt 0x180FE002000 → phys 0xFE002000 (and so on, for the full BAR4 length)

Now any mov to those virtual addresses routes through the MMU, lands at physical addresses in BAR4's range, and reaches the virtio-blk device.

Why NO_CACHE is load-bearing

For RAM, the CPU caches loads in L1/L2 cache. That's safe — the CPU is the only writer to RAM (mostly), and the cache coherency protocol keeps everything in sync.

For MMIO, caching would break correctness. Device registers change without the CPU's involvement: the device writes a status bit, posts a completion, raises an interrupt. The CPU's cache wouldn't see those changes — the next load would return the cached (stale) value, and the protocol breaks.

The NO_CACHE page table bit (called PCD — Page Cache Disable in the x86 manuals) tells the MMU "don't cache loads or stores from this page." Every access goes straight to the bus, bypassing L1/L2. The device sees every read; we see every device write.

What does NO_CACHE actually do at the hardware level?

Two mechanisms work together to keep MMIO uncached on x86:

• PCD bit in page table entries (the NO_CACHE flag we use). When set, the CPU bypasses L1/L2 cache for loads/stores from that page. The address goes straight to the L3 (or last-level) cache or directly to the memory bus.

• MTRRs (Memory Type Range Registers). Firmware-configured registers that define cache policy per physical address range. The BIOS (or in our case, QEMU's SeaBIOS) programs MTRRs so MMIO regions like PCI BARs default to uncached, even if the page table doesn't specify. Belt and suspenders — both mechanisms agree.

On modern x86 there's also PAT (Page Attribute Table), which extends the cache hints in the PTE. Together: PAT > MTRR for caching decisions, with the PCD bit being a coarse fallback. For virtio in our setup, setting NO_CACHE in the page table is sufficient.

Without any of these mechanisms, MMIO would be cached and the device protocol would silently break — we'd read stale status bytes, miss completions, and waste hours debugging "why doesn't my handshake complete."

Putting it together for virtio-blk

BAR4 at physical 0xFE000000 is the modern transport region. The common config capability (cfg_type=1) says it's at offset 0x0000 within BAR4. So:

  • Common config physical address = BAR4 base + common cap offset = 0xFE000000 + 0x0000 = 0xFE000000
  • Common config virtual address = phys_offset + physical = 0x18000000000 + 0xFE000000 = 0x180FE000000
  • device_status location = common config + 0x14 = 0x180FE000014

To read device_status, the kernel does:

src/virtio.rs — read_common_u8: actual code we use 
fn read_common_u8(&self, offset: u8) -> u8 {
    unsafe {
        read_volatile((self.common_virt + offset as u64) as *const u8)
    }
}

// Calling it:
let status = virtio_blk.read_common_u8(0x14);  // reads device_status

The read_volatile wrapper is critical. Without it, the Rust compiler would be free to elide or reorder the load — for example, if you read device_status twice in a row waiting for a bit to change, the compiler might optimize the second read away ("we just read this, return the cached value"). read_volatile tells the compiler "this access has side effects, emit every load exactly as written."

MMIO in one sentence. Map the device's BAR region into kernel memory with NO_CACHE, then access it with normal load/store instructions wrapped in read_volatile / write_volatile to prevent compiler optimization.

With MMIO under our belts, the rest of the lesson is about what lives at those MMIO addresses — the common config region's fields, the status byte, and the handshake sequence.

The common config region

The common config region (cfg_type 1) is the heart of the device. Its layout (from the virtio spec):

0x00 device_feature_select u32 RW — selects which 32-bit half of features to read 0x04 device_feature u32 RO — read the selected feature half 0x08 driver_feature_select u32 RW — selects which half to write 0x0C driver_feature u32 RW — write the features we support 0x10 msix_config u16 RW — MSI-X vector (we use polling) 0x12 num_queues u16 RO — how many virtqueues the device has 0x14 device_status u8 RW — the handshake byte (see below) 0x15 config_generation u8 RO — increments on device config change 0x16 queue_select u16 RW — which queue the queue_* fields below refer to 0x18 queue_size u16 RW — set queue size (power of 2) 0x1A queue_msix_vector u16 RW 0x1C queue_enable u16 RW — bit to activate a queue (after setup) 0x1E queue_notify_off u16 RO — offset multiplier for notifications 0x20 queue_desc u64 RW — guest-physical address of descriptor table 0x28 queue_avail u64 RW — address of available ring 0x30 queue_used u64 RW — address of used ring

That's a lot — but for Lesson 6's handshake we only touch device_feature, driver_feature, and device_status. The queue fields come back in Lesson 7.

The handshake sequence:

  1. Reset: write 0 to device_status. Device returns to fresh state.
  2. ACKNOWLEDGE: write 0x01. "Guest knows about this device."
  3. DRIVER: write 0x03 (ACKNOWLEDGE | DRIVER). "Guest has a driver for this device."
  4. Read device features: set device_feature_select, read device_feature. These are the features the device supports (VIRTIO_BLK_F_BLK_SIZE, etc.).
  5. Write driver features: write the subset we support to driver_feature.
  6. FEATURES_OK: write 0x0B (ACK | DRIVER | FEATURES_OK). Then read device_status back and verify FEATURES_OK is still set. If the device didn't accept our feature subset, it clears this bit — we'd have to retry or give up.
  7. DRIVER_OK: write 0x0F (ACK | DRIVER | FEATURES_OK | DRIVER_OK). "Guest is ready to drive." Device is now live.

After DRIVER_OK, the device is in operational state. Setting up virtqueues (Lesson 7) becomes possible. Doing actual I/O (Lesson 8) requires queues configured.

Why split the handshake into so many bits?

Each bit is a checkpoint. If the device sees a problem at any stage, it can refuse to advance — and the guest can see exactly which stage failed.

ACKNOWLEDGE vs DRIVER: distinguishes "I see you exist" from "I have a driver that understands you." A PCI bus scanner might ACKNOWLEDGE every device without having drivers for all of them.

FEATURES_OK is the trickiest. The guest proposes features, then sets FEATURES_OK, then re-reads the bit. If the device clears it, the proposed features were incompatible. This lets features be negotiated rather than the device silently ignoring unsupported bits.

DRIVER_OK is the final "go" signal. Before this bit is set, the device ignores virtqueue activity — you can configure queues safely without the device trying to use them.

FAILED (0x80) and DEVICE_NEEDS_RESET (0x40): error indicators the guest can read at any time to detect problems.

Build steps — your turn

Four substeps. Each is a focused commit. The first one is the heaviest — parsing the capability list is real work.

6.1Parse the capability list

In src/virtio.rs (new module), implement parse_capabilities(bus, device, func):

  1. Read capabilities pointer at config offset 0x34 — gives first cap's offset.
  2. Loop: at each cap offset, read cap_id, next_ptr, length.
  3. If cap_id == 0x09 (vendor specific), read the virtio sub-header: cfg_type, bar, offset, length.
  4. Print each virtio cap found (cfg_type, BAR, offset, length).
  5. Follow next_ptr to the next cap, until next_ptr == 0.

Call from main.rs after step 5.4's find_virtio_blk(). Verify you see five virtio capabilities (common, notify, ISR, device, possibly PCI).

6.2Reset, ACKNOWLEDGE, DRIVER

Build a VirtioBlk struct that holds the bus/device/func coordinates plus the parsed capability offsets (common config address, notify address, ISR address). Implement MMIO write helpers for the common config region — write_status(byte), write_driver_feature_select(u32), write_driver_feature(u32).

Implement init(): write 0 to status (reset), read back to confirm, then write ACKNOWLEDGE | DRIVER (0x03).

6.3Negotiate features

Read device_feature_select = 0, read device_feature — that's bits 0-31 of features. (Bits 32-63 are at device_feature_select = 1; for virtio-blk the basic features all fit in the low 32 bits.)

For mini-os, we support basically nothing fancy — just VIRTIO_F_VERSION_1 (bit 32, so we need to write select=1 and set bit 0 of the high half). Optionally VIRTIO_BLK_F_BLK_SIZE (bit 6) if the device offers it. Write the masked subset to driver_feature for both halves.

Set FEATURES_OK (status = 0x0B). Read status back, assert FEATURES_OK is still set.

6.4DRIVER_OK — device is live

Write ACKNOWLEDGE | DRIVER | FEATURES_OK | DRIVER_OK (0x0F) to status. Read back, assert it's 0x0F (no FAILED bit, no NEEDS_RESET). Print "[virtio] device is live".

The device is now in operational state. Lesson 7 will configure virtqueues on it; Lesson 8 will issue the first read.

Pause and think

The virtio handshake requires the guest to set FEATURES_OK, then re-read the bit to confirm the device accepted the proposed features. Why this dance? Why not just have the device accept any valid subset of features silently and let the guest assume it worked?
