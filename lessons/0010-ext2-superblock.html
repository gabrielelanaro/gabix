ext2 Superblock

Read the on-disk filesystem's first structure: the superblock. It tells us everything about how the disk is organized — block size, inode count, where things live.

Read time ~20 min Build time ~25–35 min Prereq Lesson 9

Lessons 5–9 built the disk path: PCI, virtio, virtqueues, block layer. We can read any sector by number and get 512 bytes back. Now we start interpreting those bytes as a filesystem. ext2 is the format we'll use — old, simple, well-documented, the predecessor of ext3 and ext4. The Linux kernel still has ext2 support in fs/ext2/; we'll read its source alongside.

What "filesystem on disk" means

The disk doesn't know it's ext2. Bytes are bytes — a flat array of 512-byte sectors. ext2 is a convention for how to interpret those bytes: where the metadata lives, how to find an inode, how to parse a directory entry, where file data starts. Two programs can look at the same disk and see different things — one sees random bytes, another sees a tree of files. The difference is whether they know the convention.

We're going to teach the kernel the ext2 convention. The first structure to parse is the superblock — the "header" of the filesystem that says "I am ext2, my blocks are this big, I have this many inodes, my data starts here." Everything else we'll do (looking up inodes, walking directories, reading file contents) starts from numbers in the superblock.

Historical context — where ext2 fits

ext2 (1993, designed by Rémy Card) was Linux's default filesystem for a decade. It succeeded ext (1992), which itself succeeded the MINIX filesystem — the latter limited to 64 MB disks and 14-character filenames because it was built for teaching. Linus needed something production-ready for Linux without licensing MINIX's code.

The "Extended Filesystem" family that followed kept ext2's basic on-disk structure:

  • ext3 (2001, Stephen Tweedie) — ext2 plus journaling. Mounts ext2 filesystems unchanged. The journal records metadata changes; on crash, the kernel replays the journal instead of running full fsck. Backwards compatible.
  • ext4 (2008) — ext3 plus extents, bigger size limits, metadata checksums, persistent preallocation. Extents replace the direct+indirect+double+triple block-pointer scheme with "this file is N MB starting at block X" — much better for large files. Backwards compatible with ext2/ext3.

Understanding ext2 mostly gets you the structure of all four. The differences are additions layered on top, not redesigns. ext4 is the default on most Linux distributions today; ext2 is now niche (embedded systems, recovery environments, teaching).

Why ext2 looks the way it does — designed for 1993-era hardware:

  • Block-group locality reduces seek time on spinning disks. Keeping a file's inode and its data blocks in the same group means the disk head moves less. QEMU has no seek penalty, but the design survives.
  • Bitmaps for free-space tracking were the obvious choice when RAM was scarce — one bit per block, easy to scan. Modern filesystems (XFS, Btrfs) use B-trees for the same job.
  • Direct + indirect + double-indirect + triple-indirect block pointers (Lesson 12) were a simple way to scale to large files without extents. ext4 replaced this scheme because it gets expensive for huge files.

Comparison to FAT

FAT (File Allocation Table, 1977, Microsoft) is the simplest common filesystem. Where ext2 optimizes for Unix semantics on local disks, FAT optimizes for portability across systems:

  • No journal, no checksums, no permissions, no hard links, no symlinks.
  • Linked-list allocation — each cluster points to the next, so reading a large file means seeking across the disk following pointers.
  • 4 GB max file size on FAT32; ext2 supports ~2 TB with 4 KiB blocks.
  • Filenames: 8.3 on FAT16, up to 255 chars on FAT32 (with long-filename extension); ext2 always supported 255 chars.

FAT still lives where its simplicity wins: UEFI boot partitions (the EFI System Partition on every modern PC), USB sticks for cross-OS compatibility, SD cards, embedded devices. ext2 lives in embedded Linux, recovery environments, and (for us) as a teaching vehicle.

Why we're using ext2 for mini-os: it has Unix semantics (permissions, hard links, symlinks — which we'll want later for the syscall layer) without ext4's extents complexity or ext3's journal. The parser is small enough to write in one lesson; ext4 would need extent decoding first.

Terminology — the words you'll meet

Five terms you'll see in the superblock fields. Each one solves a specific problem the filesystem designer faced.

Block. ext2's unit of allocation. Default 1024 bytes. A file occupies whole blocks; a 100-byte file wastes 924 bytes of its last block. The tradeoff: bigger blocks mean less metadata overhead (fewer block pointers per file) but more waste per file. mkfs.ext2 picks 1024 for small disks. Compare with sector: the device's unit (always 512 B for virtio-blk). Block = filesystem's unit. Two 1024-byte blocks = four 512-byte sectors.

Inode (index node). The metadata for one file. Holds: size, timestamps, permissions, link count, and pointers to the data blocks (we'll meet the pointer structure in Lesson 12). Notably does not hold the file name — multiple names (hard links) can point at one inode. ext2 inodes are 128 bytes by default. Numbered starting at 1; inode 2 is the root directory by ext2 convention. (You met inodes in Lesson 1's VFS work — same concept, here it's the on-disk representation.)

Block group. The filesystem is divided into chunks of roughly 8192 blocks each. Each group is self-contained: its own inode table, its own inode bitmap, its own block bitmap. Why? Locality — keeping a file's inode and its data blocks in the same group reduces disk seek time on physical drives. Less relevant for virtio/QEMU (no seek penalty), but the design survives from the spinning-disk era. Our 1 MB disk is small enough to have just one block group.

Superblock. The 1024-byte filesystem header at byte offset 1024 (sector 2). Holds the magic number, block size, total inode count, total block count, etc. Every kernel that mounts ext2 reads this first. Has backups in each block group (see the probe question).

Magic number. Two bytes that say "I am ext2." Always 0xEF53. If you don't see this value at offset 56 of the superblock, either the disk isn't ext2 or you're reading the wrong offset. It's the first thing our parser checks before trusting anything else.

Terms we'll meet in later lessons, not needed for Lesson 10:

  • Inode table — array of on-disk inodes within a block group (Lesson 12)
  • Block Group Descriptor Table (BGDT) — table describing where each group's structures live (Lesson 13)
  • Inode bitmap / block bitmap — used/free tracking bits (Lesson 13+)
  • Direct / indirect / double-indirect / triple-indirect block pointers — how an inode points at its data blocks (Lesson 12)

The on-disk layout of an ext2 filesystem

mkfs.ext2 (which we'll use to format our disk image) lays out the filesystem in blocks. The default block size for small filesystems is 1024 bytes (we'll see this in the superblock). Layout from byte 0:

bytes 0–1023 Boot sector block 0 · 1024 B Reserved for bootloader. ext2 ignores it.
bytes 1024–2047 Superblock ← Lesson 11 block 1 · 1024 B "I am ext2." Magic number, block size, counts, where everything else lives.
bytes 2048– Block Group Descriptor Table block 2+ · 32 B per descriptor One entry per block group: where the inode bitmap, block bitmap, and inode table live for that group.
... Block groups (repeating) many blocks Each group: superblock copy (sometimes), descriptors, bitmaps, inode table, data blocks.

For our 1 MB disk image, mkfs.ext2 will create one block group. The superblock is at byte offset 1024, which is sector 2 (1024 ÷ 512). Our read_sector(2) from Lesson 9 returns the first half of the superblock; read_sector(3) returns the second half. Most fields we care about live in the first half, but to be safe we'll read both.

The superblock's important fields (first 64 bytes)

ext2 superblock (first 64 bytes of 1024) 1024 bytes total
s_inodes_count u32 · 4 B 0x00
s_blocks_count u32 · 4 B 0x04
s_r_blocks_count u32 · 4 B 0x08
s_free_blocks u32 · 4 B 0x0C
s_free_inodes u32 · 4 B 0x10
s_first_data_block u32 · 4 B 0x14
s_log_block_size u32 · 4 B 0x18
(other fields) u32 · 28 B 0x1C–0x37
s_magic u16 · 2 B 0x38
s_inodes_count u32

Total inodes in the filesystem. An inode is the metadata for one file (or directory, or symlink, etc.). The count is fixed at mkfs time based on disk size — there's a finite number per filesystem.

mkfs.ext2 on a 1 MB disk → s_inodes_count ≈ 128
s_blocks_count u32

Total blocks in the filesystem. For a 1 MB disk with 1024 B blocks, this is ~1000 (some reserved). The unit is ext2 blocks, not sectors — important distinction.

1024 KiB / 1 KiB per block = 1024 blocks (minus reserved)
s_free_blocks_count u32

How many blocks are still unused. Decrements on file writes, increments on deletes. After mkfs, this is close to s_blocks_count (slightly less due to filesystem overhead).

s_free_inodes_count u32

Same idea for inodes. After mkfs, this is s_inodes_count minus a handful for the root directory and lost+found.

s_first_data_block u32

The index of the first block usable for data. For 1024 B block filesystems, this is 1 (block 0 is the boot sector). For larger block sizes (2048, 4096), this is 0 because the boot sector and superblock fit inside block 0.

s_log_block_size u32

Block size as a logarithm: actual block size is 1024 << s_log_block_size. So 0 → 1024 B, 1 → 2048 B, 2 → 4096 B. mkfs.ext2 picks 0 for small disks.

s_log_block_size = 0 → block size = 1024 bytes s_log_block_size = 2 → block size = 4096 bytes
s_magic u16

Magic number identifying the filesystem as ext2. Always 0xEF53 (decimal 61267). If this isn't right, you're either reading the wrong disk or the disk isn't ext2. This is the first thing our parser checks.

read s_magic at offset 56 expect 0xEF53 (little-endian: bytes 53 EF)

The superblock has another ~960 bytes of fields we won't touch yet: volume label, last-mount time, error-handling policy, reserved-block count, feature flags. They matter for a fully functional filesystem; for our purposes (read inodes, walk directories, load files) the fields above are enough.

Little-endian everywhere

ext2 fields are little-endian (LE). x86 is also LE, so reading a u32 from a properly-aligned ext2 byte slice is free — no byte swap. But we'll use u32::from_le_bytes and u16::from_le_bytes explicitly, which (a) handles alignment (no need for the slice to be 4-byte aligned) and (b) documents the endianness assumption in code. If we ever ported to a big-endian architecture, the same code would work.

Build steps — your turn

Four substeps. By the end we'll have parsed the superblock and verified it describes a real ext2 filesystem.

10.1Format the disk image as ext2

Update scripts/make-disk.sh to run mkfs.ext2 -F disk.img after creating the file. The -F flag forces mkfs to proceed despite the "this file isn't a block device" warning. After mkfs, our MINIOS_DISK_v0\n signature gets overwritten — that's fine, we'll verify the ext2 magic instead.

Verify by running dumpe2fs disk.img — should print the superblock fields. Or hexdump -C disk.img | head — bytes 1080–1081 (offset 0x438 = 1080) should be 53 EF (the magic in LE).

10.3Read the superblock from disk

Function read_superblock(dev: &mut impl BlockRead) -> Superblock (or just take &mut VirtioBlk directly for now). Reads sectors 2 and 3, concatenates into a 1024-byte buffer, parses via Superblock::parse.

The two-sector read is needed because the superblock is 1024 bytes but read_sector returns 512. Future optimization: a read_bytes(offset, len) primitive that handles multi-sector reads internally. For Lesson 11, two read_sector calls + concatenation is fine.

10.4Verify magic + sample fields

In main.rs, call ext2::read_superblock(&mut virtio_dev) and assert:

  • magic == 0xEF53 — confirms we're reading an ext2 filesystem
  • block_size == 1024 — mkfs default for small disks
  • blocks_count is around 1000 — for our 1 MB disk
  • inodes_count is around 128 — mkfs default
  • first_data_block == 1 — true for 1024-byte block filesystems

Print all the parsed fields for visual verification.

Primary source

The definitive ext2 reference is the ext2 documentation at nongnu.org — maintained, comprehensive, with every field of every structure explained. The superblock section is at DEF-SUPERBLOCK.

For Linux's implementation: fs/ext2/super.c — specifically ext2_fill_super reads and validates the superblock at mount time. Our parser is a much-simplified version of the same logic.

The on-disk struct definition lives in include/uapi/linux/ext2_fs.h — look for struct ext2_super_block.
