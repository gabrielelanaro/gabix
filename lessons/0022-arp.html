ARP — Who Has 10.0.2.2?

Ethernet delivers to MAC addresses, IP names hosts. Nothing ties the two together until someone asks. ARP is the asking protocol — broadcast a question, get a unicast reply, cache the answer, and answer questions about your own address. By the end, the kernel has had its first real two-way conversation with another machine.

Read time ~25 min Build time ~45–60 min Prereq Lesson 21

Lesson 19 introduced the two-address problem as a problem. Lesson 21 sent an ARP request as opaque bytes and proved the wire works. This lesson takes the 28 bytes you hexdumped at the end of L21 and builds them into a parser, a builder, a cache, and a reply path. The result is the first protocol layer above raw Ethernet — the glue between IP addresses and MAC addresses, specified in 1982 in a six-page RFC that still describes how the internet finds things on a wire.

The problem ARP closes

Two machines on a wire want to exchange an IP packet. The sending kernel knows the destination's IP address — it got that from the application or from a routing table. The Ethernet header it builds needs a MAC address. The mapping from 10.0.2.2 to 52:55:0a:00:02:02 lives on the local wire; the two address spaces are independent by design. The sending kernel starts without the destination's MAC and has no offline registry to query.

ARP's move is charm itself: shout. The sender broadcasts a single frame addressed to every card on the wire — "I am 10.0.2.15, my MAC is 52:54:00:12:34:56, who has 10.0.2.2?" Every other machine on the wire hears it. The one machine whose IP matches 10.0.2.2 replies unicast — "I do; my MAC is 52:55:0a:00:02:02." The sender caches the answer. The next send to 10.0.2.2 hits the cache and skips the broadcast.

Two design choices fall out of the shouting model. First, ARP packets travel inside Ethernet frames as an EtherType payload. The frame's EtherType field is 0x0806, telling the receiver's Ethernet parser to hand the payload to the ARP parser instead of the IP parser. Second, ARP stays on the local wire. Routers drop ARP at the segment boundary. The broadcast reaches the local segment instead of the wider internet.

The packet layout — 28 bytes from RFC 826

Fixed-size, big-endian, no options. The format has been frozen since the RFC was published in November 1982. Read it once, remember it forever:

ARP packet for IPv4 over Ethernet — 28 bytes RFC 826 · all multi-byte fields big-endian
htype u16 BE 0x00–0x01
ptype u16 BE 0x02–0x03
hlen u8 0x04
plen u8 0x05
oper u16 BE 0x06–0x07
sha 6 B 0x08–0x0D
spa 4 B 0x0E–0x11
tha 6 B 0x12–0x17
tpa 4 B 0x18–0x1B
htype, ptype u16 BE ×2

Hardware type and protocol type — a generic pairing so the same packet format could carry "IPv4 over Ethernet," "IPv6 over Ethernet," "IPv4 over FireWire," or any other combination. We only care about the one pairing: htype = 1 (Ethernet), ptype = 0x0800 (IPv4). If either differs, drop the packet.

hlen, plen u8 ×2

Lengths of the hardware and protocol addresses. For us: 6 (MAC) and 4 (IPv4). The generic format plus explicit lengths is what lets ARP scale across address sizes — the parser reads hlen and plen first, then knows how many bytes sha, spa, tha, tpa each occupy. We can hard-code 6 and 4 since we only do IPv4-over-Ethernet.

oper u16 BE

The demux key for this layer. Two values matter: 1 = request, 2 = reply. Same parser, same byte layout, different operation. Everything else in the parser dispatches on this field.

sha, spa 6 B + 4 B

The sender's hardware and protocol addresses — both at once, in one packet. This is the load-bearing pair. The receiver uses these to learn: "ah, 10.0.2.2 is at 52:55:0a:00:02:02, I'll cache that." A reply that contained only tha would force a second round-trip to learn the sender's MAC, defeating the purpose. Including sha in every ARP packet is the trick that makes one packet teach two machines.

tha, tpa 6 B + 4 B

The target's hardware and protocol addresses. In a request, tpa is the IP we're asking about and tha is zero because the sender is asking for the MAC. In a reply, tpa is the original asker's IP and tha is the original asker's MAC; the reply is addressed back to the one specific card that asked.

Two things to notice before moving on. First, the fixed sizes — hlen and plen advertise 6 and 4, but our parser can hard-code those because we accepted only Ethernet/IPv4 at the htype/ptype check. Second, every multi-byte field is big-endian. The from_be_bytes reflex from Lesson 21 applies to every integer in this packet. The htype field is bytes 00 01 on the wire; from_le_bytes would read it as 0x0100 = 256. That value fails the Ethernet hardware-type check and the packet is dropped.

The dance — request and reply side by side

Every field has a role. The fields that change between request and reply are highlighted; the ones that stay the same tell you which features of the protocol are load-bearing.

Request — "who has 10.0.2.2?"
Ethernet dstff:ff:ff:ff:ff:ff (broadcast)
Ethernet src52:54:00:12:34:56 (us)
EtherType0x0806
htype / ptype1 / 0x0800
hlen / plen6 / 4
oper1 (request)
sha / spa52:54:00:12:34:56 / 10.0.2.15
tha00:00:00:00:00:00 (unknown)
tpa10.0.2.2 (the question)

Goes to every card on the wire. The broadcast is the shout. Only the machine that owns 10.0.2.2 replies; everyone else silently updates their cache with the sender's mapping (the merge algorithm below).

Reply — "I do, here is my MAC"
Ethernet dst52:54:00:12:34:56 (unicast to us)
Ethernet src52:55:0a:00:02:02 (gateway)
EtherType0x0806
htype / ptype1 / 0x0800
hlen / plen6 / 4
oper2 (reply)
sha / spa52:55:0a:00:02:02 / 10.0.2.2
tha52:54:00:12:34:56 (us)
tpa10.0.2.15

Addressed to one card. sha is the answer to the question — the gateway's MAC, now cacheable. The reply structure mirrors the request exactly, with oper flipped and sender/target swapped. A reply is a request reflected back, with one bit different and the addresses rotated.

The stable fields tell you what the protocol considers immutable: the hardware/protocol pairing, the address lengths, and the EtherType. The fields that change carry the conversation: oper (which way the question flows), sha (who is speaking now), tha (who is being spoken to). One byte — oper — flips a request into a reply.

The RFC 826 merge algorithm — both sides learn

Here is where ARP earns its reputation for elegance. A naive design would have the asker broadcast a question, the answerer reply, and the asker cache the answer — one machine learns per round-trip. The actual RFC 826 algorithm, in four lines:

1.Receive an ARP packet. Check htype, ptype, hlen, plen match what we speak. Drop if not.
2.Look up spa → sha in the cache. If missing or changed, update the cache.Both sides learn from every ARP packet, even before checking if it's for them.
3.Check whether tpa is an IP we own. Other targets end processing after the cache merge.The packet can teach us even when another machine owns the target IP.
4.If oper is request, send a reply (swap sha/spa into tha/tpa, fill our MAC into sha, set oper=2). If oper is reply, complete any pending request.We answer requests for our own IP — that's what makes us "exist" on the network.

Step 2 is the move. The cache update happens before the target check, on every ARP packet the kernel sees — even ones addressed to other machines, even ones we ultimately ignore. So when machine A broadcasts "who has 10.0.2.2?", every machine on the wire learns A's MAC, including machines that are only listening. Future transmissions to A skip the broadcast. The ARP traffic on a real network is much sparser than the naive design would produce, because step 2 makes every ARP packet a learning opportunity for everyone who hears it.

For mini-os, this means the parser updates the cache on every received ARP packet, regardless of whether the packet was for us. The slirp gateway announces itself with every reply, and we learn its MAC the moment the first reply lands — the gateway never has to ask us.

The ARP cache

A simple map from IP to MAC. The choice of map matters less than the operations on it: lookup before TX, insert on RX, optional expiry. mini-os uses a BTreeMap from the alloc crate — already in our dependency tree, with ordering for [u8; 4] keys built in.

The cache state across a typical exchange:

T0 — before sending the request
(empty)
T1 — request sent, waiting for reply
(still empty — our own MAC is local device state; the gateway entry arrives with the reply)
T2 — reply received, merge step ran
10.0.2.2 52:55:0a:00:02:02 learned from reply's sha — gateway exists
T3 — gateway sends its own ARP request for us
10.0.2.2 52:55:0a:00:02:02 already cached, merge step is a no-op

Linux adds expiry and states. Entries go stale after minutes to hours, so a replaced card is discovered again. Linux's neighbour cache also has a state machine (INCOMPLETE, REACHABLE, STALE, DELAY, PROBE) that drives retransmission and validation. mini-os uses one state — present — and a synchronous poll that returns None when the entry is missing. Future scaling work can add the state machine; an echo server on a quiet slirp wire can use the small version.

Answering requests — what makes us exist

Sending ARP requests is one half of the protocol. Answering them is the other. When another machine broadcasts "who has 10.0.2.15?", we are obligated to reply — the RFC calls it a "request, if the target protocol address is me." Without this reply path, the gateway needs a way to learn us first. Every inbound connection (an nc -u localhost 5555 from the host in Lesson 26) starts with the gateway asking ARP for our MAC. Our reply gives the gateway the address it needs before it can deliver the inbound frame.

The reply is a struct mutation away. Take the request's bytes, flip oper from 1 to 2, rotate sha/spa into tha/tpa, fill our own MAC and IP into sha/spa. Wrap in an Ethernet frame addressed to the asker's MAC (which we just learned from the request's sha). Send it.

Slirp will probe the guest with an ARP request for 10.0.2.15 shortly after the kernel boots, before any of our own traffic. If our reply path works, slirp adds us to its internal ARP table and future inbound traffic can find us. A missing reply leaves slirp without a MAC for the guest, and the Lesson 26 echo server stays silent.

Our address — fixed by slirp

Real machines learn their IP address from the network via DHCP (Dynamic Host Configuration Protocol) — broadcast a "please give me an address" request, the network's DHCP server replies with a lease. DHCP is itself a small protocol built on top of UDP, and implementing it would be a worthwhile side quest outside the critical path to a UDP echo server.

Slirp's guest address is fixed at 10.0.2.15 — it's baked into slirp's design. Hard-coding it as a kernel constant is therefore an accurate statement of how slirp works. The constant lives in src/net/mod.rs as pub const OUR_IP: [u8; 4] = [10, 0, 2, 15];. The gateway IP is the same shape: pub const GATEWAY_IP: [u8; 4] = [10, 0, 2, 2];.

The MAC, by contrast, comes from device config (Lesson 20). It's per-card and read at boot. The asymmetry is real: MAC belongs to the hardware, IP belongs to the network.

The build — four steps

The packet and cache pieces live in src/net/arp.rs. The wire-facing resolver lives on NetDevice as resolve_arp(ip), because it needs to transmit a request and poll the RX queue. Lesson 23's IPv4 path will call that resolver before every TX.

1
ArpPacket parse and build. struct ArpPacket { htype, ptype, hlen, plen, oper, sha, spa, tha, tpa }. Two methods: parse(buf: &[u8]) -> Option<Self> using u16::from_be_bytes for the four multi-byte fields; to_bytes(&self) -> [u8; 28] using .to_be_bytes() on the same fields. Constants for the immutable values: HTYPE_ETHERNET = 1, PTYPE_IPV4 = 0x0800, OPER_REQUEST = 1, OPER_REPLY = 2. Unit test: round-trip a request and a reply through build → parse, verify all fields match. The boot probe checks this round trip before it talks to the network card.
2
Transmit a request, parse the reply. Build an ArpPacket with oper=REQUEST, sha=our MAC, spa=10.0.2.15, tha=zeros, tpa=10.0.2.2. Wrap in Ethernet (broadcast dst, our src, EtherType 0x0806). Send via NetDevice::send_frame from Lesson 21. Loop on recv_frame, dispatch on ethertype, parse the payload as ArpPacket. When oper=REPLY arrives, print [arp] 10.0.2.2 is at 52:55:0a:00:02:02. The serial proof is checked by tests/test_arp.sh.
3
ARP cache and resolve(). static ARP_CACHE: Mutex<BTreeMap<[u8;4], [u8;6]>>. NetDevice::resolve_arp(ip) -> Option<[u8;6]> — cache hit returns immediately; cache miss broadcasts a request, polls for the reply up to a timeout (say 1 second), returns the MAC. Pull the merge step (update on every received ARP) into the receive path. Re-test step 2's request — first call should broadcast and wait, second call should return from cache without transmitting.
4
Answer inbound requests. In the receive path, after the merge step: if oper == REQUEST and tpa == OUR_IP, build a reply (rotate sha/spa into tha/tpa, fill our MAC and IP into sha/spa, oper=2), wrap in Ethernet addressed to the asker's MAC, send via NetDevice::send_frame. Test by leaving the kernel idle for a few seconds after boot — slirp probes for us around the 30-second mark. When the probe arrives, our reply should print [arp] replied: 10.0.2.15 is at 52:54:00:12:34:56.
Lesson 22 scope

This slice keeps cache expiry, retransmission, duplicate-address probing, and gratuitous ARP for later. Those features matter on larger networks and changing hardware. The slirp path to ping and UDP echo needs the parser, cache, resolver, and reply builder first.

Primary source

RFC 826 — "An Ethernet Address Resolution Protocol", Plummer, November 1982. Six pages including the merge algorithm quoted above. The RFC is unusually readable — the protocol is small enough that the spec and the implementation are nearly the same document. For Linux's implementation: net/ipv4/arp.c — arp_process is the merge algorithm made code; net/core/neighbour.c is the generic cache machinery that ARP, IPv6 neighbor discovery, and DECnet all share. The Linux version is several thousand lines; ours will be under two hundred. The compression comes from skipping the state machine and the expiry while preserving the protocol's core exchange.

Probe — check the model before you build

Three machines on a wire: A (10.0.2.15), B (10.0.2.16), G the gateway (10.0.2.2). A broadcasts "who has 10.0.2.2?" B hears it. G hears it and replies. After this exchange, what does B's ARP cache contain? Specifically: did B learn anything? If so, what? And does B's answer change if B already had G in its cache before the broadcast?

Say your answer back to me, or push on whatever didn't land — the merge algorithm, the request/reply symmetry, the difference between broadcasting a request and replying unicast. I'm your teacher for this phase; the probe is where the conversation starts.
