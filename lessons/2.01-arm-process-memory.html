Module 2 · Memory

Two programs using the same address

How the kernel gives each ARM process its own memory.

Read the main paragraphs for the scenario. Open the ARM and code sections when you want to connect a step to the instructions in our kernel.

The scenario

We run two copies of a small user program on one Pi CPU core. Both programs store a number at address 0x41010000. Process A stores 1. Process B stores 2. Timer interrupts let them take turns.

We want A to keep reading 1 and B to keep reading 2. If both addresses referred to the same physical memory, B would overwrite A’s value.

The address in the program is a virtual address

The CPU’s memory management unit translates a program’s address into a physical memory address. It uses a translation table prepared by the kernel. Each process has its own table.

Running processAddress used by the programPhysical address on the PiStored value
A0x410100000x020100001
B0x410100000x022100002

The program uses the middle column. The selected translation table determines the physical address. These are the addresses used by our physical Pi test; QEMU’s virt board uses a different physical RAM range.

ARM and code: how one table entry translates this address

We use ARMv7’s short-descriptor translation format. Our first-level table has 4,096 entries, each four bytes wide. Each entry maps a 1 MiB region called a section. The table occupies 16 KiB and must be aligned to a 16 KiB address.

For 0x41010000, split the virtual address into a table index and an offset:

virtual address: 0x41010000
section index:   0x410        // upper 12 bits: select entry 1040
section offset:  0x00010000   // lower 20 bits: position inside 1 MiB

A's entry: physical base 0x02000000 + offset = 0x02010000
B's entry: physical base 0x02200000 + offset = 0x02210000

The entry stores the physical section base and permission bits. In memory.rs, prepare_process_table builds those entries. This excerpt shows the expression used for the two user sections:

(process_physical_base(id) + section as u32 * SECTION_SIZE)
    | NORMAL_NON_CACHEABLE
    | USER_READ_WRITE
    | SECTION_DESCRIPTOR
    | if section == 1 { 1 << 4 } else { 0 }

The | operator combines fields in one 32-bit descriptor. The physical base occupies the high bits; the flags occupy lower bits. Section 0 contains code/data. Section 1 contains the stack, so it also sets bit 4, the execute-never flag.

The MMU performs this lookup when it needs a translation. Once cached in the TLB, the translation can be reused without rereading the table for every access.

What changes when the scheduler selects B?

The scheduler already changes the stack and saved registers. It now also selects B’s translation table. ARM’s TTBR0 register holds the table’s address.

The CPU caches recent translations in a structure called the translation lookaside buffer, or TLB. Our first implementation clears this cache when switching tables. This prevents A’s cached translation for 0x41010000 from being reused while B runs.

Kernel code and kernel stacks have the same mappings in every table, so the scheduler can keep executing while it changes the user mappings.

ARM and code: select the table and discard old translations

In scheduler.rs, run_until_finished() selects the process table before switching to the task’s saved stack:

crate::memory::activate_process((*task).process);
// Then switch from the dispatcher context to the task context.

activate_process uses the following assembly in memory.rs. The brace names are Rust assembly placeholders: the compiler puts each input value into a CPU register.

mcr transfers a value from a general-purpose register to an ARM system-control register or maintenance operation. p15 selects the system-control interface, traditionally called CP15. The c2/c0 fields and numeric operands identify the operation; their meaning comes from the architecture’s instruction encoding.

The final barriers complete the maintenance before the task resumes. We run this sequence with IRQs masked, so a timer cannot interrupt a partially completed scheduler change. We currently flush the TLB on each table change; a later optimization could tag cached translations with address-space identifiers (ASIDs).

There is also a separate step when building a table: mcr p15, 0, {address}, c7, c10, 1 cleans a data-cache line. This makes the new descriptors visible to the hardware that reads translation tables. Cleaning table memory and invalidating cached translations solve different problems.

Why can’t A read B’s physical address directly?

An address used by A is still checked through A’s translation table. The mapping at B’s physical address is available only to privileged kernel code. A executes in user mode, so that access fails its permission check.

The CPU then enters the kernel’s memory-fault handler. For a scheduled user process, the handler records the fault and finishes that process. The scheduler continues with the other ready process.

Prediction: A tries to read 0x02200000. Does it read B’s memory, read A’s private memory, or fault?

Check the answer

It faults. A can access its private allocation through the permitted user mappings at 0x41000000–0x411fffff. The mapping at 0x02200000 requires kernel privilege.

ARM and code: permission bits and the fault handler

These constants in memory.rs set the section descriptor’s access-permission (AP) bits:

const PRIVILEGED_READ_WRITE: u32 = 0b01 << 10;
const USER_READ_WRITE: u32       = 0b11 << 10;

In our configured permission mode, with AP[2] clear, the first setting permits kernel read/write access and denies user access. The second permits both. The kernel initially creates privileged mappings, then replaces only the process’s two user-section entries. Domain 0 is configured as a client, which makes the MMU enforce these descriptor permissions.

Stack descriptors also set XN, execute-never, at bit 4. Reading and writing the stack is allowed; fetching an instruction from it generates a fault.

For a forbidden load or store, ARM enters a Data Abort exception. The handler in boot.S reads two system registers:

mrc p15, 0, r0, c6, c0, 0   // DFAR: faulting data address
mrc p15, 0, r1, c5, c0, 0   // DFSR: reason for the fault

mrc reads system state into a general-purpose register. Here DFAR means Data Fault Address Register; DFSR means Data Fault Status Register. The boot check expects a section-permission fault, status code 0xD. DFSR bit 11 additionally identifies a write.

An attempted instruction fetch from the stack generates a Prefetch Abort. Its handler reads the instruction equivalents, IFAR and IFSR. Both handlers call handle_memory_abort in process.rs. That function checks the saved processor mode, records a scheduled user process’s fault, and finishes that process. The other process can continue.

How do we actually enter user mode?

Permissions depend on the CPU’s current privilege mode. Our kernel runs in ARM’s Supervisor mode, abbreviated SVC. A user process runs in User mode, which cannot change the kernel’s translation-table selection or interrupt controls.

ARM and code: enter user mode and preserve its stack

user::enter(entry, stack) receives the program’s entry address in r0 and its initial stack pointer in r1. It prepares an exception return into User mode:

cpsid i                 // Mask IRQs during setup.
cps #0x1f               // Select System mode.
mov sp, r1              // Set the stack shared by System/User modes.
cps #0x13               // Return to Supervisor mode.
mov r2, #0x10           // Desired status: User mode, IRQs enabled.
msr spsr_cxsf, r2       // Prepare the status to restore.
mov lr, r0              // Prepare the program's starting address.
movs pc, lr             // Restore status and begin user execution.

System mode is privileged but shares the User-mode stack and link registers. This lets the kernel initialize the user stack. Supervisor mode has its own stack and link registers. These separate copies are called banked registers.

The Current Program Status Register (CPSR) holds the current mode, condition flags, and interrupt masks. The Saved Program Status Register (SPSR) holds status to restore on an exception return. Here the kernel deliberately prepares SPSR for the first user entry. In this exception-return form, the s in movs pc, lr causes the saved status to be restored along with the branch.

When a timer later switches processes, context::switch preserves each process’s User-mode stack and link registers:

add r2, r0, #4
stmia r2, {sp, lr}^     // Save the outgoing User-bank SP/LR.
add r2, r1, #4
ldmia r2, {sp, lr}^     // Restore the incoming User-bank SP/LR.

In this function, r0 points to the outgoing TaskContext and r1 to the incoming one. The first four-byte field holds the kernel stack pointer; adding 4 reaches user_sp and user_lr. The ^ suffix selects the user register bank while the kernel remains in SVC mode.

The full switch also saves the kernel call-preserved registers and changes the kernel stack. Its clrex instruction clears the CPU’s exclusive-access reservation, so a reservation used for an atomic operation is not carried into another task. The IRQ wrapper separately preserves the registers and status of the interrupted instruction sequence.

Trace one instruction through the code

In process_probe.S, both programs execute this store after loading their process ID into r4:

movw r5, #0
movt r5, #0x4101    // Together these set r5 = 0x41010000.
str r4, [r5]       // Store the process ID through its current mapping.

movw sets the lower half of the register and clears its upper half; movt sets the upper half. The resulting address is identical in both programs. The table selected by activate_process determines which physical memory receives the store.

Check the address and value

B’s table maps section 0x410 to physical base 0x02200000. The offset is 0x10000, so the load reads 0x02210000 and returns 2.

What the tests check

  • Both user programs keep their distinct value at the same virtual address through timer switches.
  • Each retains its private user stack and function-return address.
  • A cannot read or write the other process’s physical-memory mapping, or read kernel memory.
  • A cannot execute instructions from its user stack.
  • When A faults, B completes and the kernel can continue to its UART/Ethernet service.

The current limits

This first implementation has two fixed process allocations of 2 MiB each. Mappings use 1 MiB ARM sections. The code/data section is readable, writable and executable; the stack section is readable and writable with execution disabled. Smaller pages and separate read-only code permissions remain future work.

The boot check loads small flat test images. The existing UART ELF loader remains a separate single-program path. General process creation, ELF exec, fork, wait and dynamic memory allocation are later steps.
