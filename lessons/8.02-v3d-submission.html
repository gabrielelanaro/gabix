I type a command on my Mac. Where does it actually run?

Before drawing the gold triangle from lesson 1, we asked the Pi’s graphics hardware for its name. Our Mac printed 56334402. Where on the board did those bytes come from?

Inside the Pi’s Broadcom chip, the ARM CPU runs Gabix. A second processor, VideoCore, runs Raspberry Pi’s firmware, software loaded from the SD card at boot. V3D is the part that draws. The ARM and V3D share the board’s RAM. Pi boot files · Shared pixel buffer

How does the same program make pixels?

You suggested “instruction + input.” Try that idea on the triangle’s background. The Mac sends 01 96 42 19 ff to the same loaded program. 01 selects a clear. The other four bytes specify blue. Now V3D needs commands that describe what color, which image and where to store it. The blue clear on the Pi

Read those two writes in our driver

Here is the call the ARM executes for the blue clear. Its three arguments select hardware thread 1 and give the start and end of the render command list in RAM. v3d.rs · probe

if !submit(RENDERING, addr_of!(render_list), addr_of!(render_end)) {
    return stop_stalled_job(-21);
}

Inside submit(), read each call as write(where, what). Substituting 1 for thread selects the render thread’s register in each pair. The ARM samples the frame counter before the two writes so it can tell when V3D has finished. v3d.rs · submit

let counter = V3D + 0x134 + thread * 4;
let previous = read(counter);
write(V3D + 0x110 + thread * 4, bus(start));
write(V3D + 0x108 + thread * 4, bus(end));
wait(|| read(counter) != previous)

Imagine the ARM pauses between the two calls to write(). Where is the blue color already stored? What is V3D still waiting for?

Check your explanation

The color is in the command list in shared RAM. V3D has the list’s start address. The ARM still has to write its end address to CT1EA. That write starts V3D reading the list and, eventually, filling the image with blue.
