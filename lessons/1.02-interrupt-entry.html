Interrupt entry

How a timer or a device pulls the CPU out of a running program, runs a handler, and returns as if nothing happened.

The kernel is running a program. Left to itself, the CPU would keep fetching that program's instructions, one after another, until the program finishes. Two kinds of event need to break that run:

  • A timer fires, many times a second. Each time, the kernel can stop this program and let another run for a while — which is how one CPU appears to run several programs at once.
  • A device finishes a job the kernel gave it. A disk read completes; a network packet arrives. The kernel wants to know the instant it happens, not the next time it happens to check.

The program cannot be trusted to pause itself for either one — a buggy or hostile program would simply never yield. So the hardware has to be able to force the CPU away from the program. That is an interrupt: the hardware makes the CPU leave the program, run a handler in the kernel, then return to the program where it left off.

This lesson is how interrupts work. It reuses the pieces from lesson 1.01 — the exception table, the privileged modes, the CPSR and SPSR — and adds two new ones: a chip that tells the CPU an event has happened (the interrupt controller), and, on ARM, the step where the handler asks that chip which device caused the interrupt.

1. The two halves

An interrupt has two halves. The first is a chip that tells the CPU an event has happened — the interrupt controller. The second is a table that tells the CPU which handler to run in response. x86 and ARM both have both halves. They differ in one design choice — how many entries the table holds — and that choice changes how the handler is written.

2. The table: eight shared slots, or 256 numbered ones

From lesson 1.01: ARM keeps its exception handlers in an eight-entry table at the address held in the VBAR register. Each kind of exception owns one slot. Hardware interrupts get exactly one slot — the IRQ slot. So whether the timer fires, or a packet arrives, or a disk read finishes, the CPU jumps to that same slot every time. (A neighboring slot, FIQ, is reserved for a faster kind of interrupt that gabix does not use.)

Here is the table, from gabix's boot code:

targets/armv7/src/boot.S · the eight-entry exception table (effective assembly)
.Lvectors:                        @ the table sits at the address in VBAR
    b   .Lpark                    @ 0  reset
    b   .Lpark                    @ 1  undefined instruction
    b   .Lsvc                     @ 2  SVC — syscalls arrive here (lesson 1.01)
    b   .Lpark                    @ 3  prefetch abort
    b   .Lpark                    @ 4  data abort
    b   .Lpark                    @ 5  reserved
    b   .Lirq                     @ 6  IRQ — every hardware interrupt arrives here
    b   .Lpark                    @ 7  FIQ (unused)

Notice slot 2 — that is the SVC entry from lesson 1.01, where syscalls arrive. Slot 6 is where every hardware interrupt arrives.

x86's table is the IDT (Interrupt Descriptor Table), and it is far larger — 256 entries. More importantly, x86's interrupt controller does not just tell the CPU that an event happened — it hands the CPU a number, the entry to use. So on x86 the timer, the disk, and the network card each arrive at their own handler, because each was given its own number.

ARM's table is too small for that. With one slot for every hardware interrupt, the handler that lands there cannot yet know which device caused the interrupt — it has to ask the controller (section 4 names the exact registers). That single difference, eight shared slots against 256 numbered ones, is the reason an ARM interrupt handler is written differently from an x86 one.

3. On the way in: saving state and raising privilege

Whatever the table size, the moment an interrupt occurs the CPU has to do three things: save enough state to resume the program later, raise its own privilege, and jump to the handler.

On ARM the privilege raise and the state save are automatic and follow directly from lesson 1.01. The CPU switches to IRQ mode — privileged, and with its own private stack pointer and link register, the ones gabix set up in boot.S. It writes the address to resume at into the link register lr, and it saves the old mode (User) into the SPSR, exactly as it did for a syscall. Then it jumps to the IRQ slot.

Here is the handler that slot points at:

targets/armv7/src/boot.S · the IRQ entry (effective assembly)
.Lirq:
    sub   lr,  lr, #4            @ lr points one instruction too far; step back to the interrupted one
    stmdb sp!, {r0-r12, lr}      @ push the program's registers onto the IRQ stack
    bl    arm_irq_entry          @ call the Rust handler
    ldmia sp!, {r0-r12, lr}      @ restore them
    subs  pc,  lr, #0            @ return: PC <- lr, and (the 's') CPSR <- SPSR -> back to User mode

Read the first line carefully. When an interrupt arrives, the CPU sets lr to the address of the next instruction — one instruction past the one that was interrupted. (This comes from how the CPU fetches instructions ahead of time.) To resume correctly, the handler must step back one instruction, so it subtracts four — one ARM instruction is four bytes. The syscall handler in 1.01 did not need this, because a syscall is never mid-instruction.

The last line, subs pc, lr, #0, is the return. It sets the program counter to lr — the adjusted address — and, because of the s, it restores the CPSR from the SPSR, dropping the CPU back into User mode. It is the same "jump and restore the mode" trick as the syscall return. (movs pc, lr would do the identical thing here — the address was already fixed at the top — but the author wrote it as a subtract with zero.)

On x86 the CPU instead pushes the program's instruction pointer, its code segment, and its flags onto the kernel stack (and the stack segment and pointer too, if it was running a user program), switches to ring 0, and jumps to the IDT entry the controller named. Returning is one instruction, iretq, which pops all of that back.

4. "Which device?" — and telling the controller you are done

On x86 the controller already named the device when it supplied the number, so the handler simply does its work and returns.

On ARM the handler arrives knowing only "some hardware interrupt." It must ask the controller which one, and it must tell the controller when it has finished. This is the part where ARM platforms differ: which controller, and how you talk to it.

One ARM controller that works this way is the GIC (Generic Interrupt Controller — ARM's standard interrupt chip). Gabix meets it on the virt target, the QEMU machine used for ARM bring-up. The handler reads one of the GIC's registers — the Interrupt Acknowledge Register — which does two things at once: it returns the interrupt's number, and it tells the GIC the CPU has accepted it. The handler does its work, then writes that same number to a second register — End of Interrupt — to say it is done, which lets the next interrupt through. The GIC is the clean example of the mechanism, so it is the one shown here; it is not what the Pi uses.

targets/armv7/src/virt/timer.rs · asking the GIC which interrupt, and saying it is done
pub unsafe fn handle_interrupt() {
    let acknowledge = read32(GIC_CPU_BASE + GICC_IAR);      // which interrupt? (also acknowledges it)
    if acknowledge & 0x3ff == PHYSICAL_TIMER_INTERRUPT {    // the low 10 bits hold the number; 30 is the timer
        TICKS.fetch_add(1, Ordering::Release);              // count the tick
        reload();                                           // re-arm the timer
    }
    write32(GIC_CPU_BASE + GICC_EOIR, acknowledge);         // end of interrupt — let the next one through
}

The Raspberry Pi 2B has no GIC. Its interrupt hardware is two controllers Broadcom made, and a signal passes through both on the way to the CPU — a different design that needs its own lesson. Gabix wires only the timer on the Pi today and polls every device. That full picture — the two controllers, the bit-per-device layout, and how to wire a real USB or SD interrupt — is lesson 7.01.

5. One tick, end to end

Trace one timer tick on the emulator, all the way through. The kernel has told the ARM generic timer to count down from a chosen value and then signal. The count reaches zero. The timer signals the GIC. The GIC signals the CPU. The CPU leaves the program: it switches to IRQ mode, writes the resume address into lr and the old mode into the SPSR, and jumps to the IRQ slot. The handler there pushes the program's registers and calls the Rust routine. The routine reads the GIC's acknowledge register — interrupt 30, the timer — adds one to the tick counter, reloads the timer, and writes end-of-interrupt. The handler pops the registers and runs subs pc, lr, #0. The program resumes at the exact instruction that was interrupted, as though it had never left.

What you should be able to do after this lesson. Explain why an ARM interrupt handler has to ask the controller "which device?" while an x86 handler does not.
