The TCP three-way handshake

Agree to talk, exchange the first byte: SYN, SYN-ACK, ACK, then one payload segment each way.

Primary spec RFC 9293 Linux counterpart net/ipv4/tcp_input.c Proof target 10.0.2.3:53 (slirp DNS over TCP)

You sent datagrams through a UDP socket in Lessons 25 to 30. Each call to sendto() transmitted one self-contained message and forgot about it. If the network dropped a datagram, the sender never learned. If datagrams arrived out of order, the application had to notice and reorder. These limitations are tolerable for short request-reply protocols like DNS and DHCP, but not for transferring files, remote login, or loading a web page. A program sending a file wants to write bytes into a stream and trust that they will arrive at the peer intact, in order, exactly once.

TCP (Transmission Control Protocol) provides that stream. To keep its guarantee, both endpoints must remember per-connection state: each other's addresses, the position of the next byte to send, the next byte expected, the receive window, and the buffers holding bytes in flight. That remembered state is what makes a TCP connection a connection. Before any bytes flow, the two computers must agree that the connection exists and exchange their starting byte positions. This three-message agreement is the three-way handshake. This lesson builds the segment format, the handshake, the establishment states, and the exchange of one byte in each direction. Lesson 32 makes the byte stream reliable under packet loss. Lesson 33 adds teardown and a TCP echo server.

What "connection-oriented" means

UDP sent one datagram and forgot about it. The UDP socket object from Lesson 26 held only a port number, a receive queue, and a waiter. Nothing in it referenced a particular peer or a particular byte position.

TCP keeps state per peer. That state is what makes the protocol reliable. Every byte sent gets a sequence number. Every byte received gets an acknowledgment. A byte that goes unacknowledged for too long is sent again. None of that works without state on both sides remembering where the stream is up to.

The state lives in a struct called the TCP Control Block (TCB). Linux calls it struct tcp_sock and stores several hundred bytes per connection (timers, congestion window, SACK state, the works). mini-os will start smaller: local and remote address, local and remote port, four byte-position counters (send_next, send_unacked, recv_next, recv_window), the connection state, and a small retransmit queue.

UDP socket (Lesson 26)

  • local port
  • datagram receive queue
  • one blocked waiter
  • no peer address — each recvfrom may return a different sender

TCP connection (this lesson)

  • local and remote IP + port (a fixed peer)
  • send byte position (send_next, send_unacked)
  • receive byte position (recv_next)
  • flow-control window
  • connection state (CLOSED, SYN_SENT, ESTABLISHED, …)

The TCP segment

A TCP segment is a 20-byte header plus an optional payload. The header is two and a half times UDP's, because it carries the connection-state machinery: two 32-bit byte-position numbers (sequence, acknowledgment), a window advertisement, a flag byte, and a pointer for urgent data.

All multi-byte fields use network byte order: big-endian. The TCP pseudo-header for the checksum adds source IP, dest IP, a zero byte, protocol number 6, and the TCP length — same shape as UDP in Lesson 25.
sequence · bytes 4–7

The byte position of the first payload byte in this segment within the sender's outbound byte stream. A SYN or FIN flag consumes one sequence number even though it carries no data, which is why the receiver's ACK after a SYN is seq + 1.

ack number · bytes 8–11

The next byte the sender of this segment expects to receive. Meaningful only when the ACK flag is set. An ACK with value N tells the recipient that every byte it sent with sequence below N has arrived.

data offset · byte 12 (high nibble)

Header length in 32-bit words. With no options this field is 5 (5 × 4 = 20 bytes). With options it grows; the maximum is 15 (60 bytes total). The payload begins at byte data_offset × 4.

flags · byte 13

Eight control bits, read most-significant first: CWR ECE URG ACK PSH RST SYN FIN. The handshake uses three of them: SYN (synchronize sequence numbers), ACK (the ack-number field is valid), RST (abort the connection). The others belong to data flow and teardown.

window · bytes 14–15

The number of bytes the sender of this segment can still accept in its receive buffer. This is TCP's flow-control channel: the receiver tells the sender how much room is left. A window of zero means "stop sending until I advertise more."

checksum · bytes 16–17

RFC 1071 internet checksum, computed over the TCP header, the payload, and a 12-byte pseudo-header containing the source IP, dest IP, protocol number 6, and the TCP length. Same construction as UDP in Lesson 25.

urgent ptr · bytes 18–19

An offset from the sequence number marking the end of "urgent" data in the stream. mini-os will leave this zero and never set URG. Telnet uses it; modern protocols rarely do.

options · byte 20 onward

Variable-length option pairs (kind, length, value). Common options in a SYN: MSS (maximum segment size, kind 2), window scale (kind 3), SACK-permitted (kind 4), timestamps (kind 8). mini-os will send MSS only.

The exchange, segment by segment

client10.0.2.15:ephemeral · active open
server10.0.2.3:53 · listening
1 SYN
flags=SYN · seq=x · ack=0 · no payload
client picks its Initial Sequence Number x
2 SYN+ACK
flags=SYN,ACK · seq=y · ack=x+1
server picks y, acknowledges x by sending x+1
3 ACK
flags=ACK · seq=x+1 · ack=y+1
client acknowledges y. No SYN flag, no payload.

After segment 3, both ends agree that the connection exists and is in the ESTABLISHED state. Application bytes can now flow in either direction, with each side's sequence number advancing by the number of bytes sent.

Why three messages, not two

Two directions, two independent starting points. The client must tell the server its starting sequence number x, and the server must tell the client its starting sequence number y. Each side must also acknowledge the other's starting number so the sender of that number learns it arrived.

That is four facts to establish: x from client, ACK of x from server, y from server, ACK of y from client. The middle message combines two of them: the server's SYN-ACK carries its own starting number y and acknowledges the client's x in the same segment. Four facts fit into three packets.

The third message carries no SYN flag. It is pure ACK: "I received your SYN-ACK, here is my acknowledgment of your starting number." Without it, the server would have sent y but never learned whether the client received it. The connection would sit in SYN_RCVD on the server side indefinitely.

Why sequence numbers do not start at zero

Both ends pick an Initial Sequence Number (ISN) that is not zero, and not predictable. RFC 9293 §3.4 specifies the requirement; RFC 6528 describes the algorithm modern implementations use (a clock-driven or per-connection random offset).

The reason is an attack. If an off-path attacker can guess the ISN a server will assign to a new connection, the attacker can forge TCP segments with the correct sequence number and inject data into the connection. The classic exploit is Blind TCP Spoofing: the attacker sends a flood of guessed segments, hoping one lands in the receive window. Random ISNs make the guess astronomically unlikely. A predictable counter starting at 0 every boot would be trivially exploitable.

For mini-os the security threat is not real — the only peer is slirp — but the principle matters. The implementation will derive the ISN from the existing timer tick counter, which is monotonic and changes between connections. That is not cryptographically secure, but it satisfies the RFC's intent of "different ISN per connection" without depending on a random source we do not yet have.

Connection states for establishment

Each TCB holds a state field. The states relevant to opening a connection are five. Teardown (Lesson 33) adds six more.

StateWhat it meansWho enters it
CLOSEDNo TCB exists for this peer. Stable starting state.Both, before any segment is sent.
LISTENWaiting for an inbound SYN. A bound passive socket.The server side. mini-os will reach this state via bind + listen syscalls (Lesson 33).
SYN_SENTSent SYN, waiting for SYN-ACK.The active opener (client) after sending segment 1.
SYN_RCVDReceived SYN, sent SYN-ACK, waiting for the final ACK.The server after sending segment 2.
ESTABLISHEDHandshake complete. Data flow is permitted.Both, after the third handshake message is sent or received.

The active-open path is CLOSED → SYN_SENT → ESTABLISHED. The passive-open path is LISTEN → SYN_RCVD → ESTABLISHED. Lesson 31 exercises the active-open path — we send the first SYN to a host that is already listening, then exchange one byte in each direction.

What to build in mini-os

Lesson 31 covers the segment format, the TCB, the active-open handshake, one bounded payload sent, and the first response byte returned to user mode. The sliding-window send/recv API, retransmission, and teardown are Lessons 32 and 33. The server side (LISTEN, SYN_RCVD) waits for Lesson 33's echo server.

31.1
TCP header build/parse. Add src/net/tcp.rs with a TcpHeader struct and build/parse functions covering the 20 fixed bytes. Reuse the existing src/net/checksum.rs with a TCP pseudo-header (source IP, dest IP, zero byte, protocol 6, TCP length). Demux protocol 6 from the existing IPv4 receive path. Verify by building a SYN segment in a unit fixture and dumping the bytes.
31.2
The TCP Control Block. Define struct TcpControlBlock with fields for local/remote IP + port, send_next, send_unacked, recv_next, recv_window, and a state enum. Storage for now: a single global slot (one TCP connection at a time). A socket-table abstraction like UDP's arrives in Lesson 33 when the server side needs to demux multiple connections.
31.3
Active open — send SYN. Derive an ISN from the timer tick counter (monotonic, changes per call). Build a SYN segment with seq=ISN, flags=SYN, no payload. Transmit through the existing IPv4 + Ethernet path. Set the TCB state to SYN_SENT. Block the calling task (reuse Lesson 26's waiter mechanism) waiting for the SYN-ACK.
31.4
Receive SYN-ACK, send final ACK. In the TCP receive path, when a segment arrives with SYN and ACK flags and ack = ISN+1, accept it: record the server's ISN from seq, advance recv_next past the SYN (one byte, conceptually), build the third handshake segment (flags=ACK, seq=ISN+1, ack=server_ISN+1), transmit it, set state to ESTABLISHED, wake the blocked task.
31.5
Send one bounded payload. Once ESTABLISHED, the ring-3 fixture writes a valid 31-byte, length-prefixed DNS query through SYS_NET_TCP_SEND = 906. The kernel builds a segment with flags=PSH,ACK, seq=send_next, and ack=recv_next; transmits it; then advances send_next by 31. A DNS-over-TCP server requires a complete query before it can return a response. Retransmission arrives in Lesson 32.
31.6
Receive one data byte, send ACK. When a segment with payload arrives in ESTABLISHED, copy the payload into the TCB's receive buffer, advance recv_next by the payload length, build an ACK segment with ack=recv_next, transmit it. Deliver the byte to the ring-3 fixture through SYS_NET_TCP_RECV = 907, blocking if no byte has arrived yet (reuse the existing waiter mechanism).
31.7
End-to-end proof. New syscall SYS_NET_TCP_CONNECT = 905 triggers an active open to 10.0.2.3:53 (slirp's DNS server accepts TCP). The ring-3 fixture sends the DNS query, receives the server's first response byte, and reports both on serial output. Serial shows the chosen client ISN, the server ISN and matching ACK, the final ACK, CLOSED → SYN_SENT → ESTABLISHED, the 31-byte sequence advance, and the response-length acknowledgment advance.
Boundary — what Lesson 31 deliberately does not do

Lesson 31 sends one bounded segment and returns the first received byte. This proves the byte-position model: sequence advances by payload length, and ACK names the next expected byte. The full sliding-window send/recv API, retransmission on loss, and RTT estimation arrive in Lesson 32. Passive open (LISTEN) and teardown arrive in Lesson 33.

Why 10.0.2.3:53 instead of 10.0.2.2:80

slirp's gateway at 10.0.2.2 answers ARP and proxies DHCP, but the gateway host itself does not run services that accept inbound TCP from the guest. The DNS forwarder at 10.0.2.3 does — it implements both UDP/53 (Lesson 30's DHCP references it) and TCP/53 (RFC 7766 requires both transports for DNS). Connecting to 10.0.2.3:53 gives the handshake a live server that will respond with a real SYN-ACK without any host-side setup.

Probe — the third segment carries no SYN

The third handshake message is a pure ACK: it carries the ACK flag, no SYN flag, and no payload. Yet the connection is not ESTABLISHED until the server receives it. What state is the server in before segment 3 arrives, what does it learn from segment 3 that it did not already know from segment 2, and what happens to the connection if segment 3 is lost in transit?

Answer the probe when ready, or ask about any field, state, or build step before implementation. The build starts at step 31.1.

What this completes

Lesson 31 lands the TCP segment format, the three-way handshake, the establishment states, and one byte exchanged in each direction. The kernel gains a TCP receive path alongside UDP, a single-slot TCB, and three new syscalls (connect, send, recv). ESTABLISHED is reached and the byte-position model (sequence advances by payload length, ACK tracks the next expected byte) is proven on the wire.
