Why a request header at all

You might wonder: in Lesson 7 we had descriptors pointing at buffers. Why can't the kernel just hand the device a buffer and say "fill this"? Why does virtio-blk need a structured request header?

Because the device needs to know what to do with the buffer. A read at sector 0 is different from a read at sector 42, which is different from a write, which is different from a flush. The descriptor tells the device where the buffer is; the request header tells the device what to do. Without the header, the descriptor is just an empty envelope.

virtio-blk defines a fixed 16-byte header the kernel fills in for every request. The header travels as the first descriptor in the chain; the data buffer (and a one-byte status field) follow it. The device reads the header, does the operation, fills the buffer, writes the status.

The virtio-blk request header (16 bytes)

virtio-blk request header 16 bytes total
type u32 · 4 B 0x00–0x03
reserved u32 · 4 B 0x04–0x07
sector u64 · 8 B 0x08–0x0F
type u32

Operation code. The four common values:

VIRTIO_BLK_T_IN = 0 — read. Device reads sectors from disk and writes the bytes into the data buffer.

VIRTIO_BLK_T_OUT = 1 — write. Device reads bytes from the data buffer and writes them to disk.

VIRTIO_BLK_T_FLUSH = 4 — flush. Device writes any cached writes to persistent storage. Takes no data buffer (just header + status).

VIRTIO_BLK_T_GET_ID = 8 — read vendor ID string. Special diagnostic; we won't use it.

read sector 0: type = 0 (VIRTIO_BLK_T_IN) write sector 4: type = 1 (VIRTIO_BLK_T_OUT) flush cache: type = 4 (VIRTIO_BLK_T_FLUSH)
reserved u32

Always zero. The spec leaves this for future expansion (e.g., priority bits for advanced schedulers). Driver must zero it; device ignores it.

sector u64

Starting sector number. Sector in virtio-blk always means 512 bytes — not the filesystem's block size, not the device's physical sector size. Multi-sector reads/writes use one descriptor with len = 512 × N; sector is the starting unit.

read 1 sector at offset 0: sector = 0, len = 512 read 1 sector at offset 4096: sector = 8 (4096 / 512), len = 512 read 4 sectors at offset 4096: sector = 8, len = 2048

Note the size — 16 bytes, deliberately small. The header is allocated fresh per request and freed on completion; keeping it tight means less memory traffic per I/O. For the same reason it's a flat structure with no pointers — pointers would have to be translated across the guest/host boundary.

Side note: sector vs block

Sector = the device's unit, always 512 bytes for virtio-blk. Block = the filesystem's unit, often 1024 or 4096 bytes for ext2. The block layer (Lesson 9) translates "give me block N" into "read sectors N×(blocksize/512) through ((N+1)×(blocksize/512))-1". For Lesson 8 we deal in sectors only — one block layer abstraction higher than raw sectors is where blocks live.

The three-descriptor chain

Every virtio-blk request is a chain of three descriptors: the header (kernel writes, device reads), the data buffer (direction depends on type), and a one-byte status (device writes the result). They're chained via F_NEXT on descriptors 0 and 1; descriptor 2 is the tail.

desc[0] — head
Request header
addr → 16-byte buffer
len = 16
flags = F_NEXT
→ next = 1
desc[1] — middle
Data buffer
addr → 512-byte buffer
len = 512
flags = F_NEXT | F_WRITE
→ next = 2
desc[2] — tail
Status byte
addr → 1-byte buffer
len = 1
flags = F_WRITE

The F_WRITE flag on descriptors 1 and 2 (data and status) tells the device: "you'll be writing here, not reading." The header (descriptor 0) has no F_WRITE — the device reads the header but doesn't modify it.

The kernel submits the chain by writing the head descriptor index (0 in this example, but it's whatever the free list returned) into the available ring. The device sees the new head, follows next pointers to gather the whole chain, then acts.

The status byte

After processing, the device writes one byte to the address in descriptor 2:

0 = VIRTIO_BLK_S_OK — request succeeded, data buffer is valid.
1 = VIRTIO_BLK_S_IOERR — host-side I/O error (e.g., QEMU couldn't read the backing file).
2 = VIRTIO_BLK_S_UNSUPP — unsupported operation (e.g., FLUSH when the device doesn't support it).

Always check the status byte before trusting the data buffer. A failed read may have written partial or garbage data.

End-to-end flow — what physically happens

Trace one disk read of sector 0, from kernel code through to completion:

kernel lane (guest) device lane (QEMU host)
T0kernel

Allocate three DMA buffers — one frame each for header, data, status — and compute each buffer's physical address. BlkBuffers::new() (block.rs:130) allocates the frames and derives header_phys/data_phys/status_phys (block.rs:578–580).

T1kernel

Write the request header (type=0, reserved=0, sector=0) via new_read (block.rs:131, block.rs:529–534) and write_header (block.rs:132, block.rs:611). Then build the three-descriptor chain: build_read_chain allocates head/mid/tail via alloc_descriptor (queue.rs:227–229) and writes each descriptor's addr/len/flags/next with write_descriptor (queue.rs:235–243, queue.rs:198).

T2kernel

Publish the chain head to the available ring. submit_chain writes head into avail->ring[idx % N] (queue.rs:309–311) and advances avail->idx with fetch_add(1, Release) (queue.rs:319). Called at block.rs:140.

T3kernel

Kick the device. kick() computes notify_virt + queue_notify_off * multiplier and writes 0 there with write_volatile (block.rs:470, block.rs:481–483). The store exits the guest and signals QEMU's virtio-blk backend. Called at block.rs:141.

T4device

QEMU's virtio-blk thread wakes, sees avail->idx advanced, reads the head index, and follows the next pointers to gather the header, data, and status buffers. Host-side behavior; not in the gabix driver.

T5device

QEMU reads the request header (type=0 read, sector=0) and issues a host-side pread on the disk image at byte offset 0, reading 512 bytes into an internal buffer. Host-side behavior; not in the gabix driver.

T6device

QEMU DMAs the 512 bytes from its internal buffer into the guest data buffer (descriptor 1's physical address) and writes 0 (VIRTIO_BLK_S_OK) to the status byte (descriptor 2's address). The kernel reads that status byte back in T9 via read_status (block.rs:626). Host-side behavior; not in the gabix driver.

T7device

QEMU writes {id: head, len: 512} into used->ring[used->idx % N] and advances used->idx with Release ordering. The kernel observes the advance in T8. Host-side behavior; not in the gabix driver.

T8kernel

Poll for completion. poll_completion loads used->idx with Acquire (queue.rs:345, queue.rs:352); when it advances past last_used_idx, it reads the used ring entry's id and len (queue.rs:361–365) and returns (id, len). Called at block.rs:148.

T9kernel

Verify and clean up. Read the status byte via read_status and assert VIRTIO_BLK_S_OK (block.rs:163, block.rs:626). Read the 512-byte data buffer via read_data_prefix (block.rs:176, block.rs:634). Free the three descriptors back to the free list (block.rs:171–173, free_descriptor at queue.rs:168).

Steps T0–T3 are kernel-side and fast (microseconds). T4–T7 are host-side and dominate the latency — QEMU has to actually read a file, which may hit host OS page cache or do real disk I/O. T8–T9 are kernel-side again, also fast.

DMA-able memory: a frame allocator detour

The device needs physical addresses for the header, data buffer, and status byte — it DMAs to/from them directly, without walking kernel page tables. Our heap allocator hands out virtual addresses that we'd have to translate (walk page tables) to get physical. That's annoying.

The frame allocator gives us both for free: each frame's physical address is frame_number × 4096, and its virtual address is physical + phys_offset() via the direct map. We allocate one frame each for header (16 bytes used of 4096 — wasteful but simple), data buffer (512 bytes used of 4096), and status (1 byte used of 4096). Lesson 9 will refactor this into a proper sub-frame allocator.

What Linux does

Real Linux drivers use kmalloc for the in-kernel buffer, then dma_map_single to get the DMA address. The DMA API handles IOMMU translation on hardware that has one, and ensures proper cache flushing on hardware that needs it. Our setup is simpler: no IOMMU, the direct map gives us cache-coherent access, and the frame allocator gives us physical addresses directly.

Build steps — your turn

Five substeps. By the end you'll have read sector 0 and verified the signature. This is Keystone 1 — bytes flow from disk for the first time.

8.1Define the request header struct

Add a #[repr(C)] struct VirtioBlkReq with the three fields above. Constants for the operation types and status codes:

  • VIRTIO_BLK_T_IN = 0 (read), VIRTIO_BLK_T_OUT = 1 (write), VIRTIO_BLK_T_FLUSH = 4
  • VIRTIO_BLK_S_OK = 0, VIRTIO_BLK_S_IOERR = 1, VIRTIO_BLK_S_UNSUPP = 2

The struct lives in src/virtio.rs. Test by asserting size_of::<VirtioBlkReq>() == 16.

8.2Allocate DMA-able buffers

Helper to allocate one frame and return both its physical and virtual addresses. Three allocations per read request: header (16 B), data buffer (512 B), status (1 B). Each gets its own 4 KiB frame.

Stash all six addresses (3 virt, 3 phys) in a small BlkRequest struct so cleanup later can free them.

8.3Build the descriptor chain

Method VirtQueue::build_read_chain(&mut self, req: &BlkRequest) -> u16:

  1. Allocate 3 descriptors via alloc_descriptor: head, mid, tail
  2. Write desc[head]: addr = req.header_phys, len = 16, flags = F_NEXT, next = mid
  3. Write desc[mid]: addr = req.data_phys, len = 512, flags = F_NEXT | F_WRITE, next = tail
  4. Write desc[tail]: addr = req.status_phys, len = 1, flags = F_WRITE, next = 0
  5. Return head (this is what gets written to the avail ring)

Use the write_descriptor helper from Lesson 7's step 7.3. The chain is built entirely in the descriptor table region — no extra allocations.

8.4Submit, kick, poll

Call the Lesson 7 helpers in sequence:

  1. queue.submit_chain(head) — fills avail ring, advances idx with Release
  2. virtio_dev.kick() — writes to notify register, wakes the device
  3. queue.poll_completion() — Acquire-loads used->idx, returns (id, len) when it advances

For Lesson 8, poll in a loop with a generous cap (e.g., 100000 iterations). When QEMU is slow to wake, it can take a few iterations. If no completion arrives, fail loudly.

8.5Verify the bytes match

After the completion arrives:

  1. Read the status byte: must be VIRTIO_BLK_S_OK (0)
  2. Check len == 512 (device wrote all requested bytes)
  3. Read the first 15 bytes of the data buffer: must be b"MINIOS_DISK_v0\n"
  4. Remaining 497 bytes should be zero (the disk image was truncate -s 1M'd then the signature written)
  5. Free all 3 descriptors back to the free list

Print the verification result. If the signature matches, Keystone 1 is complete — the kernel has read its first byte from disk.

Verification — what success looks like

After step 8.5, the boot output should show: 

// ... Lesson 7 verification (queue active) ...
[test] first disk read — sector 0 (Keystone 1)
[virtio] allocating DMA buffers (header/data/status)
[virtio] building 3-descriptor read chain (sector 0)
[virtio]   desc[head=61] addr=0x0000000000B83000 len=16  flags=0x01 (F_NEXT)         next=60
[virtio]   desc[mid =60] addr=0x0000000000B84000 len=512 flags=0x03 (F_NEXT|F_WRITE) next=59
[virtio]   desc[tail=59] addr=0x0000000000B85000 len=1   flags=0x02 (F_WRITE)        next=0
[virtio] submit_chain(61): avail->idx 1 -> 2
[virtio] kick: wrote queue 0 to notify register
[virtio] poll: completion arrived after N iterations
[virtio]   id=61 len=512
[virtio] status byte = 0 (VIRTIO_BLK_S_OK)

Exact descriptor indices and addresses will vary based on allocator state. What matters: status=0, len=512, the 15-byte signature matches, the rest is zero. Once you see "Keystone 1: bytes flowed from disk," you've hit the milestone.

Primary source

The OASIS VIRTIO 1.2 spec, section 5.2 (Block Device), defines the request header layout, operation types, and status codes. Definitive reference.

For Linux's implementation: drivers/block/virtio_blk.c — specifically virtblk_queue_rq shows how each request becomes a descriptor chain. The struct virtio_blk_req is the kernel-side equivalent of our VirtioBlkReq.

Pause and think

The header's sector field is 64 bits — that's enough to address 2^64 × 512 bytes = way more than any real disk. Why is it that wide instead of, say, 32 bits (still 2 TB addressable)?
