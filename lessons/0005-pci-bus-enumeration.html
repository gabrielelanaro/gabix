PCI Bus Enumeration

How the kernel discovers what hardware exists. Walk the PCI bus, find the virtio-blk device QEMU exposes.

Read time ~20 min Build time ~30–45 min Prereq Lesson 4

The disk is attached to QEMU but the kernel has no idea it's there. Before we can talk to virtio-blk, we have to find it. On modern x86, the discovery protocol is PCI (Peripheral Component Interconnect) — a standard bus that lets the CPU enumerate every attached device, read its identity, and configure its memory mappings. This lesson: what PCI is, how to access it via I/O ports, how to walk the bus, and how to find the virtio-blk device specifically.

Why PCI exists

Before PCI, expansion cards used the ISA bus. ISA had no discovery protocol — every device had hardcoded memory and interrupt settings, configured via physical jumpers on the card. Adding a new device meant consulting manuals to avoid conflicts with existing devices. It was awful.

PCI (1992) introduced a configuration space: a standard 256-byte region per device that the CPU can read to find out what the device is, and write to assign it memory regions, interrupts, and enable bus mastering. The OS doesn't need to know about specific device models — it walks the bus, reads the vendor and device IDs, and loads the right driver. Plug-and-play becomes possible.

PCIe (Express) is the modern serial successor, but it preserves the PCI configuration space interface — old code still works. When we say "PCI" in these lessons, we mean the configuration-space access protocol that PCI defined and PCIe preserves.

The 256-byte configuration space

Every PCI device has a 256-byte configuration space. The first 64 bytes are standardized — every device has the same layout. The remaining 192 bytes are device-specific. We only need the first 64.

0x00 vendor_id u16 — identifies the manufacturer (0xFFFF = no device) 0x02 device_id u16 — identifies the specific device model 0x04 command u16 — bus mastering, I/O access, memory access enable bits 0x06 status u16 — capabilities list, etc. 0x08 revision_id u8 — hardware revision 0x09 class_code u24 — base class, subclass, programming interface (3 bytes) 0x0C cache_line_size u8 0x0D latency_timer u8 0x0E header_type u8 — bit 7 = multifunction device 0x0F BIST u8 — built-in self-test 0x10 BAR0 u32 — Base Address Register 0 0x14 BAR1 u32 — Base Address Register 1 0x18 BAR2 u32 0x1C BAR3 u32 0x20 BAR4 u32 0x24 BAR5 u32 — six Base Address Registers total 0x28-3F cardbus / etc. varies by header type

For this lesson we care about three fields: vendor_id (who made it), device_id (which model), and the BARs (where the device's registers live in memory).

Read-only vs writable: which fields can the OS change?

Config space is mixed. The identity fields are hardwired by the manufacturer and ignore writes — the device reports them, you can't change them:

• vendor_id, device_id, revision_id — who made it and which model.
• class_code — what kind of device (network, storage, display).
• header_type — layout of the rest of the header (we'll see type 0 for normal devices).
• BIST — mostly read-only.

The control fields are read-write. The OS uses these to enable the device and configure its memory layout:

• command — bit 0 enables I/O space access, bit 1 enables memory space access, bit 2 enables bus mastering (Direct Memory Access capability). The OS writes these to turn the device on.
• status — some bits are write-1-to-clear error flags (signaled target abort, master abort, parity error).
• BARs — the OS writes the desired base address into the BAR; the device then responds to that address. See the next card for details.
• cache_line_size, latency_timer — performance tuning knobs.

In practice for mini-os: SeaBIOS (QEMU's firmware) runs before the kernel and does the initial PCI setup — assigns BAR addresses, enables bus mastering. So our kernel could boot without writing any config space. We still implement config_write because Lesson 6 needs it (writing the virtio device status register to set DRIVER_OK), and because it's part of the standard PCI API.

What's a BAR (Base Address Register)?

A BAR tells the OS where the device wants its memory-mapped registers placed. The device doesn't care about the exact address — it just needs some address. The BIOS or the OS picks an unused address range and writes it into the BAR. After that, reads/writes to that virtual address reach the device instead of RAM.

Each BAR's low bits encode the type: bit 0 is 0 for memory, 1 for I/O. For memory BARs, bits 1-2 are the width (32-bit or 64-bit), bit 3 is "prefetchable." The high bits are the address (already shifted — the low 4 bits are the type flags).

For virtio-blk, the BARs hold the virtio capability structures (common config, ISR, notification, device-specific config). We'll read these in Lesson 6 to set up the device.

Accessing config space: I/O ports 0xCF8 / 0xCFC

PCI configuration space is reached through two 32-bit I/O ports. I/O ports are a separate x86 address space from memory — accessed via the in and out instructions rather than memory loads and stores. Ports 0xCF8 (address) and 0xCFC (data) are reserved by the PCI standard for config space access.

The protocol: write a 32-bit address to port 0xCF8 identifying which device and which offset you want, then read or write 32 bits at port 0xCFC.

The address encodes the bus, device, function, and register offset into 32 bits:

The enable bit (bit 31) must be 1 or the access is ignored. The reserved bits (30-24) must be 0. bus (8 bits, 0-255), device (5 bits, 0-31), function (3 bits, 0-7). The offset is in bytes but must be 4-byte aligned — that's why the low 2 bits are reserved.

— Bit math for the address word 
// Build the 32-bit PCI config address
let address: u32 = (1 << 31)              // enable bit
              | ((bus     as u32) << 16)  // bits 23-16
              | ((device  as u32) << 11)  // bits 15-11
              | ((func    as u32) << 8)   // bits 10-8
              | ((offset  as u32) & 0xFC); // bits 7-2 (low 2 bits clear)

Enumeration algorithm

PCI topology: up to 256 buses, each with up to 32 devices, each with up to 8 functions. A function is the actual addressable unit — a single physical card might expose multiple functions (e.g., a combined Ethernet + storage controller). To enumerate: nested loops.

— Pseudocode for full bus walk 
for bus in 0..=255 {
    for device in 0..=31 {
        for func in 0..=7 {
            let vendor = config_read(bus, device, func, 0x00);
            if vendor == 0xFFFF { continue; } // absent

            let device_id = (vendor >> 16) & 0xFFFF;
            let vendor_id = vendor & 0xFFFF;
            println!("PCI {:02x}:{:02x}.{:x} vendor={:04x} device={:04x}",
                       bus, device, func, vendor_id, device_id);
        }
    }
}

In practice QEMU only exposes a handful of devices, so most positions return 0xFFFF. The ones that exist are worth looking at.

What devices does QEMU's default config expose?

A typical QEMU -machine q35 or pc boot shows these PCI devices:

• Host bridge (Intel 440FX / Q35) — vendor 0x8086 (Intel), device 0x1237 (i440FX) or 0x29C0 (Q35 MCH). The bridge between CPU and PCI bus.
• ISA bridge / PIIX — vendor 0x8086, device 0x7000. Connects PCI to the legacy ISA bus, where serial ports and the PIT live.
• VGA controller (Bochs / stdvga) — vendor 0x1234, device 0x1111. Our text-mode VGA buffer lives behind this.
• virtio-blk-pci (if attached) — vendor 0x1AF4 (Red Hat / QEMU), device in the 0x1000-0x107F range. The disk we want to find.
• E1000 / virtio-net (if networking enabled) — networking cards.

By walking the bus and printing every device, we get a hardware inventory. Lesson 5 step 5.3 is exactly this.

Finding virtio-blk

The virtio vendor ID is 0x1AF4 — assigned to Red Hat (which originally designed virtio, before it became an OASIS standard). Within that vendor, the device IDs 0x1000–0x107F are virtio devices. The non-transitional (modern-only) ID for virtio-blk is 0x1042; the transitional (backward-compatible) ID is 0x1001.

Modern vs transitional. Modern virtio (PCI modern transport) is what Linux has used by default since ~2017. Transitional mode supports both modern and legacy transports for backward compatibility. We'll use modern — it's the cleaner interface and what real Linux uses. So we look for vendor 0x1AF4 and a device ID in the 0x1040-0x107F range (non-transitional), specifically 0x1042 for virtio-blk.

Once we find the device, we read its BARs to learn where the virtio capability structures live in memory. Virtio's "PCI modern" transport doesn't use a single BAR — instead, it puts a list of capabilities in the device's PCI configuration space (the upper, device-specific bytes from 0x40 to 0xFF). Each capability points at a region within one of the BARs that holds a specific virtio structure (common config, ISR, notifications, device-specific config, etc.). Lesson 6 walks through reading the capability list; for Lesson 5 we just identify the device and print its BARs.

Build steps — your turn

Four substeps. Commit each separately. The first is setup, the next three are kernel code.

5.1Create the disk image and attach to QEMU

Make a 1 MB raw disk image with a known signature at sector 0 (something like "MINIOS_DISK_v0\n" followed by zeros). This is the byte pattern we'll verify in Lesson 8's first read. Disk image lives at disk.img in the project root.

Modify the QEMU launch to attach it: -drive file=disk.img,format=raw,if=none,id=drv0 -device virtio-blk-pci,drive=drv0 (the two-step form; the shorter if=virtio form also works but is older syntax).

Verify QEMU accepts the disk and the kernel still boots unchanged. The kernel doesn't know about the disk yet — that's fine. This step is pure infrastructure.

5.2PCI config space access

Create a new src/pci.rs module. Define I/O port constants CONFIG_ADDRESS: u16 = 0xCF8 and CONFIG_DATA: u16 = 0xCFC. Implement:

fn config_read(bus: u8, device: u8, func: u8, offset: u8) -> u32 — build the address word per the bit math above, write to 0xCF8, read 32 bits from 0xCFC.

fn config_write(bus: u8, device: u8, func: u8, offset: u8, value: u32) — same address setup, write to 0xCFC.

Use the x86_64 crate's Port::new and read/write methods (we already depend on it). Add mod pci; to main.rs.

5.3Walk the bus, list every device

Implement fn enumerate() in pci.rs. Nested loops over bus 0, device 0-31, function 0-7. (Walking all 256 buses is unnecessary for QEMU's default topology — bus 0 is the only one.) For each combination, read vendor ID; if 0xFFFF, skip. Otherwise print [pci] 00:XX.X vendor=YYYY device=ZZZZ.

Call pci::enumerate() from kernel_main after the existing tests, before enter_user_mode. Boot the kernel, look at the serial output. You should see Intel 440FX, PIIX, Bochs VGA, and (if attached) virtio-blk.

5.4Identify virtio-blk, print its BARs

In enumerate(), when you find a device with vendor 0x1AF4 and a device ID in the 0x1040-0x107F range, call it virtio-blk. Print all six BARs (offsets 0x10, 0x14, 0x18, 0x1C, 0x20, 0x24). For each BAR: if the low bit is 0 (memory BAR), report the type (32-bit if bits 1-2 are 0, 64-bit if bits 1-2 are 2) and the base address (high bits, mask off the low 4 type bits). If the low bit is 1 (I/O BAR), report that.

The output should look roughly like:

[pci] virtio-blk found at 00:04.0
[pci] BAR0 = 0xFEBC0000 (memory, 32-bit)
[pci] BAR1 = 0x00000000 (unused)
[pci] BAR2..BAR5 = ...

The exact BAR values depend on QEMU's MMIO layout, which varies by machine type and BIOS. The point is to see that the device exists and has memory regions assigned.

Verification — what success looks like

Boot the kernel after step 5.4. Serial output should include a list of PCI devices, with virtio-blk among them: 

// ... boot stuff ...
[pci] 00:00.0 vendor=8086 device=1237   // Intel i440FX host bridge
[pci] 00:01.0 vendor=8086 device=7000   // PIIX ISA bridge
[pci] 00:01.1 vendor=8086 device=7010   // PIIX IDE
[pci] 00:01.3 vendor=8086 device=7113   // PIIX PM
[pci] 00:02.0 vendor=1234 device=1111   // Bochs VGA
[pci] 00:03.0 vendor=8086 device=100E   // E1000 NIC (if enabled)
[pci] 00:04.0 vendor=1AF4 device=1042   // virtio-blk (the one we want)
[pci]   virtio-blk found at 00:04.0
[pci]   BAR0 = 0xFEBC0000 (memory, 32-bit)
[pci]   BAR1 = 0x00000000 (unused)
[pci]   BAR2..BAR5 = ...

The exact bus/device positions and BAR addresses may differ — QEMU assigns them dynamically. What matters is that we can find a device with vendor=0x1AF4 and read its BARs. Lesson 6 picks up from here.

Primary source

The OSDev wiki PCI page is the practical reference — covers config space layout, the address encoding, BAR detection, and bus enumeration with working code examples. More condensed than the official spec.

For the canonical source, Linux's arch/x86/pci/direct.c implements pci_conf1_read and pci_conf1_write — exactly our config_read / config_write. The bus enumeration in drivers/pci/probe.c (pci_scan_bus and friends) is far more sophisticated than what we'll build, but the shape is the same.

The official PCI spec is large and paid. The PCI-SIG specifications page hosts it; for our purposes OSDev's summary is sufficient.

Pause and think

The configuration space is only 256 bytes per device. We saw that it holds vendor/device IDs, command/status, six BARs, and other fixed fields, with device-specific space left over. The virtio PCI modern transport uses some of that leftover space to advertise a list of capabilities — pointers to BAR regions holding specific structures. Why this design? Why not just put the structures directly in the config space at fixed offsets?
