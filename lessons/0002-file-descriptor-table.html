Lesson 2 · M4 · 4.4 VFS layer

The File Descriptor Table

First slice of real VFS plumbing — a per-process FD table and the four core file syscalls.

Read time ~15 min Build time ~45–60 min Prereq Lesson 1

Goal of this lesson: a user program calls open("/test"), gets back a file descriptor, reads bytes from it, writes bytes to it, and closes it. End-to-end. Real bytes, real cursor advancement, real FD numbers in the syscall trace. The backing is a single hardcoded inode for now; directories and multiple files come in Lesson 3.

The design — three types

Lesson 1 ended with the rule: inode = the file, file = an open instance, FD = per-process integer key. In Rust, with mini-os conventions (Arc for shared ownership, Mutex for interior mutability), that becomes three small types: 

pub struct Inode {
    pub data: Mutex<Vec<u8>>,
}

pub struct File {
    pub inode: Arc<Inode>,
    pub cursor: Mutex<u64>,
}

pub struct FdTable {
    table: Vec<Option<Arc<File>>>,
}
Task  ·  fd_table: FdTable
↓
FdTable  ·  Vec<Option<Arc<File>>>
↓ indexes by integer
File  ·  inode + cursor
↓ points at
Inode  ·  Mutex<Vec<u8>> (shared!)
Three layers because they have different sharing patterns. Two FDs from one open() are independent Files sharing one Inode. Two FDs from one dup() share one File.

The Arc on Inode is what makes two independent open() calls land on the same bytes — the File struct is fresh each time, but the underlying Inode is shared. The Arc on File inside the FD table is what makes dup() and fork() sharing work — two FD numbers, one File, shared cursor.

The four syscalls

Four new syscalls, dispatched by number from syscall_entry:

SYS_OPEN = 2  —  fn sys_open(name_ptr: u64) -> u64
For Lesson 2 we ignore name_ptr entirely — there is exactly one file in the world, a hardcoded inode. The handler allocates a fresh File (cursor=0) pointing at that inode, inserts it into the current task's FdTable, and returns the FD number. Lesson 3 will actually parse name_ptr as a path.
SYS_READ = 0  —  fn sys_read(fd, buf_ptr, len) -> u64
Look up the File for fd. Lock the inode's data and the file's cursor. Compute how many bytes are available from cursor to end-of-data (data.len() - cursor), cap at len, memcpy that many bytes into the user buffer at buf_ptr, advance the cursor, return the count actually read. Returns 0 at end-of-file.
SYS_WRITE = 1  —  fn sys_write(fd, buf_ptr, len) -> u64
Already exists for FD=1 (stdout, serial). Extend it: if fd == 1, current behavior (serial print). Otherwise, treat fd as a regular file — look up the File, lock inode data and cursor, extend data with the bytes from buf_ptr if writing past end, advance cursor, return count written.
SYS_CLOSE = 3  —  fn sys_close(fd) -> u64
Remove the entry from FdTable. The Arc<File>'s refcount drops; when it hits 0, the File drops; the File holds an Arc<Inode> whose refcount drops; if that hits 0 the inode is freed (but for our hardcoded inode, it never does — we hold a static Arc to it).
Design decision — stdio as files. Eventually FD 0/1/2 should be Files pointing at a "terminal device" inode. For Lesson 2 we keep the existing serial-output path for FD=1 special-cased inside sys_write. Lesson 5 or so will revisit and make stdin/stdout real Files. This keeps the lesson scoped to one win: regular files work.

Integration points

Three places in the existing code get touched:

  1. src/fs.rs (new file): the three types above, plus impl blocks with open, get, close methods on FdTable. Plus a global static HARDCODED_INODE: Lazy<Arc<Inode>> initialized with some bytes (say b"hello vfs\n").
  2. src/task.rs: add fd_table: FdTable field to Task. Initialize in Task::new. Expose an accessor that returns &mut FdTable for the current task.
  3. src/syscall.rs: add the four syscall numbers to the dispatch match, write the four handlers, plus a copy_bytes_from_user / copy_bytes_to_user helper (for now, just memcpy — no validation against the user's address space yet, that's a security pass for later).

Build steps — your turn

Per the hybrid track, here are six small slices. Each is a logical checkpoint you can build, run, and verify before moving to the next. Drive them yourself, or ask me to drive any of them while you review — both work.

2.1Create src/fs.rs with the three types

Define Inode, File, FdTable. Implement FdTable::new(), FdTable::open(file) -> u64 (returns lowest free index), FdTable::get(fd) -> Option<Arc<File>>, FdTable::close(fd) -> bool. Add a lazy_static! HARDCODED_INODE with some test bytes.

Module goes in main.rs: mod fs;. No syscalls yet — just types. Compile should succeed with no behavior change.

2.2Add fd_table to Task

Add the field, initialize it in Task::new via FdTable::new(). Add a helper with_current_fd_table(|t| ...) in task.rs that locks the scheduler and gives mutable access to the running task's FD table.

Still no syscalls. Compile should succeed; runtime behavior unchanged.

2.3Implement sys_open

Add SYS_OPEN = 2 to the dispatch. Handler ignores the path argument, creates Arc::new(File { inode: HARDCODED_INODE.clone(), cursor: Mutex::new(0) }), calls with_current_fd_table(|t| t.open(file)), returns the FD number.

Add a println! trace so you can see the FD returned. Build, run the existing user program (which still uses write/exit only), confirm nothing broke.

2.4Implement sys_read

Add SYS_READ = 0. Handler: look up File, lock inode data + cursor, compute available = data.len() - cursor, to_read = min(len, available), memcpy from data[cursor..cursor+to_read] to buf_ptr, advance cursor, return to_read.

Need a helper to convert a user virtual address to a kernel pointer. For now, a raw buf_ptr as *mut u8 cast works because user and kernel share the same address space (post-fork the user code runs in its own AS, but the syscall handler runs in kernel mode where the user's mappings are inherited).

2.5Extend sys_write + add sys_close

SYS_WRITE already handles FD=1 (serial). Add a branch: if fd != 1, look up the File, extend the inode's data with the bytes from buf_ptr, advance cursor, return count. SYS_CLOSE just calls FdTable::close and returns 0/−1.

2.6Update USER_PROGRAM to exercise all four

Write a new flat binary that does: open("/test") → returns FD (say 3). read(3, buf, 5) → reads "hello" from the hardcoded inode. write(1, buf, 5) → prints "hello" via serial. write(3, " world", 6) → appends to the inode. close(3) → frees the FD. exit(0).

The hand-assembled flat binary pattern is the same as the existing USER_PROGRAM — copy the structure, change the syscalls. Test output should show [syscall] sys_open -> fd=3, then hello, then exit.

Verification — what success looks like

Serial output of the test program should look roughly like: 

// ... boot stuff ...
[syscall] sys_open (ignored path) -> fd=3
[syscall] sys_read fd=3 len=5 -> read 5 bytes
hello
[syscall] sys_write fd=1 len=5 -> wrote 5 bytes
[syscall] sys_write fd=3 len=6 -> wrote 6 bytes (inode now 11 bytes)
[syscall] sys_close fd=3 -> ok
[syscall] sys_exit(0)

If you re-open the file in a second open call after closing, the inode should still contain the bytes you wrote (it is the same HARDCODED_INODE). That is Lesson 2's proof that we have a real (if tiny) filesystem underneath: writes persist across opens.

Primary source

Skim fs/read_write.c in Linux — specifically vfs_read and vfs_write. They are the real version of what our sys_read / sys_write become once they grow up: take a struct file *, do permission checks, call file->f_op->read or ->write. We do not have the function-pointer dispatch yet (we inline the inode access); Lesson 3's fops table will introduce it.

For the FD table itself, fs/file.c is the canonical reference. __alloc_fd is the function that finds the lowest free FD number — exactly what our FdTable::open does. Linux uses an fdt with a bitmap for sparse tables; we use a flat Vec for simplicity.

Pause and think

Two processes both call open("/test") at roughly the same time. Both get FD 3 in their own tables. They each read(3, buf, 5). Do they see the same 5 bytes, or different bytes? Where exactly in the type definitions does the answer live?
