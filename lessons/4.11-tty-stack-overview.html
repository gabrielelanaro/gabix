4.11 / Devices / Terminals and TTYs

Terminal input in Unix

You type a command into a terminal window and press Enter. It feels as though the shell receives a line at that moment. We can examine what “receives” means by running a program that reports exactly what it reads.

1. What can the program see?

The shell is the program that prints the prompt and runs commands. The terminal emulator is the application that displays the prompt and accepts your keystrokes. In a terminal window on macOS or Linux with Python 3 available, run this command at the shell prompt. It starts a small program in the foreground, so the program gets the next turn at reading keyboard input.

python3 -c 'import os; data = os.read(0, 64); print("received", len(data), repr(data))'

The program asks the operating system for up to 64 bytes from standard input (descriptor 0). The call waits until it can return some input. With the terminal’s usual line settings, try the following:

  1. Type l and x. Pause. You can see lx. Has the program printed a report?
  2. Press Backspace to erase the x, then type s. The screen shows ls.
  3. Press Enter. Read the program’s report.
Expected report
received 3 b'ls\n'

The three bytes represent lowercase l, lowercase s and newline. The program made one read. The intermediate x was visible on the screen and is absent from the result.

How could the screen show each correction while the program waited inside that one call?

2. Replay the same read inside the kernel

The kernel manages the terminal’s input queue. In canonical mode, its terminal input routines, called the line discipline, collect a line. Each ordinary key adds a byte. Backspace removes the last pending character. With echo enabled, the kernel also sends output to the emulator so it can draw each edit. That output accounts for what you saw before the program printed anything.

Enter completes the line. The kernel marks the waiting program Ready. Its read is still pending and the bytes are still queued. When the scheduler chooses the program, execution resumes inside the same read handler. It copies the bytes into the program’s memory and returns 3. Python can now print the report.

3. When the shell edits the line

An interactive shell can use a line editor to handle history, cursor movement and completion. The editor needs input before Enter, so it selects noncanonical mode. In this example a read can return as soon as one byte is available, up to the capacity of the buffer. The editor disables kernel echo and writes the updated line to the terminal itself.

Try Backspace in each mode below. In the second mode, the editor and command parser both run inside the shell. Enter lets the editor pass its finished line to the parser in the same process.

4. Connecting the experiment to the Pi

In the experiment, the terminal window and the reader ran on one computer. Suppose instead that the window runs on your Mac and the reader runs on a Raspberry Pi. How does a byte reach the other computer? The keyboard and printer on an early terminal make this physical connection easy to see.

A teletype combined a keyboard and a printer. Pressing a key sent a character code to the connected computer, called the host. The host could send that code back to print the character, a practice called echo. Two other codes moved the mechanism: carriage return (CR) moved the carriage to the left margin, and line feed (LF) advanced the paper. Unix kept the name TTY for its terminal interface. In our example Enter sends CR, which the kernel translates to a newline (LF).

Unix V7 tty(4): general terminal interface, teletype and carriage-return handling

Serial terminals and desktop terminal windows

A physical serial terminal has its own keyboard and display or printer. At the computer end of the cable, a hardware receiver called a UART assembles the incoming bits into bytes. A kernel driver reads those bytes. A desktop emulator instead writes bytes to the master end of a pseudoterminal (PTY). The kernel presents the paired slave end as a terminal that the shell can open. In both cases the kernel applies terminal settings through code called the line discipline.

pty(7), DESCRIPTION · targets/armv7/src/console.rs:24

How does the shell give a program its turn to read?

When a local shell starts, its standard input (descriptor 0), ordinary output (1), and diagnostic output (2) typically refer to the PTY slave. Each descriptor can also be redirected, for example to a file.

A session contains the shell and its jobs. A job can contain several processes in a process group, as in a pipeline. The session can have a controlling terminal. When a job-control shell starts a foreground job, it gives that job’s group the foreground role. The job can then read from the terminal. The terminal continues to own its input queue throughout.

A blocking read in the x86 socket implementation

Suppose a reader finds an empty queue. Input arrives before the reader registers to sleep. The sender sees nobody waiting, and the reader could then sleep with data already queued. Gabix handles this timing problem for an x86 TCP socket.

loop {
    if let Some(count) = socket.read(output) {
        return count as u64;
    }
    crate::task::block_current_if(|pid| socket.register_recv_waiter(pid));
    crate::task::yield_now();
}

Actual x86 TCP branch: src/syscall/file.rs:19

The waiter registration rechecks whether input is still absent while holding the socket state lock. block_current_if registers and marks Blocked with interrupts disabled on this single-core kernel. If data arrived before registration, registration declines to block. The receive path appends data and wakes its recorded waiter. After scheduling resumes the task, the loop checks again. src/net/tcp.rs:358 · src/net/tcp.rs:827 · src/task/scheduler.rs:597

A TTY implementation would make the same check using a completed line as its condition. When that condition holds, waking the reader makes it eligible for scheduling. src/task/scheduler.rs:613

6. Proposed experiment with serial input

Use a tiny user program that calls read(0, buf, 64) and reports the returned count and bytes. For this proposed experiment, connect a COM1 receiver on x86 or a PL011 receiver on ARM to the same canonical input queue. Give the Pi test exclusive use of UART input so the uploader cannot consume its bytes. ARM would also need a way to block and wake the reader.

Start the read, then send ls over serial. A separate trace buffer should record the two received bytes while the read remains pending. Press Enter. Look for the following events in order:

line ready     6c 73 0a   // l, s, newline
reader ready
reader scheduled
read returned  3 bytes

Repeat with Enter arriving before the read begins. The same three bytes should already be queued, so the read can finish without sleeping.
