How Networks Work

From two machines sharing a wire to a datagram crossing the planet: frames, the two kinds of address, ports, best-effort delivery, and why the whole thing is built as layers. Then a short build: attach a network card and find it on the PCI bus.

Read time ~20 min Build time ~20–30 min Prereq none for the concept; Lesson 5 for the build

Networking has its own founding problem, its own vocabulary, and its own design logic, and this lesson teaches them from the ground up. The founding problem: two independent computers, each with its own memory and its own clock, want to exchange bytes over a shared medium that either of them can use at any moment. Every header, address, and layer in the modern stack is a direct answer to some part of that sentence. We will build the picture the way history did — one wire first, then a world of wires — because each addition earns its keep only once you've seen the problem it solves.

Two machines, one wire

Start with the smallest possible network: three computers attached to one shared cable. This is Ethernet as it was born in 1973 — literally a coaxial cable running through a building, with machines tapped into it. Electrically, the cable is a broadcast medium: when one machine transmits, every machine on the cable receives the signal. There is no central controller deciding who speaks; any card may transmit whenever the wire is quiet.

Two consequences follow immediately, and they shape everything downstream.

First: bytes must travel in self-contained bursts, called frames. A machine cannot hold the wire open indefinitely — others need their turn. So a transmission is a bounded chunk: some bookkeeping up front, up to ~1500 bytes of payload, a checksum at the end, then silence. Anything bigger than one frame gets split into several. This is the wire's native unit, and every protocol above inherits its rhythm: networking is chunk-at-a-time, all the way up.

Second: since everyone hears everything, every frame must say who it's for. That bookkeeping up front begins with two addresses: destination first, then source. Each network card ships from the factory with a globally unique 6-byte number burned into it — the MAC address (Media Access Control, e.g. 52:54:00:12:34:56). A card normally reads the first 6 bytes of every frame on the wire and discards frames addressed to someone else; the one machine whose MAC matches keeps reading. The all-ones address ff:ff:ff:ff:ff:ff means everyone — broadcast — and we will need it sooner than you'd think.

That's the complete link layer, conceptually: framed bursts, flat identity-based addressing, polite discard. A MAC address carries no structure — it names the card, like a serial number, and tells you nothing about where the card is. On a single cable, that's enough: "where" and "who" coincide, because everyone is in earshot.

What happens when two talk at once

Nothing coordinates who may speak and when. So two machines can transmit at the same moment, and on a shared cable their signals collide — the two waveforms add on the wire, both frames come out garbled, and neither arrives. Ethernet's original rule for this is CSMA/CD (Carrier Sense Multiple Access with Collision Detection): listen before talking to avoid the obvious collisions, and listen while talking too; if what comes back differs from what you sent, a collision is underway. Stop, send a short jam so everyone knows, then wait a random interval before retrying.

Random is the whole trick. If both machines waited the same fixed time they would collide again on the dot. So the wait is drawn from a range that doubles on each successive collision for the same frame (binary exponential backoff, capped at 10 doublings) — a congested wire spreads its retries out automatically. After 16 tries the frame is dropped and the best-effort nature shows through.

The wire went away

Collisions shaped the protocol's design in 1973, but they don't touch modern Ethernet. The shared coax is gone; today each machine has a private cable to a switch. Each port on a switch is a point-to-point link, not a shared bus — machine A's cable to port 1 and machine B's cable to port 2 are electrically separate, so simultaneous transmissions on different ports can't interfere. Each link is also full-duplex: separate wire pairs for each direction, so even sending and receiving on the same port at the same instant is collision-free. CSMA/CD sits dormant in the spec for gigabit and faster.

The only place contention could reappear is inside the switch: two inputs targeting one output port. The switch handles this with store-and-forward — it buffers each incoming frame into per-port memory, looks up the destination MAC in a learning table (it remembers which card lives on which port), finds the right output, and if that output is busy, queues the frame behind whatever's already there instead of colliding. MAC learning keeps traffic local so fewer outputs contend; buffering is what actually prevents collisions at the output.

The logical model is unchanged — frames, MAC addresses, broadcast — so the 1973 picture remains the right one to reason with. Inside QEMU, our "wire" is a virtual one connecting the guest's virtual card to QEMU's built-in network, and collisions are physically impossible there too.

A network of networks

One wire covers one building. The interesting problem starts when your machine in Stockholm wants to reach a server in Tokyo. You cannot put ten million machines in earshot of each other — physics (signal degrades with distance and listeners) and practicality (every machine hearing all traffic on Earth) both forbid it. So the world is built as many small networks, connected by machines called routers that sit on two or more networks at once and copy frames between them.

Delivery is now a relay. Your frame reaches your local router; that router passes the payload to the next network over, whose router passes it on again — typically 10–20 hops for a transatlantic packet. This is the point where MAC addresses run out. A MAC address is flat: 52:54:00:bb:00:02 contains no hint of which network on Earth that card sits on. A router holding a frame for an unknown MAC would have to ask all networks everywhere — the very broadcast-the-planet problem we're escaping. Relaying needs an address that encodes location.

That address is the IP address (Internet Protocol, e.g. 10.0.2.15) — 4 bytes, and unlike a MAC, hierarchical: a prefix of the number names the network, the remainder names the host within it. Read 10.0.2.15 in our QEMU playground as "network 10.0.2.x, host 15." Routers exploit the hierarchy: a router doesn't know where every host on Earth is, only, for each network prefix, which neighbor is one step closer. Each hop consults that table, forwards, and the packet descends toward its destination network like a letter routed country → city → street. The table is small because it names networks, of which there are thousands, rather than hosts, of which there are billions.

So a machine on the internet holds two addresses with two different jobs, and the division of labor between them is the central idea of this phase:

Hold onto that last row; it's the one that makes the machinery click. The IP packet — "from 10.0.2.15 to 172.217.164.110" — is the letter, unchanged from source to destination. The Ethernet frame is the envelope used for one leg of the trip: your machine addresses a frame to its router's MAC, the router unpacks the IP packet, decides the next hop, and re-wraps the same packet in a fresh frame addressed to the next router's card. Envelope discarded and renewed at every hop; letter untouched.

One gap remains in the story. Your machine knows its router's IP address (it's part of network configuration, like 10.0.2.2 in QEMU). To hand it a frame, though, it needs the router's MAC — frames are addressed to cards, and nothing so far connects the two address systems. The fix is charming in its simplicity: shout. The machine broadcasts (that ff:ff:ff:ff:ff:ff address) a small question onto the local wire — "who has 10.0.2.2?" — and the owner replies with its MAC. This is ARP, the Address Resolution Protocol, and it is Lesson 22 in its entirety. Broadcast is affordable here precisely because ARP never leaves the local wire.

Many programs, one machine

The packet has crossed the planet and arrived at the right card. Delivery still isn't done — machines don't converse, programs do, and the destination is running dozens: a web server, an SSH session, our echo server. The IP header names the machine only. So one more address layers on top: the port, a 16-bit number that names a conversation endpoint within a host. A program tells its kernel "I am taking port 5555" — that's bind(), Lesson 26 — and from then on the kernel delivers any arriving payload marked port 5555 to that program's buffers. Source packets carry a port too, so the reply knows where to return. The full address of a conversation endpoint on Earth is therefore the pair (IP address, port) — 10.0.2.15:5555 — and routing a received packet to the right program is a table lookup keyed by it.

Nothing is promised

One more piece of worldview before the layers, because it separates networking from every kernel subsystem you've built: the network is allowed to fail silently, per packet. A router whose queues overflow drops packets on the floor — no error, no notification, nothing. Packets taking different routes can arrive out of order, or duplicated. The internet's designers chose this on purpose: a relay of best-effort hops needs no shared state and scales without coordination, and any reliability a conversation needs can be rebuilt at the endpoints — number the packets, acknowledge receipt, retransmit what's missing. That reconstruction is TCP (Transmission Control Protocol), a machine of real subtlety, deferred to a post-phase arc. This phase ends with UDP (User Datagram Protocol), which adds ports and a checksum to raw IP delivery and passes the best-effort nature straight through to the application. For an echo server on a quiet virtual wire, best-effort is plenty.

The layers, and one packet dissected

Look back at what the story accumulated, in order of appearance:

application — the payload itself "hello\n" — whatever the programs mean to exchange
transport (UDP) — port → which program Lessons 25–26
network (IP) — address across networks, hop by hop Lessons 22–24 (ARP glues this layer to the one below)
link (Ethernet) — framed bursts on one wire, MAC → which card Lessons 19–21 ← we start here
physical — signals on the medium QEMU's problem, thankfully

Each layer arose to solve one delivery problem — which card, which network, which program — and each needs a few bytes of bookkeeping to do its job. The design that keeps them independent is encapsulation: every layer prepends its bookkeeping as a header and treats everything after it as an opaque payload belonging to the layer above. Transmission wraps: UDP wraps the application bytes, IP wraps the UDP datagram, Ethernet wraps the IP packet. Reception unwraps in reverse, and each header carries one field — a demux key — naming which parser owns the bytes that follow.

ver/IHL u8

Two 4-bit fields packed into one byte: version (4, always) and IHL (Internet Header Length) in 4-byte units. 0x45 = version 4, header 5×4 = 20 bytes — the minimum, no options.

total len u16

Everything from the IP header's first byte to the last payload byte. Big-endian: bytes 00 22 read as 0x0022 = 34 (20 IP + 8 UDP + 6 payload). The ext2 from_le_bytes reflex will give you 0x2200 = 8704 — silently wrong.

TTL u8

Time To Live — a hop budget. Every router that forwards this packet decrements it by one; if it hits zero the packet is discarded (prevents routing loops from looping forever). Starts at 64 here, will be 255 on a reply from the gateway.

protocol u8

The demux key for the network layer. 17 = UDP (hand payload to the UDP parser). 1 = ICMP (Lesson 24). 6 = TCP (post-phase). This single byte is how IPv4 stays agnostic about what rides on top of it.

src IP / dst IP u32

The two addresses that stay constant end to end — unlike the MAC addresses, which are rewritten at every hop. These are the addresses named in the letter-and-envelope analogy: the letter says who the packet is from and who it's for, regardless of which envelope (Ethernet frame) carries it across this particular hop.

Receiving is four table lookups, outside in — EtherType 0x0800 → the IPv4 parser, protocol 17 → the UDP parser, port 5555 → your socket — each one stripping a header and dispatching the remainder. Transmitting runs the same chain backwards, each layer prepending its header to whatever the layer above handed down. Our whole network stack, as software, is those two chains plus the driver underneath.

Two rules for the implementer

1 — Network byte order is big-endian

Every multi-byte integer in those headers puts its most significant byte first: the UDP destination port 15 b3 reads as 0x15B3 = 5555. The convention (RFC 791, Appendix B) was fixed years before little-endian CPUs won the desktop, and it means the ext2 reflex of u16::from_le_bytes must become u16::from_be_bytes in every network parser. A swapped port number fails silently — the packet simply goes somewhere else — which makes this the top bug class in from-scratch stacks.

2 — Receive is unsolicited

Every disk sector your kernel ever saw was one it had asked for. A network peer transmits whenever it wants — your kernel holds no outstanding request, yet bytes arrive. The driver must therefore keep empty buffers pre-registered with the card ahead of time, ready for frames it cannot predict, and refill the supply as frames land; if the supply runs dry, frames are silently lost (the wire does not wait). Lesson 20 builds exactly this. It also means the stack above the driver is reactive by nature — "a frame arrived, classify and route it" runs as its own flow, without any requesting process to hand the result to.

What you already own

New concepts, familiar machinery. The card QEMU gives us is virtio-net — a sibling of the virtio-blk device you drove in Lessons 5–9. Finding it is the same PCI enumeration (vendor 0x1AF4, device 0x1041). Waking it is the same modern-transport handshake from Lesson 6. Exchanging buffers with it uses the same virtqueue rings from Lesson 7 — one queue for transmit, one (with those pre-posted buffers) for receive. And the header parsing of Lessons 21–25 exercises the byte-layout skills ext2 built, with the endianness flipped. The genuinely new material is everything above in this lesson, plus the protocol state to come — which is why the concept half of this phase gets the conversation time, and the driver half moves fast.

The playground: QEMU user-mode networking

QEMU's default network backend ("slirp", or user-mode networking) provides a complete simulated network with zero host configuration:

  • 10.0.2.15 — the guest, us. Real machines learn their IP address by asking the network (DHCP, the Dynamic Host Configuration Protocol — a possible side quest later); we will hardcode ours.
  • 10.0.2.2 — the gateway router, played by QEMU itself. It answers ARP and ping, making it our first conversation partner (Lessons 22–24).
  • hostfwd=udp::5555-:5555 — the door inward. Slirp lets the guest speak out freely but delivers inbound traffic only through explicitly declared port forwards, and the host cannot ping the guest. This constraint shapes our milestones: the ping hello-world (Lesson 24) is guest-initiated, and the echo server (Lesson 26) listens behind a port forward.

The build — three small commits

The build half of this lesson is deliberately light — the concept half was the work. All three steps reuse Lesson 5's PCI code.

1
Attach the card. Add -netdev user,id=n0 -device virtio-net-pci,netdev=n0 to the QEMU invocation in the run script. Boot. The kernel should behave exactly as before — the card sits unclaimed on the bus. Commit.
2
See it in the PCI walk. The Lesson 5 enumeration should now list a second virtio device: vendor 0x1AF4, device 0x1041 — virtio device type 1 (network) offset by 0x1040, the same rule that made blk 0x1042 (VIRTIO 1.2 §4.1.2). Print its BARs (Base Address Registers) alongside blk's. Commit.
3
Generalize the finder. Lesson 5's find-virtio-blk helper gets a generic sibling: find_virtio_device(device_id: u16) -> Option<PciDevice>, called twice at boot — once with 0x1042, once with 0x1041. Verify both serial lines print, and run ./tests/run.sh to confirm the disk path still passes. Commit.
