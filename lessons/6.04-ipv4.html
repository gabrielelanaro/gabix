IPv4 — Header, Checksum, Demux

The layer that survives multi-hop journeys. Twenty bytes of header, one byte of protocol demux key, one byte of TTL, and a checksum algorithm written once here and reused by ICMP and UDP later. Build, validate, dispatch.

Read time ~30 min Build time ~60–90 min Prereq Lesson 22

ARP connected two address spaces on one wire. IPv4 is the layer above — the one whose addresses survive the whole multi-hop journey, the one that gets re-wrapped in a fresh Ethernet frame at every router hop without being touched. This lesson builds the IPv4 header parser and builder, plus the internet checksum algorithm that protects it. Once these are in place, the layer above (ICMP in Lesson 24, UDP in Lesson 25) has somewhere to dispatch to.

The 20-byte IPv4 header

Fixed part is 20 bytes, no options, specified in RFC 791 (1981, still current). Every multi-byte field is big-endian — the Lesson 21 reflex continues. The header is small enough to memorize and large enough to do real work:

IPv4 header — 20 bytes (no options) RFC 791 · all multi-byte fields big-endian
ver/IHL u8 · packed 0x00
DSCP/ECN u8 0x01
total len u16 BE 0x02–0x03
id u16 BE 0x04–0x05
flags/frag u16 BE 0x06–0x07
TTL u8 0x08
protocol u8 0x09
checksum u16 BE 0x0A–0x0B
src IP [u8; 4] 0x0C–0x0F
dst IP [u8; 4] 0x10–0x13
ver / IHL u8 packed

Two 4-bit fields in one byte. Version (4, always — this is IPv4) and IHL (Internet Header Length) in 4-byte units. 0x45 = version 4, header 5×4 = 20 bytes. Options exist and would make IHL larger. This slice only accepts the 20-byte base header.

total length u16 BE

Everything from the IP header's first byte to the last payload byte. Big-endian: bytes 00 22 read as 0x0022 = 34 (20 IP + 8 UDP + 6 payload). The ext2 from_le_bytes reflex gives 0x2200 = 8704 — silently wrong.

id, flags, frag_off u16 BE ×2

Fragmentation machinery. The Identification field groups fragments of one original packet; the Flags + Fragment Offset field says "this is fragment N of packet X." We set DF=1 (Don't Fragment) on outbound and reject any inbound packet with the More-Fragments flag or a non-zero fragment offset. Slirp keeps our packets small, and this slice only accepts complete packets.

TTL u8

Time To Live — a hop budget. Every router that forwards this packet decrements TTL by 1. If it hits zero, the packet is dropped (and an ICMP Time Exceeded goes back to the sender, in a full implementation). The reason TTL exists: routing loops happen. Without a hop counter, a packet caught in a loop (A→B→C→A→B→C→...) would circle forever, consuming bandwidth. We set TTL to 64 outbound.

protocol u8

The demux key for the network layer. One byte that tells the receiving kernel which parser owns the payload. 1 = ICMP (Lesson 24), 6 = TCP (post-phase), 17 = UDP (Lesson 25). This single byte is how IPv4 stays agnostic about what rides on top of it.

0x11 → 17 → UDP parser
checksum u16 BE

The Internet checksum (RFC 1071, covered below) over the 20-byte header. Verified on RX (sum should fold to 0xFFFF); computed and inserted on TX. If RX checksum fails, the packet is corrupt — drop it. Same algorithm reused by ICMP and UDP, so we implement it once.

src IP / dst IP [u8; 4] ×2

The two addresses that stay constant end-to-end across every hop. The Ethernet MAC addresses get rewritten at every router. Source IP and destination IP stay stable across the route. This is the letter-and-envelope analogy from Lesson 19 made concrete: src/dst IP are on the letter, src/dst MAC are on the envelope, and only the envelope is replaced per hop.

The Internet checksum — RFC 1071

One algorithm, shared by IP, ICMP, UDP, and TCP. Written once as a utility in this lesson, reused three times in the next three lessons. The design is from 1988, when routers computed checksums in software on slow CPUs, so the algorithm had to be cheap. It is.

The recipe, in four moves:

1.Treat the bytes as a sequence of 16-bit words, big-endian on the wire.
2.Sum all words, treating the 16-bit result as one's-complement (carries fold back). If the running sum exceeds 0xFFFF, add the carry (high 16 bits) back into the low 16 bits.
3.At the end, fold any final carry in. A long header can produce one final carry that didn't get folded during accumulation.
4.Invert the result (one's complement) to get the checksum. Write the inverted value into the checksum field.

Worked example with the four bytes 00 01 f2 03:

1.Words: 0x0001, 0xf203
2.Sum: 0x0001 + 0xf203 = 0xf204
3.No carry to fold.
4.Invert: !0xf204 = 0x0dfb
=checksum = 0x0dfb

Two properties make this algorithm clever. Verify by re-summing: if you sum the header (including the checksum field) the same way, you get 0xFFFF — any bit flip in transit makes the sum something else. So RX validation is just "sum and check for 0xFFFF after inversion." Endian-independent if you sum consistently: the bytes 00 01 and 01 00 both sum to the same value if you treat them as 16-bit words the same way every time. This is why the algorithm could be deployed on mixed-endian 1980s hardware without per-machine fixes.

Three things to remember when implementing:

  • When computing the checksum to insert, treat the checksum field as zero. The header being checksummed is still waiting for its checksum bytes.
  • When verifying, sum the header including the existing checksum. The result inverts to zero. Any other result means the header is corrupt.
  • Odd byte length is allowed for some payloads (UDP, ICMP) — pad the last byte with zero to make a final 16-bit word.

One utility function covers IP, ICMP, UDP, TCP, and any future protocol that uses this checksum (almost all of them). It takes &[u8] and returns u16. Lesson 24's ICMP and Lesson 25's UDP both call it with their respective header bytes plus (for UDP) the pseudo-header.

The protocol demux tree

On the receive side, mini-os now has a real poll-and-dispatch path. NetDevice::poll_rx() receives one Ethernet frame, sends ARP frames to the ARP handler, sends EtherType 0x0800 frames to the IPv4 handler, and returns a small NetRxEvent. IPv4's protocol byte then names the next payload owner.

Ethernet frame arrives, recv_frame returns it
↳ EtherType == 0x0800 (IPv4)? → IPv4 parser
↳ protocol == 1 (ICMP)? → icmp::receive (L24)
↳ protocol == 17 (UDP)? → udp::receive (L25)
↳ protocol == 6 (TCP)? → drop (post-phase)
↳ anything else? → drop with log line
↳ EtherType == 0x0806 (ARP)? → arp::receive (L22) ✓ done
↳ anything else? → drop

One print line per dispatch keeps the kernel's network log readable: [ip] rx proto=17 src=10.0.2.2 dst=10.0.2.15 len=43. The host-forward test sends UDP to 127.0.0.1:5555; QEMU user networking forwards it to guest UDP port 5555; mini-os receives the resulting IPv4 frame through virtio-net.

Routing — which MAC to ARP for

Lesson 22 covered how ARP turns an IP address into a MAC address on the local wire. There's a decision before that lookup: is the destination IP even on our wire, or does the frame need to go to the gateway router first? That decision is the routing step. It picks which IP we hand to ARP — the destination itself, or the gateway's IP.

The test is one bitwise AND. We compute the network prefix of our own IP and the network prefix of the destination IP using the same mask. If the prefixes match, the destination is on our local network — we can ARP for the destination directly. If they differ, the destination is somewhere else on the internet — we ARP for the gateway, and the gateway takes the packet from there. 

fn next_hop_for(dst_ip: Ipv4Addr) -> Ipv4Addr {
    if dst_ip & NETMASK == OUR_IP & NETMASK {
        dst_ip                  // local network — ARP for the host
    } else {
        GATEWAY_IP              // somewhere else — ARP for the gateway
    }
}

Slirp hands mini-os three constants at boot: OUR_IP = 10.0.2.15, GATEWAY_IP = 10.0.2.2, NETMASK = 255.255.255.0. The mask 255.255.255.0 in binary is 24 leading ones followed by 8 zeros — keep the top three octets, ignore the bottom one. So 10.0.2.15 & mask = 10.0.2.0 and 10.0.2.2 & mask = 10.0.2.0 — same prefix, local. A destination like 142.250.190.78 has a different top three octets, different prefix, gateway. One if-statement, no lookup table.

The compact notation for "first N bits are network, rest are host" is CIDR (Classless Inter-Domain Routing) — written address/N. Slirp's network is 10.0.2.0/24: 24 network bits, 8 host bits, 256 addresses (254 usable). The /N prefix length and the dotted-quad mask are two spellings of the same bitmask.

CIDRNetmaskHost bitsUsable hostsWhere you see it
/8255.0.0.02416,777,214Legacy class A blocks
/16255.255.0.01665,534Large enterprise, cloud VPC
/24255.255.255.08254Home LAN, slirp, small office

The mask itself comes from somewhere. On a real LAN, the host learns it from DHCP (Dynamic Host Configuration Protocol) at the same time it learns its own IP — both arrive in the same lease. On a statically-configured server, an operator wrote it into a config file. On mini-os under slirp, the mask is hardcoded alongside OUR_IP and GATEWAY_IP, because slirp's network layout is fixed by QEMU and never changes.

One network, one mask, one gateway. Mini-os's routing table is a single row. Linux on a real machine has many rows — ip route shows them, sorted by prefix length so the most specific match wins. The kernel data structure is the forwarding information base (FIB), implemented in net/ipv4/fib_trie.c as a compressed trie for fast longest-prefix lookup. Every entry names an output interface, a next-hop gateway (or "on-link" for direct delivery), and a prefix. The decision algorithm — longest matching prefix — is the generalization of mini-os's single if-statement to many overlapping networks.

TX and RX — the two paths

TX — send IP packet to dst IP
1Build Ipv4Header: ver/IHL=0x45, total_len=20+payload_len, id=0, flags=0x4000 (DF), ttl=64, protocol=N, src=OUR_IP, dst=target_ip, checksum=0
2Compute internet_checksum over the 20-byte header, write it into the checksum field
3Concatenate: Ipv4Header bytes + payload
4Call NetDevice::resolve_arp(next_hop_ip) — returns the next-hop MAC from Lesson 22's cache
5Build Ethernet header (dst=resolved MAC, src=OUR_MAC, ethertype=0x0800), wrap IP packet
6Call net::send_frame(eth_frame) from Lesson 21
The two-layer assembly mirrors the two-layer dispatch on RX. Each layer prepends its header; the receiving side will strip them in reverse order.
RX — IPv4 packet arrived
1Ethernet parser already stripped its 14-byte header and dispatched on EtherType 0x0800 to us
2Parse Ipv4Header from the next 20 bytes
3Validate: ver == 4, IHL == 5, dst_ip == OUR_IP, total_len sane, checksum folds to 0xFFFF
4Reject fragments: if MF flag set or frag_off != 0, drop with log
5Dispatch on protocol byte: 1 → ICMP, 17 → UDP, else drop with log
Every layer above Ethernet is opt-in. Unknown protocols get a small log line and the frame is ignored. The print line per dispatch is what makes the network stack debuggable when L24 or L25 misbehaves.

Two validation steps deserve emphasis. dst_ip == OUR_IP: the packet might have been broadcast at L2 and therefore addressed to us by MAC, but carry a different IP destination. Drop it — IP delivery is for us specifically, not "everyone who heard the broadcast." Checksum folds to 0xFFFF: any other folded value means the header is corrupt and later parsing would be guesswork.

Fragmentation — parse, reject

RFC 791 lets routers split a packet too large for the next link's MTU into fragments. Each fragment is a separate IP packet with the same Identification field, the More-Fragments flag set on all but the last, and a non-zero Fragment Offset naming where in the original this fragment belongs. The receiver collects all fragments and reassembles before handing to the layer above.

Reassembly stays outside this slice for three reasons. First, slirp keeps our packets small enough for the link MTU. Second, reassembly needs timers for lost fragments, ordering by offset, a buffer pool for partial packets, and reassembly-attack defenses. Third, modern Path MTU Discovery keeps fragments rare on the public internet: senders learn the smallest MTU on the path and size packets before sending. This lesson sets DF=1 on outbound packets and rejects inbound packets with MF set or a non-zero fragment offset.

The build — what landed

1
Internet checksum utility. New file: src/net/checksum.rs. Function pub fn internet_checksum(data: &[u8]) -> u16 implementing RFC 1071: sum 16-bit BE words with carry folding, then invert. The boot proof checks the four-byte example above: [ip] checksum example 00 01 f2 03 -> 0x0DFB.
2
Ipv4Header parse and validate. New file: src/net/ipv4.rs. The parser accepts a full IP packet, checks version 4, IHL 5, sane total length, checksum validity, and the fragment flags. A valid header returns an Ipv4Header with total length, TTL, protocol, checksum, source IP, and destination IP fields.
3
Ipv4Header build. Ipv4Header::build(protocol, src_ip, dst_ip, payload_len) fills the 20-byte header with 0x45, DF set, TTL 64, protocol number, source/destination IPs, and a computed checksum. The boot proof builds a UDP-marked packet, parses it back, and prints: [ip] parsed header proto=17 src=10.0.2.15 dst=10.0.2.2 len=24 checksum ok.
4
RX dispatch + user-triggered TX integration. NetDevice::poll_rx is the central receive dispatcher. It recycles one RX buffer, handles ARP requests or replies, parses IPv4 frames, and returns NetRxEvent. NetDevice::send_ipv4_packet builds the IPv4 header, asks ARP for the next-hop MAC, wraps the packet in an Ethernet frame, and calls send_frame. The /net_smoke.elf user program asks the kernel to run this path through SYS_NET_TX_TEST. The QEMU TX test locks this proof: [ip] tx proto=17 src=10.0.2.15 dst=10.0.2.2 len=24 next-hop=10.0.2.2 (52:55:0a:00:02:02). For RX, the same user program calls SYS_NET_RX_WAIT, the shell test sends UDP from the host to 127.0.0.1:5555, and QEMU forwards it into the guest. The expected proof line is: [ip] *** user-triggered host-forwarded UDP packet received through QEMU: src=10.0.2.2 dst=10.0.2.15 len=45 ***.
