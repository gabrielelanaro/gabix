Lesson 4 · M4 · 4.7 Disk path begins

Shape of the Storage Stack

Where disk, filesystem, block layer, and drivers sit — and what each one's job is.

Read time ~15 min Build time many lessons Prereq Lesson 3

The goal is concrete: plug a disk into QEMU, load an ELF (Executable and Linkable Format) binary from it, execute it. The path from where we are now (a memory-only VFS) to that goal is a series of layers. Each layer has a Linux counterpart we can read alongside. This lesson introduces the stack and what each layer is for, so the next several lessons (PCI, virtio, block layer, ext2, ELF, exec) fit into a coherent picture instead of feeling like disconnected topics.

The stack, top to bottom

When a user program calls read(fd, buf, len), the request flows downward through several layers, hits hardware, and the data flows back up. Each layer has a specific job. Read the diagram top-down — the top is what user code sees, the bottom is the physical disk.

Each layer transforms the request into a more concrete form. VFS asks for "the next 10 bytes of file 17." The filesystem translates that into "block 42 from disk." The driver translates that into a virtqueue read request. The hardware does the read.

What each layer is for

VFS — the generic interface

Already built (Lessons 1–3). The user-facing open / read / write / close API. Doesn't know or care where the bytes come from — heap Vec, page cache, network. Dispatches through a file operations table (fops) on each open file. Our mini-os VFS has the same shape as Linux's; what we're missing is the dispatch — our sys_read reaches directly into data.lock() instead of calling file->f_op->read().

Page cache — the in-RAM window over disk

Future. In Linux, every inode has an address_space: a mapping from page offset to a cached 4 KB page. When you read from a file, the kernel checks the page cache first. On a hit, the read returns straight from RAM (microseconds). On a miss, the kernel asks the filesystem to fetch the page from disk (milliseconds — a thousand times slower).

For ramfs (Linux's in-memory filesystem), the page cache is the storage — there's no disk behind it. Our mini-os VFS is in this category: Mutex<Vec<u8>> on the inode is essentially a ramfs page cache, just using the heap allocator instead of frames. The Lesson 2 sidebar on memory layering covered this.

For disk-backed filesystems like ext2, the page cache is a window: it caches what's been read, and writes get flushed back to disk eventually (writeback).

Filesystem — interpret bytes as files

Future — ext2. The filesystem translates file-level operations ("read byte 1000 of inode 17") into block-level operations ("read block 42, then block 43, then take bytes 0-999 of the concatenation"). Each filesystem has its own on-disk byte format: ext2's inodes are different from FAT's directory entries, which are different from XFS's B-trees.

ext2 was chosen for mini-os because it's the simplest disk filesystem Linux supports — no journal, no extents, no checksums. The format is well-documented and stable. Linux's fs/ext2/ directory is small enough to actually read.

Block layer — block-number abstraction

Future. Filesystems don't talk directly to device drivers — they go through the block layer, which provides a uniform read_sector(n) / write_block(n) interface. The block layer also handles request queuing, merging, scheduling (deadline, BFQ, none), and plugging. In Linux, requests become struct bio (block I/O) objects that get submitted to the device's request queue.

For mini-os we'll start with the simplest possible block layer: a function read_sector(n: u64) -> [u8; 512] that calls straight into the virtio-blk driver. No merging, no scheduling, no async. Just a synchronous read.

Device driver — virtio-blk

Next. The driver is the layer that knows how to talk to a specific piece of hardware. For virtio-blk, that means: find the device on the PCI bus, initialize it via the virtio PCI modern transport, set up virtqueues (the shared-memory ring buffers used to submit requests), and submit read/write requests.

Virtio is a special kind of device: it's designed specifically for virtual machines. Real hardware doesn't speak virtio. The host (QEMU) and the guest (our kernel) share memory, and the guest writes "do this I/O" requests into a ring buffer. The host polls the ring, does the actual I/O against the backing file (our disk.img), and writes responses into another ring. Much faster than emulating a real hardware disk controller.

PCI — how the kernel finds the device

Next. Before we can talk to virtio-blk, we have to find it. On x86, PCI (Peripheral Component Interconnect) is the bus that connects peripherals to the CPU. Every PCI device has a 256-byte configuration space that the CPU reaches via I/O ports 0xCF8 (address) and 0xCFC (data). Reading that space tells us the device's vendor ID, device ID, class, and the addresses of its memory-mapped registers (the BARs — Base Address Registers).

To enumerate the bus: walk every device number (0-31) on every bus number (0-255), every function (0-7), read the vendor ID, and see what's there. Vendor 0x1AF4 = Red Hat / QEMU (virtio's owner). Within virtio, device IDs 0x1000–0x107F are the modern virtio devices; 0x1042+ are non-transitional (modern only). virtio-blk specifically is 0x1042 in the modern non-transitional form.

Hardware — QEMU's virtio-blk-pci device

Already attachable. QEMU exposes a virtio-blk device when launched with -drive file=disk.img,format=raw,if=none,id=drv0 -device virtio-blk-pci,drive=drv0 (or the shorter -drive file=disk.img,format=raw,if=virtio). From the kernel's perspective, this is a PCI device at some bus/device position; we'll find it via PCI enumeration.

The read() journey

Trace a read(fd, buf, 10) on a disk-backed filesystem. Request flows down the stack; bytes flow back up the same path.

User read(fd, buf, 10)

The user program invokes the read system call. On x86-64, arguments go in registers — rax=0 for SYS_READ, rdi=fd, rsi=buf, rdx=10 — and the syscall instruction traps into the kernel. Same convention mini-os already uses; Lesson 2 walked through the calling code.

↓ syscall enters kernel
VFS look up Arc<Inode> from fd table

The integer fd (file descriptor — a small integer like 3) is an index into the per-process file descriptor table. Each slot holds an Arc<File>, which holds an Arc<Inode> — the file itself.

This is exactly what mini-os's sys_read does today (built in Lesson 2). Linux adds one more layer: the File struct has a function-pointer table called fops (file operations) so each filesystem can plug in its own read, write, seek, etc. Our VFS inlines that dispatch — real disk-backed filesystems make it real.

↓ dispatch via fops
Page cache check (inode 17, page 0)   MISS

The page cache is the kernel's cache of recently-accessed 4 KB file chunks in RAM. Indexed by (inode, page_offset) — so inode 17, page 0 means "the first 4 KB of file 17."

Hit: bytes already in memory, return immediately. Miss: have to fetch from disk. mini-os doesn't have a page cache yet — our Inode::data: Mutex<Vec<u8>> IS the storage (like Linux's ramfs, where the cache is the storage). When we add disk backing in Lesson 10, we'll need to introduce the page cache as a separate layer that sits between the VFS and the filesystem.

↓ ask fs which blocks hold bytes 0-9
Filesystem (ext2) read inode 17, i_block[0] = 42

ext2 stores file contents in fixed-size blocks (typically 1 KB or 4 KB each) scattered across the disk. Each inode has an i_block array of 15 entries:

• Slots 0–11: direct pointers — each points at one data block.
• Slot 12: single-indirect — points at a block full of pointers.
• Slot 13: double-indirect. Slot 14: triple-indirect.

For a 10-byte file, only i_block[0] is used; it points at the block holding the bytes. Reading bytes 0–9 means: read block 42, take its first 10 bytes.

↓ read_sector(42)
Block layer passthrough (no merging yet)

Linux's block layer queues and merges requests across processes, applies I/O schedulers (deadline, BFQ, none), and submits them to device drivers as struct bio objects. It also handles request plugging, batching, and priority.

mini-os will skip all of that. A synchronous read_sector(n) -> [u8; 512] function that calls the driver directly. Good enough for a learning kernel; the optimization machinery is a whole separate topic.

↓ submit read request, sector 84
virtio-blk driver push to virtqueue, kick device

virtio uses shared-memory ring buffers called virtqueues. Three regions:

• Descriptor table — each entry points at a kernel buffer (the data being read or written).
• Available ring — kernel appends descriptor indices here to submit work.
• Used ring — device appends descriptor indices here to signal completion.

To submit a read: write a descriptor pointing at your buffer, add its index to the available ring, then kick the device by writing to a specific MMIO register — the "hey, there's work" notification. We'll build this in Lesson 6.

↓ via PCI MMIO write
QEMU (hardware) reads sector 84 of disk.img

QEMU is the host process running our VM. When it sees the kick, it polls the virtqueue, reads the request from shared memory, performs the actual file read against disk.img on the host filesystem, writes the response bytes into the kernel's buffer, and adds an entry to the used ring.

From QEMU's perspective: a file read on the host. From the guest kernel's perspective: "the hardware delivered data." That interface symmetry — kernel code can't tell virtual from real hardware — is what makes virtio a clean abstraction.

↓ writes 512 bytes into kernel buffer, posts completion
Disk bytes 512 bytes in kernel buffer

One disk sector is 512 bytes. With 1 KB ext2 blocks, block N maps to sector 2N — so block 42 = sector 84. After the read completes, those 512 bytes sit in a kernel-allocated buffer, ready to flow back up.

The journey reverses: block layer caches the page in the page cache, ext2 extracts bytes 0–9, VFS copies them to the user buffer, read() returns 10.

↑ bytes return up the same stack: driver → block layer (cache page) → ext2 (extract bytes 0–9) → VFS (copy_to_user) → user buffer

Each layer is replaceable. Swap ext2 for ext4 and the middle stages change; swap virtio-blk for NVMe and the bottom stages change; the user program at the top never notices. That replaceability is what makes the layering worth the indirection cost.

What we'll build, in order

The next several lessons work upward from the hardware. We don't build ext2 first and then figure out how to read its blocks — we build the pipe that delivers bytes first.

  1. Attach the disk — QEMU launched with a raw disk image. No kernel code; just infrastructure.
  2. PCI bus enumeration — find every device on the PCI bus. Print the list. Foundation for finding virtio-blk.
  3. virtio device initialization — for the virtio-blk device specifically, do the virtio PCI modern handshake. Probe, negotiate features, enable.
  4. Virtqueues — set up the request ring. Allocate buffers. Implement submit_request.
  5. First disk read — read sector 0, verify the signature bytes match what we wrote. End-to-end proof that the driver works.
  6. Block layer — wrap the driver in read_sector(n). Trivial wrapper, but it's the API the filesystem will use.
  7. ext2 superblock — parse the on-disk superblock at offset 1024. Validate the magic. Print filesystem parameters.
  8. ext2 inodes and directories — find the root inode (number 2 by ext2 convention), parse its directory entries.
  9. Mount — wire ext2 into our existing VFS. Path resolution now reads from disk instead of the lazy_static root.
  10. ELF loader — parse an ELF file's program headers, map its segments into a fresh address space.
  11. exec() syscall — load an ELF from the filesystem and run it. The culmination: an externally-compiled binary, written to the disk image, executed by the kernel.

Each step unlocks the next. The disk read is the keystone — once bytes flow from disk, every step after that is parsing and dispatch.

Primary source

The canonical reference for the storage stack is the filesystems chapter of the Linux documentation. For the block layer specifically, the block layer docs cover struct bio, request queues, and the I/O scheduler.

For virtio, the spec is OASIS Virtual I/O Device (VIRTIO) version 1.2. Heavy reading, but authoritative. The block device chapter specifically defines the request format we'll be sending.

For ext2, the canonical reference is the Ext2 Disk Storage Structure documentation. Field-by-field, every structure laid out.

For PCI, the OSDev wiki PCI page is the practical "how do I do this" reference. The official spec is large and expensive; OSDev condenses what an OS implementor actually needs.

Pause and think

Linux supports dozens of disk-backed filesystems — ext2, ext4, XFS, Btrfs, FAT, NTFS, F2FS — and dozens of disk drivers — virtio-blk, NVMe, SATA, SCSI, USB mass storage. Pick a combination the Linux kernel actually runs (say, ext4 on NVMe) and trace a read() through the eight layers above. Which layers change? Which stay identical?
