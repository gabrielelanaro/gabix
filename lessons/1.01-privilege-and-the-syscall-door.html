Module 1 · The CPU · Lesson 1.01

Privilege and the syscall door

How x86 and ARM each let a kernel run an untrusted program — fenced off from the dangerous instructions, yet able to call the kernel for help.

A kernel has to run programs it does not trust. Those programs must not read the kernel's memory, must not disable interrupts, must not change how memory is mapped, must not talk to the disk or the network card directly. If any program could do these things, no program would be safe from any other.

But isolating the program completely is no use either. The program needs the kernel to act on its behalf — read a file (which means touching the disk), send a packet (the network card), get the time of day. So the same CPU that restricts the program must also give it a controlled way to ask the kernel for help.

This lesson is the two CPU mechanisms that make that possible. The first is a privilege setting the program cannot change on its own. The second is a single instruction — the door — that is the only way to cross from low privilege to high. x86 and ARM each provide both; the vocabulary differs, the security property is the same.

1. The privilege setting

x86 calls its levels rings. Four exist in the design (0 through 3) but only two are used in practice: ring 0 for the kernel, with every instruction and every byte of memory available, and ring 3 for user programs, with the dangerous parts blocked. The ring the CPU is currently running in — the Current Privilege Level — is a two-bit field kept inside the code-segment register, a CPU register that describes the code presently executing.

In ring 3 a set of instructions simply refuses to run: cli (turn off interrupts), hlt (halt the CPU), the moves that reprogram the address-translation table, and the in/out that talk straight to devices. Memory carries its own check too: each page is marked kernel-only or not, so a ring-3 program that reaches for the kernel's bytes is stopped before the read happens. When the CPU catches a ring-3 program trying any of this, it does not crash — it traps: it saves where the program was and jumps into the kernel at a prearranged handler, the same mechanism it uses for a divide-by-zero. The kernel then decides what to do, which is usually to kill the program.

ARM uses the word modes instead of rings, and there are more of them, but the idea is identical. One mode — User mode — is the only unprivileged one; the program runs there. The rest are privileged and owned by the kernel: Supervisor mode for ordinary kernel code, IRQ mode for interrupt handlers, and a few others for handling errors. The mode the CPU is in right now is a five-bit field at the bottom of a register called the Current Program Status Register, or CPSR.

One ARM detail has no direct x86 parallel and matters when you read the code. Each privileged mode comes with its own private copy of two registers: the stack pointer (sp) and the link register (lr, which holds return addresses). When the CPU enters IRQ mode, it switches to IRQ mode's sp and lr automatically — the interrupt handler gets a fresh stack without having to save the old one. That is why gabix's first code, in targets/armv7/src/boot.S, deliberately switches into IRQ mode just to give it a stack, then switches back:

targets/armv7/src/boot.S · giving each mode its own stack
    cps   #0x12                @ change to IRQ mode
    ldr   sp, =IRQ_STACK_TOP   @ give IRQ mode its own stack
    cps   #0x13                @ change to Supervisor mode
    ldr   sp, =STACK_TOP       @ give Supervisor mode its stack

(cps means "change processor state" — an immediate switch to a named mode, allowed only when already privileged.) Whatever sits in User mode's sp and lr is left untouched, waiting for the program.

2. The door: crossing from low to high

With the program held in ring 3 (or User mode), it cannot raise its own privilege — the privilege field is not an ordinary register it can write. So how does it ever call the kernel? Through one instruction the CPU treats specially.

On x86 that instruction is syscall. Before any program can use it, the kernel writes the address of its handler into a special register — a model-specific register, or MSR, named LSTAR — and tells the CPU how to find a kernel stack. Then, when a ring-3 program runs syscall, the CPU does a controlled jump: it notes where to return, loads the handler address from LSTAR into the program counter, switches to ring 0, and starts running the handler. The program chose to run syscall; the CPU chose everything else. The syscall number rides in one register (rax), the arguments in a fixed set of others. (The x86 side you already built lives in src/arch/x86_64/syscall.rs.)

ARM's instruction is svc (it once stood for "supervisor call"; older assemblers spelled it swi). The setup differs: the kernel has already written the address of a small eight-entry table into a register called VBAR (Vector Base Address Register). When a User-mode program runs svc, the CPU saves the program's return address into the link register lr, saves the current mode (User) into a register called SPSR (Saved Program Status Register) — saved so the CPU can put itself back into User mode on the way out — switches to Supervisor mode, and jumps to the table entry reserved for svc. The syscall number rides in r7 in gabix; the first arguments in r0 through r3.

Here is gabix's handler for that jump, with each line explained:

targets/armv7/src/boot.S · the SVC (syscall) entry
.Lsvc:
    stmdb sp!, {r0-r12, lr}    @ push the program's registers onto the SVC stack
    mov   r0,  sp              @ pass the Rust handler a pointer to those saved registers
    bl    arm_svc_entry        @ call the handler in syscall.rs
    ldmia sp!, {r0-r12, lr}    @ restore them; r0 now holds the value the handler returned
    movs  pc,  lr              @ return to the program

(stmdb is "store multiple, decrement before" — a push. ldmia is "load multiple, increment after" — a pop. bl is "branch with link", a call.) The handler in syscall.rs reads r7 to learn which syscall was requested, does the work, writes its result into the saved r0, and returns.

3. The return: crossing back from high to low

The program called the kernel; now the kernel has to give control back, and the privilege has to drop again. That drop must happen on the kernel's terms: if the program could choose where to return, or at what privilege, the privilege setting would be meaningless.

x86 has a dedicated partner instruction, sysret: it restores the return spot the CPU saved, drops back to ring 3, and resumes the program. One instruction, one job.

ARM does not give you a dedicated "return from syscall" instruction. Instead it reuses the one trick every exception return uses. There is a mov instruction, and when its destination is the program counter and it carries the s suffix, the CPU does two things in a single step: it loads the program counter from lr, and it loads the CPSR from the SPSR — restoring the mode the CPU was in before the exception, which was User. That combined move-and-restore-mode is the entire return mechanism. The last line of the handler above, movs pc, lr, is it.

The same line does the opposite job — the kernel's first deliberate drop into a fresh program. You can see it in targets/armv7/src/user.rs:

targets/armv7/src/user.rs · the kernel enters a user program (comments added)
pub unsafe extern "C" fn enter(entry: u32, stack: u32) -> ! {
    naked_asm!(
        "cpsid i",            // mask interrupts while we set up
        "cps #0x1f",          // switch to System mode (privileged, shares User's registers)
        "mov sp, r1",         // build the program's stack
        "cps #0x13",          // switch back to Supervisor mode
        "mov r2, #0x10",      // 0x10 is User mode
        "msr spsr_cxsf, r2",  // stage User mode into SPSR
        "mov lr, r0",         // the program's entry address goes into lr
        "movs pc, lr",        // jump there — and load CPSR from SPSR -> User mode
    );
}

The kernel cannot just jump to the program: a plain jump would stay in Supervisor mode and the program would run privileged. So the kernel stages "User mode" into the SPSR, points lr at the program's entry, and runs the same movs pc, lr. (msr means "move to a status register" — here, writing the SPSR.) The detour into System mode earlier in the routine is how the kernel sets the program's stack pointer: System mode is privileged, but it uses the same register bank as User mode, so writing sp while in System mode sets the program's sp. One instruction, and the program starts running unprivileged. The same movs pc, lr returns from a syscall and starts a program, because in both cases the job is identical: jump to an address and land in the mode staged in the SPSR.

4. One round trip

Put it together with a real call. A program wants to write to the screen. It places the syscall number for write in r7 (rax on x86), the file descriptor (1, the screen), the buffer address, and the length in the argument registers, and runs syscall (or svc). The CPU crosses into the kernel. Gabix's handler reads the number, calls the write routine, which checks that the buffer really belongs to the program and copies the bytes to the console. The handler puts the byte count into r0 (rax on x86) and runs the return — sysret, or movs pc, lr. The program resumes in User mode (ring 3) with its answer in r0, never having held privilege for an instant.

What you should be able to do after this lesson. For either CPU, explain why a user program cannot raise its own privilege; name the single instruction it uses to ask the kernel in; and say where the kernel registered the address that instruction lands at. Then explain why gabix uses the same movs pc, lr both to return from a syscall and to enter a program for the first time.
