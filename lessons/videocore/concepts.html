What to learn, and in what order

The branches below make up the curriculum. Read each row as a sentence. The same component appears in multiple branches when it has more than one relationship.

1. Where does the driver run?

Start here. First place the software and hardware on the board.

ARM CPUexecutesGabix driver

Rust compiles into instructions for the Pi’s main processor.

Driverrequests power through the mailbox fromPi firmware

Firmware runs on the VideoCore processor. It provides the service the probe calls before reading V3D.

ARM loadselects an identity register by address insideV3D graphics hardware

A register is a hardware interface with a defined meaning. Reading IDENT0 returns a device ID.

Main RAMholds buffers used byboth ARM and V3D

The driver converts CPU addresses to addresses V3D can use on the system bus.

2. How does a drawing request become GPU work?

Requires the distinction between RAM and device registers.

Driverwrites command packets intocontrol lists in RAM

A packet describes an operation such as drawing three vertices or storing a tile.

Driverwrites start and end addresses tocontrol thread registers

CT0 runs the binning list. CT1 runs the rendering list. The end-address write starts execution.

Control List Executor (CLE)reads packets and configuresgeometry and rendering hardware

A draw packet gives a vertex count. A shader state record identifies the vertex data and the shader program.

Shader instructionsare fetched and executed bya Quad Processor (QPU)

The command list selects the work. Inside that work, a separate instruction stream computes values.

3. How do three corners become work for a tile?

Requires a draw command and a vertex. A vertex holds one corner’s position and associated values.

Vertex Cache Manager and DMA (VCM/VCD)fetch vertex records from RAM intoVertex Pipe Memory (VPM)

DMA moves data without the ARM copying each word. Gabix supplies positions already expressed in screen coordinates (NV mode).

Coordinate or vertex shader in GL modewrites transformed vertex data back toVPM

A QPU can compute positions too. The NV path used by this probe skips this shader step.

Primitive Tile Binner (PTB)uses vertex positions to buildone list per touched tile in RAM

A primitive is a shape such as a triangle. A tile is a rectangular patch of the image. Our 64 × 64 draw fits in one tile.

Rendering control listcalls the list forthe current tile

This reconnects the two passes. The binning pass left a list of work that the rendering pass can now replay.

4. How does the GPU find the inside of the triangle?

Requires a triangle assigned to the current tile. Corner coordinates alone do not enumerate the covered locations.

Primitive Setup Engine (PSE)derives edge and interpolation parameters fromthe three vertices

These parameters let later hardware evaluate the triangle at many screen locations.

Front End Pipeline (FEP)rasterizes the triangle intogroups of sample locations with coverage

Coverage identifies which samples fall inside. The front end also handles depth interpolation and early depth testing.

Per-vertex attributessupply values forinterpolation at fragment positions

A varying can carry a different color at each corner. Hardware supplies interpolation data to the shader.

QPU scheduler (QPS)assigns ready fragment work toa QPU

A fragment is a candidate contribution to an image location. The shader computes a color for that work.

Broadcom architecture guide

5. What can one programmable processor do?

Requires the difference between finding covered locations and choosing their colors.

Slicegroups QPUs and providesshared instruction cache and lookup units

A slice is a hardware grouping. A shader is the program that a QPU in the slice executes.

One QPU instructionoperates across16 lanes

A lane holds one work item’s values. Four physical lanes process the sixteen positions over four cycles.

Registers and accumulatorssupply operands toadd and multiply arithmetic units

Instruction fields select sources, a destination and operations. Other encodings load constants or branch.

Shader programcan readuniforms, varyings and texture samples

Uniforms supply shared program parameters. The texture and memory unit (TMU) looks up data by address or texture coordinates. The special functions unit handles operations such as reciprocals.

Gabix fragment shaderwrites its packed color tothe tile buffer color interface

The program consumes its varying inputs, loads the literal color, waits for tile access and issues a color write.

6. Where do intermediate values live?

Revisit the same draw and ask who needs each value next.

VPMstages batches forvertex processing

VCD reads main memory into VPM. The VPM DMA Writer (VDW) supports transfers back to main memory.

Slice caches and shared L2supply repeated reads ofinstructions and data

Texture layout, format and filtering matter when the shader samples a texture. Our constant-color shader needs no texture.

QPU color writesupdateon-chip tile buffer (TLB)

The scoreboard orders tile access. The tile buffer also supports depth and stencil operations. Multisampling can keep several samples for one pixel.

Store-tile commandwrites finished color values intoframebuffer in main RAM

A framebuffer holds the image in memory. This probe requests linear RGBA8888, four bytes per pixel.

Other rendering modesreuse some hardware fordifferent work

For example, the OpenVG coverage accumulation pipeline (CAP) accumulates coverage for vector paths. It is a separate branch of the architecture.

7. How does the CPU get the image back?

Requires the difference between issuing a command and completing its memory writes.

Completed binning or frameadvancesa V3D completion counter

Gabix polls the binning counter before submitting rendering and the frame counter before reading pixels. V3D also provides interrupts and error/status registers.

CPU cache maintenancemakes shared buffer contents usable bythe next reader

Gabix cleans input ranges before submission and invalidates the CPU’s cached pixel range after rendering. The driver also manages GPU caches.

Finished framebufferis copied intothe probe reply

At this point the ARM has the pixels. The remote GUI can use this result as its image source.

Planned Mac pointer eventwould update vertices and triggeranother draw

The planned VNC server would send the new framebuffer to the viewer over Wi-Fi. The existing probe already returns pixel bytes.

Test the map with one change

Keep the three corners fixed. Change the shader’s gold constant to green. Which hardware will see different instructions or data, and what should stay in the same place?

Trace the change

The QPU loads a different literal and writes green into the tile buffer. The tile store copies different color bytes to RAM. The binner still assigns the triangle to the same tile and the rasterizer still covers the same locations because the positions stayed fixed.

Where the map meets Gabix

write(V3D + 0x110 + thread * 4, bus(start));
write(V3D + 0x108 + thread * 4, bus(end));
wait(|| read(counter) != previous)

These are ARM instructions after Rust compilation. Here thread selects a hardware command executor, 0 for binning or 1 for rendering. The first two writes give it the list boundaries. The final line waits for the selected counter to change.
