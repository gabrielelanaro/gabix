Real Inodes and Paths

Replace the single hardcoded inode with a directory tree you can walk by path.

Read time ~15 min Build time ~30–45 min Prereq Lesson 2

Goal of this lesson: a user program calls open("/hello.txt"), the kernel parses the path, walks a directory, finds the right inode, and returns a file descriptor pointing at that specific file's bytes — not the one global file from Lesson 2. A second file at a different path returns different bytes. We earn real directories, real inode numbers, and real path resolution.

The big idea — directories are bytes

Lesson 2 left us with HARDCODED_INODE: one global file, every open() returns it, the path argument is ignored. To support more than one file we need directories — name-to-inode mappings the kernel can search.

The faithful-to-Linux design: a directory is just an inode whose bytes are formatted as a sequence of directory entries. Each entry says "this name points at that inode number." A regular file is an inode whose bytes are the file's contents. Same struct, different interpretation of the bytes. This is exactly how Linux does it.

Design choice — byte-format directories. The alternative was hanging a BTreeMap<String, Arc<Inode>> off each directory inode — simpler in Rust, but a complete departure from how real filesystems work. We picked bytes so the design generalizes when we add a disk-backed filesystem in milestone 4.7 (ext2).

The directory entry format

Each entry is a self-contained record. The format we'll use: 

+--------+-------------+----------+
| name_len | name [N bytes] | ino [u64 LE] |
+--------+-------------+----------+
   1 byte      name_len       8 bytes

One byte for the length, then the name bytes (no terminator — the length tells you where they end), then the inode number as a little-endian 8-byte integer. Total entry size is 1 + name_len + 8 bytes.

A directory with two entries — foo.txt → inode 1, hello → inode 2 — looks like this in memory:

offset 0: entry 1 07 66 6F 6F 2E 74 78 74 01 00 00 00 00 00 00 00 ↑ len=7 └── "foo.txt" ──┘ └─── inode 1 ─────┘ offset 16: entry 2 05 68 65 6C 6C 6F 02 00 00 00 00 00 00 00 ↑ len=5 └ "hello" ─┘ └─── inode 2 ─────┘

Why length-prefixed names

Two alternatives we considered:

  • Null-terminated (C-style): scan forward until a \0 byte. Parsing requires reading every name byte.
  • Fixed-width: reserve say 32 bytes per name, pad short names with zeros. Wastes space; names longer than 32 bytes are illegal.

Length-prefix wins because advancing to the next entry is O(1). To skip entry 1 without parsing it: read 1 byte (name_len = 7), compute 1 + 7 + 8 = 16, advance the cursor by 16. One byte read, one addition. You never touch the name or the inode field. Linux does the same trick via its d_reclen field, which is the total record length (entry size, including padding).

Linux's actual format is struct linux_dirent64: a 64-bit inode number, a 64-bit offset to the next entry, a 16-bit record length, a single byte for the file type, then the null-terminated name, then padding. More fields than we need (we'll grow into them as permissions and types land).

Why inode numbers, not pointers

We could store a raw &Inode pointer in each entry. In memory it would work — the pointer would lead straight to the inode struct. We use integers instead. The reason is persistence.

Picture the directory bytes written to a disk, then reboot. Memory gets re-allocated on boot — the old pointer address is garbage. An inode number ("inode 17") is still inode 17. The kernel looks up 17 in a fresh registry, finds the cached inode struct or loads it from disk into a new location. Same on every reboot, every machine that mounts the same disk.

So: the number is the stable identifier (survives reboot, survives eviction from the inode cache, is what stat() returns to userspace, is what hard-link counts are computed against). The pointer is a transient cache location. mini-os has no disk yet, but using numbers means the design generalizes when we add one.

The registry

Since directory entries reference inodes by number, we need somewhere to look the number up. A global, lazily-initialized map: 

pub static REGISTRY: Lazy<Mutex<BTreeMap<u64, Arc<Inode>>>> =
    Lazy::new(|| Mutex::new(BTreeMap::new()));

Each inode, on creation, registers itself and gets a fresh ino (a monotonic counter is fine — Linux allocates inode numbers per-superblock from a counter too). Lookups go through REGISTRY.lock().get(&ino). The registry is the mini-os analog of Linux's inode cache (inode_hashtable in older kernels, xarray-indexed in modern ones).

Two kinds of inode

We need to mark whether an inode's bytes should be interpreted as file contents or as directory entries. Add a discriminant field: 

pub enum InodeKind { File, Dir }

pub struct Inode {
    pub ino: u64,
    pub kind: InodeKind,
    pub data: Mutex<Vec<u8>>,
}
Design choice — enum vs mode bitmask. Linux uses a single mode field — file-type bits OR'd with permission bits. Faithful but heavy: we'd have to define S_IFREG, S_IFDIR, permission constants, and bit-twiddling helpers before writing any logic. An enum is cleaner in Rust, pattern-matches nicely, and we can swap to a bitmask when permissions land (probably Lesson 6 or 7).

The path resolution algorithm

open("/foo/bar/baz.txt") becomes a walk:

  1. Split the path on /: ["foo", "bar", "baz.txt"].
  2. Start at the root inode (a well-known number — Linux uses inode 2 for the root of an ext4 filesystem; we'll use 1).
  3. For each component except the last:
    1. Read the current directory's bytes.
    2. Parse entries left to right; find the one whose name matches the component.
    3. If not found, return ENOENT.
    4. Look up the entry's inode number in the registry.
    5. Verify it's InodeKind::Dir (else ENOTDIR).
    6. Descend: current = looked-up inode.
  4. For the last component, do steps (a)–(d) but skip the directory check; wrap the resolved inode in a File and return.
open("/foo/bar/baz.txt")
↓ split on "/"
components: ["foo", "bar", "baz.txt"]
↓
current = root inode (ino=1, Dir)
↓ find "foo" in root's entries
current = foo inode (ino=5, Dir)
↓ find "bar" in foo's entries
current = bar inode (ino=12, Dir)
↓ find "baz.txt" in bar's entries
resolved = baz.txt inode (ino=47, File)
↓ wrap in File, add to fd table
return fd = 3
Each "find X in entries" step is a linear scan of the directory's bytes. Linux caches resolved paths in the dentry cache so repeated lookups are O(1); we won't bother for mini-os.

Build steps — your turn

Six slices. Commit each one separately (per the workflow preference recorded after Lesson 2). Each is independently verifiable.

3.1Extend Inode with ino and kind; add REGISTRY

Add the ino: u64 and kind: InodeKind fields to Inode. Define the InodeKind enum. Create REGISTRY: Lazy<Mutex<BTreeMap<u64, Arc<Inode>>>>. Write Inode::new_file(bytes) and Inode::new_dir() constructors that allocate a fresh ino from a counter, insert into the registry, and return the Arc<Inode>.

Compile should succeed. HARDCODED_INODE still exists, still works. We'll remove it in step 3.3.

3.2Dirent encode/decode helpers

Write two functions:

fn encode_dirent(name: &str, ino: u64) -> Vec<u8> — produces the [name_len][name][ino] byte sequence.

fn lookup_in_dir(dir_bytes: &[u8], name: &str) -> Option<u64> — walks the directory bytes, returns the ino for the matching name, or None.

Add a tiny unit test (or a println!-driven check at boot) that encodes two entries into a Vec, then looks up both names, then looks up a missing name. Verify before moving on.

3.3Build the root directory and a file inside it

At boot (or in a lazy_static initializer), create the root inode: Inode::new_dir(), remember its ino as ROOT_INO. Then create a file inode with the bytes b"hello vfs\n". Then mutate the root directory's bytes to append an entry mapping "hello.txt" → the file's ino.

Replace HARDCODED_INODE references with the new file inode. Compile and boot — existing test program should still print hello vfs via the old sys_open path that ignores the path (we'll fix that next).

3.4Implement path resolution in sys_open

Replace the "ignore path, return hardcoded inode" stub. New behavior:

  1. Read the path string from the user pointer (null-terminated, max length 256).
  2. Validate it starts with / (we only support absolute paths for now).
  3. Split on /, drop empty components (handles trailing slash, double slash).
  4. Walk per the algorithm above. Use ROOT_INO as the starting point.
  5. On success, wrap the resolved Arc<Inode> in a File, insert into the FD table, return the fd number.
  6. On any failure (component not found, intermediate isn't a directory, path doesn't start with /), return u64::MAX (our sentinel for errors — Linux returns -ENOENT etc.).
3.5Update USER_PROGRAM and verify single-file case

Change the test program's open call from open("ignored") to open("/hello.txt"). Rebuild, run, confirm "hello vfs" still prints. This proves the path parser actually walks the root directory and resolves the entry.

3.6Add a second file and verify both resolve correctly

In the boot setup, add a second file: "secret.txt" with different bytes (say b"top secret\n"). Append another dirent to the root. Update USER_PROGRAM to open("/hello.txt"), read, print; then open("/secret.txt"), read, print. Two different paths, two different contents. This proves path resolution isn't accidentally always returning the same inode.

Verification — what success looks like

Serial output of the test program in step 3.6: 

// ... boot stuff ...
[syscall] sys_open path="/hello.txt" -> fd=3
[syscall] sys_read fd=3 len=10 -> read 10 bytes
hello vfs
[syscall] sys_close fd=3 -> ok
[syscall] sys_open path="/secret.txt" -> fd=3
[syscall] sys_read fd=3 len=10 -> read 10 bytes
top secret
[syscall] sys_close fd=3 -> ok
[syscall] sys_exit(0)

The win: two different paths returned two different inodes. The kernel parsed the path, walked the root directory's bytes, found the matching entry, looked up the inode number in the registry, and wrapped the right one in a file descriptor. That is the load-bearing operation of every filesystem.

Primary source

Skim fs/libfs.c — specifically generic_file_llseek and the simple-directory helpers. Linux's struct linux_dirent64 is defined in include/uapi/linux/dirent.h; the getdents64 man page has the full layout and field semantics.

For path resolution, fs/namei.c is the canonical reference — specifically path_lookupat and walk_component. Our six-step algorithm is a drastic simplification of what Linux does (no symlink handling, no mount traversal, no permission checks, no dentry cache) but the shape is the same: walk components left-to-right, look up each in the parent directory.

Pause and think

Two paths point at the same file: /foo.txt and /bar.txt are both entries in the root directory, both with ino = 17. (This is a hard link — created by ln foo.txt bar.txt.) You open("/foo.txt"), write "hello", close. Then you open("/bar.txt") and read. What bytes come back, and where in the data model does that answer live?
