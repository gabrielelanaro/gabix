exec()

Take a parsed ELF, map its PT_LOAD segments into a fresh AddressSpace, set up a user stack, jump to e_entry. Plug in a disk, load a binary, run it. The mission.

What exec() does — the four-step recipe

exec(path) in Linux replaces the current process's image with a new program loaded from a file. The old code, data, and stack are discarded; a fresh address space is built from the ELF; the CPU jumps to e_entry as if the process had just been born.

For mini-os, "the current process" is the kernel itself (we have no real process table yet). So exec_elf(path) for us means: build a new user address space from the ELF, switch to it, jump to user mode at e_entry. The recipe:

1
Parse — read the file via VFS, run ElfHeader::parse + walk the PHT (Lesson 15).
2
Map — for each PT_LOAD segment: create a fresh AddressSpace, allocate frames for each page in [p_vaddr, p_vaddr + p_memsz), map them with the segment's permissions.
3
Copy + zero — for each mapped segment, copy p_filesz bytes from p_offset in the file into the new memory. Then zero the p_memsz − p_filesz tail (this is how .bss appears — no file bytes, just zeros).
4
Stack + jump — map a few pages of user stack at a high virtual address with rw-. Switch to the new AddressSpace. Push the user state (ss, rsp, rflags, cs, rip = e_entry) and iretq. The CPU is now running the program.

The p_memsz > p_filesz trick (how .bss works)

Programs have global variables that start at zero. The C declaration static int counter; (no initializer) doesn't waste file bytes storing zeros — the linker just records "this segment needs N bytes of zero at the end." The ELF encodes this as p_filesz < p_memsz: p_filesz bytes come from the file, the remaining p_memsz − p_filesz bytes get zeroed by the loader.

hello.elf doesn't use this trick (its two segments have p_filesz == p_memsz — no uninitialized globals). But a real program would, and the loader has to handle it correctly. Lesson 16's map_segment helper will: copy p_filesz bytes, then explicitly zero the rest of the last page (and any additional pages).

The user stack

The ELF doesn't say where the stack goes — that's the kernel's call. Linux puts it near the top of the user half of the address space (typically 0x7fff_ffff_xxxx) and grows it downward. We'll do the same: allocate a few frames, map them as rw- at a high address, point rsp at the top.

Arguments and environment would normally live on the stack at startup. hello.elf's _start loops forever and ignores them, so we can skip that for now and come back when a program actually reads argc / argv.

Build steps — your turn

Four steps. 16.1 writes the per-segment mapper. 16.2 wraps it in a full exec_elf(path) driver. 16.3 adds the stack. 16.4 switches address space and jumps.

16.1map_segment — allocate, map, copy, zero one PT_LOAD

In src/elf.rs (or a new src/exec.rs, your call), add a helper that takes a parsed ProgramHeader, the raw file bytes, and a target &AddressSpace, then installs the segment: 

// Map one PT_LOAD segment into `aspace`. Returns total bytes copied.
pub fn map_segment(
    aspace: &memory::AddressSpace,
    ph: &ProgramHeader,
    file_bytes: &[u8],
) -> Result<u64, &'static str> {
    assert!(ph.is_load(), "map_segment called on non-LOAD");

    // Page-align the segment's memory range. The ELF spec guarantees
    // p_vaddr ≡ p_offset (mod p_align), but the segment may start
    // mid-page. Round down to the page containing p_vaddr.
    const PAGE: u64 = 4096;
    let page_start = ph.p_vaddr & !(PAGE - 1);
    let page_end   = (ph.p_vaddr + ph.p_memsz + PAGE - 1) & !(PAGE - 1);
    let num_pages  = (page_end - page_start) / PAGE;

    // Translate p_flags to x86-64 page-table flags. PRESENT + USER
    // always; WRITABLE and NO_EXECUTE conditional.
    let mut flags = PageTableFlags::PRESENT | PageTableFlags::USER;
    if ph.p_flags & PF_W != 0 { flags |= PageTableFlags::WRITABLE; }
    // NX bit needs the CPU to support it — check via CPUID earlier.
    // If supported: if ph.p_flags & PF_X == 0, flags |= NO_EXECUTE.

    for i in 0..num_pages {
        let vaddr = page_start + i * PAGE;
        let frame = frame_allocator::allocate()
            .ok_or("out of frames during exec")?;
        unsafe { aspace.map_to(vaddr.into(), frame.start_address(), flags)?; }

        // Zero the whole frame first — handles .bss tail automatically.
        memory::write_to_frame(frame.start_address(), &[0u8; PAGE][..]);

        // Overlay file bytes that fall inside this page.
        let file_range_start = ph.p_offset;
        let file_range_end   = ph.p_offset + ph.p_filesz;
        let mem_page_start  = page_start + i * PAGE;
        let mem_page_end    = mem_page_start + PAGE;

        // Where does this page fall in the segment's memory range?
        let copy_mem_start = mem_page_start.max(ph.p_vaddr);
        let copy_mem_end   = mem_page_end.min(ph.p_vaddr + ph.p_filesz);
        if copy_mem_start >= copy_mem_end { continue; }  // nothing in this page

        // Translate the memory range back to a file range.
        let copy_off = file_range_start + (copy_mem_start - ph.p_vaddr);
        let copy_len = (copy_mem_end - copy_mem_start) as usize;
        let file_slice = &file_bytes[copy_off as usize..copy_off as usize + copy_len];

        // Write into the frame at the right page offset.
        let page_offset = (copy_mem_start - mem_page_start) as usize;
        memory::write_to_frame_at(frame.start_address(), page_offset, file_slice);
    }

    Ok(ph.p_filesz)
}

Two helpers (memory::write_to_frame, write_to_frame_at) already exist or are easy single-frame helpers to add. The shape: allocate one frame per page, zero it, overlay the file bytes that fall inside it. Doing it per-page keeps the p_filesz < p_memsz case trivial — pages past the file range just stay zeroed.

16.2exec_elf(path) — drive the whole load

In src/main.rs (or a new module), a function that takes a path, returns nothing on success. It chains VFS → parser → mapper: 

pub fn exec_elf(path: &str) -> Result<(), &'static str> {
    // 1. Resolve + read via VFS (Lesson 14 path).
    let inode = fs::resolve_path(path).ok_or("no such file")?;
    let bytes = inode.data.lock();
    let bytes: &[u8] = &bytes;

    // 2. Parse header + validate (Lesson 15).
    let header = elf::ElfHeader::parse(bytes).ok_or("not ELF")?;
    if !header.is_x86_64_exec() { return Err("not x86-64 ET_EXEC"); }

    // 3. Fresh address space — clean slate.
    let aspace = memory::AddressSpace::new();

    // 4. Walk PHT, map each PT_LOAD into the new AS.
    let mut mapped = 0;
    for i in 0..header.phnum {
        let off = header.phoff as usize + i as usize * header.phentsize as usize;
        let ph = elf::ProgramHeader::parse(&bytes[off..]).ok_or("ph parse")?;
        if ph.is_load() {
            map_segment(&aspace, &ph, bytes)?;
            mapped += 1;
        }
    }
    if mapped == 0 { return Err("no PT_LOAD segments"); }

    // 5. Set up the user stack (16.3).
    let stack_top = setup_user_stack(&aspace)?;

    // 6. Switch to the new AS, jump to entry (16.4).
    aspace.switch_to();
    enter_user_at(header.entry, stack_top);  // never returns
}

Note inode.data.lock() borrows the bytes via MutexGuard; the slice into &bytes works as long as the guard lives. Don't clone() the file — it's already in kernel memory via Lesson 14's resolve_path.

16.3Set up the user stack

The ELF doesn't say where the stack goes — the kernel picks a high address. Two pages is plenty for a program that does nothing but loop: 

// Map `num_pages` rw- user frames at a fixed high address.
// Returns the top-of-stack virtual address.
fn setup_user_stack(aspace: &memory::AddressSpace) -> Result<u64, &'static str> {
    const STACK_TOP:   u64 = 0x7fff_ffff_f000;
    const STACK_PAGES: usize = 2;
    const PAGE:       u64 = 4096;

    let flags = PageTableFlags::PRESENT
            | PageTableFlags::WRITABLE
            | PageTableFlags::USER;

    for i in 0..STACK_PAGES {
        let vaddr = STACK_TOP - (STACK_PAGES - i) as u64 * PAGE;
        let frame = frame_allocator::allocate()
            .ok_or("out of frames for stack")?;
        unsafe { aspace.map_to(vaddr.into(), frame.start_address(), flags)?; }
        memory::write_to_frame(frame.start_address(), &[0u8; PAGE as usize][..]);
    }

    Ok(STACK_TOP)  // first push will land just below this
}

Pointing rsp at the very top of the highest mapped page is fine — the first push decrements rsp before writing, so it lands inside the mapped region.

16.4Switch address space + jump to entry

Reuse the M3 user-mode entry path, just with a different rip: 

fn enter_user_at(entry: u64, stack_top: u64) -> ! {
    // Build the iretq frame on the kernel stack:
    //   ss:rsp:rflags:cs:rip
    // ss = user data segment (DPL 3)
    // cs = user code segment (DPL 3)
    // rflags = interrupts enabled
    // rip = entry
    // rsp = stack_top
    unsafe {
        core::arch::asm!(
            "push rax",                // ss
            "push rdi",                // rsp
            "push 0x202",              // rflags: IF set
            "push rbx",                // cs
            "push rsi",                // rip
            "iretq",
            in("rax") 0x18 | 3,         // user data seg (GDT entry 3, DPL 3)
            in("rdi") stack_top,
            in("rbx") 0x10 | 3,         // user code seg (GDT entry 2, DPL 3)
            in("rsi") entry,
            options(noreturn),
        );
    }
}

Exact GDT entry numbers depend on what's in src/gdt.rs from M2/M3 — check there before copy-pasting the segment selectors.

Verification — what success looks like

[test] exec /hello.elf
[elf] /hello.elf: 1344 bytes
[elf] parsed: entry=0x201190, 2 PT_LOAD segments
[exec] mapping segment 1: vaddr=0x200000 size=388 perms=r--
[exec] mapping segment 2: vaddr=0x201190 size=4   perms=r-x
[exec] user stack mapped at 0x7ffffffe000 (2 pages)
[exec] switching to new address space (CR3=0x...)
[exec] jumping to entry 0x201190
[user] running in user mode at rip=0x201190

hello.elf's body is just jmp . — an infinite loop. There's no observable output. The success signal is that the kernel doesn't crash: no page fault, no GP fault, no triple-fault. To prove user-mode is actually running, instrument a syscall or a timer tick that preempts the user process and prints "still running."

The deeper success signal: change hello.elf's source to call syscall with a magic number the kernel recognizes, and have the kernel print "[user] syscall received." That closes the loop — disk → ELF → user mode → syscall → kernel. End-to-end proof that exec landed.

Primary source

Linux's execve implementation lives in fs/exec.c, and the ELF-specific loader is fs/binfmt_elf.c (specifically load_elf_binary). Both are large — they handle credentials, auxv, coredump headers, ASLR, ld.so bootstrapping. Read them as "the production version of what we just wrote."

The x86-64 iretq frame layout (ss / rsp / rflags / cs / rip) is documented in the Intel SDM, volume 3, "Interrupt and Exception Handling." Same layout the bootloader used to enter the kernel; we're just doing it again with user segments.
