3.07 · ARM scheduling

How does B get a turn while A keeps running?

One CPU core, two tasks, and a timer interrupt.

You have already seen the Pi check UART and Ethernet in one loop. That worked because each check returned, allowing the loop to call the next check. Here we want a second function to run even while the first function keeps looping.

The scenario

We have created two kernel tasks. A task is a function the kernel can pause and resume. We use one CPU core, so only one task executes at a time.

Task A · already runningloop { counter_a += 1; }

A keeps counting. It never calls yield_now().

Task B · ready to startloop { counter_b += 1; }

B also wants to count. The kernel knows about B, but B has not run yet.

Our question: how can B run if A never voluntarily pauses?

Three components have different jobs

The timer is hardware that measures elapsed time and can request an interrupt. The CPU responds by entering the kernel’s interrupt handler. The scheduler is kernel code that chooses which ready task should run next.

The handler and scheduler execute on the same CPU as A and B. They are functions in our kernel; there is no separate CPU running them in the background.

Which component chooses B?

What made the switch possible?

The timer interrupted A. That made the CPU execute kernel code, giving the scheduler an opportunity to select B. The kernel saved A’s state so A can continue later.

Preemption means the kernel can pause a running task without waiting for that task to call yield_now().

Try one comparison

Disable Timer interrupts enabled and press Let A keep counting a few times. A’s counter increases; B stays Ready. In this example there is no explicit yield or other scheduling event, so the scheduler never gets to choose B.

Enable the timer again and step through. Find the first moment the CPU stops executing A. Then find the later moment when the scheduler actually selects B. Those are separate events.

Why doesn’t every timer interrupt switch tasks?

A handler can acknowledge the timer and return directly to the interrupted task. Our earlier ARM kernel did that. We added a call to the scheduling code. That call makes a task switch possible; the scheduler still needs another ready task to select.

What is “saved task state”?

The CPU uses registers to hold values while executing instructions. A’s counter might be in a register when it is interrupted. B will use those registers too. The kernel must keep a copy of A’s values in memory, along with the information needed to resume A’s code.

Our implementation saves this information on A’s stack. A stack is memory used for a task’s function calls and local data. The register-by-register sequence is in the optional detailed simulator.

How does this match the code on our Pi?

The local timer requests an interrupt. The entry code in boot.S saves the interrupted state. arm_irq_entry acknowledges the timer and calls preempt_on_timer(). In scheduler.rs, that function calls yield_now(); the dispatcher selects the next ready task. context.rs performs the low-level context switch.
