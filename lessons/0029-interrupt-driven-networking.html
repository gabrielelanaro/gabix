Lesson 29 · Interrupt-driven I/O

Interrupt-Driven Networking

Move virtio-net work into a blockable deferred task, program MSI-X, and use a timer backstop for reliable QEMU delivery.

Prereq Lesson 28 Focus deferred RX + wakeup + valid Ethernet TX Build status implemented and tested

Lesson 28 put virtio-blk on interrupts. virtio-net still polls: a cooperative task spin-yields checking the RX ring forever, TX busy-waits 200,000 iterations, and ARP resolution busy-polls. This lesson gives virtio-net the same treatment, deletes the polling worker, and wires socket wakeups to fire from the RX ISR. End state: zero polling in the entire I/O path.

Verified implementation boundary

The implemented path programs per-device MSI-X entries and keeps tiny RX/TX handlers, while QEMU does not deliver virtio-net MSI-X reliably in this machine setup. A 100 Hz timer wakes the blocked network_task as a bounded-latency backstop. Ring draining, protocol parsing, socket delivery, and task wakeups all run in task context. The implementation tour follows the observed path and explains the Ethernet TX padding diagnosis.

What the polling worker does today

The network_worker task (src/virtio.rs:808) does two jobs in a single function:

pub unsafe extern "C" fn network_worker() { loop { let _ = with_net_device(|device| device.poll_rx()); crate::task::yield_now(); } }

Job one: drain the RX used ring — check whether the device wrote new frames, parse them, and recycle the receive buffers. Job two: dispatch each frame — Ethernet→IPv4→UDP→socket::deliver, which pushes the datagram to the matching socket's receive queue and wakes any task blocked on that socket.

Both jobs are the right work. The problem is the trigger: yield_now means the task wakes every schedule cycle and polls, even when no frames have arrived. The ISR does the same two jobs but only when the device actually has frames.

What stays, what changes

Today — cooperative poll

network_worker task runs in a loop. Each schedule cycle: lock NET_DEVICE, call poll_rx, dispatch frame, deliver to socket, wake waiter, unlock, yield. Repeats forever regardless of whether frames arrived.

After — interrupt-triggered

RX ISR fires when the device writes to the RX used ring. ISR: lock NET_DEVICE, drain poll_rx in a loop, dispatch each frame, deliver to socket, wake waiter, unlock, EOI. Runs only when there is work. No polling task.

The socket layer does not change. socket::deliver, register_waiter_if_empty, register_poll_waiter_if_empty, task::wake — all stay exactly as they are. What changes is who calls deliver and when. A cooperative task calling it every 10 ms becomes an ISR calling it the instant a frame lands.

The RX delivery path, end to end

Trace a UDP datagram arriving at the echo server, from wire to woken task:

Hardware
1 QEMU delivers a frame to virtio-net. The device writes the frame bytes into a pre-posted RX buffer, advances the RX used ring, and performs an MSI-X write to 0xFEE00000 with the RX vector.
↓
APIC delivers to CPU
2 Local APIC receives the write, raises the dedicated RX vector 0x30 to the CPU core
↓
3 CPU pushes interrupt frame, consults IDT[0x30], jumps to virtio_net_rx_wrapper
↓
ISR — the new network_worker
4 Wrapper pushes 15 registers, calls virtio_net_rx_inner
↓
5 Lock NET_DEVICE. Drain poll_rx in a loop: for each frame, call dispatch_frame
↓
6 dispatch_frame: parse Ethernet → IPv4 → UDP. Call socket::deliver(dst_port, sender, payload)
↓
7 deliver: push datagram to socket's receive queue. Extract recv_waiter and poll_waiters under the socket lock. Call task::wake(pid) for each.
↓
8 Unlock NET_DEVICE. Send EOI to APIC (write 0 to 0xFEE00xB0). iretq.
↓
Scheduler resumes the woken task
9 Next yield_now: the woken task is now Ready. Scheduler picks it. Task resumes in recvfrom or poll loop, calls pop(), gets the datagram.

Steps 5–7 are the same code network_worker runs today. The only difference is the trigger: step 1 is a hardware event instead of a schedule cycle.

The locking question

The RX ISR needs to lock NET_DEVICE to call poll_rx. If a send is in progress (send_frame holds the lock), the ISR must not deadlock waiting for it.

The fix: use try_lock instead of lock. try_lock returns immediately if the lock is held. If it fails, the ISR sends EOI and returns. The frame stays in the RX used ring. The next timer tick calls poll_rx once as a fallback — a lightweight safety net for the rare case where the ISR and a send collide.

try_lock + timer fallback = hybrid design

This is the same shape as Linux NAPI: the hardware interrupt is the primary trigger, but a timer-based poll catches frames the ISR missed due to lock contention. The timer check is one poll_rx call per tick (100 Hz), not a spin-yield loop. No separate task. No wasted CPU.

The idle problem

network_worker is always Ready. Delete it and a new situation appears: every task blocked on I/O, nothing runnable. The scheduler's yield_now has a branch for this case today:

// No other runnable task. let current_state = sched.tasks[old_index].state; if current_state == TaskState::Blocked { // Current is blocked AND nothing else can run. // System is effectively done. x86_64::instructions::hlt(); // ← currently halts forever }

That hlt halts forever. Today it never triggers because network_worker is always ready to run. Once the worker is deleted, this branch fires the moment the echo server blocks on recvfrom and no other task exists.

The fix: replace the halt-forever with a loop that sleeps until an interrupt, then rescans:

// All tasks blocked. Wait for a device interrupt to wake one. loop { unsafe { core::arch::asm!("sti; hlt; cli"); } // An interrupt fired. The ISR may have woken a task. // Re-acquire the scheduler lock and re-scan. if any_runnable(&sched) { break; } }

sti; hlt; cli is the idiom: enable interrupts so hlt can wake, halt the CPU, then immediately disable interrupts again before re-acquiring locks. The RX ISR fires during hlt, calls deliver → wake, and returns. The rescan finds the woken task and the scheduler continues normally.

This branch is the kernel's idle loop. Every real OS has one: Linux calls it the idle task. When there is nothing to do, the CPU sleeps. When an interrupt arrives, it wakes, processes the interrupt, and reschedules.

The lost-wakeup race

When deliver ran inside network_worker, it could never fire while a task was in the middle of registering itself as a waiter — both ran in task context, serialized by yield_now. Now deliver runs in the RX ISR, which can interrupt a task at any moment.

Consider this sequence without protection:

Task (recvfrom)
1. pop() → None (queue empty)
2. register_waiter(pid)
 
 
3. block_current() → Blocked
4. yield_now() → switched away
5. stuck Blocked forever
RX ISR
 
 
← fires between steps 2 and 3
→ deliver: queue datagram, wake(pid)
→ but task is still Running, wake is a no-op
 

The datagram arrived and the waiter was registered, but wake found the task in Running state (not yet Blocked), so it did nothing. Then the task blocked itself and nobody woke it. Lost wakeup.

The existing code already solves this. Both recvfrom and poll wrap the register + block sequence in without_interrupts:

let should_block = x86_64::instructions::interrupts::without_interrupts(|| { if socket.register_waiter_if_empty(current_pid()) { block_current(); true } else { false // queue became non-empty; retry pop } }); if should_block { yield_now(); }

without_interrupts executes cli before the closure and restores the interrupt flag after. While interrupts are off, the ISR cannot fire. The register and the block happen atomically with respect to the ISR. By the time interrupts are re-enabled, the task is already Blocked — so if the ISR fires now, wake finds Blocked and flips it to Ready. Correct.

The register_waiter_if_empty re-check (it returns false if the queue is non-empty) handles the inverse case: a datagram arrived before without_interrupts ran. In that case, the task skips blocking and loops back to pop, which succeeds.

No code changes needed here. The defense was already built in Lesson 27. What changes is understanding why it matters: with ISR delivery, the race is against hardware interrupts, not just cooperative yields. The defense works for both.

TX completion — same pattern as read_sector

send_frame (src/virtio.rs:880) has the same 200,000-iteration poll loop as read_sector had before Lesson 28. The fix is identical: program a TX MSI-X vector, add an ISR that sends EOI, and replace the poll loop with the hlt-based wait.

ARP resolution (resolve_arp, src/virtio.rs:1065) busy-polls RX for 200,000 iterations waiting for a reply. Same fix: the RX ISR delivers the reply to the ARP cache, and resolve_arp sleeps via hlt until the cache entry appears.

Build steps

29.1
Program MSI-X vectors for virtio-net RX and TX. Two new MSI-X table entries (entry 1 for RX queue 0, entry 2 for TX queue 1). Program their message addresses to 0xFEE00000, data to vectors 0x30 (RX) and 0x31 (TX). Write the entry indices to the queues' COMMON_QUEUE_MSIX_VECTOR fields. Unmask both entries. This reuses the exact pattern from Lesson 28's steps 28.2–28.3.
29.2
RX ISR — the new network_worker. Write a naked wrapper for vector 0x30 (same shape as timer_wrapper). The inner handler: try_lock NET_DEVICE. If locked: send EOI, return. If unlocked: drain poll_rx in a loop (each call parses a frame and calls dispatch_frame → deliver → wake). Unlock. Send EOI to APIC. Register in IDT[0x30], reload IDT. Verify: send a UDP packet from the host, confirm the ISR fires and the datagram reaches the socket queue.
29.3
TX ISR + replace send_frame poll. Write a naked wrapper for vector 0x31. Inner handler: EOI only (same design as Lesson 28's virtio-blk ISR — send_frame checks the used ring itself after hlt wakes). Replace send_frame's 200,000-iteration find_map at virtio.rs:854 with the hlt-based wait loop. Verify: ARP request transmits, ping reply transmits, echo server sends responses.
29.4
Delete network_worker + fix the idle path. Remove the network_worker function and its spawn call in main.rs. In yield_now's "no runnable task" branch (src/task.rs): replace the halt-forever with sti; hlt; cli + rescan loop. Add one poll_rx call inside timer_inner (the timer-tick fallback for frames the ISR missed due to lock contention). Verify: echo server blocks on recvfrom, CPU halts, send a packet from host, ISR wakes the task, echo comes back.
29.5
Replace resolve_arp poll. Replace the 200,000-iteration RX poll loop in resolve_arp (src/virtio.rs:1065) with a hlt-based wait that checks arp::lookup(ip) after each wake. The RX ISR (or timer fallback) will deliver the ARP reply to the cache; resolve_arp just needs to wake up and check. Verify: ping gateway resolves ARP successfully.
29.6
End-to-end verification. Run the full test suite: ping the gateway (ICMP + ARP), echo server on port 5555 (UDP + sockets + blocking recvfrom), two-port echo server with poll. Confirm no busy-poll loops remain anywhere: grep -rn '200.000' src/ should return nothing. The I/O path is fully interrupt-driven.
End state: zero polling

After Lesson 29, every device I/O path is interrupt-driven. virtio-blk reads sleep via hlt (Lesson 28). virtio-net RX fires from the MSI-X ISR. virtio-net TX sleeps via hlt. ARP resolution sleeps via hlt. The network_worker task is gone. When all tasks block on I/O, the CPU enters the idle loop (sti; hlt; cli) until a device interrupt arrives. No polling, no spin-yield, no wasted CPU cycles.

Primary sources

The VIRTIO 1.2 specification §5.1 covers the network device's interrupt model (queue 0 = receiveq, queue 1 = transmitq). Linux's drivers/net/virtio_net.c shows the production RX ISR (virtnet_receive) and the NAPI hybrid interrupt+poll design. The idle loop is Linux's kernel/sched/idle.c — the cpu_idle_loop does the same sti; hlt pattern we build here. OSDev's APIC page covers EOI and interrupt masking. For the lost-wakeup problem, Linux's memory barriers documentation §"CACHE COHERENCY" and the completion API show the production-grade patterns for the race we solve with without_interrupts + re-check.

What this completes

Lessons 28–29 together convert the entire device I/O path from polling to interrupts. Every read, every frame, every ARP resolution sleeps the CPU until the hardware signals completion. The network_worker polling task is gone. The kernel has a real idle loop.
