The Pi 2B's interrupt controllers

How a device on the Raspberry Pi 2B reaches the CPU — through two Broadcom controllers, not the GIC.

Plug in the Pi 2B on Monday and you will want the kernel to notice the instant a network packet arrives, or the instant the SD card finishes reading a sector — without sitting in a loop asking "done yet? done yet?" That notice is an interrupt: the device raises a signal, the CPU leaves whatever program it was running, runs a small handler in the kernel, then returns.

On x86, and on the ARM board the QEMU emulator calls virt, one chip collects every device's signal and hands it to the CPU. That chip is the GIC, and lesson 1.02 used it as the clean example of an interrupt controller.

The Pi 2B has no GIC. Broadcom split the job across two pieces of hardware, each with its own list of registers, and a signal passes through both on the way to the CPU. Gabix today talks to only one of those pieces (the timer). This lesson is how the two fit together, so you can read the manual and wire a real device interrupt yourself.

1. The signal's path

Follow one signal from a device to the CPU. A network packet arrives. The USB controller must signal the CPU (the Pi's Ethernet port is a chip that hangs off the USB bus, so the network's interrupt is the USB interrupt). The signal goes through two controllers before it reaches a core:

the path of one device interrupt on the Pi 2B
   USB controller   (device needs service)
        │  sets bit 9
        ▼
   GPU interrupt controller   address 0x3F00_B200
   every peripheral has one bit here; USB is bit 9 in bank 1
        │  raises one wire — the "GPU IRQ" line
        ▼
   ARM-local region   address 0x4000_0000
   routes the signal to one of the four CPU cores — here, core 0
        │  delivers to core 0
        ▼
   CPU takes the IRQ → your .Lirq handler runs
   the handler reads the GPU pending bits to learn that bit 9 (USB) fired

Two things to fix in your mind from that picture:

  • The GPU interrupt controller is where every peripheral's signal shows up as one bit. USB is one bit; the SD controller is another; the UART is another. There are about a hundred bits, grouped into banks of 32.
  • The ARM-local region decides which of the four CPU cores receives the signal, and it owns a few sources of its own — including the local timer, the one interrupt gabix actually uses on the Pi. (The region also holds the inter-core mailboxes, but gabix is single-core and never uses them; lesson 7.03 covers both.)

So the first controller reports which device fired (one bit per peripheral), and the second routes that signal to one core. Your IRQ handler reads the first controller's pending bits to find the device.

2. Why two controllers, and the confusing "GPU" name

These two pieces exist because of the Pi chip's history. The chip has two halves: a graphics processor (the VideoCore GPU) that boots first and owns most of the peripherals, and the ARM CPU(s) that run your code. The peripherals physically live on the GPU half of the chip, so their interrupts are called "GPU interrupts" even when the device is a USB port or an SD card slot. The name means "forwarded from the GPU side to the ARM," not that the graphics processor itself fired.

The ARM-local region was added for the Pi 2, because the Pi 2 has four CPU cores and each interrupt must be routed to one of them.

The name "GPU interrupt controller" applied to a USB or SD signal is the single most confusing thing about the Pi's interrupts. With the history, it makes sense: those controllers live on the GPU half of the chip.

3. The GPU interrupt controller — where the devices live

This controller sits at address 0x3F00_B200. It has three banks of bits, because there are more than 32 sources and one 32-bit register cannot hold them all:

BankPending register (read what fired)Enable register (turn a source on)
1 — sources 0 to 31+0x04+0x10
2 — sources 32 to 63+0x08+0x14
Basic — a shortlist of common ones+0x00+0x18

(Every offset is from 0x3F00_B200. Matching Disable registers sit at +0x1C, +0x20, +0x24.)

Each device has a fixed bit number in a fixed bank, set by the hardware design. The BCM2836 ARM Peripherals manual lists them in a table called "Interrupts." The one you will care about for networking: the USB controller is bit 9 in bank 1. Because the Pi 2B's Ethernet port hangs off the USB bus, the network's interrupt is the USB interrupt.

To turn a device's interrupt on, you write a 1 to its bit in the right Enable register. From then on, when the device needs servicing, the controller sets the bit in its Pending register and raises a single output wire — the "GPU IRQ" line — toward the ARM cores.

4. The ARM-local region — the core router

The second controller is the ARM-local region, at 0x4000_0000. Its job is routing: it takes the GPU IRQ wire from the first controller (and the local sources it owns) and delivers it to one of the four cores. It has a set of registers per core — core 0's, core 1's, and so on — so you can choose which core handles which signal. For a single-core kernel like gabix, everything goes to core 0.

This region also owns the local timer — the one interrupt source gabix actually uses on the Pi. The local timer is special: it is entirely inside this region, so it skips the GPU controller and routes straight to a core. That is why gabix's timer setup is short — three register writes and the CPU's interrupt enable:

targets/armv7/src/raspi2b/timer.rs · gabix's only real interrupt on the Pi: the local timer
pub unsafe fn init() {
    write32(LOCAL_TIMER_ROUTE, 0);                                   // send the timer interrupt to core 0
    write32(LOCAL_TIMER_ACK, TIMER_INTERRUPT_FLAG | TIMER_RELOAD_NOW); // clear and reload the countdown
    write32(LOCAL_TIMER_CONTROL, TIMER_ENABLE | TIMER_INTERRUPT_ENABLE | TIMER_RELOAD); // arm it
    asm!("dsb sy", "cpsie i", "isb");                                 // drain writes, enable CPU interrupts, sync
}

No GPU controller, no pending-register scan — the timer signals the core router directly, and the core router delivers it to core 0.

5. What gabix does today

Gabix enables only the local timer. Every device driver — the SD card, the USB controller — polls its own status register in a loop instead of waiting for an interrupt. The function sdhci.rs calls wait_interrupt is a poll: it reads the SD card's status bit over and over until it changes, up to a limit, then gives up. No signal from the SD card or the USB port ever reaches the CPU.

So on the Pi today, gabix has exactly one real interrupt (the timer) and busy-waits on every device. That works, badly: it wastes the CPU spinning, and it is fragile on real hardware where the timing differs from the emulator. Wiring a real device interrupt fixes both.

6. Wiring a real device interrupt

The USB interrupt (bit 9) is the example. Wiring it takes five steps:

  1. Find its bit. The manual's Interrupts table says USB is bit 9 in bank 1.
  2. Enable it at the source. Write a 1 to bit 9 of the Enable 1 register (0x3F00_B210). Now the GPU controller will latch USB and raise its output wire when USB has news.
  3. Route it to a core. In the ARM-local region, enable the GPU IRQ line to reach core 0. (The manual's ARM-local section names the per-core routing register; set the GPU IRQ bit for core 0.)
  4. Handle it. In the IRQ handler — the .Lirq path from lesson 1.02 — read the Pending registers. If bit 9 of Pending 1 is set, the USB controller fired; run the USB receive code.
  5. Clear it at the device. The GPU pending registers are read-only; you do not clear them by writing. Instead you clear the interrupt condition at the device itself (in the USB controller's own status registers), and the GPU pending bit drops on its own once the device stops signalling. The local timer is the exception: you clear it by writing its acknowledge register, which is what gabix's handle_interrupt does.

Steps 1, 2, and 4 are the same for every device — only the bit number and bank change. That is the durable skill: find the bit, enable it, scan pending in the handler, clear it at the device.

7. When it does not work on metal

When a device interrupt fails to arrive on the real Pi, the signal has four places to break, and now you know where each one lives:

  • The source's bit was not enabled in the GPU controller's Enable register. No bit set, no signal.
  • The GPU IRQ line was not routed to core 0 in the ARM-local region. The signal latched in the controller but never reached a core.
  • The CPU was not taking IRQs — interrupts masked, or the vector table at VBAR not set. The signal reached the core, but the CPU ignored it.
  • The device's own interrupt enable was off at the device. The device never signalled in the first place.

Each is one register read. Knowing the two-controller path tells you which register to read at each step.

What you should be able to do after this lesson. Draw the path of a USB packet's interrupt from the device to core 0, naming both controllers. For each of the four failure points above, say which controller (or the CPU) it lives in. And explain why gabix's timer code is three lines while its SD and USB code busy-waits.
Primary source, and where to go when it is not enough. The BCM2836 ARM Peripherals manual documents the ARM-local region and the GPU interrupt controller, including the Interrupts table that gives each source its bit number. The manual is famously sparse and has errors in places — the bare-metal Pi community fills the gaps: the Bare Metal forum, the OSDev Pi guide, and the source of an existing Pi OS such as Circle. When the manual disagrees with a working driver, trust the driver.

If anything here is unclear, ask. The agent can re-draw the signal path, look up the bit number for a specific device (SD card, UART) in the manual, or walk the four debug checks against a real symptom you see on Monday.
