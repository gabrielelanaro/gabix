Lesson 7 · M4 · Disk path — set up the request ring

Virtqueues

Shared-memory ring buffers between guest and host. After this lesson, the device has a queue to receive work.

Read time ~25 min Build time ~40–60 min Prereq Lesson 6

Lesson 6 left the device in DRIVER_OK state — live and ready, but with no way to receive work. To submit a disk read or write, we need a virtqueue: a shared-memory ring buffer the kernel writes requests into and the device reads from. This lesson covers the split virtqueue format (descriptor table, available ring, used ring), the request flow, memory barriers, and the queue configuration registers in the common config region. Lesson 8 will use what we build here to send the first actual disk request.

Why virtqueues

The device has MMIO registers (Lesson 6's common config region), but you wouldn't want to use them for the actual data. Every disk read would mean thousands of register writes (one per byte) and thousands of traps from guest to host. Slow, and wasteful of QEMU's time.

virtio's answer: shared memory. The guest allocates ordinary RAM, fills it with request data, and tells the device "go look at this address." The device reads the request via DMA (Direct Memory Access), does the I/O, and writes the response into guest-allocated buffers. The guest and host communicate via ring buffers in this shared memory, not via register writes.

The ring buffer design lets both sides batch work. The kernel can queue 64 descriptors and kick once; the device processes them all, then writes 64 completions back. Polling register per request would be hundreds of context switches; virtqueues are dozens.

Split vs packed virtqueue. Two formats exist. Split (the original, simpler) uses three separate regions: descriptor table, available ring, used ring. Packed (newer, more efficient) uses one ring of descriptor entries that get recycled in place. We'll use split — it's what the spec's basic examples use and what Linux's virtio_ring.c implements alongside packed. Packed is a future optimization; split is the load-bearing reference design.

The split virtqueue: three regions in guest memory

A split virtqueue is three arrays the kernel allocates in physically-contiguous, page-aligned RAM. The device accesses them via DMA using guest physical addresses (NOT virtual addresses — the device doesn't see the kernel's page tables).

Descriptor Table
Array of 16-byte entries.
Each entry points at a guest buffer (GPA + length + flags).
Kernel writes; device reads.
Available Ring
Array of u16 descriptor indices.
Kernel appends indices here to submit work.
Kernel writes; device reads.
Used Ring
Array of (id, len) entries.
Device appends entries here on completion.
Device writes; kernel reads.

All three live in guest RAM, allocated by the kernel. The device reaches them via DMA. From the kernel's perspective they're just data structures; from the device's perspective they're a contract for what work needs doing.

The descriptor entry (16 bytes)

Descriptor entry 16 bytes total
addr u64 · 8 B 0x00–0x07
len u32 · 4 B 0x08–0x0B
flags u16 · 2 B 0x0C–0x0D
next u16 · 2 B 0x0E–0x0F
addr u64

Guest physical address of the data buffer this descriptor points at. The device reaches it via DMA (Direct Memory Access) using the physical address bus — it does not walk your page tables, so a virtual address would be meaningless to it. You allocate a buffer in kernel virtual memory, then translate to physical before writing this field.

buffer at kernel virt 0xFFFF_8880_0040_0040 maps to phys 0x0000_0000_0040_0040 → addr = 0x0000_0000_0040_0040
len u32

Size of the buffer in bytes. For a one-sector disk read: 512. For a four-sector disk write: 2048. The device may legitimately write fewer bytes than this on completion — the actual bytes written show up in the used ring's len field. Must be non-zero and bounded by the device's max segment size.

read 1 sector (512 B) into a 512 B buffer addr = 0x40_0040, len = 0x200 (=512)
flags u16

Two bits matter for virtio-blk:

VIRTQ_DESC_F_NEXT = 0x01 — this descriptor is not standalone; the chain continues at the index stored in next. Use it when a request needs multiple buffers.

VIRTQ_DESC_F_WRITE = 0x02 — the device writes to this buffer (read direction). If unset, the device reads from this buffer (write direction). The direction is from the device's point of view.

disk-read request = 3 chained descriptors: desc[0] header flags=0x01 (F_NEXT, device reads it) desc[1] data buf flags=0x03 (F_NEXT | F_WRITE, device fills it) desc[2] status flags=0x02 (F_WRITE only, last in chain)
next u16

Index (0 to queue_size − 1) of the next descriptor in the chain. Only meaningful when F_NEXT is set; ignored otherwise. The chain is a singly-linked list of indices, walked by the device to gather all buffers belonging to one request.

descriptors 5, 6, 7 form one request chain: desc[5].flags = F_NEXT, desc[5].next = 6 desc[6].flags = F_NEXT, desc[6].next = 7 desc[7].flags = 0 (tail — no next)

Each descriptor points at one buffer. A request that needs multiple buffers (e.g., a request header + a data buffer + a status byte) chains descriptors together via next. The chain is a singly-linked list of descriptor indices.

The available ring

Available ring 6 + 2·N bytes (N = queue_size)
flags u16 · 2 B 0x00–0x01
idx u16 · 2 B 0x02–0x03
ring[N] u16[] · 2·N B 0x04–
used_event u16 · 2 B end
flags u16

VRING_AVAIL_F_NO_INTERRUPT = 0x01 — if set, the device will not raise an interrupt each time it consumes a descriptor. Most performance-sensitive drivers set this and rely on polling or batched interrupts instead. mini-os will leave it at 0 (interrupts enabled) but in practice poll the used ring synchronously.

flags = 0 → "interrupt me on each consumption" flags = 1 → "I'll poll, don't interrupt"
idx u16

Free-running counter the kernel increments each time it adds a new head descriptor index to ring[]. Wraps at 65536 (u16 max), not at queue_size — the modulo into ring[] handles indexing. The device remembers "last idx I processed" and works through any new entries it sees.

queue_size = 64, kernel submits 3 requests in a row: idx 0 → 1 (write head into ring[0]) idx 1 → 2 (write head into ring[1]) idx 2 → 3 (write head into ring[2]) device wakes, sees idx=3, processes ring[0,1,2]
ring[N] u16[]

Array of head descriptor indices — the first descriptor of each chain. The device follows next pointers from there to gather the rest of the chain. Indexed by idx % N. Don't put non-head indices here; that would confuse the device.

chain of descriptors 5→6→7 was built avail->ring[idx % N] = 5 (NOT 6 or 7)
used_event u16

Legacy event-suppression field from the original virtio spec. In modern transport (which we use), event suppression is handled via the avail_event field in the used ring instead. We allocate space for it for layout compatibility but never read or write it.

To submit a chain: kernel writes the chain's head descriptor index into ring[idx % N], then increments idx. The device polls idx for changes; when it sees idx advance, it processes every entry it hasn't seen yet.

The used ring

Used ring 6 + 8·N bytes (N = queue_size)
flags u16 · 2 B 0x00–0x01
idx u16 · 2 B 0x02–0x03
ring[N] {u32,u32} · 8·N B 0x04–
avail_event u16 · 2 B end
flags u16

VRING_USED_F_NO_NOTIFY = 0x01 — set by the device to tell the kernel "don't kick me on the next submission; I'm already processing this queue." The kernel checks this before writing the notification register, saving an MMIO store on each submit. Cleared by the device when it goes idle.

kernel wants to submit, checks used->flags: flags = 0 → write notify register (kick the device) flags = 1 → skip the kick (device already polling)
idx u16

Free-running counter the device increments each time it completes a request. Kernel polls this field to detect completions. Wraps at 65536 like avail->idx. The kernel remembers "last idx I processed" and reads entries ring[last % N .. new % N] on each advance.

kernel polls used->idx: sees 0 → 1 → read ring[0] (one completion ready) sees 1 → 3 → read ring[1], ring[2] (two completions ready)
ring[N] struct { id, len }

Array of 8-byte completion entries:

id: u32 — the head descriptor index the kernel originally submitted. Use this to find the chain to free.

len: u32 — number of bytes the device actually wrote. For a read of one sector: 512. For a write: 0 (no data returned). For a read shorter than requested (e.g., last sector of disk): the actual bytes written, which may be less than the buffer length.

disk read of sector 0 completes: ring[0].id = 5 (chain head was descriptor 5) ring[0].len = 512 (device wrote 512 bytes to the data buffer) kernel frees descriptors 5 → 6 → 7 (the chain)
avail_event u16

Legacy event-suppression field, twin of the available ring's used_event. Modern transport handles event suppression elsewhere. Allocated for layout compatibility; not read or written by mini-os.

The kernel polls used->idx for changes. When it advances, the entries in ring[old_idx % N .. new_idx % N] are completed requests. Each entry says "descriptor head X is done; the device wrote len bytes to its buffer."

The request flow

Trace what happens when the kernel submits a single descriptor chain and waits for completion:

T0 Kernel allocates descriptor(s) from the free list, fills in addr, len, flags.
T1 Kernel writes avail->ring[avail->idx % N] = head_index, then increments avail->idx.
T2 Memory barrier (core::sync::atomic::fence or compiler_fence) — forces all writes before this point to be visible before any write after.
T3 Kernel writes to the notification register (kicks the device). One MMIO store to the address from the notifications capability.
T4 Device sees avail->idx advance. Reads descriptor head index from avail->ring. Follows the chain via desc.next if needed.
T5 Device DMAs into the guest buffer(s). For a read: writes the requested sector bytes. For a write: reads the bytes the guest wants persisted.
T6 Device writes used->ring[used->idx % N] = { id: head_index, len: bytes_written }, then increments used->idx.
T7 Kernel polls used->idx for changes. Sees it advance. Reads the new entry to find the completed descriptor and how many bytes were written.
T8 Kernel processes the response (read the buffer, check status, free the descriptor back to the free list).

Steps T0–T3 are guest-side, T4–T6 are host-side, T7–T8 are guest-side again. The kernel doesn't necessarily wait synchronously — it can submit multiple requests, then poll for completions later. But for our simple case we'll submit one and wait.

Read vs write — what actually differs

The T0–T8 flow is the same shape for both. What changes is the direction the data flows, controlled by the F_WRITE flag on each descriptor (from the device's point of view). Here's the full chain for a one-sector request in each direction:

Disk read
Goal
Kernel wants sector N's 512 bytes in memory. Allocates an empty buffer first.
Descriptor chain
desc[0] header flags=0x01 (F_NEXT) // device reads desc[1] data flags=0x03 (F_NEXT|F_WRITE) // device fills desc[2] status flags=0x02 (F_WRITE) // device writes 0=ok
What the device does
Reads sectors from disk → writes the bytes into desc[1]'s buffer → writes 0 to desc[2] (success).
Used ring completion
id = head_index, len = 512 (bytes written to data buffer).
Disk write
Goal
Kernel wants to persist 512 in-memory bytes to sector N. Fills the buffer first.
Descriptor chain
desc[0] header flags=0x01 (F_NEXT) // device reads desc[1] data flags=0x01 (F_NEXT) // device reads desc[2] status flags=0x02 (F_WRITE) // device writes 0=ok
What the device does
Reads bytes from desc[1]'s buffer → writes them to disk → writes 0 to desc[2] (success).
Used ring completion
id = head_index, len = 0 (no data returned to guest).

Three differences, all in the data descriptor (desc[1]): the F_WRITE bit flips, the device's read-vs-write role flips, and the completion's len reports bytes written to the buffer (read) or zero (write). The header descriptor (carrying the virtio-blk request type field) and the status descriptor are identical in both. Lesson 8 will build the read chain for real.

Memory barriers — why the spec mandates them

Between writing the descriptor data (T0) and writing avail->idx (T1), the spec requires a write memory barrier. Without it, the CPU's store buffer might reorder the writes — the device could see the new idx before the descriptor's addr field is visible, then DMA from a garbage address.

On x86 this is mostly automatic (the architecture has strong ordering), but the spec is architecture-neutral and the same code runs on ARM (which has weaker ordering). Using Rust's core::sync::atomic::Ordering::Release on the avail->idx write, or an explicit compiler_fence(Release), generates the right barrier on every architecture.

What does Release ordering actually do?

Rust's atomics have orderings that map to CPU memory barriers:

• Relaxed — no ordering guarantees, just atomicity. Fine for counters where you don't care about other writes' visibility.
• Release — all prior writes become visible before this write. Use when publishing data: write the data first, then write a "ready" flag with Release.
• Acquire — all subsequent reads see the latest values. Use when reading a "ready" flag: read it with Acquire, then read the data.
• SeqCst — both Release and Acquire plus a global total order. Slowest, most correct.

For virtqueues: writing avail->idx with Release ensures the descriptor data is visible first. Reading used->idx with Acquire ensures we see the device's response data after seeing the index advance. The spec mandates this pattern; getting it wrong causes impossible-to-debug races.

Queue configuration

Before any of the ring mechanism works, the kernel has to tell the device where the rings live. This is done via the queue fields in the common config region (introduced in Lesson 6's layout box, but not used until now):

Common config — queue fields 34 bytes · offsets 0x16–0x37
queue_select u16 · 2 B 0x16–0x17
queue_size u16 · 2 B 0x18–0x19
queue_msix u16 · 2 B 0x1A–0x1B
queue_enable u16 · 2 B 0x1C–0x1D
queue_notify_off u16 · 2 B 0x1E–0x1F
queue_desc u64 · 8 B 0x20–0x27
queue_avail u64 · 8 B 0x28–0x2F
queue_used u64 · 8 B 0x30–0x37
queue_select u16 RW

Selector for which queue the following field writes target. virtio-blk has only queue 0 (the request queue we're setting up). Other device types use multiple queues (e.g., virtio-net has separate RX/TX queues) — you configure each by writing its index here, then setting the fields below.

write 0 → "the next writes (queue_size, queue_desc, ...) configure queue 0"
queue_size u16 RW

Negotiated queue size, must be a power of 2. Read first to learn the device's maximum (commonly 256), then write back the size you actually want. We'll use 64 — small, fits each region in a single 4 KiB page.

read queue_size = 256 (device max) write queue_size = 64 (our choice)
queue_msix_vector u16 RW

Which MSI-X (Message Signaled Interrupts, Extended) vector to fire on completion. We're not using MSI-X (we poll the used ring), so we leave it at 0 (no vector assigned). Real Linux virtio-blk uses MSI-X for performance — interrupts are how it avoids polling.

queue_enable u16 RW

Write 1 to activate the queue. The device treats this as the "I'm done configuring" signal — before that, it ignores the queue entirely. Write it last; setting it before the addresses are in place is undefined behavior.

order: queue_select → queue_size → queue_desc → queue_avail → queue_used → queue_enable = 1 (last!)
queue_notify_off u16 RO

Read-only multiplier used to compute this queue's notification register address: notify_cap_base + queue_notify_off × notify_off_multiplier. The base and multiplier come from the notifications capability parsed in Lesson 6. Step 7.5 uses this for the kick.

queue_desc u64 RW

Guest physical address of the descriptor table. Must be page-aligned (4 KiB). The device reads it once at queue_enable time and DMAs from this address forever after. Write the physical address, not virtual — the device doesn't walk your page tables.

descriptor table at kernel virt 0xFFFF_8880_0042_0000 maps to phys 0x0000_0000_0042_0000 → queue_desc = 0x0000_0000_0042_0000
queue_avail u64 RW

Guest physical address of the available ring. Same rules as queue_desc: page-aligned, physical address.

queue_used u64 RW

Guest physical address of the used ring. Same rules. The virtio spec recommends (and some implementations require) the used ring to live on a separate 4 KiB page from the descriptor table and available ring — we'll align it that way to be safe.

Note the addresses are guest physical, not virtual — the device does DMA via the physical address space, not through the guest's page tables. The kernel has to translate its virt allocations to physical before writing them here.

Build steps — your turn

Five substeps. The first three set up the data structures; the last two implement the ring mechanics. Step 7.5 ends with the device acknowledging the queue is ready.

7.1Allocate the three regions

Compute the sizes:

  • Descriptor table: queue_size * 16 bytes (16 bytes per entry)
  • Available ring: 2 + 2 + (queue_size * 2) + 2 bytes (header + queue_size u16 indices + used_event)
  • Used ring: 2 + 2 + (queue_size * 8) + 2 bytes (header + queue_size 8-byte entries + avail_event)

Use Box::new_zeroed().assume_init() or a similar aligned allocation. Each region needs to be page-aligned (4 KiB) and physically contiguous. For our 64-entry queue the sizes are small enough to fit in single pages.

Stash the virtual addresses and the physical addresses — you'll need both (kernel uses virtual, device uses physical).

7.2Configure the queue in common config

Write the queue fields in order:

  1. queue_select = 0 (select request queue)
  2. Read queue_size — this is the maximum the device supports; pick the largest power of 2 that fits your allocation
  3. queue_size = N (write back the negotiated size)
  4. queue_desc = descriptor_table_phys_addr
  5. queue_avail = available_ring_phys_addr
  6. queue_used = used_ring_phys_addr
  7. queue_enable = 1

Read back queue_enable — if it's still 1, the device accepted the configuration. Print success.

7.3Descriptor free list

Maintain a stack of free descriptor indices (e.g., a Vec<u16> initialized with [0, 1, 2, ..., N-1]). alloc_descriptor() -> Option<u16> pops the top. free_descriptor(idx) pushes back. Provides O(1) allocation/free with no fragmentation concerns.

When a chain completes, free every descriptor in the chain by following next pointers until you hit one without F_NEXT.

7.4Available ring submission

Implement submit_chain(head_index: u16):

  1. Read current avail->idx
  2. Write avail->ring[idx % N] = head_index
  3. Increment avail->idx with Release ordering (the memory barrier)

The Release ordering ensures the descriptor data and the ring entry are visible to the device before idx advances. Don't skip this.

7.5Used ring polling + kick

Two functions:

poll_completion() -> Option<(u32, u32)> — read used->idx with Acquire ordering. If it's advanced past what we last saw, read the new entry from used->ring and return (id, len). Otherwise return None.

kick() — write the queue number (0) to the notification register. The address is notify_cap_base + queue_notify_off * notify_off_multiplier (from the notifications capability's offset and a multiplier field in the cap structure). One MMIO store wakes the device.

For Lesson 7's verification, you can submit dummy descriptors and verify used->idx advances. Real reads come in Lesson 8.

Primary source

The OASIS VIRTIO 1.2 spec, section 2.6 (Virtqueues), defines the split virtqueue format, the descriptor / available / used layouts, and the memory ordering requirements. Definitive reference.

For Linux's implementation: drivers/virtio/virtio_ring.c handles both split and packed formats. drivers/block/virtio_blk.c uses virtqueues to submit disk I/O — specifically the virtblk_queue_rq function shows how a virtio-blk request becomes a descriptor chain.

For DMA basics: the Linux DMA API guide covers the kernel's view of device memory access. Our implementation is much simpler (no IOMMU, no bounce buffers) but the concepts are the same.
