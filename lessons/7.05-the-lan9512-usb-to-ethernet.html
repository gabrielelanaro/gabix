The LAN9512: USB to Ethernet

The chip on the Pi that turns the USB port from lesson 7.04 into an Ethernet link — reached entirely through USB transfers.

The DWC2 from lesson 7.04 gives the ARM one USB port. On its own that port does nothing useful; it needs a device plugged in. On the Pi 2B the device soldered behind the Ethernet socket is the LAN9512, a single chip from SMSC (now Microchip) that holds two things: a USB hub and a 10/100 Ethernet controller. The ARM never touches an Ethernet wire directly. It sends USB transfers to the LAN9512, and the LAN9512 turns those bytes into Ethernet frames on the wire — and frames on the wire back into USB transfers.

This lesson covers how gabix configures that chip and moves frames through it. Every operation reuses the USB machinery from 7.04: register access is a USB control transfer, and frame I/O is a USB bulk transfer. There is no second driver to learn — only a new use for transfer().

One caveat up front. QEMU has no LAN9512, so gabix's QEMU port talks to an RNDIS Ethernet dongle instead. Both chips sit behind the same FrameDevice trait, so the whole network stack above (modules 5 and 6) is unchanged. That abstraction is the last section.

1. One chip, two functions, behind the USB port

The LAN9512 is a USB device. Electrically it hangs off the DWC2's port — the same port the handshake from 7.04 brought up. gabix enumerates it with the routine from 7.02, and it reports vendor 0x0424, product 0xec00 (the part on the Pi 2B). is_lan9512() matches that pair. Inside the chip are a two-port USB hub (so further devices could hang off it) and an Ethernet MAC and PHY. gabix uses only the Ethernet controller.

The ARM's view of the chip is two USB endpoints: a bulk IN and a bulk OUT, which configure_bulk_device() from 7.04 locates. There are no memory-mapped registers and no interrupt line to wire. Configuration and frame I/O both travel as USB transfers over those endpoints (plus a control endpoint for register access).

2. Registers over USB: the vendor request

The LAN9512 has dozens of internal registers — MAC control, hardware config, EEPROM access. The ARM reaches them not by load and store but by USB control transfers carrying vendor requests. read_register() issues a control READ (request type 0xc0, request READ_REGISTER = 0xa1) naming the register; the chip returns four bytes. write_register() issues a control WRITE (request type 0x40, request WRITE_REGISTER = 0xa0) carrying the four-byte value.

targets/armv7/src/raspi2b/lan9512.rs · register access over USB
unsafe fn read_register(host: &mut Dwc2, device: UsbDevice, register: u16) -> Option<u32> {
    let mut bytes = [0u8; 4];
    if host.control_read(device, 0xc0, READ_REGISTER, 0, register, &mut bytes)? != bytes.len() {
        return None;
    }
    Some(u32::from_le_bytes(bytes))
}

unsafe fn write_register(
    host: &mut Dwc2, device: UsbDevice, register: u16, value: u32,
) -> Option<()> {
    host.control_write(device, 0x40, WRITE_REGISTER, 0, register, &value.to_le_bytes())
}

"Write register HW_CFG" is therefore, on the USB wire, a SETUP+DATA+STATUS transaction — the same control-transfer shape as the GET_DESCRIPTOR from 7.02, addressed to a vendor register instead of a descriptor. The DWC2 performs it; the ARM only fills in the setup packet and reads the four bytes back.

3. Bring-up: reset, MAC, enable

configure() runs a fixed sequence of register writes that take the chip from reset to "transmit and receive enabled." In order: reset the MAC; read the factory MAC address out of the EEPROM; program it back into the address registers; set the hardware config (burst, offsets, flow control); then enable the MAC's transmitter and receiver and turn TX on. Each step is one write_register or read_register call — that is, one USB control transfer.

targets/armv7/src/raspi2b/lan9512.rs · configure, trimmed
write_register(&mut host, device, HW_CFG, HW_CFG_LRST)?;            // reset the MAC
wait_register_clear(&mut host, device, HW_CFG, HW_CFG_LRST)?;

let mac = read_mac_address(&mut host, device)                     // MAC from the EEPROM
    .filter(valid_mac_address)
    .unwrap_or([0x02, 0x47, 0x41, 0x42, 0x49, 0x58]);
write_register(&mut host, device, ADDRL, ...)?;                    // program the MAC low
write_register(&mut host, device, ADDRH, ...)?;                    // program the MAC high

let hardware = read_register(&mut host, device, HW_CFG)?;          // HW_CFG: bursts on, RX offset off
write_register(&mut host, device, HW_CFG, (hardware | HW_CFG_BIR) & !HW_CFG_RXDOFF)?;
write_register(&mut host, device, BURST_CAP, 0)?;
write_register(&mut host, device, AFC_CFG, AFC_CFG_DEFAULT)?;
write_register(&mut host, device, COE_CR, 0)?;

let mac_control = read_register(&mut host, device, MAC_CR)?;        // enable MAC: full duplex, TX, RX
write_register(&mut host, device, MAC_CR,
    mac_control | MAC_CR_FULL_DUPLEX | MAC_CR_TX_ENABLE | MAC_CR_RX_ENABLE)?;
write_register(&mut host, device, TX_CFG, TX_CFG_ON)?;               // transmit on

Read the sequence top to bottom. The reset write sets HW_CFG_LRST; wait_register_clear polls HW_CFG over USB until the chip clears that bit, which means reset finished. The MAC address comes out of the EEPROM one byte at a time through the E2P_CMD/E2P_DATA register pair (read_mac_address); if the EEPROM is absent or the address is the all-zero or broadcast default, gabix falls back to a fixed locally-administered address. The final two writes enable the MAC's transmitter and receiver and switch TX on — after which the chip will accept frames for sending and deliver received frames to the bulk IN endpoint.

4. Frames over bulk: TX and RX

Once configured, frames move over the two bulk endpoints. transmit() prefixes the Ethernet frame with an eight-byte smsc95xx header (a command/length word followed by a length word) and sends the whole thing with bulk_out. receive() pulls bytes with bulk_in, then read_rx_frame strips the four-byte RX status header and the four-byte trailing frame-check sequence and returns the frame. The header layout lives in crates/kernel-core/src/net/smsc95xx.rs, shared so the same framing parses on any target.

crates/kernel-core/src/net/smsc95xx.rs · TX header
let command_a = length as u32 | TX_FIRST_SEGMENT | TX_LAST_SEGMENT;
out[..4].copy_from_slice(&command_a.to_le_bytes());      // command + length
out[4..8].copy_from_slice(&(length as u32).to_le_bytes());  // frame length
out[TX_HEADER_LEN..total].copy_from_slice(frame);            // the Ethernet frame

USB bulk transfers carry a one-bit packet ID that toggles between DATA0 and DATA1 from packet to packet. update_pid() flips gabix's tx_pid/rx_pid when an odd number of packets crossed the endpoint, so the next transfer uses the opposite PID. A wrong PID makes the device reject every packet with a NAK, so this bookkeeping is not cosmetic.

targets/armv7/src/raspi2b/lan9512.rs · transmit / receive over bulk
fn transmit(&mut self, frame: &[u8]) {
    let mut bytes = [0u8; TX_HEADER_LEN + MAX_ETHERNET_FRAME_LEN];
    let Some(length) = write_tx_frame(frame, &mut bytes) else { return; };
    unsafe {
        if self.host.bulk_out(self.device, self.bulk_out_endpoint,
            self.bulk_max_packet, self.tx_pid, &bytes[..length]).is_some() {
            Self::update_pid(&mut self.tx_pid, length, self.bulk_max_packet as usize);
        }
    }
}

5. One trait, two chips

The network stack above this point (ARP, IP, UDP — modules 5 and 6) never names the LAN9512. It holds a FrameDevice: a trait with mac_address(), transmit(), and receive(). On the Pi, UsbEthernet::Lan9512 supplies it; in QEMU, UsbEthernet::Rndis supplies it. configure() picks which by reading the vendor and product ID from enumeration.

targets/armv7/src/raspi2b/ethernet.rs · dispatch by vendor/product ID
pub enum UsbEthernet { Lan9512(Lan9512Ethernet), Rndis(RndisEthernet) }

impl UsbEthernet {
    pub unsafe fn configure(host: Dwc2, device: UsbDevice) -> Option<Self> {
        if is_lan9512(device.vendor_id, device.product_id) {
            Lan9512Ethernet::configure(host, device).map(Self::Lan9512)
        } else if device.vendor_id == 0x0525 && device.product_id == 0xa4a2 {
            RndisEthernet::configure(host, device).map(Self::Rndis)
        } else { None }
    }
}

This is why the Pi port and the QEMU port share every line of the network code. The hardware-specific work — USB control transfers for registers, USB bulk transfers for frames, smsc95xx or RNDIS framing — lives below the trait. Above it, the ARP table, the IP route, and the UDP sockets are the same code on both machines.
