Lesson 17 · Phase 1 · real processes

A Real Process Table

Stop using tasks.len() as a process identifier. Pull process identity out of the scheduler into its own table with stable, monotonically-allocated PIDs.

Read time ~12 min Build time ~30–45 min Prereq fork + wait work (slices 4.4–4.5)

The kernel can already fork, exec, and wait. But it has no process table. It has a scheduler that doubles as one. This lesson pulls those two jobs apart — the first structural step toward a kernel where processes are first-class citizens rather than scheduler entries with extra fields bolted on.

Where we are in the process layer

syscalls (fork / exec / wait / exit) working, end-to-end
ProcessTable ← Lesson 17 stable PIDs, separate from the scheduler
Scheduler (run queue + context switch) already built; will hold Tasks, not processes
AddressSpace + frame allocator M2 — unchanged

The bug hiding in tasks.len()

Today, a task's identifier is assigned like this: 

let id = sched.tasks.len() as u64;

It works because the vector only ever grows. The first fork child is tasks[1], so its PID is 1. The next is tasks[2], PID 2. PIDs come out monotonic and unique — exactly the property you want.

It breaks the moment a task is removed. Suppose the parent reaps the child at index 1 and the slot is freed. The vector now has length 1. The next fork assigns id = 1 again. Two different processes, same PID, no way to tell them apart. Any code that stashed a PID (a wait queue, a parent pointer, a log line) is now lying.

The invariant a PID must hold

A PID is a name. Once a process has been assigned PID N, no other process may ever be seen as N until that process is gone and the name has been retired long enough that no live reference to it remains. Linux retires PIDs by rolling a 32-bit counter and wrapping only after millions of allocations. We will do the simpler thing: never recycle, ever.

Two jobs, one struct

Look at what Task currently carries: 

pub struct Task {
    pub id: u64,                       // identity
    pub name: &'static str,             // identity
    pub state: TaskState,               // scheduler
    pub context: TaskContext,           // scheduler
    pub stack_top: u64,                 // scheduler
    pub entry_fn: unsafe extern "C" fn(), // scheduler
    pub parent: Option<u64>,             // process tree
    pub children: Vec<u64>,             // process tree
    pub exit_status: Option<i64>,        // process tree
    pub address_space: AddressSpace,     // process memory
    pub syscall_stack_top: u64,         // scheduler
    pub fd_table: FdTable,              // process resources
}

Two unrelated concerns are tangled together. Scheduler fields exist to make switch() work — they describe how to resume a paused register state on a known stack. Process fields exist to answer questions like "who is my parent," "what memory do I own," "what files have I opened." Nothing about context-switching needs a parent pointer; nothing about wait needs a saved RSP.

Today — one struct

Task {
  // scheduler:   state, context,
  //              stack_top, entry_fn,
  //              syscall_stack_top
  // process:     id, name, parent,
  //              children, exit_status,
  //              address_space, fd_table
}

After Lesson 17 — two structs

Process {
  pid, parent, children,
  exit_status, name,
  address_space, fd_table,
}

Task {
  pid,            // back-ref
  state, context,
  kernel_stack, entry_stack,
  entry_fn,
}

The Task keeps a pid back-reference so the scheduler can ask "which process does this runnable thing belong to?" Everything else process-shaped moves into Process, owned by the new ProcessTable.

Linux parallel: Linux collapses both into one struct — struct task_struct — for cache-locality reasons. It can do that because it has a separate PID-allocator (alloc_pid() in kernel/fork.c) that hands out stable identifiers regardless of where the task lives in memory. We are splitting them because it makes the teaching clearer; once the model is solid you can collapse them back.

The shape of ProcessTable

Two storage shapes work. Pick one:

BTreeMap<Pid, Process>
Key/value lookup. Removing a process is one call. Slightly more allocation per insert. Best when PIDs will be sparse (long-lived kernel, lots of churn).
Vec<Option<Process>> indexed by PID
O(1) lookup by index. Wastes slots when PIDs are sparse, because we are choosing not to recycle IDs. Fine for a teaching kernel that will not live long enough to wrap a 32-bit counter. Recommended for mini-os.

Either way, the table owns three things: 

pub struct ProcessTable {
    next_pid: Pid,
    processes: Vec<Option<Process>>,
}

impl ProcessTable {
    fn allocate(&mut self, proc: Process) -> Pid {
        let pid = self.next_pid;
        self.next_pid = self.next_pid.checked_add(1)
            .expect("PID counter wrapped");
        if pid as usize >= self.processes.len() {
            self.processes.resize((pid as usize) + 1, None);
        }
        self.processes[pid as usize] = Some(proc);
        pid
    }

    fn get(&self, pid: Pid) -> Option<&Process> { ... }
    fn remove(&mut self, pid: Pid) -> Option<Process> { ... }
}

Note what is not here: no recycling, no free list, no "lowest available PID" search. The counter only goes up. A reaped slot becomes None permanently. This is the simplest shape that satisfies the PID invariant from the callout above.

The build — five small commits

1
New module src/process.rs. Define Pid (a #[derive(...)] wrapper around u64), Process, and ProcessTable. Add a lazy_static! static ref PROCESS_TABLE: Mutex<ProcessTable>. Allocate PID 0 for the kernel's first process at boot. Nothing reads it yet.
2
Move the process-shaped fields off Task. Trim Task to scheduler-only fields plus a pid: Pid back-reference. Update Task::new, init_main, spawn, and spawn_fork_child to construct a Process in the table and a Task pointing at it. Build will fail in many places — that is the point.
3
Re-point the accessors. current_pid(), with_current_fd_table, replace_current_address_space, wait_for_zombie_child, mark_current_zombie — each now resolves "current process" by reading the running Task's pid and looking it up in PROCESS_TABLE. Every lookup happens under without_interrupts.
4
Rename syscall_stack_top → entry_stack_top. It already serves both syscall entry and TSS.RSP0. The rename makes that dual role honest. Update yield_now, syscall::init, gdt::set_rsp0 callers.
5
Run the smoke tests. ./tests/test_fork_smoke.sh and ./tests/test_hello.sh must both still pass. Behaviour does not change in this lesson — only structure. If a test fails, the refactor crossed a boundary it should not have.
What this lesson does not do

No new syscalls. No wait-by-PID yet. No resource reclamation. No file descriptor inheritance. Those are Lessons 18 and 19. Lesson 17 only rearranges the furniture so the next lessons have somewhere to put their new state.

The win

After step 5, all of the following are true:

  • ProcessTable is the single source of truth for "does this PID exist, and whose child is it?"
  • Reaping a process sets its slot to None; a later fork gets a new, higher PID. No collision is possible.
  • The scheduler's Vec<Task> can shrink and reorder (Lesson 18 will need this) without invalidating any PID reference held anywhere else in the kernel.
  • current_pid() no longer reads sched.current — it reads the running task's pid field, which is stable across scheduler-vector mutations.

None of that is visible to a user program. It is all load-bearing for the next lesson, where wait(specific_child) and real reaping will need PIDs that survive their scheduler slot going away.

Primary source

Read the comment block above struct task_struct in Linux's include/linux/sched.h. It is the single best one-file summary of what a process is in a real kernel. Notice how Linux folds scheduler state, identity, memory, files, signals, and timers into the one struct — then notice how many of those are marked with separate locks. That is the same separation we are drawing here, expressed as fields-with-their-own-locks rather than separate structs.

For the PID-allocation question specifically, kernel/fork.c around the alloc_pid() call shows the recycling machinery we are deliberately not building.

Conceptually, OSTEP's Chapter 4 — "The Process" (free PDF) is the cleanest statement of the process abstraction itself: the "machine state" section is exactly the list of fields that belong on Process, not Task.

Probe — check the model before you build

A process opens a file, then forks. The child exits, and the parent reaps it. Later, the parent forks again. After this lesson, is the new child's PID 1, 2, or 3 — and which one of those is the right answer, and why?
