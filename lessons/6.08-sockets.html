Lesson 25 proved that mini-os can receive and return a UDP message. The kernel chose port 5555 with an if statement and echoed the bytes itself. Lesson 26 gives that endpoint to a ring-3 program. The kernel’s job becomes delivery: find the socket, queue the message, and wake its sleeping owner.

In this lesson, a datagram means one complete UDP message. It carries some bytes plus the addressing information needed to deliver them. UDP keeps each datagram separate, so one receive gets one message.

Why sockets exist

The word socket predates the programming interface. Early ARPANET documents used it for one named end of network communication: a host/process attachment identified by network addressing information. RFC 147 described communication as moving from one socket associated with a process on one host to another. The 1974 TCP specification made the address concrete as network identifier + TCP identifier + port, and described a connection as a pair of sockets. That lineage is visible in today’s local and remote endpoint tuples.

Berkeley’s 4.2BSD release turned the idea into the API shape used across Unix-like systems today. Its 1983 Interprocess Communication Primer presented sockets as a general facility for communication between processes. The API separated three concerns: create a communication object, give it an address, then transfer data through a descriptor. TCP/IP was one protocol family behind that interface; local Unix-domain communication could use the same API structure.

The useful definition for systems work

A socket is a kernel communication object that exposes one process-facing handle to a transport protocol. It stores the local communication state the protocol and application need: addresses, options, receive data, errors, and—depending on the transport—connection state.

The three arguments choose three different things

The call socket(domain, type, protocol) asks the kernel to compose an interface. Each argument answers one question.

Domain · how is an address written?

AF_INET selects IPv4 addresses and ports. AF_INET6 selects IPv6. AF_UNIX selects local kernel-managed names such as filesystem paths.

Type · what data contract is exposed?

SOCK_DGRAM exposes independent messages with boundaries. SOCK_STREAM exposes an ordered byte stream.

Protocol · who implements that contract?

IPPROTO_UDP implements IPv4/IPv6 datagrams. IPPROTO_TCP implements an Internet byte stream. A value of 0 asks for the domain/type default.

Result · how does the process refer to it?

The kernel installs the object in the process’s descriptor table and returns the lowest available FD.

IPv4 UDPsocket(AF_INET, SOCK_DGRAM, IPPROTO_UDP)
IPv4 TCPsocket(AF_INET, SOCK_STREAM, IPPROTO_TCP)
local streamsocket(AF_UNIX, SOCK_STREAM, 0)

Socket, endpoint, connection, and FD name different layers

Socket

The kernel object holding communication state and queues.

Endpoint

One addressable end. For UDP over IPv4: local IP address + local port.

Connection

Persistent communication state relating local and remote endpoints. TCP creates this state through its handshake.

File descriptor (FD)

A small process-local number, such as 3, that names the socket in the process’s FD table.

The program uses an FD to reach the socket

The program holds the number 3. The kernel holds the socket object. The process’s FD table connects them: fd 3 → UDP socket → receive queue.

The FD is the number passed into every socket call. The socket stores the network state and queued messages. fork or dup can give another FD access to the same socket.

socket(...)

Creates the kernel socket object. Returns an FD, such as 3.

bind(fd, address)

Gives the socket a local address, such as 10.0.2.15:5555. Returns success or an error.

recvfrom(fd, buffer)

Waits for one queued UDP message. Copies its bytes into buffer and returns the byte count plus the sender’s address.

sendto(fd, bytes, client)

Sends one UDP message from the socket to the chosen client. Returns the number of bytes sent or an error.

Here, a client is the other program that sends messages to the server. The client might run on another computer, or on the same computer.

Imagine a UDP server bound to port 5555. Client A and Client B can both send datagrams to it. recvfrom returns one message and the client that sent it. sendto chooses where the reply goes. One socket can talk to many clients.

Calling connect on a UDP socket records one client as its default destination. Outgoing messages go there by default, and the OS delivers only messages from that client to this socket. UDP still sends separate messages and performs no handshake. A TCP server follows bind → listen → accept; each accept creates a socket for one client.

Why sockets look like files—and where the analogy ends

Unix descriptor machinery gives sockets familiar lifetime and sharing operations: close, dup, inheritance across fork, blocking mode, and readiness monitoring. The descriptor table provides common process bookkeeping. The referenced object determines the operation’s meaning.

For a regular file, read consumes bytes at a stored file offset. UDP recvfrom consumes one queued message and reports its sender. TCP read consumes whichever stream bytes are currently available and preserves no application-message boundary. This distinction explains many production bugs: one TCP send does not promise one matching recv, while one UDP receive corresponds to at most one datagram.

Blocking is the original interface; readiness scales it

The classic call model lets recvfrom sleep until data arrives. Production servers frequently set sockets nonblocking and ask a readiness facility—select, poll, epoll, or kqueue—which descriptors can make progress. Async runtimes build task scheduling around the same kernel readiness and completion mechanisms. Lesson 26 implements blocking first because it exposes the queue, sleep, delivery, and wakeup machinery directly. Those mechanisms remain underneath a future readiness API.

How mini-os stores the relationship

socket() creates a communication endpoint and returns a File Descriptor (FD). The integer remains a per-process lookup key. Its table entry can refer to a regular file or a socket.

user fd 3small integer carried in bind(3, …), recvfrom(3, …), and sendto(3, …)
FD table[3]OpenObject::Socket(Arc<UdpSocket>)
UdpSocketbound local port + owned receive queue + waiting Process Identifiers (PIDs)
port table5555 → Weak<UdpSocket>, used by UDP receive demultiplexing

socket() creates an unbound object. bind() assigns its local endpoint. In this lesson the guest has one IP address, so binding port 5555 establishes 10.0.2.15:5555.

A server binds a known port so clients know where to send messages. A client often skips bind(); the kernel then chooses a temporary source port when the client sends its first message.

FD table owns access

Arc<UdpSocket> lets inherited or duplicated descriptors share one socket object.

Port table owns routing

A weak reference lets RX find the socket while the FD table controls its lifetime.

Socket owns messages

VecDeque<Datagram> preserves UDP message boundaries and arrival order; a waiter queue handles shared sockets safely.

Each datagram keeps its sender

Payload bytes stay with the source IP address and source port needed by recvfrom().

Four calls define the user-space loop

let fd = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);
bind(fd, UdpEndpoint { ip: OUR_IP, port: 5555 });

loop {
    let (count, client) = recvfrom(fd, &mut buffer);
    sendto(fd, &buffer[..count], client);
}

recvfrom() returns the next complete datagram and the sender’s address. sendto() names the destination for one outgoing datagram. The echo program can therefore return bytes to the exact source endpoint without knowing it beforehand.

A syscall ABI change is part of this lesson

The current mini-os dispatcher carries three syscall arguments. Standard sendto and recvfrom need more. Step 26.2 extends syscall entry to preserve arguments 4–6 in registers r10, r8, and r9, then validates every user buffer and address structure before dereferencing it.

Socket journey · stage 1 of 8

1 · User space creates fd 3

socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP) allocates a kernel UdpSocket and installs an Arc in the current process’s lowest free FD slot.

2 · User space binds port 5555

bind(3, 10.0.2.15:5555) checks that the port is free, records the local endpoint, and adds a weak socket reference to the global port table.

3 · recvfrom finds an empty queue

The syscall resolves fd 3 to the socket. No datagram is queued, so it records the current Process Identifier (PID) as a waiter and marks the task Blocked.

4 · The scheduler runs the network worker

The blocked echo server leaves the CPU. A small kernel task continues polling virtio-net and yields whenever no frame is ready.

5 · UDP selects the bound socket

A host datagram reaches protocol 17 with destination port 5555. The port table upgrades its weak reference and finds the socket.

6 · Delivery enqueues and wakes

The kernel copies the payload and sender endpoint into one owned Datagram, pushes it onto the socket queue, and marks the waiting PID Ready.

7 · recvfrom returns to ring 3

The scheduler resumes the same paused syscall. It pops exactly one datagram, copies its bytes and source endpoint into validated user buffers, and returns the payload length.

8 · sendto returns the message

The user program supplies the source endpoint from stage 7 as its destination. UDP, IPv4, Ethernet, and virtio-net carry the reply back to the Mac socket.

Blocking needs a network worker

Lesson 25’s syscall spins inside device.poll_rx(), so the calling process stays in the kernel until a packet arrives. A blocking socket should release the CPU. mini-os already has TaskState::Blocked, but a blocked process cannot poll its own packet into existence.

echo server: recvfrom → queue empty → register waiter → Blocked → yield kernel net task: poll RX → UDP parse → port lookup → enqueue → wake PID → yield echo server: Ready → resume recvfrom → dequeue → copy to user → return

The network worker is the active half of this design. It polls the existing virtio receive queue while applications sleep. Interrupt-driven receive remains a later optimization; the socket contract and wake path stay the same.

check queue + register waiter + mark Blocked must be one atomic decision

This rule prevents a lost wakeup. If a packet could arrive after the empty check and before waiter registration, the queue would contain data while the process slept forever. On mini-os’s single CPU, disabling interrupts around that short transition prevents the network worker or timer from observing a half-finished state.

Each queue entry owns one payload and one source endpoint. If the user buffer is smaller than the first payload, Lesson 26 follows datagram semantics: copy the available prefix, discard the remainder of that datagram, and move to the next queue entry on the next call.
