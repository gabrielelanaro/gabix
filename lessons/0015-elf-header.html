ELF Header Parser

Read an ELF (Executable and Linkable Format) file from disk through VFS. Parse its 64-byte header and 56-byte program headers. Next lesson, map its PT_LOAD segments and exec().

Read time ~25 min Build time ~30–45 min Prereq Lesson 14

Lesson 14 ended with the kernel reading a file from disk via VFS. The file's bytes came back as a Vec<u8>. Lesson 15 asks the next question: what bytes? A user program is a file. To execute it, the kernel has to know how that file is laid out — where the code lives, where to put it in memory, where execution starts. On Linux, that layout is ELF.

What ELF is

ELF (Executable and Linkable Format) is a file format for binaries. The kernel uses it for one specific job: knowing which bytes from the file go where in memory when running a program.

The same container holds four kinds of artifact. The e_type field in the header says which:

  • Relocatable object files (.o): compiler output before linking. Contains code and data but no fixed addresses — the linker stitches many of these together into an executable.
  • Executables: a finished program, ready to run. Has fixed virtual addresses. This is what exec() loads.
  • Shared libraries (.so): code that multiple processes map into their address space at runtime. Same format, just consumed differently.
  • Core dumps: a snapshot of a crashed process's memory, saved for debugging. Same container so the same tools can introspect it.

ELF's design goal: a binary should describe how to load itself. The kernel reads the header, finds the program headers (a table of segments — contiguous byte ranges that go into memory), and for each loadable segment it copies bytes from p_offset in the file to p_vaddr in memory. Then it jumps to e_entry. That's exec() in three sentences.

Segments vs sections. Two different ways to slice the same file. Segments are for the loader — "what bytes go into memory." Sections are for the linker and debugger — finer-grained regions like .text (code), .data (initialized globals), .rodata (read-only constants), .bss (zero-initialized globals — takes no file space, just a memory-size hint). The kernel reads segments; it ignores sections entirely.
Linux counterpart: the kernel's ELF loader lives in fs/binfmt_elf.c. It opens the file via VFS (the same path we just built), reads the header, validates the magic, walks the program headers, and maps each PT_LOAD segment into the new process's address space. Our Lesson 15 + 16 mirrors this path, just smaller.

The diagram shows the load-bearing pieces. Real binaries have more program headers (notes, GNU property, GNU stack — Lesson 16 ignores those). The kernel's exec() reads the header, walks the PHT (Program Header Table), and for each PT_LOAD entry: allocates frames, copies p_filesz bytes from p_offset to p_vaddr, zeros the rest if p_memsz > p_filesz (that's how .bss works), then jumps to e_entry.

The 56-byte program header

Each entry in the program header table describes one segment. For Lesson 15, the load-bearing fields are p_type (is this loadable?), p_offset (where in the file), p_vaddr (where in memory), p_filesz and p_memsz (how much to copy, how much to zero).

The four load-bearing facts

Magic

First 4 bytes must be 0x7F 'E' 'L' 'F'. Otherwise the file isn't ELF.

Class & data

class=2 (64-bit) and data=1 (little-endian) — x86-64 binaries.

Entry point

e_entry is the virtual address to jump to after loading.

Segments

e_phoff + e_phnum + e_phentsize locate the program headers. Each PT_LOAD becomes a mapped region.

15.1Put a hello.elf on the disk image

Update scripts/make-disk.sh to cross-compile a tiny x86-64 ELF and write it to the ext2 filesystem. The binary doesn't need to do anything useful — we're parsing its header, not running it yet (that's Lesson 16). 

# Lesson 15: cross-compile a tiny x86-64 ELF and add it to the disk.
HELLO_ELF_SRC=$(mktemp /tmp/mini-os-hello-user.XXXXXX.rs)
cat > "$HELLO_ELF_SRC" <<'EOF'
#![no_std]
#![no_main]
#[no_mangle]
pub extern "C" fn _start() -> ! { loop {} }
#[panic_handler] fn panic(_: &core::panic::PanicInfo) -> ! { loop {} }
EOF

HELLO_ELF=$(mktemp /tmp/mini-os-hello-user.XXXXXX.elf)

# Two flags matter:
#   --target x86_64-unknown-none  → bare-metal ELF, no host OS ABI
#   -C relocation-model=static    → ET_EXEC (fixed addresses), not PIE
# Without -C relocation-model=static rustc emits ET_DYN, which would
# force us to handle dynamic relocations in Lesson 16. We skip that.
rustc --target x86_64-unknown-none --edition 2021 \
      -C relocation-model=static \
      -o "$HELLO_ELF" "$HELLO_ELF_SRC"

# Verify it's a real ELF.
file "$HELLO_ELF"   # → ELF 64-bit LSB executable, x86-64

# Write into ext2 via debugfs, same pattern as hello.txt.
printf 'write %s /hello.elf\nquit\n' "$HELLO_ELF" \
    | "$DEBUGFS" -w "$DISK_IMG"
rm -f "$HELLO_ELF_SRC" "$HELLO_ELF"
Prerequisite

x86_64-unknown-none Rust target must be installed: rustup target add x86_64-unknown-none. The make-disk script should check for it and error out with a clear message if missing.

Run ./scripts/make-disk.sh to rebuild the image. file disk.img won't help (it's a filesystem, not an ELF); instead, use debugfs -R "ls /" disk.img to confirm hello.elf appears alongside hello.txt.

15.2ElfHeader struct + parse + validate

Create src/elf.rs. Define an ElfHeader struct holding the load-bearing fields. Parse from &[u8] with from_le_bytes at fixed offsets. 

// src/elf.rs — Lesson 15
use alloc::string::String;

pub const ELF_MAGIC: [u8; 4] = [0x7F, 0x45, 0x4C, 0x46]; // 0x7F 'E' 'L' 'F'
pub const ELFCLASS64: u8 = 2;
pub const ELFDATA2LSB: u8 = 1; // little-endian
pub const ET_EXEC:  u16 = 2;
pub const EM_X86_64: u16 = 0x3E;

pub struct ElfHeader {
    pub class: u8,         // must be ELFCLASS64
    pub data: u8,          // must be ELFDATA2LSB
    pub osabi: u8,
    pub e_type: u16,       // must be ET_EXEC
    pub machine: u16,      // must be EM_X86_64
    pub entry: u64,         // e_entry — the kernel's jump target
    pub phoff: u64,         // file offset of program header table
    pub shoff: u64,         // ignored at load time
    pub flags: u32,
    pub ehsize: u16,
    pub phentsize: u16,    // should be 56
    pub phnum: u16,         // number of program headers
    pub shentsize: u16,
    pub shnum: u16,
    pub shstrndx: u16,
}

impl ElfHeader {
    pub fn parse(bytes: &[u8]) -> Option<Self> {
        if bytes.len() < 64 { return None; }
        if &bytes[0..4] != ELF_MAGIC { return None; }

        let u16_at = |off: usize| u16::from_le_bytes(bytes[off..off+2].try_into().ok()?);
        let u32_at = |off: usize| u32::from_le_bytes(bytes[off..off+4].try_into().ok()?);
        let u64_at = |off: usize| u64::from_le_bytes(bytes[off..off+8].try_into().ok()?);

        Some(Self {
            class:      bytes[4],
            data:       bytes[5],
            osabi:      bytes[7],
            e_type:     u16_at(0x10),
            machine:    u16_at(0x12),
            entry:      u64_at(0x18),
            phoff:      u64_at(0x20),
            shoff:      u64_at(0x28),
            flags:      u32_at(0x30),
            ehsize:     u16_at(0x34),
            phentsize:  u16_at(0x36),
            phnum:      u16_at(0x38),
            shentsize:  u16_at(0x3A),
            shnum:      u16_at(0x3C),
            shstrndx:   u16_at(0x3E),
        })
    }

    pub fn is_x86_64_exec(&self) -> bool {
        self.class == ELFCLASS64
            && self.data == ELFDATA2LSB
            && self.e_type == ET_EXEC
            && self.machine == EM_X86_64
    }
}

Don't forget to declare mod elf; in src/main.rs and extern crate alloc; at the top of elf.rs if you use String / Vec.

15.3ProgramHeader struct + parse

Same file src/elf.rs. Add the program-header struct and constants for the p_type values we recognize. 

pub const PT_LOAD:  u32 = 1;
pub const PT_DYNAMIC: u32 = 2;
pub const PT_INTERP:  u32 = 3;
pub const PT_NOTE:    u32 = 4;
pub const PT_PHDR:     u32 = 6;

pub const PF_X: u32 = 0x1; // execute
pub const PF_W: u32 = 0x2; // write
pub const PF_R: u32 = 0x4; // read

pub struct ProgramHeader {
    pub p_type:   u32,
    pub p_flags:  u32,
    pub p_offset: u64,
    pub p_vaddr:  u64,
    pub p_paddr:  u64,  // ignored
    pub p_filesz: u64,
    pub p_memsz:  u64,
    pub p_align:  u64,
}

impl ProgramHeader {
    pub fn parse(bytes: &[u8]) -> Option<Self> {
        if bytes.len() < 56 { return None; }
        let u32_at = |off: usize| u32::from_le_bytes(bytes[off..off+4].try_into().ok()?);
        let u64_at = |off: usize| u64::from_le_bytes(bytes[off..off+8].try_into().ok()?);

        Some(Self {
            p_type:   u32_at(0x00),
            p_flags:  u32_at(0x04),
            p_offset: u64_at(0x08),
            p_vaddr:  u64_at(0x10),
            p_paddr:  u64_at(0x18),
            p_filesz: u64_at(0x20),
            p_memsz:  u64_at(0x28),
            p_align:  u64_at(0x30),
        })
    }

    pub fn is_load(&self) -> bool { self.p_type == PT_LOAD }

    pub fn perms_str(&self) -> &'static str {
        let r = self.p_flags & PF_R != 0;
        let w = self.p_flags & PF_W != 0;
        let x = self.p_flags & PF_X != 0;
        match (r, w, x) {
            (false, false, false) => "---",
            (false, false, true ) => "--x",
            (false, true,  false) => "-w-",
            (false, true,  true ) => "-wx",
            (true,  false, false) => "r--",
            (true,  false, true ) => "r-x",
            (true,  true,  false) => "rw-",
            (true,  true,  true ) => "rwx",
        }
    }
}
15.4Read ELF via VFS, parse, validate, print

In src/main.rs, after the Lesson 14 mount block, add a Lesson 15 verification block. The bytes come from VFS — the ELF parser doesn't know or care that they came from ext2 over virtio-blk. 

println!("[test] ELF header parser (15.1-15.4)");
{
    let elf_inode = fs::resolve_path("/hello.elf")
        .expect("hello.elf should resolve");
    let bytes = elf_inode.data.lock();

    println!("[elf] /hello.elf: {} bytes", bytes.len());

    let header = elf::ElfHeader::parse(&bytes)
        .expect("ELF header parse failed");

    // Validate
    assert!(header.is_x86_64_exec(),
        "not an x86-64 ET_EXEC ELF");
    assert_eq!(header.phentsize, 56, "expected 56-byte program headers");

    // Print
    println!("[elf]   e_type   = {} (ET_EXEC)", header.e_type);
    println!("[elf]   machine  = 0x{:X} (x86-64)", header.machine);
    println!("[elf]   entry    = 0x{:X}", header.entry);
    println!("[elf]   phoff    = {}", header.phoff);
    println!("[elf]   phnum    = {}", header.phnum);

    // Walk program headers
    let mut loadable = 0;
    for i in 0..header.phnum {
        let off = header.phoff as usize + i as usize * header.phentsize as usize;
        let ph = elf::ProgramHeader::parse(&bytes[off..])
            .expect("program header parse failed");

        let kind = if ph.is_load() { "LOAD" } else { "    " };
        println!(
            "[elf]   [{}] {} off=0x{:X} vaddr=0x{:X} filesz={} memsz={} {}",
            i, kind, ph.p_offset, ph.p_vaddr, ph.p_filesz, ph.p_memsz, ph.perms_str()
        );
        if ph.is_load() { loadable += 1; }
    }

    println!("[elf] {} loadable segments (Lesson 16 will map these)", loadable);
    println!("[elf] *** ELF header parsed — ready for exec() ***");
}

The exact numbers will differ — rustc version and optimization level change sizes. What matters: e_type = 2, machine = 0x3E, at least one LOAD segment, entry inside one of the loadable ranges.

Primary source

The ELF format is specified in the System V ABI Generic Introduction (the "gABI"). A more readable walkthrough is the elf(5) man page, which documents both Elf64_Ehdr and Elf64_Phdr with field-by-field comments.

The Linux counterpart of our parser is fs/binfmt_elf.c, specifically load_elf_binary() (~300 lines, very dense). It does what we do — read header, walk program headers, map PT_LOAD segments — plus dynamic linking, BPF annotations, and credential handling.

A nice companion: run readelf -l hello.elf on the cross-compiled binary. The output is the same program-header table the kernel parses, formatted for humans.
