The DWC2 host controller

The chip on the Pi that drives the USB wire — and the four registers the ARM fills in to make it send a transfer.

The ARM has no USB pins of its own. It cannot put a SETUP token on the USB wire, read a device's descriptors, or assign that device an address. On the Pi 2B a controller called the DWC2 does all of that — it is built into the Pi's main chip (the BCM2836). In USB terms this role is "the host". This lesson explains that controller: how one transfer turns into four register writes, how the controller moves the bytes itself, and why the result comes back through a poll rather than an interrupt.

Every desktop PC has the equivalent: its own host-controller chip — the xHCI, eXtensible Host Controller Interface — reached through the PCI bus. The names and the register layouts differ; the arrangement is the same. The CPU cannot drive USB pins directly, so it programs a controller that can, and that controller performs each transfer on the wire using its own access to memory (called DMA — defined in section 4). The DWC2 is the Pi's instance of that arrangement.

1. The controller drives the wire; the ARM decides what to send

The DWC2's registers occupy a block of memory addresses starting at 0x3f98_0000. The ARM reaches them by ordinary load and store instructions — memory-mapped I/O, the same mechanism as the mailbox registers in lesson 7.03 and the interrupt controller in 7.01. The split of labor between the two is fixed: the ARM decides which transfer (which device, which endpoint, how many bytes, in or out); the DWC2 performs that transfer electrically on the USB cable.

A host controller is the chip (or the reusable hardware block, an "IP block") that drives a bus the CPU cannot drive itself. The DWC2 is Synopsys's DesignWare USB 2.0 host controller IP block, embedded inside the BCM2836. The CPU programs it; it owns the USB port.

2. A channel: four registers that describe one transfer

The DWC2 exposes host channels. A channel is a set of four registers that together describe one transfer to one endpoint (the endpoint is the device-side target from lesson 7.02). gabix uses a single channel — channel 0 — and runs one transfer at a time. The four registers of a channel are:

  • HCCHAR (channel characteristics) — the target: the device's address, the endpoint number, the direction (in or out), the endpoint type (control or bulk), the max packet size, and a single ENABLE bit.
  • HCTSIZ (transfer size) — the payload: how many bytes to move, how many packets that is, and the PID (the SETUP or DATA1 tag from lesson 7.02's control transfer).
  • HCDMA (DMA address) — where the buffer lives in memory, given as a bus address.
  • HCINT (interrupt status) — the result: TRANSFER_COMPLETE, NAK (the device was not ready), STALL (the device refused), or an error.

The first three registers describe the transfer. Setting the ENABLE bit in HCCHAR starts it.

3. The transfer, end to end

The transfer() function in usb.rs fills those four registers, sets ENABLE, and waits for the result. Trimmed to the essential writes:

targets/armv7/src/raspi2b/usb.rs · transfer, trimmed
write32(CHANNEL_BASE + HCINT, u32::MAX);            // clear old completion flags
write32(CHANNEL_BASE + HCDMA, dma_address(buffer)); // the buffer's BUS address (section 4)
write32(CHANNEL_BASE + HCTSIZ,                      // how much to move
    length as u32 | (packet_count as u32) << 19 | pid << 29);
write32(CHANNEL_BASE + HCCHAR,                      // the target, then GO
    CHANNEL_ENABLE | (address as u32) << 22 | endpoint_type
    | (endpoint as u32) << 11 | max_packet_size as u32);

wait_until(|| read32(CHANNEL_BASE + HCINT) & DONE != 0)?; // poll until it finishes
let interrupt = read32(CHANNEL_BASE + HCINT);
if interrupt & (STALL | ERRORS) != 0 || interrupt & TRANSFER_COMPLETE == 0 {
    return None;                                           // device refused or errored
}
let remaining = read32(CHANNEL_BASE + HCTSIZ) & 0x7ffff;  // bytes not moved
Some(length.saturating_sub(remaining))

When a bit appears, the ARM reads HCINT to see which one. TRANSFER_COMPLETE means the transfer moved bytes; the ARM reads HCTSIZ again to learn how many bytes remain, in case the device sent a short packet (fewer bytes than requested). NAK means the device was not ready; the full driver loops and retries. STALL or an error bit means the transfer failed. (This listing drops the NAK-retry loop and the outer retry limit for brevity; the real transfer() has both.)

4. DMA: the controller moves the bytes itself

The ARM writes the buffer's address into HCDMA, and the DWC2 fetches or stores the bytes itself — so the CPU never copies USB data through a register. That is DMA — Direct Memory Access, a controller that reads and writes memory on its own, without the CPU moving each byte. For an OUT transfer the DWC2 reads the SETUP or DATA buffer and sends it down the wire; for an IN transfer it writes the received bytes into the buffer for the ARM to read afterward.

This is the same bus-address problem from lesson 7.03. The CPU reaches the buffer at one address; the DWC2's DMA engine reaches memory over its own bus (the AHB, ARM's AMBA High-performance Bus, the DWC2's path to main memory), at a different address. gabix converts the pointer with a mask and a fixed offset:

targets/armv7/src/raspi2b/usb.rs · dma_address
fn dma_address(buffer: *const u8) -> u32 {
    (buffer as u32 & 0x3fff_ffff) | 0xc000_0000   // CPU address → BUS address
}

The low 30 bits are identical — only the top two bits change, set to 11 (the 0xc000_0000 bus alias). CPU and DWC2 reach the same bytes; the addresses differ because each reaches memory over a different bus.

Because DMA bypasses the CPU, the buffers must be aligned to a cache line: the 64-byte-aligned DmaBuffer that holds the SETUP packet and the DATA region. The alignment keeps each transfer buffer inside one cache line. On the Pi the DWC2's DMA bypasses the CPU cache, so a buffer must not straddle two lines or share one with unrelated data — a single cache line is the granularity at which cached and uncached memory diverge.

5. Initialization: power, reset, the port handshake

Before any transfer, the controller must be initialized. initialize() does, in order:

  1. Power it on — through the property mailbox from lesson 7.03 (mailbox::power_on_usb()). The ARM cannot do this by itself; that was the point of the mailbox lesson.
  2. Configure the physical interface — the PHY, the analog circuit that puts bits onto the USB pins — for the Pi's wiring, and force the controller into host mode rather than device mode.
  3. Soft-reset the core and reset its internal FIFOs (the small on-chip buffers the controller uses for packet data).
  4. Enable its DMA access to main memory.
  5. The port handshake — the part that initializes the device that was just plugged in.

The port handshake is where the host initializes a device electrically. The ARM powers the port (turns on the socket's power), waits, then sets the PORT_RESET bit for 50 milliseconds. PORT_RESET drives the USB reset signal (SE0 — both data lines held low), which forces the device to reset and re-initialize. The ARM clears the reset bit and waits for PORT_ENABLE: the device has come back up and is ready. The enumeration that follows — GET_DESCRIPTOR, SET_ADDRESS, GET_DESCRIPTOR again — is exactly the sequence from lesson 7.02, and every step of it is one call to transfer().

The four panels above are electrical bring-up — no packet has crossed the wire yet. The enumeration that follows (GET_DESCRIPTOR, SET_ADDRESS, GET_DESCRIPTOR again, from lesson 7.02) sits on top of this foundation, and every request in it is one call to transfer() — the four-register write sequence from section 3.

targets/armv7/src/raspi2b/usb.rs · initialize, the port handshake
write32(HPRT, port_value() | PORT_POWER);                       // turn the port on
delay_us(100_000);
write32(HPRT, port_value() | PORT_POWER | PORT_RESET);          // hold reset (SE0)
delay_us(50_000);
write32(HPRT, port_value() & !PORT_RESET | PORT_POWER);         // release reset
wait_until(|| read32(HPRT) & PORT_ENABLE != 0)?;                // device came back up

6. Why it polls, again

The DWC2 can raise an interrupt when a channel completes. gabix spin-polls HCINT in a bounded loop instead of wiring the channel-completion interrupt — the same poll-everything pattern as the mailbox, the SD card, and the timer. For a controller that runs one transfer at a time on a kernel that has no other work yet, polling is enough. Wiring the completion interrupt is the same unfinished piece carried over from lessons 7.01 and 7.02; it returns in the next lessons, when the LAN9512 — the chip that adds a USB hub and an Ethernet controller to the Pi — moves real Ethernet traffic over the USB port.
