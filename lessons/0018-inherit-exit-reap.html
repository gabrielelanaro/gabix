Lesson 18 · Phase 1 · process lifecycle

Inherit, exit, reap

Three lifecycle transitions, three resource consequences. Fork gives the child the parent's open files. Exit releases them. Wait retires the PID — and now waits for a specific child.

Read time ~12 min Build time ~40–60 min Prereq Lesson 17 (ProcessTable with stable PIDs)

The kernel can fork, exec, wait, and exit — and the transitions between those states leak. A fork child starts with an empty file descriptor table, so it loses every file the parent had open. An exit leaves the file descriptors sitting in the ProcessTable until the parent reaps, so an orphaned process leaks its files forever. A wait reaps any child, never the specific one the parent asked for. This lesson closes all three gaps.

The lifecycle, three transitions

A process moves through four states. Three transitions connect them, and each transition moves a different kind of resource.

   not yet runnable)      being scheduled)         exit_status set)        PID retired)

Three resources, three release points. Mixing them — releasing FDs at reap instead of at exit, or retiring the PID at exit instead of at wait — breaks a property the system depends on. The next three sections take each transition in turn.

Fork inherits — POSIX semantics

When a process forks, the child must see the same open files the parent had. POSIX (Portable Operating System Interface, the IEEE standard that Unix-like systems follow) specifies: the child's FD numbers match the parent's, and each FD in the child points to the same open file description — same cursor, same inode. This is the property that makes shell pipelines work. The parent opens a pipe on fd=3, forks, the child inherits fd=3 and reads from it; the bytes flow through the one shared open file.

In our types this is one Arc<File> clone per slot. The File (cursor + inode reference) is shared; the FdTable (the integer→File map) is copied. The Arc refcount goes from 1 to 2. A separate open() of the same inode by a different process produces an independent File with its own cursor — the Arc is the dividing line. 

  Parent fd_table                 Child fd_table (after fork)
  ┌──────────┐                    ┌──────────┐
  │ fd=3 ────┼──→ Arc<File> ◀──────┤ fd=3   shared cursor, shared inode
  │ fd=4 ────┼──→ Arc<File> ◀──────┤ fd=4   shared cursor, shared inode
  │ fd=5     │ (empty)             │ fd=5     │ (empty — both see the same hole)
  └──────────┘                    └──────────┘

  Two separate open()s of /hello.txt would produce TWO Arc<File>s
  (independent cursors). fork() and dup() produce ONE Arc<File> seen
  through two table entries (shared cursor). The Arc is the unit of sharing.
Linux parallel: dup_fd() in kernel/fork.c is the function that copies the parent's files_struct into the child. It clones each file pointer (bumping f_count) and copies the FD bitmap. Our FdTable::clone_shallow is the same operation with Arc standing in for the atomic refcount.

Exit closes — release at the right moment

When a process calls sys_exit, it enters the zombie state. A zombie keeps three things: its PID, its parent PID, and its exit status. Those stay so the parent's wait can read them. Everything else is gone — the FD table, the address space contents, the register frame.

Today, sys_exit calls mark_current_zombie, which sets the state and the exit status and yields. The Process in the table still holds its fd_table. The FDs only get released when the parent reaps — wait_for_zombie_child calls table.remove(child_pid), the Process drops, the fd_table drops, the Arc<File> refcounts fall. If the parent never reaps — a buggy parent, or an orphan whose original parent died before waiting — the FDs leak. The file stays "open" forever, its inode pinned alive.

The fix is to close the FDs at exit, at the moment the process stops using them. mark_current_zombie swaps the zombie's fd_table for an empty one before it yields. The old table drops in scope; the Arc<File> refcounts fall; files with no remaining references get freed. The zombie keeps its PID and exit status for the parent. It carries no file resources.

Before exit (Running)

Process {
  pid: 7,
  parent: 2,
  exit_status: None,
  fd_table: [fd3, fd4],   ← held
  address_space: ,  ← held (leaks on exit,
                             deferred to a later slice)
}

After exit (Zombie)

Process {
  pid: 7,                ← kept for wait
  parent: 2,              ← kept for wait
  exit_status: Some(42),  ← kept for wait
  fd_table: [],           ← released
  address_space: ,  ← still leaks (deferred)
}

The address space also leaks, on purpose for this lesson. Releasing it requires unmapping every user page and recursively freeing the PML4 (Page Map Level 4), PDPT, PD, PT (Page Table) frames — a real page-table walk. That cleanup is bigger than this lesson and deserves its own slice. FDs close here because their lifecycle matches exit: a process that has exited will never read or write another file.

Wait reaps — and now by PID

sys_wait today takes one argument — a user pointer to write the exit status into — and reaps whichever zombie child it finds first. A parent with three children cannot wait for a specific one. It gets whichever one happened to die first.

Linux's wait4(pid, wstatus, options, rusage) takes a pid argument that selects the target:

pid argumentMeaningMini-os
pid > 0wait for that specific childimplemented this lesson
pid == -1wait for any childalready works (current behavior, kept as default)
pid == 0wait for any child in the same process groupout of scope — no process groups exist yet
pid < -1wait for any child in process group |pid|out of scope

We add the pid argument to sys_wait and a WaitTarget enum (Any or Specific(Pid)) to wait_for_zombie_child. The reap itself — table.remove, child Task marked Dead — already works from Lesson 17. This lesson only changes the selection of which zombie to reap.

Linux parallel: do_waitpid() in kernel/exit.c branches on the pid argument the same way. release_task() in the same file is the actual reap — it removes the task from all the lists and frees the task_struct. Our table.remove is the slot-indexed analog.

The build — four commits

1
New method FdTable::clone_shallow in src/fs.rs. Iterates self.table, clones each Option<Arc<File>> into a fresh Vec, returns a new FdTable sharing every File the parent had open with matching FD numbers. Pure addition — no syscall, no behavior change, nothing calls it yet.
2
FD inheritance in spawn_fork_child (src/task.rs). Read the parent's fd_table out of PROCESS_TABLE (under the existing lock, before allocating the child), call clone_shallow, pass the result to Process::new instead of FdTable::new(). The comment that said "Lesson 5 will inherit" comes true. The existing fork_smoke test must still pass.
3
Close FDs at exit in mark_current_zombie (src/task.rs). After setting exit_status, swap proc.fd_table for FdTable::new() and drop the old one in scope. Add a log line counting how many FDs were closed. A zombie carries PID + parent + exit status; it carries no file resources.
4
wait(pid, status_ptr) — extend sys_wait (src/syscall.rs) and wait_for_zombie_child (src/task.rs). Add a WaitTarget enum (Any / Specific(Pid)). sys_wait reads arg1 as the target pid (positive = specific, -1 / u64::MAX = any) and shifts the status pointer to arg2. The WouldBlock arm now blocks if the specific child is still alive, even when other children are zombies. Update the fork smoke test (or add a new test_inherit.sh) to wait for a child by PID and read its exit code.
What this lesson does not do

Address-space teardown at exit — the PML4 and user pages leak. Real Linux does this in exit_mm() in kernel/exit.c; we defer it to its own memory-cleanup slice. Dead Task removal from the scheduler's Vec<Box<Task>> — Dead tasks stay in the vector, skipped by the run-queue scan. Removing them shifts indices and requires fixing sched.current; deferred to a scheduler-cleanup slice. SIGCHLD — the parent still blocks inside sys_wait and gets woken by mark_current_zombie's parent-wake path. Asynchronous signal delivery is a separate lesson.

The win

After step 4, all of the following are true:

  • A forked child inherits the parent's open files. Shell-style FD plumbing works: parent opens a file, forks, child reads from the inherited fd and sees the same cursor the parent left.
  • A process that exits releases its files immediately, at the moment it stops using them — not when the parent gets around to reaping. An orphan releases its FDs on the exit path.
  • A parent can wait for a specific child by PID, reading that child's exit code. wait(-1) still reaps any child.

Together, the three transitions now move the right resources at the right moment. The process layer has a real lifecycle, where every resource acquired at fork is released at exactly one later point.

Primary source

Read dup_fd() in kernel/fork.c for the FD-inheritance machinery — it is the cleanest statement of "clone each file pointer, bump the refcount, copy the FD bitmap" in the kernel. Then read do_exit() and release_task() in kernel/exit.c for the symmetric teardown: do_exit calls exit_files() to close FDs at exit (the point this lesson makes), and release_task is the actual reap that frees the task_struct once the parent has read the exit status. The separation between those two functions is exactly the separation between this lesson's step 3 (close at exit) and step 4 (reap at wait).

For the conceptual framing of the process lifecycle, OSTEP's Chapter 5 — "Interlude: Process API" (free PDF) covers fork, wait, and exec as the three primitives and walks through why a parent waits on a specific child.

Probe — check the model before you build

A parent opens /hello.txt on fd=3, reads 5 bytes, then forks. The child reads 5 bytes from fd=3, then exits. The parent returns from wait and reads 5 more bytes from fd=3. How many bytes has the parent read in total — 5, 10, or 15 — and which one is right, and why?

What this unlocks

A real shell (the Phase 1 endpoint) can now fork, let the child inherit stdin/stdout, and wait for that specific child to finish before prompting again. The next Phase 1 item — signal delivery (SIGCHLD when a child exits) — builds on the parent-wake path this lesson keeps intact.
