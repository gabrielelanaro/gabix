2. Two processors run two programs

The Pi’s CPU runs our Rust kernel. A small processor inside the dongle runs Realtek’s firmware.

We obtained the firmware from OpenBSD’s firmware package. Rust copies it into the dongle during initialization. The dongle also contains hardware that handles the radio signals and packet encryption.

WhereWhat happens in this setup
Rust on the PiSelects the network, performs the WPA2 exchange, supplies encryption keys, runs DHCP, and retries a lost connection.
Firmware in the dongleRuns the vendor’s internal control program. Our driver sends it commands such as registering a station and its transmission rates.
Hardware in the dongleSends and receives radio signals; encrypts and decrypts packet data using installed keys.

What can we actually know about the firmware?

We have a compiled binary. We can inspect the commands our driver sends and the results it reads. We have not inspected the firmware’s internal program, so the lesson does not assign every timing or radio operation to that program.

The exact file we loaded is urtwn-rtl8192cfwT. OpenBSD’s urtwn manual documents the adapter family and its need for firmware. Our setup notes record the tested file’s checksum.

3. Follow one message

Suppose the Pi replies to the Mac’s request for its status. The Wi-Fi connection and IP address are already ready.

Rust builds the reply → USB carries its bytes → Dongle encrypts + transmits → Router forwards to Mac

A frame is a packet formatted for the Wi-Fi link. Rust puts the reply into a frame, then places a small set of device instructions in front of it. Those instructions specify the transmission queue, encryption mode, and radio rate.

wifi_ethernet.rs · send_encrypted · rtl8188cu.rs · transmit

Why do we currently transmit at 1 Mbps?

Our driver explicitly selects the 1-megabit-per-second radio rate for outgoing frames. We kept it fixed while validating the connection. Enabling and testing higher rates is separate work.

This setting controls Pi-to-router transmissions. File transfer also includes replies, processing, and storage operations, so its measured speed is lower than the radio rate.

What if the router disappears while the Pi runs?

Our code waits up to 15 seconds without a beacon or accepted data before dropping the connection. It waits another two seconds before scanning again. A fresh connection starts a new security exchange.

We physically tested a deliberate station disconnect and successful reconnection. A full router-outage test remains a follow-up; the deadlines above describe the implemented code.

5. What made this work on our Pi?

First: make USB register reads reliable

The USB controller uses internal buffers for incoming and outgoing data. Its old buffer settings exceeded the memory reported by the controller. We configured three non-overlapping buffers of 1,024 words each; repeated reads then passed on the Pi.

usb.rs · buffer layout · Physical test: 4,096 repeated reads

Then: initialize the radio and complete security

We loaded firmware, configured the radio, and received the router’s replies. The remaining authentication failure came from a mismatch between the supplied key and the router’s configured key. Updating the private key allowed WPA2 and DHCP to complete.

No password or derived secret is shown in this lesson.

Radio and authentication test results

Finally: prove that the saved kernel survives reboot

The Mac uploaded the Wi-Fi kernel to the inactive SD copy. Every uploaded byte matched when read back. After a remote reboot, the Pi loaded that copy, joined Wi-Fi, obtained its address, and answered management requests. Previous-boot logs were still readable.
