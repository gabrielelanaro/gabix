Case 01

The shared cursor

A process opens /var/log.txt and gets fd = 3. It then calls fork(). The child calls lseek(3, 0, SEEK_END) — moving the cursor to the end of the file. Then the parent runs read(3, buf, 10).

Where does the parent's read start reading from?

The cursor lives on the File struct — not on the file descriptor (FD), not on the process. fork() duplicates the FD table (child gets its own FD numbers), but each FD entry still points at the same underlying File objects. So when the child moves the cursor, the parent sees the new position.

Same reason shell >file redirection survives fork() + exec(): the FD and the File it points at travel together.

From Lesson 2 — File Descriptor Table and learning-record 0002 (dup and FD sharing).

Case 02

Count the inodes

A program calls open("/home/gab/notes.txt"). The kernel resolves the path component by component.

How many distinct inodes does the kernel touch during resolution (before reading any file data)?

Resolution starts at the root inode. The kernel reads root's directory entries, finds home, and gets home's inode. Reads home's directory, finds gab, gets gab's inode. Reads gab's directory, finds notes.txt, gets notes's inode. Four inodes touched: /, home, gab, notes.txt.

Three directory reads, three name lookups, four inodes visited. Counting carefully matters because each hop is one disk read in a naive implementation — the dentry cache exists to skip them.

Case 03

Reading the directory bytes

You hexdump a directory's raw bytes:

offset 0: 05 68 65 6c 6c 6f 02 00 00 00 00 00 00 00 // "hello", ino=2
offset 14: 06 73 65 63 72 65 74 03 00 00 00 00 00 00 00 // "secret", ino=3

The format is [name_len: 1 byte][name: N bytes][ino: 8 bytes little-endian]. You add a third file data.txt.

At what byte offset does the new entry begin?

Each entry is 1 + N + 8 bytes — one byte for the length, N bytes for the name, eight bytes for the inode number. hello (5 chars) took 1 + 5 + 8 = 14 bytes (offsets 0–13). secret (6 chars) took 1 + 6 + 8 = 15 bytes (offsets 14–28). So the next entry starts at offset 29.

The length-prefix isn't decoration: it lets the kernel skip to the next entry in O(1) instead of scanning for a delimiter. Worth the extra byte per entry.

From Lesson 3 — Real Inodes and Paths, step 3.2 (directory entry encode/decode).

Case 04

What survives a reboot

You power-cycle the machine. Same disk, fresh boot. The kernel reads inode data from disk into RAM. On disk, each inode is identified by ino = 17 — a small integer.

Why is the inode identified by a number on disk, instead of a memory pointer like 0xFFFF_8000_1234_5678?

A pointer is a RAM address — it points at where the inode happened to be last time the kernel ran. After a reboot, RAM is empty; that address is meaningless. The on-disk format has to use a stable label (the inode number) that the freshly-booted kernel re-resolves to a fresh RAM pointer via the inode cache or registry.

Persistence is what drives this design. Size and speed are secondary — you'd make the same choice even if numbers were bigger than pointers.

Case 05

Order in the stack

A program calls read(fd, buf, 10) on a disk-backed file. The request flows down through the storage stack to the hardware, then the bytes flow back up.

Top to bottom: VFS dispatches by file operations table (fops); the filesystem translates the file-level request into block numbers (which block holds these bytes?); the block layer wraps it (in our mini-os, passthrough); the driver pushes the request onto a virtqueue and "kicks" the device; PCI (Peripheral Component Interconnect) is the physical path the kick travels along. The hardware reads the disk, then the response flows back up the same stack.

Each layer is replaceable. Swap ext2 for ext4 and the middle stages change; swap virtio-blk for NVMe (Non-Volatile Memory Express) and the bottom stages change; the user program at the top never notices.

Why this format

Recognition (the answer looks right when you see it) feels like mastery but decays in days. Retrieval (producing the answer cold) is what builds storage strength. The cases above force retrieval by asking you to apply concepts to fresh scenarios.

What low scores mean

Nothing about your progress — they're a map of what to revisit before going further. A shaky Case 01 (FD vs File vs Inode) matters more than a shaky Case 05 (storage stack), because everything you build next will assume the earlier concept is solid.

Spaced repetition

One session helps, but the real lever is spacing: come back to these concepts tomorrow, then in three days, then in a week. Each recall strengthens the trace. Ask the agent to schedule a follow-up review or generate a Round 02 with different scenarios.
