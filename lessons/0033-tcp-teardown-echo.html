Teardown and the echo server

Close the connection cleanly. Build the server side. Run TCP echo end to end.

Primary spec RFC 9293 §3.5 Linux counterpart net/ipv4/tcp_minisocks.c Proof ring-3 TCP echo server, host client connects and exchanges data

Every TCP connection holds kernel memory: a TCB, a retransmit queue, send and receive buffers, and a port number that cannot be reused while the connection exists. Lessons 31 and 32 left those resources held forever. Once a connection reached ESTABLISHED it stayed there until the kernel rebooted. For a kernel that opens one connection per boot this is tolerable. For a real program it is not. A web browser opens dozens of TCP connections to load a single page; a database server opens thousands per minute. Each connection must release its memory and its port when the work is done.

TCP provides a structured close for exactly this purpose. One side signals "I have no more bytes to send" by transmitting a segment with the FIN flag. The other side acknowledges, eventually sends its own FIN when its work is done, the first side acknowledges that, and the connection's resources are released. This exchange is teardown. This lesson builds teardown, adds the server side of TCP (the listen and accept machinery that lets mini-os accept inbound connections rather than only initiate them), and finishes with a ring-3 TCP echo server that opens, exchanges data, and closes cleanly.

The four-segment close

Each direction of a TCP connection closes independently. The side that calls close() first is the active closer; it sends a segment with the FIN flag set. FIN means "I have no more bytes to send on this stream." The receiver of FIN acknowledges it, exactly like a data segment: the FIN consumes one sequence number, and the ACK carries that sequence plus one.

The passive closer can still send data after acknowledging the active closer's FIN. It is in the CLOSE_WAIT state, which permits outbound data. When the passive closer has no more bytes to send either, it transmits its own FIN. The active closer acknowledges it. The connection is fully closed.

The exchange is symmetric: each direction closes with one FIN and one ACK, four segments total. Both FINs consume one sequence number, so each ACK is fin_seq + 1.

Half-close

Between segment 2 and segment 3, the passive closer may continue sending data. The active closer has shut down its outbound direction (no more bytes will be sent) but its inbound direction is still open: it can receive the data the passive closer sends and ACK each segment.

This state is called a half-close. Most applications do not use it; they close both directions nearly simultaneously. Real uses include the shutdown(fd, SHUT_WR) syscall, which sends FIN but keeps the socket readable. mini-os implements the protocol's half-close correctly even though the echo server does not use it explicitly.

The six teardown states

Teardown adds six states to the five establishment states from Lesson 31. The full TCP state machine has eleven.

Why TIME_WAIT lasts 2*MSL

The active closer enters TIME_WAIT after sending the final ACK (segment 4) and stays there for 2*MSL, typically 60 to 240 seconds. MSL is the Maximum Segment Lifetime: an assumption about how long a packet can wander the internet before being discarded. RFC 9293 section 3.5 assumes 2 minutes; modern deployments use shorter values.

Two reasons justify the wait:

  1. The final ACK might be lost. Segment 4 can vanish in transit. The passive closer's FIN retransmit timer fires, it resends FIN, the active closer (still in TIME_WAIT) replies with another ACK. If the active closer had already gone to CLOSED, the resend would arrive at no socket and trigger an RST, which the passive closer would log as a connection error.
  2. Old duplicate segments from the previous incarnation must drain. A delayed segment from the connection that just closed could still be in flight on some path. If the same 4-tuple (local IP, local port, remote IP, remote port) is reused immediately for a new connection, that old segment could be accepted by the new connection and corrupt its byte stream. Waiting 2*MSL guarantees any old segment has been discarded: maximum time in flight one way (MSL) plus maximum time the ACK can take to come back (another MSL).

For mini-os the threat is not real (slirp has no wandering duplicates), but the wait is implemented for protocol correctness.

The passive side: listen and accept

The TCP connection in Lesson 31 was active-open: the kernel sent the first SYN. A server does the opposite. It binds a port, marks it as willing to accept incoming SYNs, and waits. When a SYN arrives, the kernel completes the handshake on a fresh TCB and hands that TCB to the application.

Two new syscalls implement the server side:

  • listen(fd, backlog) marks the bound socket as passive. backlog is the maximum number of half-open connections (received SYN, sent SYN-ACK, waiting for final ACK) the kernel will queue.
  • accept(fd) blocks until a handshake completes on the listening socket, then returns a new file descriptor for the established connection. The original listening socket stays in LISTEN, ready to accept more connections.

The TCP socket table

Lesson 31 stored one TCB in a single global slot. A server needs many: the listening socket has its own TCB, and each accepted connection has its own. mini-os generalizes the single slot into a BTreeMap<SocketId, TcpControlBlock> keyed by the four-tuple (local IP, local port, remote IP, remote port), the same shape as the UDP socket table from Lesson 26.

Incoming TCP segments demux by destination port. A SYN to a listening port goes to the listener's accept queue. A segment with both endpoints filled in goes to the matching established TCB.

The echo server

The ring-3 echo server is the lesson's proof. Its main loop:

listen(server_fd, backlog=4); loop { let conn = accept(server_fd); // blocks until SYN arrives fork(); // child serves this connection if (child) { loop { let n = read(conn, buf, sizeof buf); if (n == 0) break; // peer closed write(conn, buf, n); } close(conn); // sends FIN exit(); } }

This is the structure of every TCP server since 4.2BSD (1983). accept returns one new file descriptor per connection. fork lets the parent loop back to accept the next connection while the child serves the current one. mini-os's fork from Lesson 18 supplies the process machinery.

What to build in mini-os

33.1
Send FIN (active close). When the application calls close on a TCP socket in ESTABLISHED state, build a segment with flags=FIN,ACK, seq=send_next, ack=recv_next, no payload. Transmit it, push it onto the retransmit queue (FIN consumes a sequence number and must be reliably delivered). Set state to FIN_WAIT_1.
33.2
Receive FIN, send ACK. In the TCP receive path, when a segment arrives with the FIN flag set: send an ACK with ack = received_seq + payload_len + 1 (the +1 accounts for the FIN's consumed sequence number). If state was ESTABLISHED, move to CLOSE_WAIT. If state was FIN_WAIT_1, move to CLOSING. If state was FIN_WAIT_2, move to TIME_WAIT and start the 2*MSL timer.
33.3
Passive close from CLOSE_WAIT. When the application calls close on a socket in CLOSE_WAIT, send our own FIN, transition to LAST_ACK. When the final ACK arrives (segment 4 in the diagram), transition to CLOSED and free the TCB.
33.4
TIME_WAIT 2*MSL timer. On entering TIME_WAIT, record the tick count plus 2*MSL worth of ticks (use 30 seconds for mini-os, shorter than the spec's 4 minutes). Each timer tick, check TIME_WAIT TCBs for expiry and free them. Handle retransmitted FINs by replying with another ACK; do not transition out of TIME_WAIT, but reset the timer.
33.5
Listen and accept syscalls. Add SYS_LISTEN = 908 and SYS_ACCEPT = 909. listen marks a TCP socket's TCB as LISTEN and stores a half-open queue. accept blocks on that queue. When a SYN arrives for a listening port, allocate a new TCB in SYN_RCVD, send SYN-ACK, complete the handshake on the new TCB, push the established TCB onto the listener's accept queue, wake the blocked accept call.
33.6
Multi-connection socket table. Replace the single global TCB slot from Lesson 31 with a BTreeMap<SocketId, TcpControlBlock>. SocketId is the four-tuple (local IP, local port, remote IP, remote port). Demux incoming segments by full four-tuple; fall back to local-port-only for segments destined to a LISTEN socket. Free TCBs on transition to CLOSED.
33.7
Ring-3 echo server. Add /tcp_echo.elf: bind a port (for example 8080), listen, loop on accept, fork per connection, read until EOF, write back each chunk, close. Configure QEMU with -netdev user,hostfwd=tcp:127.0.0.1:8080-10.0.2.15:8080 so a host-side client (for example nc 127.0.0.1 8080) can reach the guest. Host-side verification: send a string, receive the same string back, send EOF, observe clean close in serial output and on the host's packet capture.
What this lesson skips

RST-based abort (sent in response to a segment on a nonexistent TCB, or on a half-open connection). SO_REUSEADDR, the option that lets a socket bind a port still in TIME_WAIT. Keepalive, the timer that probes an idle connection. These all live in real TCP and are out of scope for the mini-os arc.

Probe — TIME_WAIT's two jobs

TIME_WAIT lasts 2*MSL (typically 1 to 4 minutes). The connection sits in that state, holding its TCB and four-tuple, after the active closer has sent the final ACK. Two distinct reasons justify the wait. Name both, and identify which one matters on a real internet path with wandering duplicate packets, versus which one matters even on a perfectly reliable link where the final ACK can still be lost.

Answer the probe when ready, or ask about any state, syscall, or build step before implementation. The build starts at step 33.1.

What this completes

Lesson 33 closes the planned TCP arc. mini-os opens active connections (Lesson 31), retransmits stream bytes under loss (Lesson 32), accepts inbound connections, echoes their bytes, and completes the passive-close path through CLOSE_WAIT, LAST_ACK, and CLOSED. The connection table routes server traffic by four-tuple. TIME_WAIT expiry, FIN retransmission, and fork-per-connection service remain later extensions.
