How Terminals Work

Scan codes and UART bytes, the line discipline, the TTY file descriptor, the shell. The fourth stack in mini-os, from the hardware up.

Read time ~20 min Build time ~15 min Prereq Lessons 17–18 (fork/exec/wait) for the shell; Lessons 28–29 (interrupts) for the driver

The kernel writes two devices. The VGA text buffer at 0xB8000 places characters on screen; the 16550 UART at I/O port 0x3F8 emits bytes to the host terminal through QEMU's -serial stdio. Output works. Input does not. The serial driver in src/serial.rs:28 writes only — nothing reads the UART's receive register, nothing reads port 0x60 where the keyboard controller deposits its bytes, and src/pic.rs:42 masks every device interrupt but the timer with 0xFE, 0xFF. A program in mini-os cannot ask what you typed. This phase builds the path.

Four layers

"Terminal" names four pieces, each doing one job. Bytes travel bottom to top.

application — the shell A user program that calls read(0, buf, len), parses the line, forks and execs a command. Lesson 38.
TTY device — fd 0 (stdin) The file-descriptor surface. read(0, ...) blocks until a line is ready, then copies it into the caller's buffer. Lesson 37.
line discipline — cooked vs raw Policy over raw bytes. Cooked mode: buffer until Enter, echo each byte to output, handle backspace, generate signals on Ctrl-C. Lesson 36.
driver — bytes from hardware Read the device register, translate if needed (scan code → character), hand the byte to the discipline. Lessons 35 and 39.
hardware — keyboard controller or UART The Intel 8042 keyboard controller at ports 0x60/0x64, or the 16550 UART at 0x3F8. QEMU emulates both.

The shape repeats the storage and network stacks: hardware at the bottom, a thin driver, a kernel subsystem that turns raw device output into something a file descriptor can deliver, a user program on top. The discipline is the new piece. Storage and network pass bytes through untouched. A terminal edits them: backspace, echo, Ctrl-C. None of those is a property of the keyboard or the program. They live in the discipline, applied to every byte that crosses it. The new piece is the line discipline. Storage and network stacks pass bytes through untouched; a terminal edits them. The two input devices

QEMU delivers keystrokes to the guest by two paths. They differ in how much translation the driver performs.

data register port 0x60 port 0x3F8 (offset 0)
status register port 0x64, bit 0 = byte ready port 0x3FD, bit 0 = byte ready
interrupt IRQ 1 → vector 0x21 IRQ 4 → vector 0x24

The UART is the simpler device by a wide margin. One in instruction returns the character the user typed. The keyboard sends scan codes — numbers that name physical keys — and the driver reconstructs characters from them with a keymap and a state machine. The serial path is built first (Lesson 35); the keyboard path last (Lesson 39), so the discipline and shell develop against the easier device.

The keyboard: scan codes, not characters

A keyboard is a grid of switches. When a switch closes, the keyboard's controller scans the grid, identifies the key by row and column, and sends a number — the scan code — to the motherboard. The number names the key's position, not what is printed on its keytop. Code 0x1C returns from the slot inhabited by 'A' on a US keyboard, 'Q' on a French AZERTY keyboard, nothing on a stenotype board. Layout is a software problem; the keyboard is layout-agnostic. The IBM PC keyboard (1981) transmitted set 1. The IBM AT (1984) introduced set 2, the default ever since. QEMU emulates the AT controller and produces set 2 codes.

The motherboard side is the 8042 keyboard controller — a single-chip microcontroller Intel designed in 1979 for the IBM AT, still emulated on every PC-compatible motherboard. The 8042 receives scan codes over a serial PS/2 cable, buffers one byte at I/O port 0x60, and raises IRQ 1. The CPU reads the byte with in al, 0x60. Status at port 0x64, bit 0, reports "output buffer full" for polling.

Each press produces a make code; each release produces a break code. This is how the driver learns Shift, Ctrl, and key-down duration. The keyboard offers three scan code sets; set 2 is the AT default and what QEMU produces. The byte sequence for typing 'A' then Enter:

PS/2 scan codes, set 2 — typing "A" then Enter 6 bytes for 2 keystrokes
A make u8 · 1 B 0x00
break u8 · 1 B 0x01
A break u8 · 1 B 0x02
Enter make u8 · 1 B 0x03
break u8 · 1 B 0x04
Enter break u8 · 1 B 0x05
make code u8

Sent on key-down. Identifies the key's physical slot. The driver looks it up in a keymap to produce a character; Caps Lock and Shift select which entry the lookup returns.

1C → lookup[0x1C] → 'a' (or 'A' under Shift)
break sequence u8 u8

0xF0 followed by the key's make code, sent on key-up. The driver clears modifier state here: Shift break (0xF0 0x12) ends the shifted lookup. Break codes for letter keys carry no character and can be ignored; breaks for modifiers must be tracked.

F0 1C → "A released" → no character

Six bytes for two keystrokes. The driver walks a state machine over them: was the previous byte 0xF0? is Shift held? did this key already send its make — autorepeat, or a new press? Shift+A grows the sequence to eight bytes (12 1C F0 1C F0 12 for Shift make, A make, A break, Shift break); the driver must remember the Shift make when the A make arrives several bytes later. Lesson 39 builds the machine.

One snag, surfaced now

src/interrupts.rs:23 sets VIRTIO_BLK_VECTOR: u8 = 0x21. Vector 0x21 is PIC IRQ 1 — the keyboard's line. If virtio-blk is genuinely wired to that vector (MSI-X table entry, or legacy INTx fallback), the keyboard collides with it. The UART's IRQ 4 lands at vector 0x24, which is free, so Lesson 35's serial build is unaffected. Lesson 39 must resolve 0x21 before its ISR goes in.

The serial port: bytes already

The 16550 UART sends and receives one byte at a time over a serial line. QEMU's -serial stdio wires the host terminal's stdin and stdout to the guest's first UART: bytes written to port 0x3F8 land in the host terminal; bytes typed in the host terminal arrive at port 0x3F8 in the guest. No translation, no keymap, no make/break. The byte the user typed is the byte the kernel reads. The original IBM PC (1981) used the 8250 UART, which had no FIFO. The 16550 (1987) added a 16-byte receive FIFO that interrupts once per several bytes instead of once per byte — the difference between an interrupt storm and a quiet line at 115200 baud. QEMU emulates the 16550.

The UART raises IRQ 4 when its receive register holds a byte the CPU has not read. Status at port 0x3FD, bit 0, reports the same condition for polling: set means receive holding register full, in al, 0x3F8 returns a valid byte. Bit 5 reports the transmit side. The mini-os driver already uses transmit; Lesson 35 adds receive.

The UART transmits and receives independently. The kernel must echo each received byte back to the transmit register, or the user types blind. One out per received byte; the first act of the Lesson 35 build.

The line discipline

Raw bytes from either device are not what a program wants. A program calls read(0, buf, 128) expecting one full line of text — the characters typed, ending at Enter, mistakes corrected. The line discipline turns the stream of individual bytes into that line. It sits between the driver and the TTY device. Linux carries a table of disciplines. n_tty is the default. ppp, slip, and mouse-protocol readers were once loaded for serial lines carrying non-terminal traffic.

Two modes. Cooked (canonical) buffers bytes until Enter, lets the user edit with Backspace and Ctrl-U, echoes each byte as it arrives, delivers one completed line per read(). Raw passes bytes through immediately, one at a time, with no editing and no echo — what a full-screen editor or a serial console protocol wants. mini-os starts cooked; raw is a flag away once the structure exists.

Cooked mode performs three actions on every byte from the driver:

cooked-mode byte handling — one byte in, possibly zero or more bytes out
byte from driver │ ├─ 0x08 (Backspace) or 0x7F (DEL)? │ └─ buffer not empty? │ ├─ yes: drop last byte from buffer, write "\b \b" to output │ └─ no: do nothing (bell is optional) │ ├─ 0x0A (LF) or 0x0D (CR)? │ └─ append '\n' to buffer, echo '\r\n' to output, │ mark buffer "line ready", wake any blocked reader │ ├─ 0x03 (Ctrl-C)? │ └─ discard buffer, deliver SIGINT to the foreground process group │ (signal delivery is later work; for now: reset buffer, print "^C") │ └─ any other printable byte? └─ append to buffer, echo the byte to output

Three jobs in one component. Edit: backspace fixes the current line before Enter commits it. Echo: the user sees each character as they type, because the device shows nothing on its own. Commit: Enter turns the accumulated bytes into a deliverable line. Without the discipline, every program implements all three itself, and a typo is permanent.

The TTY device and the shell

The discipline's output — completed lines — must reach a program. The bridge is the TTY device, an entry in the file descriptor table that returns bytes from the discipline's line buffer when read. By Unix convention the first three descriptors a process inherits are 0 (stdin, read side), 1 (stdout, write side), 2 (stderr, write side). sys_read(0, buf, len) in mini-os returns EOF immediately; Lesson 37 routes it to the discipline's tty_readline(), which blocks the caller until Enter commits a line, then copies the line into the caller's buffer. "Everything is a file" earns its keep here. A program reads from a keyboard, a pipe, a socket, a regular file with the same read(). The discipline is what fits the keyboard to that interface.

Above the TTY sits the shell — an ordinary user program, no kernel privileges, looping over four operations:

the shell loop — a user program built on fork/exec/wait (Lessons 17–18)
loop { write(1, "$ ", 2); // print the prompt n = read(0, line, 128); // block until Enter if (n <= 0) exit(0); // EOF (Ctrl-D) → exit parse line into argv[]; // split on spaces if (is_builtin(argv[0])) { // exit, cd, ... run_builtin(argv); continue; } pid = fork(); // Lesson 17 if (pid == 0) { exec(argv[0], argv); // Lesson 16 — replace image exit(127); // exec failed } else { wait4(pid, &status, 0); // Lesson 18 — reap child } }

Every primitive in that loop already exists in mini-os. fork was Lesson 17; exec was Lesson 16; wait4 was Lesson 18. The shell proves those syscalls compose: a program whose only job is to launch other programs from input it reads itself. The new kernel work is the bottom three layers — driver, discipline, TTY device — because the top reuses Phase 1's process machinery wholesale.

What Linux does

The Linux TTY subsystem is the production version of this stack.

  • drivers/tty/tty_io.c — the TTY core. tty_read and tty_write are the file-operation methods behind every /dev/tty file descriptor. The layer the discipline plugs into.
  • drivers/tty/n_tty.c — the default line discipline. n_tty_receive_char_lnext and friends implement cooked-mode editing, echo, and signal generation. The flowchart above as C.
  • drivers/tty/serial/8250/8250_port.c — the 16550 UART driver. serial8250_handle_irq drains the receive register on IRQ 4 and hands each byte to the discipline. The Lesson 35 counterpart.
  • drivers/input/keyboard/atkbd.c — the AT keyboard driver. Set 2 scan-code reception and the make/break state machine. Read for Lesson 39.
  • include/linux/tty.h — struct tty_struct, the object that ties driver, discipline, and file descriptor together. A useful reference for the shape even when the mini-os version is simpler.

The Linux serial-console documentation describes how a kernel attaches a shell to a UART at boot — exactly what mini-os builds.

Reuse from earlier phases

  • The interrupt infrastructure (Lessons 28–29). The IDT-entry shape, the naked-asm wrappers, the APIC EOI path, and the task-wakeup-from-ISR pattern that virtio-net RX uses are exactly what the UART receive ISR needs. Lesson 35's serial_rx_wrapper is the virtio-net RX wrapper with two port reads swapped in.
  • The serial port (since Lesson 1). The UART is already mapped and the transmit path works. Lesson 35 adds the receive path to the same driver, in the same file — no new device discovery.
  • The process syscalls (Lessons 16–18). The shell is a user program with no new syscalls of its own. fork, exec, and wait4 compose directly into the shell loop above. The one new syscall is sys_read(0, ...) learning to block on the discipline instead of returning EOF.

The genuinely new work is the line discipline. It has no counterpart in the disk or network stacks, which pass bytes through untouched. The discipline is the first mini-os component whose job is to edit a byte stream, and its placement — between driver and file descriptor — is what lets one discipline serve both keyboard and UART.

The build — a smoke test

Like Lesson 19's "attach the card and see it on the PCI bus," this lesson's build proves one thing: a byte you type reaches the kernel. No ISR, no discipline, no shell — a polling read of the UART receive register in the main loop, echoed straight back. The full stack starts in Lesson 35.

1
Add a receive method to src/serial.rs. Read the line status register at port 0x3FD; if bit 0 is set, in al, 0x3F8 returns the byte the user typed. Expose as pub fn try_read_byte() -> Option<u8> so the main loop can poll without blocking.
2
Poll and echo in the kernel main loop. Where main.rs currently spins after exec, insert if let Some(b) = serial::try_read_byte() { serial::write_byte(b); }. Type into the QEMU window; characters appear as typed. First input the kernel has ever seen.
3
Verify and commit. Run with -serial stdio, type hello, observe hello echoed back. The disk path and existing tests must still pass (this is a read-only addition). Commit, e.g. "Lesson 34: serial UART receive polling smoke test."

Probe — check the model before you build

The TTY is in cooked mode. You type a, b, c, then Backspace, then d, then Enter. Trace the three layers: what bytes does the UART deliver to the driver, what does the discipline's buffer hold after each step, and what bytes does the application receive from read()? Then the same keystrokes in raw mode — what changes at the application boundary, and why does the screen stay blank unless the application prints each byte itself?

Answer back, or push on what did not land — why the discipline echoes, why break codes are needed at all, how sys_read(0, ...) blocking on a line differs from blocking on a socket. The probe is where the conversation starts.

What this unlocks

Lesson 35 turns the polling read into IRQ-driven receive: unmask IRQ 4, install the receive ISR at vector 0x24, buffer bytes into a ring, echo each one back. The keystone — a typed character reaching the kernel through hardware interrupts, not a busy loop.
