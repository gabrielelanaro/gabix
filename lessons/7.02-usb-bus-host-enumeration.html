USB: the bus, the host, and enumeration

What USB is — a single host that controls the bus, a tree of devices, and numbered endpoints — and the fixed sequence the Pi runs the moment you plug something in.

You plug a keyboard into the Pi's USB socket. The CPU cannot just read the keyboard — there is no direct wire between them. Between the CPU and the keyboard sits a protocol called USB, and a chip called the host controller that speaks it. The CPU tells the host controller what to do; the host controller does the actual talking to the keyboard, byte by byte, over the USB wire.

This lesson is the model you need before any of that makes sense: which side controls a USB bus, what a device looks like to the host, and the fixed sequence the host runs every time something gets plugged in — a sequence called enumeration. The Pi's specific controller (the DWC2) and its specific USB chip (the LAN9512, the Ethernet port) come in lessons 7.03 and 7.04. Here we build the model, grounded in gabix's real USB code.

1. The host starts every transfer

USB is not symmetrical. One side is the host — the Pi — and it is the only side that ever starts a conversation. A device never sends data on its own; it waits to be asked. The host asks each device, over and over, many times a second, whether it has anything to say, and the device answers in the moment the host gave it.

This is the first thing to fix in your mind: every byte that moves on a USB wire moves because the host asked for it. When someone says "the keyboard sent a keypress," what physically happened is: the host asked the keyboard "anything new?", the keyboard answered "yes, the letter A," and the host took it.

That raises an obvious question: if the device never speaks first, how does the host even know one was plugged in? Three actors are involved. First, the device: a small resistor inside it, the instant it is plugged in, pulls one of the two data lines to a voltage — passive, no packet. Second, the host controller (the DWC2): a separate piece of silicon whose job is to manage the USB bus. It has circuitry that watches the data lines continuously, in hardware, on its own — whether the CPU is busy or idle. When it sees the voltage change, it sets a “connect detected” bit in one of its registers. That is the controller doing the looking, not the CPU. Third, the CPU: that register bit does not interrupt the CPU. gabix’s CPU finds out by polling — reading that register in a loop until the bit is set (in usb.rs, after powering the port). gabix does not use the controller’s hardware interrupt for this, the same poll-everything gap noted in lessons 7.01 and 7.02. So: the controller’s hardware detects the connect electrically and records it; the CPU later reads the record by polling. The device sent nothing.

2. The host controller: the chip the CPU programs

The CPU does not speak USB. It speaks to a chip on the board — the host controller — and that chip speaks USB to the devices. On the Pi 2B the host controller is the DWC2 (a Synopsys DesignWare USB 2.0 controller), and gabix reaches it at address 0x3f98_0000.

The host controller is a set of registers. The CPU writes those registers to make things happen and reads them to learn what happened. Two parts of the controller matter for the model:

  • The host port — the physical USB socket. The CPU powers it on, resets it, and reads whether something is plugged in. The DWC2 has one root port. (The Pi's Ethernet hangs off a hub behind that port, but a hub is a device, not another controller port.)
  • The host channels — the transfer engines. To move bytes to or from a device, the CPU programs a channel: which device, which endpoint, what kind of transfer, which direction, and a buffer holding the bytes. Then it fires the channel and waits for it to finish.

So the CPU's job is: bring up the port, then run channels. One channel is one transfer.

3. Devices, addresses, and endpoints

When you plug a device in, it starts at address 0 — every unconfigured device uses address 0, briefly. The host's first job is to give it a real address (1, 2, 3, …) so it can tell devices apart. After that, the device answers only its own address.

Within a device, communication happens at endpoints. An endpoint is one numbered channel into the device, with a direction (in — device to host — or out — host to device) and a type. Endpoint 0 is special: every device has it, it is always a control endpoint, and the host uses it for setup. Other endpoints appear in the device's descriptor (section 7) and carry the real data.

To talk to a device, the host names three things: the device's address, the endpoint number, and the direction. Gabix packs exactly those into one channel register — the device address, the endpoint number, the direction — alongside the endpoint type and the max packet size.

4. The four transfer types

USB defines four kinds of transfer, and each endpoint is one of them. The kind decides how the host schedules it:

  • Control — the setup and configuration traffic. Every device has a control endpoint (endpoint 0). A control transfer is a fixed three-part handshake (section 6). This is how the host asks "what are you?" and tells the device "your address is now 1."
  • Bulk — large bursts of data that must arrive intact but have no deadline. Network frames, mass-storage blocks. The Pi's Ethernet uses bulk endpoints.
  • Interrupt — small amounts of data the host fetches on a fixed schedule. A keyboard reports each keypress on an interrupt endpoint; the host polls it every few milliseconds. Despite the name, this is not a hardware interrupt: the host still does the asking. The name means "polled on a schedule," not "the device raised a wire" (the wires from lesson 7.01).
  • Isochronous — a fixed slice of bandwidth every millisecond, for real-time data that can tolerate loss. Audio, video. Gabix does not use it.

The transfer type is the endpoint's property, set in its descriptor; the host reads it and honors it.

5. Enumeration — the sequence the host runs on plugin

Once the host controller's hardware has detected a connect — the electrical pull-up from section 1, not a packet from the device — the host runs a fixed sequence to bring the device online. This is enumeration, and gabix's enumerate_device is a textbook version of it, in three control transfers:

targets/armv7/src/raspi2b/usb.rs · enumeration, trimmed to its three steps
// Step 1: read the first 8 bytes of the device descriptor, at address 0.
//        Endpoint 0, control transfer, "GET_DESCRIPTOR" (request 6).
//        The host assumes a 64-byte packet for this first read, because it
//        does not yet know the device's real size.
let mut first = [0u8; 8];
self.control_in(0, 64, SetupPacket::new(0x80, 6, 0x0100, 0, 8), &mut first)?;
let max_packet_size = first[7];   // byte 7 holds the real packet size for endpoint 0

// Step 2: SET_ADDRESS — "from now on, answer to address 1" (request 5).
self.control_no_data(0, max_packet_size, SetupPacket::new(0, 5, 1, 0, 0))?;

// Step 3: re-read the full 18-byte device descriptor, at the new address.
let mut descriptor = [0u8; 18];
self.control_in(1, max_packet_size, SetupPacket::new(0x80, 6, 0x0100, 0, 18), &mut descriptor)?;
// byte 4 = device class; bytes 8-9 = vendor id; bytes 10-11 = product id

Read the sequence in order: a device appears at address 0; the host reads eight bytes to learn its packet size; the host assigns the device a real address; then the host reads the full eighteen-byte descriptor at that new address. After step 3 the device has an address and the host knows its class (is it a hub? a keyboard? a network adapter?), its vendor, and its product.

If the device is a hub (class 9), the host then runs a similar power-and-status sequence on the hub's downstream ports to reach the devices behind it (gabix's enumerate_hub_child). If it is a bulk device like the LAN9512, the host reads its configuration, finds the bulk endpoints, and sends a SET_CONFIGURATION to put it in a working state (gabix's configure_bulk_device).

6. The control transfer, up close

Enumeration is all control transfers, so it is worth seeing exactly what one is. A control transfer always has three phases:

the three phases of a control transfer (an IN, like GET_DESCRIPTOR)
   host                                   device
     │   1. SETUP  — an 8-byte packet: "I want X"     │
     │──────────────────────────────────────────────▶ │
     │   2. DATA   — the bytes the host asked for     │
     │◀────────────────────────────────────────────── │
     │   3. STATUS — a zero-length packet: "received" │
     │──────────────────────────────────────────────▶ │

The 8-byte setup packet is fixed by the standard: a request type (in or out), a request number, a value, an index, and a length. The request numbers are shared by every device — 6 means GET_DESCRIPTOR, 5 means SET_ADDRESS, 9 means SET_CONFIGURATION. A device that did not understand these could not be enumerated at all.

7. Descriptors — the device's self-description

USB devices describe themselves in nested byte structures called descriptors, which the host reads during enumeration:

  • The device descriptor (18 bytes): the device class, the vendor and product IDs, and the max packet size of endpoint 0 (that byte 7 from step 1).
  • The configuration descriptor: a tree of interfaces, each listing its endpoints with their types and directions.

Gabix walks the configuration descriptor's bytes to find the bulk endpoints (parse_bulk_endpoints): it scans for endpoint descriptors (type 5) whose type field is bulk (2), and records the IN endpoint, the OUT endpoint, and the max packet size. That is how the host learns where to send and receive the device's actual data.

One open gap, same as lesson 7.01. Gabix waits for each channel to finish by polling its status register in a loop — the same busy-wait pattern as the SD card driver. A device never raises a hardware interrupt; gabix asks "done yet?" until it is. Wiring the DWC2's own interrupt through the two Pi controllers from lesson 7.01 is the fix, and it is open work.

What you should be able to do after this lesson. Explain why a USB device cannot send anything until the host asks. Name the three things the host specifies to reach an endpoint (address, endpoint number, direction). Recite the three phases of a control transfer and the three steps of enumeration. And say why a "USB interrupt transfer" is not a hardware interrupt.
Primary source. The USB 2.0 specification defines the transfer types, the standard requests, and the descriptor layouts. Chapter 9 is the device framework (enumeration, descriptors, requests) and is the part you will re-read most. The Pi's controller and Ethernet chip are lessons 7.03 and 7.04.
