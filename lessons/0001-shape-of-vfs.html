The Shape of VFS

Why Linux has a Virtual File System, and what we are about to build.

Read time ~15 min Style concept (hybrid track) Next file descriptor table

When your program calls open("/etc/hosts") in Linux, the kernel asks: which filesystem is this path on, and how does that filesystem spell 'open'? That indirection — one API, many backends — is what a Virtual File System (VFS) is for.

The problem VFS exists to solve

Linux runs many filesystems at once. Your root partition is ext4. /tmp is tmpfs (in memory). /proc and /sys are synthetic — they expose kernel state as files. /home might be on a network filesystem (NFS). Each of these stores bytes very differently, with very different on-disk formats.

Without a layer between them and user programs, every program would need to know which filesystem each file lived on. Your shell would need different code for cat /etc/hosts (ext4) versus cat /proc/cpuinfo (procfs). That is absurd.

user program: open("/etc/hosts"), read(fd, buf, 4096)
↓ same API regardless of filesystem
VFS (Virtual File System) — the dispatch layer
↓ routes to the right backend
ext4 driver
tmpfs driver
procfs driver
nfs driver
The user sees one API. The kernel sees many backends. VFS is the bridge.

VFS exists so that read(fd, buf, len) works the same way whether fd points at a regular file, a pipe, a device, or a kernel-produced synthetic file. The user program does not know, and does not need to know.

"Everything is a file"

The Unix slogan everything is a file means: everything you can read from or write to is reachable through the file interface — open, read, write, close, plus a few more (lseek, ioctl, mmap). That includes:

  • regular files (/etc/hosts)
  • directories (yes — opendir internally opens them as files)
  • devices (/dev/null, /dev/sda)
  • pipes (created by pipe(2) or | in the shell)
  • Unix sockets
  • kernel-synthetic files (/proc/cpuinfo, /sys/...)

Tools like cat, grep, less work on all of these. Without this convention, you would need a separate cat for devices, another for pipes, etc.

Why this matters for us: mini-os's VFS will start small (just regular files in ramfs), but the abstraction needs to be designed so that pipes (roadmap item 4.6) plug in without rewriting the syscall layer.

The four core abstractions

VFS gives every file backend the same shape by defining four objects. Each one captures a different aspect of "what a file is."

1. Superblock — "a filesystem is mounted here"
One per mounted filesystem. Holds global info: block size, free space, root directory, and the table of operations this filesystem supports. The superblock is the entry point — it is how VFS knows "for files under /, talk to ext4; for files under /proc, talk to procfs."
2. Inode (Index Node) — "a file exists; here is its metadata"
Represents the file itself, independent of any name or any open instance. Holds size, permissions, timestamps, and a way to fetch the bytes. An inode has no name. Multiple names (hard links) can point at one inode. The ls -i command shows you inode numbers.
3. Dentry (Directory Entry) — "this name points to this inode"
A link between a name ("hosts") and an inode. Dentries form the directory tree: / contains etc contains hosts. VFS caches them heavily so repeated path lookups (/etc/hosts opened by 100 processes) do not walk the disk each time.
4. File — "an open instance, with its own cursor"
Created when you open something. Holds the read/write offset, the access mode (read-only, write-only, read-write), and a reference to the underlying inode. If two processes open the same file, they each get their own File with its own cursor — but they share the same inode underneath.
Intuition check

Inode = the file. Dentry = the name. File = an open instance. Superblock = the filesystem. The split exists because these four things have different lifetimes and different sharing patterns. (Two open instances share one inode. One inode can have many dentries. One superblock owns all the inodes for a mount.)

The dispatch path — anatomy of open

Here is the lifecycle of open("/foo") in Linux, simplified. Each step is either VFS-generic work or a dispatch into the filesystem-specific code. 

// User calls open("/foo", O_RDONLY). The kernel:

1.  walk the path "/foo":
        for each component (here just "foo"):
            ask the parent directory's dentry:
              // dispatch: calls the filesystem's "lookup" method
              dentry = parent_inode->ops->lookup(parent_inode, "foo")
            this returns a dentry pointing at foo's inode

2.  load foo's inode (if not cached):
        inode = superblock->ops->read_inode(inode_number)

3.  check permissions (can this user read foo?)

4.  allocate a struct file:
        file->inode = foo's inode
        file->pos = 0
        file->mode = O_RDONLY
        file->ops = inode->fops  // copy the file-operations table from the inode

5.  allocate a file descriptor (FD) in this process's FD table:
        fd_table[fd] = file

6.  return fd

The indirection lives in file->ops, a table of function pointers (one for read, one for write, etc.). When you call read(fd, buf, len), the kernel looks up the file, follows file->ops->read, and lands in the filesystem-specific read function. The same read syscall ends up calling ext4 code or procfs code depending on what fd points at.

Linux source to skim: fs/read_write.c — specifically ksys_read() and vfs_read(). The whole syscall is about 40 lines and shows the dispatch pattern clearly.

What we will build in mini-os

mini-os is small enough that we can skip most of Linux's complexity. Concretely:

Keep

  • File descriptor table — per-process, indexed by small integers (0=stdin, 1=stdout, 2=stderr, 3+)
  • File struct — open instance with cursor and access mode
  • Inode — file identity with metadata (size, type) and a way to get bytes
  • Superblock-ish root — a single mounted ramfs (we will not support multiple mounts at first)
  • Dentry-ish path resolution — enough to walk /foo/bar, but no cache
  • Four syscalls: open, read, write, close

Skip (for now)

  • Permissions / ownership / ACLs
  • The dentry cache (we will do naive path walks)
  • Multiple mounts (one filesystem, mounted at /)
  • Locking (single CPU, cooperative scheduler — same convention as the rest of mini-os)
  • Disk-backed storage (ramfs only; ext2 is roadmap item 4.7)
The build order

Lesson 2 will start with the file descriptor table — the smallest piece, the one with the clearest test, and the one that lets us stub open/read/write/close before we have a real filesystem. Once those syscalls work against a fake backing, lesson 3 will swap in ramfs (the inode layer) underneath. Pipes (4.6) plug in last as another file type.

Pause and think

If open("/foo") creates a new file struct every time, and two processes both open /foo, they get two file structs sharing one inode. What should happen to the cursors when one process reads and the other reads immediately after — should they see the same offset, or independent offsets? Why?
