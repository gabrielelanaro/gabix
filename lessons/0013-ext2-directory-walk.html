ext2 Directory Walk

Parse the linked-list of directory entries inside an inode's data block. Find ., .., and lost+found.

Read time ~20 min Build time ~25–35 min Prereq Lesson 12

Lesson 12 found inode 2 (the root directory) and parsed its metadata. The inode says "my data lives in block 40." Lesson 13 reads that block and parses the directory entries inside it — a linked list of variable-length records, each linking to the next via rec_len.

What a directory is on disk

In ext2 (and Unix filesystems generally), a directory is just a file whose data block contains directory entries (dirents). A dirent is a small header + a name. The kernel walks the list, comparing names, to translate "find me foo.txt" into "give me inode N."

The entries are not fixed-size. Names vary from 1 to 255 bytes. Each entry's rec_len field says how many bytes to skip to reach the next entry — accommodating variable names plus padding for alignment. The last entry's rec_len takes you to the end of the block.

The on-disk dirent layout (8-byte header + name)

ext2 directory entry (header + variable name) 8 bytes minimum · variable total
inode u32 · 4 B 0x00 4B
rec_len u16 · 2 B 0x04 2B
name_len u8 · 1 B 0x06 1B
file_type u8 · 1 B 0x07 1B
name name_len bytes 0x08+ N B
Click any field for what it stores.

Each cell shows the entry's inode, name, type, and total size (header + name + padding). The last entry (lost+found) has a large rec_len that consumes the rest of the block — when a new file is added, its rec_len shrinks to make room.

The walk — a linked-list traversal

Reading a directory is just walking a linked list, where each link is a rec_len instead of a pointer:

1
offset 0
Read entry header: inode, rec_len, name_len, file_type
2
+8
Read name_len bytes — that's the name
3
—
If inode != 0: this is a live entry, record (name, inode, type)
4
+rec_len
Advance to the next entry: offset += rec_len
5
—
If offset < block_size: go to step 1. Else: done.

For our disk: three live entries (., .., lost+found) followed by unused padding consumed by the last entry's rec_len. The walk produces a list of (name, inode, type) tuples.

Build steps — your turn

Five substeps. By the end we'll list the root directory contents and look up "lost+found" by name.

13.1Dirent struct + parse-one-entry helper

Dirent struct holding inode (u32), file_type (u8), name (Vec<u8>), and rec_len (u16). The name is owned by the struct (heap-allocated) so callers don't have to deal with byte slices + lengths.

Dirent::parse_at(bytes, offset) -> (Dirent, next_offset) — read the 8-byte header + name_len bytes from bytes[offset..], return the parsed struct and the offset of the next entry (= offset + rec_len).

13.2read_block helper (2 sectors)

Extract the "read 2 sectors, concat into 1024 bytes" pattern into read_block(dev, block_n) -> [u8; 1024]. Used by Lesson 10's read_superblock and Lesson 12's read_inode; now made a top-level function so Lesson 13 can use it for the directory block.

Assumes 1024-byte blocks (our disk's only size). A block-size-aware version is a future refactor.

13.3walk_directory function

walk_directory(dev, dir_inode) -> Vec<Dirent>:

  1. For each direct block pointer (block_pointers[0..12]) that's non-zero:
  2. Read the block via read_block
  3. Walk the linked list: parse_at offset 0, advance by rec_len, repeat
  4. Collect every entry with inode != 0

Returns a Vec of live dirents. For our root: 3 entries. Doesn't follow indirect/double/triple pointers — root fits in one direct block.

13.4lookup_in_dir — find by name

lookup_in_dir(dev, dir_inode, name) -> Option<u32>: walk the directory, return the inode number of the entry whose name matches, or None if not found. Used by path resolution in Lesson 14.

13.5Test in main.rs

After Lesson 12's inode-2 verification:

  • Call walk_directory(&mut virtio_dev, &root_inode)
  • Print each entry: ".", "..", "lost+found"
  • Assert we got exactly 3 entries
  • Assert "." and ".." both point at inode 2
  • Assert "lost+found" points at inode 11
  • Call lookup_in_dir(&mut virtio_dev, &root_inode, "lost+found") — expect Some(11)
  • Call lookup for a missing name — expect None

Pause and think

When a file is deleted from an ext2 directory, the entry's inode is set to 0 but the slot stays. The previous entry's rec_len grows to skip past the dead slot. Why this design instead of compacting the directory by shifting entries left?
