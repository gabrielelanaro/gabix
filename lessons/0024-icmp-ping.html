ICMP Echo: Ping the Gateway

A 20-byte IPv4 packet already reaches the wire. Add eight bytes of ICMP state, then make QEMU’s gateway answer.

ICMP (Internet Control Message Protocol) echo is the smallest conversation that exercises the entire network stack. mini-os creates a request, sends it through IPv4, Ethernet, and virtio-net, then proves that its receive path identifies the matching reply.

Where ICMP came from

ICMP was written for the early Internet, when researchers were connecting distinct packet networks through machines called gateways. An IPv4 packet could leave a host and later encounter a missing route, a full gateway queue, an expired Time To Live (TTL), or a destination that could not handle its protocol. The sender needed a compact way for the network itself to report those conditions.

Jon Postel published RFC 792 in September 1981. It defines ICMP as an integral part of IP: a family of control and diagnostic messages carried inside IPv4 packets. The protocol reports network conditions and supplies no delivery guarantee. TCP, UDP, and applications build their own behavior on top of that foundation.

Echo is the deliberately simple member of this family. A host marks a packet with an identifier, a sequence number, and a payload; the destination returns the same marks. The familiar ping program turns that exchange into a diagnostic. A matching reply shows that the request reached a live IP module and that a return packet came back through the network. Missing replies leave a chain of possible failures to investigate: frame construction, ARP, IPv4, the gateway, or the receive path.

Why this is the keystone

QEMU’s user-mode network assigns the guest 10.0.2.15 and provides a local router at 10.0.2.2. QEMU documents that ICMP echo to this router works. A reply proves outbound framing, ARP lookup, IPv4 construction, receive polling, Ethernet parsing, IPv4 demultiplexing, and ICMP parsing in one round trip.

One message, two forms

An echo request and an echo reply use the same layout. The gateway returns the identifier, sequence number, and data unchanged. The response changes the ICMP type from 8 to 0 and recomputes the checksum. RFC 792 defines this exact exchange.

ICMP echo message 8-byte header + payload
typeu80x00T
codeu80x01C
checksumu160x02–03Σ
identifieru160x04–05ID
sequenceu160x06–07SQ
payload[u8]0x08……
All multi-byte fields use network byte order: big-endian.

The checksum is the existing RFC 1071 internet checksum from Lesson 23, this time over the entire ICMP message. Set the checksum field to zero, compute the checksum, and write the result into bytes 2..4. A receiver accepts a complete valid message only when its checksum verifies across every byte.

type · byte 0

The kind of ICMP message. mini-os writes 8 for “please echo this”; the gateway writes 0 for “here is your echo reply.”

code · byte 1

A subtype for the chosen ICMP type. Echo has one form, so this byte is always 0. Other ICMP messages use it to refine their meaning.

checksum · bytes 2–3

A 16-bit integrity check over the header and payload. mini-os writes it after building the message; the receiver recomputes it to reject damaged bytes.

identifier · bytes 4–5

The tag for one ping owner. mini-os chooses it, stores it with the pending request, and expects the reply to return the exact same 16-bit value.

sequence · bytes 6–7

The counter within that owner’s pings. Sending sequence 0, then 1, then 2 lets mini-os match delayed replies to the request that caused them.

payload · byte 8 onward

The bytes being echoed. A known payload gives mini-os one more proof that this reply belongs to its request and makes the packet useful for a future round-trip-time measurement.

Follow one ping through mini-os

Start in the ring-3 program /icmp_ping.elf. It asks the kernel to send four requests with identifier 0x2400, sequences 7..10, and payload mini-os. ICMP writes those values into the layout above, IPv4 wraps the ICMP bytes with protocol number 1, and the Lesson 23 path carries each IPv4 packet through ARP, Ethernet, and virtio-net.

The one question the return path answers

“Did the reply that came back belong to this request?” The source and destination IP addresses identify the network path. Type, code, and checksum show that the bytes form a valid echo reply. Identifier, sequence, and payload connect that reply to the request that /icmp_ping.elf sent.

Implementation boundary

The implementation keeps ICMP responsible for its wire format and matching rule. The device driver owns DMA and virtqueues. IPv4 supplies protocol number 1 and the payload boundary. The ring-3 fixture asks for a ping through syscall 902. 

// src/net/icmp.rs — implemented public boundary
pub const ECHO_REQUEST: u8 = 8;
pub const ECHO_REPLY: u8 = 0;

pub struct EchoMessage<'a> {
    pub message_type: u8,
    pub code: u8,
    pub identifier: u16,
    pub sequence: u16,
    pub payload: &'a [u8],
}

impl<'a> EchoMessage<'a> {
    pub fn parse(bytes: &'a [u8]) -> Option<Self>;
    pub fn is_reply_to(&self, id: u16, seq: u16, payload: &[u8]) -> bool;
}
