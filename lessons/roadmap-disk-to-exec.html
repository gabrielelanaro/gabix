Roadmap · Disk to ELF execution

How We Get to exec()

Twelve lessons from where we are now (memory-only VFS) to loading and running an externally-compiled binary from disk. Each layer of the storage stack gets its own concept-plus-build lesson — nothing skipped.

Start Lesson 4 End Lesson 15 Status 1 of 12 done

Objective

A user program written in Rust, compiled externally as an ELF (Executable and Linkable Format) binary, written to a raw disk image, attached to QEMU via virtio-blk-pci, loaded by the kernel's ext2 driver through a real block layer and page cache and VFS, parsed by an ELF loader, mapped into a fresh address space, and executed — replacing the hand-assembled USER_PROGRAM we've been running so far. Every layer of the Linux storage stack re-implemented, not skipped.

Twelve lessons. Each layer gets both a concept section (what it does in Linux, why it exists, what tradeoffs it makes) and a build section (concrete steps to re-implement it in mini-os). Two keystones along the way: Lesson 8 — first disk read proves the driver works end-to-end; Lesson 13 — first full-stack file read proves the layering works end-to-end.

Where we are: VFS foundation complete (Lessons 1–3). User programs can open, read, write, close files by path against an in-memory filesystem. Next: Lesson 5, attaching a disk and finding it on the PCI bus.

L5

PCI Bus Enumeration

Next · concept + build

How the kernel finds devices on the PCI (Peripheral Component Interconnect) bus. PCI configuration space via I/O ports 0xCF8 (address) and 0xCFC (data). Walking every bus/device/function, reading vendor and device IDs, listing every device QEMU exposes. Identifying the virtio-blk device by its vendor 0x1AF4 and device ID. Reading BARs (Base Address Registers) to find the device's memory-mapped registers. Why PCI exists as a discovery protocol separate from any specific device driver.

Build steps:

  • 5.1 — Create the raw disk image (~1 MB) with a known signature at sector 0. Attach to QEMU via -device virtio-blk-pci. Verify QEMU accepts it.
  • 5.2 — PCI config space access functions (pci_config_read, pci_config_write) via ports 0xCF8/0xCFC.
  • 5.3 — Walk bus 0, all 32 devices, all 8 functions. Print a table of vendor ID, device ID, class for each present device.
  • 5.4 — Find the virtio-blk specifically. Read its BARs, print the MMIO region layout.

Linux counterparts: arch/x86/pci/direct.c (PCI config space access), drivers/pci/probe.c (bus enumeration), drivers/virtio/virtio_pci_modern_dev.c (virtio PCI modern layout).

L6

virtio Device Initialization

Upcoming · concept + build

What virtio is (a paravirtualized device standard — devices designed for VMs, with shared-memory communication instead of emulated hardware registers). The virtio PCI modern transport: capability list, common config region, ISR config, device-specific config. The virtio handshake: reset, acknowledge, negotiate features, FEATURES_OK, DRIVER_OK. Why the handshake exists — feature negotiation lets old guests and new hosts coexist.

Build steps:

  • 6.1 — Read the virtio PCI capability list. Find common config, ISR, device config, notification structures.
  • 6.2 — Reset the device, set ACKNOWLEDGE status bit, set DRIVER status bit.
  • 6.3 — Read device features, write the subset we support (VIRTIO_BLK_F_BLK_SIZE etc.), set FEATURES_OK.
  • 6.4 — Set DRIVER_OK. Device is now live.

Linux counterparts: drivers/virtio/virtio_pci_modern.c, drivers/virtio/virtio.c. Spec: OASIS VIRTIO 1.2.

L7

Virtqueues — The Ring Buffer Mechanism

Upcoming · concept + build

The data structure that makes virtio fast: shared-memory ring buffers used to submit work to the device. Three regions: the descriptor table (each entry points at a kernel buffer with a length and flags), the available ring (kernel appends descriptor indices to submit work), the used ring (device appends descriptor indices to signal completion). Split virtqueue format vs packed (modern alternative). Free-list management for descriptors. The kick (notify device of new work) and the device's response mechanism. Memory barriers — why they matter for shared-memory protocols.

Build steps:

  • 7.1 — Allocate descriptor table, available ring, used ring. Each must be page-aligned and physically contiguous.
  • 7.2 — Implement descriptor allocation from a free list.
  • 7.3 — Implement submit_chain(descriptors) — write descriptors, append to available ring.
  • 7.4 — Implement poll_completion() — check used ring for responses.
  • 7.5 — Implement kick() — write to the queue notify register to wake the device.

Linux counterparts: drivers/virtio/virtio_ring.c (the ring buffer implementation — both split and packed), drivers/virtio/virtio_ring_split.c.

L8

First Disk Read — Keystone 1

Keystone · build

The end-to-end proof that the driver stack works. Build a virtio-blk read request (sector 0, kernel buffer, read flag), submit it through the virtqueue from Lesson 7, poll for completion, verify the bytes match the signature written in Lesson 5.1. From here on, every step above this layer is parsing and dispatch — the bytes-flowing-from-disk problem is solved.

Build steps:

  • 8.1 — Define virtio-blk request header struct (sector, type, reserved).
  • 8.2 — Submit a read of sector 0 into a 512-byte kernel buffer.
  • 8.3 — Poll for completion, verify bytes match the disk signature.
  • 8.4 — Generalize: virtio_blk_read_sector(n, buf).

Linux counterparts: drivers/block/virtio_blk.c — specifically virtblk_queue_rq which builds and submits the request.

L9

Block Layer — bio, Request Queue, Scheduler

Upcoming · concept + build

The block layer's job: take "read block N" requests from any filesystem, queue them, optimize the order, and dispatch to device drivers. Why it's not just a passthrough — merging adjacent requests reduces device round-trips; scheduling prevents starvation and respects priorities; multi-queue design scales across CPUs. Linux's struct bio (the unit of work — sector, length, buffer, completion callback), struct request (merged bios ready for dispatch), struct request_queue (per-device pipeline). I/O schedulers: elevator (sort by sector), deadline (prevent starvation), BFQ (latency for desktops), Kyber, none (for fast devices like NVMe). blk-mq multi-queue: per-CPU software queues feeding per-device-hardware queues.

Build steps:

  • 9.1 — Define Bio struct: sector, length, buffer pointer, completion flag. Async by design — submission returns immediately.
  • 9.2 — Define Request: a Bio (or merged chain of Bios) ready to dispatch.
  • 9.3 — Per-device request queue: Vec<Request> with submit + drain operations.
  • 9.4 — Adjacent-block merging: if incoming bio's sector follows the queue tail's, merge them.
  • 9.5 — Simple elevator scheduler: sort pending requests by sector before dispatch.
  • 9.6 — submit_bio public API: filesystems use this; queue handles the rest.
  • 9.7 — read_sector(n) becomes a thin synchronous wrapper that submits a bio, waits for completion.

Linux counterparts: block/blk-core.c, block/bio.c (struct bio), block/blk-mq.c (multi-queue design), block/elevator.c, block/mq-deadline.c, include/linux/blkdev.h. Reading: "The Linux Kernel: Block Layer" documentation.

L10

Page Cache — address_space and Page Lookup

Upcoming · concept + build

The page cache: the kernel's cache of recently-accessed 4 KB file pages in RAM. Indexed by (inode, page_offset). Hit: return instantly from RAM. Miss: ask the filesystem to fill the page from disk. struct page (represents one physical page frame, with state flags — dirty, locked, writeback, etc.). struct address_space (per-inode structure that holds the page cache tree — historically a radix tree, modern kernels an xarray). Dirty page tracking and writeback: writes go to the page cache, marked dirty; a kernel thread eventually flushes them back to disk. Read-ahead: predictively load sequential pages.

The mini-os design will use a simple BTreeMap<u64, Box<[u8; 4096]>> per inode (page offset → page contents). The Vec<u8>-on-heap from Lesson 2 retires — disk-backed inodes go through the page cache. Ramfs inodes keep their heap-Vec shape (since the cache IS the storage for ramfs).

Build steps:

  • 10.1 — Define Page struct: 4 KB byte array, dirty flag.
  • 10.2 — Define AddressSpace: BTreeMap<page_offset, Page>, lock.
  • 10.3 — lookup_page(inode, offset) — hit returns cached page, miss triggers fill.
  • 10.4 — Fill path: allocate page, call filesystem's readpage(inode, offset, page) to populate from disk.
  • 10.5 — Update disk-backed Inode to hold an AddressSpace instead of Mutex<Vec<u8>>.
  • 10.6 — (Deferred to later) dirty page writeback via a kernel thread.

Linux counterparts: include/linux/pagemap.h, mm/filemap.c (file page cache operations), mm/page-writeback.c, include/linux/fs.h (struct address_space).

L11

ext2 On-Disk Format — Superblock and Inodes

Upcoming · concept + build

ext2's on-disk byte layout. The disk is divided into fixed-size blocks (1 KB or 4 KB). Blocks are organized into block groups, each with its own superblock backup, block group descriptor, block bitmap, inode bitmap, and inode table. Superblock at offset 1024 — magic 0xEF53, block size, inodes per group, blocks per group, total inode count. Block group descriptor table follows, one entry per group. Inode struct (128 bytes for ext2 rev 0, 256 for rev 1): i_mode (file type + permissions), i_size, i_block array (12 direct pointers + 1 single-indirect + 1 double-indirect + 1 triple-indirect). Reading bytes 0–4095 of a file = read i_block[0]; bytes 12 KB+ need indirect blocks.

Build steps:

  • 11.1 — Build an ext2 image with mkfs.ext2, attach to QEMU, replace the test disk.
  • 11.2 — Parse superblock struct. Validate magic. Print block size, total blocks, inodes per group.
  • 11.3 — Parse block group descriptor table. Print layout of block group 0.
  • 11.4 — Implement read_ext2_inode(ino) -> Ext2Inode. Compute block group, index within group, offset into inode table.
  • 11.5 — Read inode 2 (root). Print its i_mode, i_size, i_block array.

Linux counterparts: fs/ext2/super.c, fs/ext2/balloc.c, fs/ext2/inode.c, include/linux/ext2_fs.h. Reference: Ext2 Disk Storage Structure.

L12

ext2 Directory Walking

Upcoming · concept + build

ext2 directory entries: variable-length records, each containing inode (4 bytes), rec_len (2 bytes — distance to next entry), name_len (1 byte), file_type (1 byte — regular, dir, symlink, etc.), then the name (no null terminator — name_len covers it). This is a different format from the dirents we built in Lesson 3 (which were length-prefixed with a u64 inode) — ext2 uses a u32 inode and the record length doubles as the "advance to next" pointer. Walking a directory means iterating its data blocks, parsing each entry, checking the name. Path resolution: /foo/bar.txt walks inode 2 → "foo" → inode N → "bar.txt" → inode M.

Build steps:

  • 12.1 — Parse directory entries from an inode's data blocks.
  • 12.2 — Implement ext2_lookup(dir_inode, name) -> Option<u64> (returns child inode number).
  • 12.3 — Implement path resolution: walk /foo/bar/baz.txt through ext2.

Linux counterparts: fs/ext2/dir.c, fs/ext2/namei.c (path lookup).

L13

Mount ext2 and First Full-Stack Read — Keystone 2

Keystone · build

Wire ext2 into the existing VFS. Replace the lazy_static ROOT_INODE with an ext2-backed root. Path resolution calls through to ext2 directory walking; reads go through the page cache; misses submit bios to the block layer; the block layer dispatches to virtio-blk; virtio-blk talks to QEMU; bytes flow back up the whole stack and land in the user buffer. The VFS API (open, read, write, close) stays identical — only the storage backend changes. User programs that worked against ramfs keep working.

Build steps:

  • 13.1 — Add a backend field to Inode: enum Backend { Ramfs(Vec<u8>), Ext2(Ext2Inode) }.
  • 13.2 — Replace ROOT_INODE with an ext2-backed inode. Read root directory from disk.
  • 13.3 — Update resolve_path to walk ext2 directories when the root is ext2-backed.
  • 13.4 — Add /hello.txt to the disk image. Boot, run a user program that reads it, verify bytes come back.

Linux counterparts: fs/super.c (mount, mount_bdev), fs/ext2/super.c (ext2's mount callback).

L14

ELF Loader

Upcoming · concept + build

The ELF (Executable and Linkable Format) byte layout: ELF header (magic 0x7F 'E' 'L' 'F', class, endianness, machine type, entry point virtual address, program header table offset and entry count), then program headers describing each segment. PT_LOAD segments are the ones to map — they have a file offset, a virtual address, sizes in file and in memory (the difference being zero-fill). The loader reads headers, allocates a fresh AddressSpace, maps each loadable segment at its virtual address with the right permissions (R/W/X), and returns the entry point address.

Build steps:

  • 14.1 — Parse ELF header struct. Validate magic and class (we want ELF64 little-endian x86-64).
  • 14.2 — Parse program headers. Identify PT_LOAD segments.
  • 14.3 — Allocate a fresh AddressSpace, map each PT_LOAD segment with permissions.
  • 14.4 — Compile a tiny Rust user program as a static ELF (no dynamic linker). Load it from a file, verify segments land at expected addresses.

Linux counterparts: fs/binfmt_elf.c (the ELF binary format handler — specifically load_elf_binary), fs/exec.c (do_execve common code). Reference: ELF format specification.

L15

exec() Syscall — The Objective

Objective

The culmination. exec(path) opens a file via VFS (now reading from ext2 on disk), reads its bytes (through the page cache, populated by the block layer, fetched by virtio-blk), parses ELF, allocates a fresh address space, maps the segments, sets up a fresh user stack, and iretqs into the entry point. The current hand-assembled USER_PROGRAM is gone — programs are now real Rust crates compiled externally, written to the disk image, and loaded by the kernel at runtime.

Build steps:

  • 15.1 — Add exec(path) -> ! syscall. Body: open via VFS, read, parse ELF, switch address space, jump to entry.
  • 15.2 — Build a Rust user-program crate that compiles to a static ELF. Cross-compile for our x86_64-mini-os target.
  • 15.3 — Write the compiled ELF to the disk image as /init.
  • 15.4 — Boot the kernel. Kernel calls exec("/init"). The external program runs.

Linux counterparts: fs/exec.c, fs/binfmt_elf.c. This is where everything we built connects: VFS opens the file, page cache holds its bytes, ext2 parses its blocks, the block layer dispatches requests, virtio-blk fetches them, the ELF loader maps segments, the scheduler transfers control to the entry point.

After the objective

Reaching exec() is the objective, not the end of the road. Natural follow-ups once disk-loaded ELF execution works:

  • Shell. A user program that reads commands from stdin and fork+execs them. Requires fork (already exists in mini-os) and wait.
  • Argument passing. exec(path, argv) — push argv onto the new user stack.
  • Multiple programs. Concurrent execution via the existing scheduler. Each runs from its own ELF on disk.
  • Writeback. Extending write() to actually persist to disk via the virtqueue write path. Page cache dirty pages get flushed by a kernel thread.
  • pipe(), mmap(), signals. Each a lesson of its own.
