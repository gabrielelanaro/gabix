Roadmap · Phase 2 · Networking

From virtio-net to a UDP Echo Server

Eight lessons that build a network stack the same way the disk path was built: discover the device, initialize the transport, move raw bytes, then climb the protocol layers one at a time. Two hello-worlds along the way: a ping reply from the gateway, and a user-space echo server the host can talk to.

Objective

A user program running in ring 3 calls socket(), bind(), recvfrom(), and sendto(). On the host, nc -u localhost 5555 sends a line of text; QEMU forwards it to the guest; the frame travels up through virtio-net → Ethernet → IPv4 → UDP → socket → user buffer; the user program echoes it; the reply travels back down the same stack and appears in the host terminal. Every layer of the Linux network receive and transmit path re-implemented, not skipped.

This phase is a deliberate parallel of the disk path (Lessons 5–14). The bottom three lessons reuse mental models you already own — PCI enumeration, the virtio modern transport, virtqueues. The new material starts where virtio-blk had nothing to teach: a device with two queues, buffers you must post before data arrives, and a protocol tower where each layer wraps the next.

Environment constraint — slirp shapes the milestones

QEMU user-mode networking (slirp) gives the guest address 10.0.2.15, gateway 10.0.2.2, with no host configuration and no root. The tradeoff: inbound traffic only reaches the guest through explicit port forwards (hostfwd), and the host cannot ping the guest.

So the ICMP hello-world is guest-initiated: the kernel pings the gateway and prints the reply (keystone 1). The UDP echo server is reachable from the host via hostfwd=udp::5555-:5555 (the objective). See QEMU network emulation docs.

L19

How Networks Work + Find virtio-net

Next · concept + build

Concept: networking from first principles. Two machines on a shared wire → frames and MAC addresses; a world of connected networks → routers, IP addresses, and why identity (MAC) and location (IP) must be separate address systems; many programs per machine → ports; best-effort delivery and where reliability lives; encapsulation and the layer model, made concrete by a byte-by-byte dissection of one real UDP packet. Two implementer's rules: network byte order is big-endian, and receive is unsolicited.

Build: familiar territory, done just-do-it style. Attach a virtio-net NIC (Network Interface Card) to QEMU, find it on the PCI bus with the Lesson 5 enumeration code, confirm its identity.

Build steps:

  • 19.1 — Add -netdev user,id=n0 -device virtio-net-pci,netdev=n0 to the QEMU invocation. Boot; confirm nothing breaks.
  • 19.2 — Extend the PCI walk output: virtio-net appears as vendor 0x1AF4, device 0x1041 (modern; virtio device ID 1). Print its BARs.
  • 19.3 — Generalize the Lesson 5 "find virtio-blk" helper into find_virtio_device(device_id) so both drivers share it.

Linux counterparts: drivers/net/virtio_net.c (probe entry), drivers/virtio/virtio_pci_modern.c (shared with blk). Spec: VIRTIO 1.2 §5.1 Network Device.

L20

virtio-net Initialization — Two Queues, MAC, RX Posting

Upcoming · concept + build

The handshake is the one you know: reset → ACKNOWLEDGE → DRIVER → feature negotiation → FEATURES_OK → DRIVER_OK. What's new is the device on the other side. Feature bits to negotiate: VIRTIO_NET_F_MAC (device supplies its MAC address in device config) and explicitly not VIRTIO_NET_F_MRG_RXBUF (one frame per buffer keeps the RX path simple). Two virtqueues instead of one: queue 0 is the receive queue, queue 1 is the transmit queue. Every frame in both directions is prefixed by a 12-byte virtio_net_hdr (checksum-offload and segmentation metadata — all zeros for us, since we negotiate none of those features). The conceptual novelty: the RX queue must be stocked with empty buffers before anything can arrive. The device is a consumer of buffers you produce.

Build steps:

  • 20.1 — Reuse the virtio modern-transport code from Lesson 6 for the net device: capability walk, common config mapping, handshake through FEATURES_OK.
  • 20.2 — Read the MAC address from device config space; print it.
  • 20.3 — Set up virtqueue 0 (RX) and virtqueue 1 (TX) with the Lesson 7 VirtQueue code.
  • 20.4 — Post 8 empty 2048-byte RX buffers (device-writable descriptors) into the receive queue. Set DRIVER_OK.

Linux counterparts: drivers/net/virtio_net.c — virtnet_probe (feature negotiation, MAC read), try_fill_recv (RX buffer posting). Spec: VIRTIO 1.2 §5.1.4 (device config), §5.1.6 (device operation, virtio_net_hdr).

L21

First Frames on the Wire

First RX bytes · build

The Ethernet frame layout: destination MAC (6 bytes), source MAC (6), EtherType (2, big-endian — 0x0806 ARP, 0x0800 IPv4), then payload. Transmit path: build a broadcast frame, prefix the zeroed virtio_net_hdr, chain it into the TX queue, kick, confirm the device consumed it. Receive path: poll the RX used ring, strip the header, parse the Ethernet header, print source/destination/EtherType, recycle the buffer back into the queue. Slirp answers broadcast ARP traffic, which guarantees something arrives to parse. Driver abstraction at the end: send_frame(&[u8]) and recv_frame() -> Option<Frame> — the network parallel of Lesson 9's read_sector.

Build steps:

  • 21.1 — EthernetHeader parse/build with explicit big-endian handling (from_be_bytes enters the codebase).
  • 21.2 — TX: send a broadcast frame with a recognizable payload; verify the used ring reports completion.
  • 21.3 — RX: poll, strip virtio_net_hdr, hexdump the first frame that arrives.
  • 21.4 — Buffer recycling: consumed RX buffers get re-posted, keeping the queue stocked.
  • 21.5 — Wrap as NetDevice { send_frame, recv_frame, mac }.

Linux counterparts: drivers/net/virtio_net.c — start_xmit, receive_buf; net/ethernet/eth.c — eth_type_trans.

L22

ARP — Who Has 10.0.2.2?

Upcoming · concept + build

The problem ARP (Address Resolution Protocol) solves: IP addresses name hosts, but Ethernet delivers to MAC addresses, and nothing ties the two together until someone asks. The packet layout from RFC 826: hardware type, protocol type, operation (1 = request, 2 = reply), then sender/target MAC+IP pairs. The kernel adopts its slirp identity — 10.0.2.15 — as a compile-time constant (no DHCP client; that is a side quest). Broadcast "who has 10.0.2.2?", receive the reply, cache the mapping. Also answer incoming requests for our own address: that is what makes the guest exist on the network. First two-way conversation the kernel has ever had.

Build steps:

  • 22.1 — ArpPacket parse/build (28 bytes for IPv4-over-Ethernet).
  • 22.2 — Transmit a request for 10.0.2.2; parse the reply; print the gateway MAC.
  • 22.3 — ARP cache: BTreeMap<Ipv4Addr, MacAddr> with a resolve() entry point.
  • 22.4 — Reply path: answer requests targeting 10.0.2.15.

Linux counterparts: net/ipv4/arp.c — arp_process (the RFC 826 merge algorithm), net/core/neighbour.c (the cache). Spec: RFC 826.

L23

IPv4 — Header, Checksum, Demux

Upcoming · concept + build

The 20-byte IPv4 header from RFC 791: version + IHL (Internet Header Length), total length, TTL (Time To Live), protocol number (1 = ICMP, 17 = UDP — the demux key for the layer above), source and destination addresses, and the header checksum. The internet checksum algorithm (RFC 1071): sum 16-bit words in one's complement, fold the carries, invert — shared by IP, ICMP, and UDP, so it is written once as a utility and reused three times. Fragmentation fields get parsed and rejected rather than implemented (slirp will not fragment our small packets). Transmit side: build a header, compute its checksum, resolve the next hop via Lesson 22's ARP cache, hand to send_frame.

Build steps:

  • 23.1 — internet_checksum(&[u8]) -> u16 utility + unit test against a hand-computed example.
  • 23.2 — Ipv4Header parse: validate version, IHL, checksum; extract protocol + addresses.
  • 23.3 — Ipv4Header build: fill fields, compute checksum, prepend to payload.
  • 23.4 — RX demux: Ethernet EtherType → IPv4 → protocol number dispatch (ICMP / UDP / drop). Print one line per received packet.

Linux counterparts: net/ipv4/ip_input.c — ip_rcv, net/ipv4/ip_output.c, lib/checksum.c. Specs: RFC 791, RFC 1071.

L24

ICMP — Ping the Gateway (Keystone 1)

Keystone · complete

The network hello-world. ICMP (Internet Control Message Protocol) echo request: type 8, code 0, checksum, identifier, sequence number, payload. The gateway's reply is the same packet with type 0 and a recomputed checksum. The kernel sends four sequential echo requests to 10.0.2.2 through the full transmit stack (ICMP → IPv4 → ARP-resolved Ethernet → virtio-net) and matches the reply coming back up the receive stack. When reply id=0x2400 seq=7..10 ttl=255 prints on serial, the stack works end-to-end — the moment that parallels Lesson 8's first disk read. Echo replies to inbound pings are also implemented, even though slirp can't deliver any from the host — correctness per RFC 792 costs five lines here.

Build steps:

  • 24.1 — EchoMessage parse/build; checksum over header + payload.
  • 24.2 — Send echo requests to 10.0.2.2 through syscall 902; poll RX until the matching replies arrive.
  • 24.3 — Loop: 4 pings with sequences 7..10, verifying all 4 replies.
  • 24.4 — Reply path: answer inbound echo requests addressed to 10.0.2.15.

Linux counterparts: net/ipv4/icmp.c — icmp_echo, icmp_reply. Spec: RFC 792.

L25

UDP — Datagrams In, Datagrams Out

Complete · host round trip

The 8-byte UDP (User Datagram Protocol) header from RFC 768: source port, destination port, length, checksum. Ports are the new idea — the address within a host, the demux key that lets one machine hold many conversations. The UDP checksum covers a pseudo-header borrowing fields from the IP layer (a deliberate layering violation worth understanding, since TCP inherits it). In-kernel echo first: a hardcoded port-5555 handler that swaps source and destination and sends the payload back. QEMU gains hostfwd=udp::5555-:5555; the host runs nc -u localhost 5555 and sees its line come back. First inbound traffic from outside the virtual machine.

Build steps:

  • 25.1 — UdpHeader parse/build; pseudo-header checksum (reusing internet_checksum).
  • 25.2 — RX: IPv4 protocol 17 dispatch → parse UDP → print (src port, dst port, payload).
  • 25.3 — TX: send_udp(dst_ip, dst_port, src_port, payload) down the full stack.
  • 25.4 — In-kernel echo on port 5555 + hostfwd in the QEMU script; verify with nc -u from the host.

Linux counterparts: net/ipv4/udp.c — __udp4_lib_rcv, udp_send_skb. Lesson: Open Lesson 25. Tour: Follow the implementation. Spec: RFC 768.

L26

Sockets — The User-Space Echo Server (Objective)

Complete · verified

The syscall surface. A socket is a file descriptor whose backing object is a network endpoint instead of an inode — the same move Lesson 2 made for files, now for the network. Kernel side: a Socket struct (bound port, RX datagram queue), a port → socket demux table replacing Lesson 25's hardcoded handler, and four syscalls: socket(), bind(), recvfrom() (blocking — the process yields until a datagram lands, exercising the Phase 1 scheduler), sendto(). User side: echo_server.elf, compiled externally like hello.elf, loaded from the ext2 disk by exec, serving UDP echo from ring 3. Phase 1 and Phase 2 and the original mission all meet in this one binary.

Build steps:

  • 26.1 — Socket struct + kernel socket table; UDP RX demux delivers into per-socket queues.
  • 26.2 — Syscalls: socket, bind, sendto, recvfrom (with user-pointer validation, as in Lesson 2).
  • 26.3 — Blocking recvfrom: park the process, wake on datagram arrival.
  • 26.4 — echo_server.elf user program; write to disk image; exec it; drive it from the host with nc -u localhost 5555.

Linux counterparts: net/socket.c — sys_socket, sys_bind, sys_recvfrom; net/ipv4/udp.c — __udp4_lib_lookup (the port demux). This is where everything connects: virtio-net fetches frames, Ethernet/ARP/IP/UDP parse them, the socket table routes them, the scheduler wakes the blocked process, and a ring-3 binary loaded from your ext2 disk answers the host. Lesson: Open Lesson 26. Tour: Follow the implementation.

L27

Nonblocking Sockets and Readiness

Concept · implementation pending

Extend the blocking socket model with nonblocking recvfrom, EAGAIN, and a small readiness-driven event loop. Readiness follows each FD to its socket queue and lets one task serve many sockets without sleeping on an idle one. Device polling or interrupts remain beneath this user-space readiness layer.

Lesson: Open Lesson 27. Reference: Nonblocking socket quick reference.

After the objective

  • TCP. The deferred arc: three-way handshake, sequence/acknowledgment numbers, the state machine, retransmission. ~4–5 lessons on top of the same IPv4 layer. RFC 9293 is the modern consolidated spec.
  • DHCP client. Replace the hardcoded 10.0.2.15 with real address acquisition. ~1 lesson, pure UDP application code. Lesson 30 concept page ready.
  • DNS resolver. Query 10.0.2.3, parse the response. ~1 lesson, also pure UDP.
  • Interrupt-driven RX. Replace polling with the virtio ISR (Interrupt Status Register) → MSI-X or legacy interrupt → wake the stack. Pairs well with Phase 1 signal work.
  • tap networking. Swap slirp for a tap device to let the host ping the guest and run tcpdump on real frames. Host-side setup, no kernel changes.

How to use this roadmap

Same convention as the disk roadmap: each lesson is a discrete HTML file with a concept section and a build section; build substeps are each independently committable; a code tour (tours/tour-NNNN-*.html) gets built alongside. Open this roadmap to orient, pick the current lesson, drive the steps, commit each.

Pace expectation from the disk phase: 1–3 hours per lesson once the concept lands, and the concept conversation is the long pole. L19–L21 are mostly familiar (virtio-shaped); expect them fast. L22 (ARP) and L26 (blocking sockets) carry the genuinely new models; protect conversation time there.
