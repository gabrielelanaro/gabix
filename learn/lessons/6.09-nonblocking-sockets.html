Lesson 27 · Networking extension

Nonblocking Sockets and Readiness

Let one event loop serve many UDP sockets without sleeping inside any one receive call.

Prerequisite Lesson 26Focus queue stateBuild status implemented and tested

Lesson 26’s echo server works well for one socket. A server handling many sockets needs one place to wait for whichever socket has work. Nonblocking calls and readiness APIs provide that structure.

The problem: one thread, two sockets

Imagine a server that needs to listen on two UDP ports. Port 5555 handles time queries. Port 7777 handles chat messages. Both receive requests unpredictably. How does one server thread handle both?

Socket A:fd 3, bound to port 5555
Socket B:fd 4, bound to port 7777
Server:one thread, must serve both

A blocking recvfrom on fd 3 sleeps until port 5555 receives data. While that call sleeps, port 7777’s queue fills with unread messages. The thread never checks fd 4. One socket blocks all others.

The wrong approaches

You might try two naive fixes. Both fail for specific reasons.

Sequential blocking

Call recvfrom(3), then recvfrom(4), then repeat. Each call sleeps until its socket receives data. The thread spends most of its time asleep on the wrong socket.

Two threads

One thread per socket works, but scales poorly. A thousand concurrent connections means a thousand threads. Each thread consumes a kernel stack and scheduler overhead.

The underlying problem: blocking recvfrom commits the calling thread to one specific socket until data arrives. You need a way to wait on all sockets simultaneously and wake when any of them has work.

Nonblocking calls return immediately

A nonblocking socket changes the contract. When the receive queue is empty, the kernel does not put the task to sleep. It returns an error code immediately.

CallQueue has a datagramQueue is empty
blocking recvfrompop one datagram and returnput the calling task to sleep until data arrives
nonblocking recvfrompop one datagram and returnreturn immediately with EAGAIN or EWOULDBLOCK

EAGAIN means “this operation would need to wait; try again later.” POSIX permits either EAGAIN or EWOULDBLOCK for an empty nonblocking socket. Portable code checks for both.

Nonblocking mode solves the thread commitment problem. A loop can check both sockets without getting stuck on one.

// Busy-wait: check both sockets constantly
loop {
    match recvfrom_nonblocking(3, buffer) {
        Datagram(bytes, client) => handle_time_query(bytes, client),
        EAGAIN => {},  // Not ready yet, keep going
        error => handle(error),
    }

    match recvfrom_nonblocking(4, buffer) {
        Datagram(bytes, client) => handle_chat_message(bytes, client),
        EAGAIN => {},
        error => handle(error),
    }
}

This loop works, but it burns CPU. The thread never sleeps. It spins through both checks even when both queues are empty. You need a way to sleep until at least one socket has data.

Readiness tells you when to try

Readiness APIs answer the question “which operations can make progress without blocking?” You register a set of file descriptors with the kernel. The kernel sleeps your thread and wakes it only when one of those descriptors becomes ready.

The three POSIX readiness facilities are select, poll, and epoll. They solve the same problem with different tradeoffs.

select: bitsets modified in-place

select uses fixed-size bitsets. You pass a bitset of fds you care about; the kernel clears it and sets only the bits for ready fds.

// Before select: set bits for fds 3 and 4
fd_set readfds;
FD_ZERO(&readfds);
FD_SET(3, &readfds);  // "I care about fd 3"
FD_SET(4, &readfds);  // "I care about fd 4"

// select() returns with ONLY ready fds set
int n = select(5, &readfds, NULL, NULL, NULL);  // 5 = max fd + 1

// After select: check which bits are still set
if (FD_ISSET(3, &readfds)) { /* fd 3 is ready */ }
if (FD_ISSET(4, &readfds)) { /* fd 4 is ready */ }

The bitset is modified in-place. Every call copies the entire bitset to and from the kernel. The bitset size is fixed at compile time: FD_SETSIZE, usually 1024. You cannot monitor fd 1025 with select.

poll: array of structs, linear scan

poll uses an array of struct pollfd. Each entry has an fd, the events you want, and the events that are ready.

struct pollfd fds[] = {
    { .fd = 3, .events = POLLIN, .revents = 0 },
    { .fd = 4, .events = POLLIN, .revents = 0 },
    { .fd = 5, .events = POLLIN, .revents = 0 },
};

// poll() returns number of ready fds
int n = poll(fds, 3, -1);  // 3 fds, -1 = wait forever

// After poll: check revents for each fd
for (int i = 0; i < 3; i++) {
    if (fds[i].revents & POLLIN) {
        /* fds[i].fd is ready */
    }
}

No fixed limit on fd count. But every call copies the entire array to and from the kernel, and the kernel checks every fd in the array. For 10,000 connections, poll checks 10,000 fds even if only 5 are ready.

epoll: registration separate from waiting

epoll creates a separate epoll file descriptor that maintains state in the kernel. You register interest once with epoll_ctl, then wait with epoll_wait.

int epfd = epoll_create1(0);

// Register fds ONCE
struct epoll_event ev = { .events = EPOLLIN, .data.fd = 3 };
epoll_ctl(epfd, EPOLL_CTL_ADD, 3, &ev);

ev.data.fd = 4;
epoll_ctl(epfd, EPOLL_CTL_ADD, 4, &ev);

// Wait in a loop - only ready fds are returned
struct epoll_event events[10];
while (1) {
    int n = epoll_wait(epfd, events, 10, -1);
    for (int i = 0; i < n; i++) {
        int fd = events[i].data.fd;  // Only READY fds
        /* handle fd */
    }
}

epoll_wait returns only the fds that are actually ready. For 10,000 connections where 5 are ready, epoll_wait returns 5 entries. The kernel maintains the watch list; you don’t copy it on every call.

Kernel-side cost: why epoll scales

The user-space iteration difference matters, but the kernel-side difference is why epoll handles large connection loads. select and poll do work per poll call. epoll does work per event.

select and poll: kernel scans all fds on each call

// Kernel-side poll implementation (simplified)
sys_poll(user_fds, nfds, timeout) {
    for (i = 0; i < nfds; i++) {           // Scan ALL fds
        struct pollfd *p = &user_fds[i];
        struct file *f = resolve_fd(p->fd);

        if (f->socket->queue.is_not_empty()) {
            p->revents = POLLIN;
            count++;
        }
    }
}

For 10,000 connections, the kernel checks all 10,000 fds on every poll call, even if only 5 have data. This happens each time your server calls poll.

epoll: kernel maintains ready state incrementally

// When you register interest with epoll_ctl
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev) {
    struct epoll *ep = get_epoll(epfd);
    ep->watched_fds.insert(fd);        // O(1) add to watch list
    socket->epoll_watchers.push(ep);   // Link socket → epoll
}

// When a packet arrives (network delivery path)
udp_deliver(socket, packet) {
    socket->queue.push(packet);

    // Check: is anyone watching this socket via epoll?
    if (socket->epoll_watchers) {
        for (ep : socket->epoll_watchers) {
            ep->ready_list.push(socket->fd);  // O(1) add to ready
            wake_anyone_waiting_on(ep);
        }
    }
}

// When you call epoll_wait
epoll_wait(epfd, events, max_events, timeout) {
    struct epoll *ep = get_epoll(epfd);

    // Just copy the ready list - no scanning!
    n = min(ep->ready_list.len, max_events);
    memcpy(user_events, ep->ready_list, n);
    ep->ready_list.clear();
    return n;
}

With epoll, the kernel does O(1) work per packet (add fd to ready list) and O(ready_fds) work per epoll_wait call (copy the ready list). The expensive scan becomes an incremental update as events arrive.

APIKernel work per callKernel work per event
selectScan all watched fdsNone
pollScan all watched fdsNone
epollCopy ready listAdd fd to ready list

For 10,000 connections with steady traffic: poll scans 10,000 fds on every call. epoll does one O(1) operation per arriving packet and copies only the ready fds on each wait.

For UDP receive readiness, the kernel resolves each file descriptor through the FD table to its socket object and checks whether the receive queue contains a datagram.

fd 3 → process FD table → UDP socket → receive queue → nonempty?

Putting it together: the event loop

Nonblocking calls plus readiness yield the event loop pattern. Wait for any socket to become ready. Drain each ready socket completely. Repeat.

// Ask for read readiness on both sockets
pollfds = [
    { fd: 3, events: READABLE },
    { fd: 4, events: READABLE },
];

loop {
    // Sleep until ANY socket has data
    ready = poll(pollfds, timeout);

    // Drain each ready socket completely
    for fd in ready {
        loop {
            match recvfrom_nonblocking(fd, buffer) {
                Datagram(bytes, client) => sendto(fd, bytes, client),
                EAGAIN | EWOULDBLOCK => break,  // Queue drained
                error => handle(error),
            }
        }
    }
}

If socket A has an empty queue while socket B receives a message, poll returns B. The event loop serves B without ever sleeping inside A’s recvfrom. One idle socket cannot stop progress on the others.

Readiness is a hint, not a promise

Another task may consume the data between poll and your recvfrom. Keep sockets nonblocking and handle EAGAIN even after a readiness notification. The inner loop that drains until EAGAIN handles this race.

How poll actually works: the waiter registration trick

The event loop pattern is clear from user space. But what happens inside the kernel when you call poll([3, 4], timeout)? The trick is called waiter registration.

What is “your task”?

Your echo server is a process with a Process Identifier (PID). When it calls poll, the kernel looks up which PID is making the call. That PID is “your task.”

Each socket tracks waiters

A socket stores its receive queue and a list of PIDs waiting for that socket to become readable. This is the wait queue.

When your echo server (PID 42) calls poll([3, 4]):

// For each fd you passed
for fd in [3, 4] {
    socket = resolve_fd_to_socket(fd);

    // Check if data is already available
    if socket.queue.is_not_empty() {
        ready_list.push(fd);
    }
}

// If ANY socket had data, return immediately
if ready_list.is_not_empty() {
    return ready_list;
}

// ALL sockets empty: register as waiter on each
for fd in [3, 4] {
    socket = resolve_fd_to_socket(fd);
    socket.waiters.push(42);  // Register PID 42
}

// Sleep the calling task
mark_task_blocked(42);
yield_to_scheduler();

Your task is now asleep. The kernel will run other tasks. But your PID (42) is registered on both sockets’ waiter lists.

Wakeup: delivery notices waiters

Later, when a UDP packet arrives for port 7777:

// Network driver receives frame
frame = nic.receive_frame();
packet = parse_udp(frame);

// Find destination socket by port
socket = port_table.lookup(7777);

// Enqueue the datagram
socket.queue.push(packet);

// Check: anyone waiting for this socket?
if socket.waiters.is_not_empty() {
    for pid in socket.waiters {
        mark_task_ready(pid);  // Wake them up
    }
    socket.waiters.clear();
}

PID 42 is marked Ready. The scheduler eventually runs your echo server again. You resume inside poll, which rechecks the sockets and returns fd 4 as ready.

The atomicity requirement

The check-and-register must be one atomic operation. If a packet arrives between the empty check and waiter registration, you would sleep forever while data sits in the queue. On single-CPU mini-os, disabling interrupts around this transition prevents the network worker from observing a half-finished state.

Two ways the kernel learns about packets

The waiter mechanism works the same regardless of how the kernel discovers packets. There are two approaches:

Interrupt-driven (real OSes)

NIC receives packet → hardware interrupt → CPU jumps to handler → handler processes packet → enqueues → wakes waiters. The interrupt preempts whatever is running and the handler runs immediately.

Polling worker (mini-os now)

A kernel task repeatedly polls the virtio-net device. When it finds a packet, it processes it → enqueues → wakes waiters. No interrupt, just a task that keeps checking.

Your echo server does not care which approach the kernel uses. poll() abstracts it away. User space says “sleep me until fd 4 has data,” and the kernel decides how to detect that data. Lesson 26 built the polling worker. Interrupt-driven receive can replace it later without changing the socket APIs.

See it happen: two sockets, one loop

Event loop · stage 1 of 5

1 · Register interest

The event loop calls poll asking for read readiness on fd 3 and fd 4. Both resolve through the FD table to separate UDP socket queues.

2 · Both queues are empty

The kernel checks each socket’s receive queue. Both are empty, so poll sleeps the event-loop task. Calling blocking recvfrom(3) here would commit the task specifically to socket 3, ignoring socket 4 until port 5555 receives traffic.

3 · A datagram reaches fd 4

The driver receives a frame, UDP selects fd 4’s socket by port lookup, and delivery changes its queue from empty to nonempty.

4 · Readiness wakes the event loop

poll reports fd 4 as readable. fd 3 remains absent because its queue is empty. The event loop wakes knowing exactly which socket to check.

5 · Drain until EAGAIN

Nonblocking recvfrom(4) consumes available datagrams. When the socket queue empties, the call returns EAGAIN. The inner loop breaks, the outer loop returns to poll, and the thread sleeps again until another socket becomes ready.

Retrieval check. fd 3 is empty and fd 4 contains one datagram. What should a readiness-driven server do first?

Device arrival and socket readiness are separate layers

Readiness APIs answer “can this user operation make progress?” But the kernel must first learn that a frame arrived from the network. That involves a different mechanism.

The network interface card (NIC) transfers a frame into a driver receive buffer. The kernel learns about that work by polling the device or receiving an interrupt. The network stack parses Ethernet, IPv4, and UDP, finds the destination socket by port lookup, and enqueues the datagram. That queue transition makes the socket readable and wakes tasks waiting in poll, select, or epoll.

NIC frame ready
→ device poll or interrupt
→ driver receives frame
→ Ethernet → IPv4 → UDP
→ port lookup → socket queue becomes nonempty
→ user-space readiness waiter wakes

Device polling and interrupts answer “does the hardware have work for the kernel?” Socket readiness answers “can this user operation make progress?” mini-os currently uses a polling network worker from Lesson 26. Readiness can be built above that worker; interrupt-driven receive can arrive later.

Two contracts, same path

Blocking and nonblocking recvfrom both reach the same socket object through the same path. The difference appears only when the receive queue is empty.

fd 3 → process FD table → UDP socket → receive queue

The queue owns the datagrams. The readiness API inspects that queue from the outside and decides whether a waiter should wake. When the queue has data, both calls return a datagram. When the queue is empty, blocking calls sleep and nonblocking calls return EAGAIN.

What to build next in mini-os

27.1
Nonblocking socket flag. Add a nonblocking: bool field to UdpSocket. When a socket has this flag set, modify recvfrom to return EAGAIN immediately instead of blocking when the receive queue is empty. All other behavior stays the same: if the queue has data, pop and return one datagram regardless of blocking mode.
27.2
Set nonblocking mode. mini-os accepts Linux's SOCK_NONBLOCK bit in the socket type argument. The socket starts in nonblocking mode, so this slice does not need a separate fcntl syscall.
27.3
Poll syscall structure. Define a struct pollfd with fd: i32, events: u16, and revents: u16 fields. Add SYS_POLL to the syscall enum. The syscall accepts a user pointer to an array of pollfd, the array length, and a timeout (ignored for now; return immediately if no fd is ready).
27.4
Poll kernel implementation: check all fds first. Resolve each fd in the array through the calling process’s FD table. Skip any that are not sockets (poll on regular files can wait). For each socket, check whether its receive queue is nonempty. Build a list of ready fds. If any socket has data, copy the revents bits back to user space and return the ready count. No sleep happens.
27.5
Poll kernel implementation: register waiters when empty. If all sockets are empty, you must register the calling task as a waiter on each socket before blocking. For each socket: atomically check that the queue is still empty, then push the current task’s PID onto the socket’s waiter list. This check-and-register must happen with interrupts disabled to prevent a lost wakeup. After registering on all sockets, mark the current task Blocked and yield.
27.6
Modify UDP delivery to wake waiters. When the network worker delivers a datagram to a socket, after pushing to the receive queue, check whether the socket’s waiter list is nonempty. If it is, mark each waiting PID Ready and clear the waiter list. This ensures poll resumes when any watched socket receives data.
27.7
Poll return path. When the task resumes after blocking, recheck all socket queues. Copy POLLIN into revents for each socket that currently has data. Return the count of ready fds. The recheck is necessary because another task might have consumed the data before this task resumed.
27.8
Two-port echo program. Modify the echo server to create two UDP sockets, bind one to port 5555 and the other to port 7777. Set both nonblocking. Enter an event loop: call poll on both fds, then drain whichever is ready with nonblocking recvfrom until EAGAIN, echo each datagram back to its sender. Verify from the Mac that echo 5555 and echo 7777 both receive prompt replies.
27.9
Keep the polling worker. The network worker from Lesson 26 continues unchanged. It polls virtio-net, parses packets, and delivers to sockets. The new poll syscall builds on top of this worker; interrupt-driven receive is a separate enhancement for later.
Current mini-os boundary

mini-os implements SOCK_NONBLOCK, empty-queue EAGAIN, and syscall 7 poll for UDP POLLIN. Poll timeouts support zero and infinite waits. select, epoll, writable readiness, and finite poll timers remain future work.
