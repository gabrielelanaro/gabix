The LAN9512: USB to Ethernet

The chip on the Pi that turns the USB port from lesson 7.04 into an Ethernet link — reached entirely through USB transfers.

The DWC2 host controller from 7.04 gives the ARM one USB port. A port with nothing attached carries no data, so the next step is a device. On the Pi 2B the chip soldered behind the Ethernet socket is the LAN9512, from SMSC (now Microchip). It packages a USB hub and a 10/100 Ethernet controller in one chip. The ARM never drives the Ethernet wire directly. It sends USB transfers to the LAN9512; the LAN9512 puts those bytes on the wire as Ethernet frames and returns received frames as USB transfers.

This lesson covers how gabix configures that chip and sends and receives frames through it. Every operation reuses the USB transfers from 7.04: register access is a USB control transfer, and frame I/O is a USB bulk transfer. The driver reuses transfer(); there is no second USB driver to write.

QEMU has no LAN9512, so gabix's QEMU port drives an RNDIS Ethernet dongle instead. Both chips implement the same FrameDevice trait, so the network stack above it (modules 5 and 6) is unchanged on both. Section 5 covers that trait.

1. One chip, two functions, behind the USB port

The LAN9512 is a USB device. It connects to the DWC2's port — the same port 7.04 brought up. gabix enumerates it with the routine from 7.02; it reports vendor 0x0424 and product 0xec00, the part on the Pi 2B, and is_lan9512() matches that pair. Inside the package are a two-port USB hub (further devices could attach to it) and an Ethernet MAC and PHY. gabix uses only the Ethernet controller.

The ARM reaches the chip through two USB endpoints: a bulk IN and a bulk OUT, which configure_bulk_device() from 7.04 locates. The ARM accesses adapter registers through control endpoint zero. Frame data uses the bulk endpoints. The current driver polls transfers through DWC2; it does not install an adapter interrupt handler.

2. Registers over USB: the vendor request

The LAN9512 has dozens of internal registers — MAC control, hardware config, EEPROM access. None is memory-mapped. The ARM reaches each one through a USB control transfer that carries a vendor request. read_register() issues a control READ (request type 0xc0, request READ_REGISTER = 0xa1) naming the register; the chip returns four bytes. write_register() issues a control WRITE (request type 0x40, request WRITE_REGISTER = 0xa0) carrying the four-byte value.

The ARM fills the setup packet (request type 0x40, request WRITE_REGISTER=0xa0, the register index) and the four-byte value; the DWC2 performs the SETUP+DATA+STATUS transaction on EP0; the LAN9512 writes the register. read_register is the reverse — control_read with type 0xc0, request 0xa1, four bytes returned (lan9512.rs:159, 173-175).

targets/armv7/src/raspi2b/lan9512.rs · register access over USB
unsafe fn read_register(host: &mut Dwc2, device: UsbDevice, register: u16) -> Option<u32> {
    let mut bytes = [0u8; 4];
    if host.control_read(device, USB_VENDOR_DEVICE_READ, READ_REGISTER, UNUSED_REQUEST_VALUE, register, &mut bytes)? != bytes.len() {
        return None;
    }
    Some(u32::from_le_bytes(bytes))
}

unsafe fn write_register(
    host: &mut Dwc2, device: UsbDevice, register: u16, value: u32,
) -> Option<()> {
    host.control_write(device, USB_VENDOR_DEVICE_WRITE, WRITE_REGISTER, UNUSED_REQUEST_VALUE, register, &value.to_le_bytes())
}

On the USB wire, "write register HW_CFG" is a SETUP+DATA+STATUS transaction — the same control-transfer sequence as the GET_DESCRIPTOR request from 7.02, addressed to a vendor register instead of a descriptor. The DWC2 performs the transaction; the ARM fills in the setup packet and reads the four bytes back.

3. Bring-up: reset, MAC, enable

configure() runs a fixed sequence of register writes that take the chip from reset to "transmit and receive enabled." In order: reset the MAC; read the factory MAC address out of the EEPROM; program it back into the address registers; set the hardware config (burst, offsets, flow control); then enable the MAC's transmitter and receiver and turn TX on. Each register access is a USB control transfer; reset polling and EEPROM reads require several accesses. See lan9512.rs::configure and read_mac_address.

write_register(&mut host, device, HW_CFG, LITE_RESET_REQUEST)?;            // reset the MAC
wait_register_clear(&mut host, device, HW_CFG, LITE_RESET_REQUEST)?;

let mac = read_mac_address(&mut host, device)                     // MAC from the EEPROM
    .filter(valid_mac_address)
    .unwrap_or([0x02, 0x47, 0x41, 0x42, 0x49, 0x58]);
write_register(&mut host, device, ADDRL, ...)?;                    // program the MAC low
write_register(&mut host, device, ADDRH, ...)?;                    // program the MAC high

let hardware = read_register(&mut host, device, HW_CFG)?;          // read current hardware configuration
write_register(&mut host, device, HW_CFG, (hardware | BULK_IN_EMPTY_RESPONSE) & !RX_DATA_OFFSET_MASK)?;
write_register(&mut host, device, BURST_CAP, 0)?;
write_register(&mut host, device, AFC_CFG, AFC_CFG_DEFAULT)?;
write_register(&mut host, device, COE_CR, CHECKSUM_OFFLOAD_DISABLED)?;

let mac_control = read_register(&mut host, device, MAC_CR)?;        // enable MAC: full duplex, TX, RX
write_register(&mut host, device, MAC_CR,
    mac_control | MAC_CR_FULL_DUPLEX | MAC_CR_TX_ENABLE | MAC_CR_RX_ENABLE)?;
write_register(&mut host, device, TX_CFG, TX_CFG_ON)?;               // transmit on

The reset write sets LITE_RESET_REQUEST; wait_register_clear polls HW_CFG over USB until the chip clears that bit, which signals reset finished. The MAC address comes out of the EEPROM one byte at a time through the E2P_CMD/E2P_DATA register pair (read_mac_address); if the EEPROM is absent or the address is the all-zero or broadcast default, gabix substitutes a fixed locally-administered address. The final two writes set MAC_CR_FULL_DUPLEX | MAC_CR_TX_ENABLE | MAC_CR_RX_ENABLE and write TX_CFG_ON, after which the chip accepts frames for sending and delivers received frames to the bulk IN endpoint.

4. Frames over bulk: TX and RX

Once configured, frames cross the two bulk endpoints. transmit() prefixes the Ethernet frame with an eight-byte smsc95xx header — a command/length word followed by a length word — and sends the result with bulk_out. receive() reads bytes with bulk_in, then read_rx_frame strips the four-byte RX status header and the four-byte trailing frame-check sequence and returns the frame. The header layout is defined in crates/kernel-core/src/net/smsc95xx.rs, shared so the same framing parses on any target.

let command_a = length as u32 | TX_FIRST_SEGMENT | TX_LAST_SEGMENT;
out[..4].copy_from_slice(&command_a.to_le_bytes());      // command + length

USB bulk transfers carry a one-bit packet ID that toggles between DATA0 and DATA1 from packet to packet. update_pid() flips gabix's tx_pid and rx_pid when an odd number of packets crossed the endpoint, so the next transfer uses the opposite PID. A wrong PID makes the device reject every packet with a NAK; keeping the PID in sync is required.

targets/armv7/src/raspi2b/lan9512.rs · transmit / receive over bulk
fn transmit(&mut self, frame: &[u8]) -> bool {
    unsafe { self.transmit_frame(frame) }
}

transmit_frame builds the eight-byte adapter header, submits the buffer with bulk_out, and advances the USB data PID after success. Its boolean reports local submission success. Confirming that another computer received the Ethernet frame requires a reply or a packet capture. Source: lan9512.rs, lines 135–156 and 170–172.

5. A shared frame interface

The network stack above this point (ARP, IP, UDP — modules 5 and 6) never names the LAN9512. It holds a FrameDevice: a trait with mac_address(), transmit(), and receive(). On the Pi, UsbEthernet::Lan9512 supplies it; in QEMU, UsbEthernet::Rndis supplies it. configure() selects an adapter using the enumerated vendor/product IDs. Wi-Fi builds also support UsbEthernet::Wifi; that adapter converts between Ethernet frames and Wi-Fi frames. See raspi2b/ethernet.rs::UsbEthernet. The diagram below shows the two wired adapters.

On the Pi, UsbEthernet::Lan9512 supplies the trait; in QEMU, UsbEthernet::Rndis supplies it (ethernet.rs:7-24). configure() picks which by reading the vendor and product ID from enumeration (ethernet.rs:13-19). The ARP/IP/UDP stack above the trait holds FrameDevice and is the same code on both machines.

targets/armv7/src/raspi2b/ethernet.rs · dispatch by vendor/product ID
pub enum UsbEthernet { Lan9512(Lan9512Ethernet), Rndis(RndisEthernet) }

impl UsbEthernet {
    pub unsafe fn configure(host: Dwc2, device: UsbDevice) -> Option<Self> {
        if is_lan9512(device.vendor_id, device.product_id) {
            Lan9512Ethernet::configure(host, device).map(Self::Lan9512)
        } else if device.vendor_id == 0x0525 && device.product_id == 0xa4a2 {
            RndisEthernet::configure(host, device).map(Self::Rndis)
        } else { None }
    }
}

That is why the Pi port and the QEMU port share every line of the network code. The hardware-specific work — USB control transfers for registers, USB bulk transfers for frames, smsc95xx or RNDIS framing — is in the trait implementations. The ARP table, the IP route, and the UDP sockets above the trait are the same code on both machines.
