Cooperative scheduling on ARM

How a kernel task pauses, how another task runs, and how the first task resumes.

Course map · Quick reference

This lesson explains cooperative scheduling in isolation. Timer preemption has since been added; lesson 3.06 explains that addition. The simulations here keep preemption disabled.

1. Start with the loop already running on the Pi

The Pi checks UART input and Ethernet packets repeatedly. After checking one device, the loop checks the other. Both devices receive attention because each check returns to the loop.

Suppose we want two functions to run independently. Each function has a loop and local variables. If we call the first function normally, the second function must wait until that call returns. Scheduling lets the first function pause before it returns, so the second function can run.

In this implementation, a task is a function with its own stack and a record of the CPU state needed to resume it. The scheduler is kernel code that chooses which task runs. These tasks share kernel memory; they have no process memory isolation.

2. A task pauses by calling yield_now()

Here is the first task from our boot test. Its local variable starts at 10.

fn first_task() {
    let mut local = 10;
    for _ in 0..3 {
        record(local);
        local += 1;
        yield_now();
    }
}

record(local) appends the number to the test’s output array. The first iteration records 10, changes local to 11, and calls yield_now().

That call pauses this task and resumes the scheduler. The scheduler can then run another task. When it selects the first task again, execution continues after the call to yield_now(). The local variable is still 11, so the next iteration records 11.

This is cooperative scheduling: a running task must call yield_now() or return before another task can run. A task that loops forever without yielding prevents the other tasks from running.

4. What must be saved when a task pauses?

The CPU has registers: small storage locations used while executing instructions. A task may have values in registers as well as in its stack in memory. When another task runs, it uses those same CPU registers.

To resume the paused task correctly, we save the register values required by our function-call rules and remember its stack pointer. Later we restore those values and continue at the saved return address. This save-and-restore operation is a context switch.

Each task has a separate stack, so its suspended function calls remain in memory while another task runs. The compiler decides whether a particular local variable is held in a register or on the stack.

The following simulation simplifies this to one CPU value and one saved value per task. With saving enabled:

  1. Increment A’s value from 10 to 11.
  2. Switch to B. The simulation saves 11 for A and loads B’s value, 20.
  3. Switch back to A. It loads A’s saved value, 11.

Increment A, then switch twice. Compare the restored value with your prediction.

Reset the values, disable saving, and repeat. A returns with 10 because its saved value was never updated to 11. This illustrates why the context switch must preserve the values a suspended function expects to keep.

5. Find these operations in the Rust code

Open scheduler.rs. Read these functions in order:

  1. spawn(entry) registers a task and prepares its private stack.
  2. run_until_finished() scans the task slots in order. It selects a Ready task, marks it Running, and switches to it. This selection loop is the dispatcher.
  3. yield_now() marks the current task Ready and switches back to the dispatcher. The next selection resumes another ready task, if one exists.
  4. task_entry() calls the registered task function. When that function returns, it marks the task Finished and switches back to the dispatcher.

task_entry() is a wrapper that runs when a task first starts. You may see such a wrapper called a trampoline. Its purpose here is to handle the task’s return, so every task function can return normally.

6. Compare ARM with x86

Both implementations choose a task and restore the state needed to continue its function call. The CPU instructions and register names differ.

Saved state or operationARMx86_64
Stack pointer: address of the current stack positionsprsp
Integer registers preserved by the switchr4–r11rbx, rbp, r12–r15
Continue at the saved return addressRestore the link register lr, then execute bx lrret reads the return address from the restored stack

Our x86 scheduler also supports timer-driven preemption. The cooperative behavior modeled in this lesson switches at explicit yields and task returns. ARM now also supports timer preemption, described in lesson 3.06.

Optional: read the ARM context-switch instructions

In context.rs, register r0 points to the context being saved and r1 points to the context being resumed.

push {r4-r11, lr}  // Copy these registers onto the current stack.
str sp, [r0]      // Store this stack position in the saved context.
ldr sp, [r1]      // Load the other context's stack position.
pop {r4-r11, lr}  // Load registers from that stack.
bx lr            // Continue at the restored return address.

The set of registers follows the function-call rules, also called the calling convention. Because yielding happens through a function call, the compiler already handles values in registers that a function call may overwrite.

A new task has no suspended call to restore. spawn therefore prepares nine words on its stack in the layout that pop expects: eight register values and the address of task_entry. The first switch starts that wrapper. After those words are removed, the stack pointer is aligned to eight bytes as required at function entry.

Compare the x86 context switch. For the ARM register and stack rules, see the ARM procedure-call standard.

7. What currently runs on the Pi

The boot test runs two tasks, checks that their recorded numbers are exactly 10, 20, 11, 21, 12, 22, and checks that both tasks finish. This passed in QEMU and on the physical Pi after UART reboot and kernel upload.

After that test, the Pi starts the existing UART/Ethernet polling loop. The device handlers have not yet been moved into separate scheduled tasks.

The scheduler currently has four task slots with 16 KiB stacks. It runs on one core and supports integer register state. Floating-point register state, blocking operations, and process memory isolation remain further work.
