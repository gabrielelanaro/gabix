Timer preemption on ARM

How a timer interrupt pauses a kernel task that has not called yield.

Previous: cooperative scheduling · Reference

Open the CPU and stack simulator to follow the register saves and restores step by step.

1. Why the timer calls the scheduler

In the previous implementation, task A had to call yield_now() or return before task B could run. A loop that kept doing work could prevent B from running indefinitely.

The timer now interrupts A periodically. Its handler acknowledges the interrupt and calls preempt_on_timer(). If a scheduled task is running, that function calls yield_now(). The dispatcher can then select B. This is timer-driven preemption.

The existing x86 kernel uses the same sequence: acknowledge the timer, then ask the scheduler to select a task. ARM needs different assembly to save the interrupted state and return to it.

2. An interrupt can arrive between any two instructions

A normal function call follows rules about which registers the called function must preserve. The compiler accounts for those rules when it generates a call to yield_now().

A timer interrupt can arrive while a calculation is using any general-purpose register. The interrupt wrapper therefore saves r0–r12, the kernel link register, the interrupted program address, and the processor status. The status includes condition flags and the interrupt-enable setting. Restoring these lets the interrupted instruction sequence continue correctly.

For example, the timer could arrive between a comparison and a conditional branch. The comparison’s condition flags must survive, so the branch makes the same decision after the task resumes.

3. Each paused task keeps its interrupt state on its own stack

ARM enters IRQ mode when the interrupt arrives. IRQ mode has its own stack pointer and link register. Our old handler used one shared IRQ stack.

A task can now remain paused inside its timer handler while another task runs. That other task may also receive a timer interrupt. We therefore save each interrupted task’s return state on its own kernel stack, called the SVC stack in this code.

The IRQ entry in boot.S performs these operations:

  1. Adjust the IRQ return address to the instruction where execution should resume.
  2. Use srsdb to store that address and the saved processor status on the SVC stack.
  3. Change to SVC mode and save the general-purpose registers. Also preserve the SVC saved-status register, which a syscall handler may be using.
  4. Align the stack for a Rust function call, then call the timer handler.
  5. When this task resumes, restore its registers and use rfeia to restore the interrupted address and processor status.

Inside the handler, the existing context switch saves its function-call state on the same task stack. The stack therefore contains both the interrupted task’s state and the handler’s suspended calls. Resuming the handler eventually restores the interrupted task.

4. Scheduler updates must finish before another timer interrupt

When choosing a task, the scheduler updates the current task number, task state, and stack pointer. An interrupt halfway through those updates could observe inconsistent values.

mask_irqs() saves the previous IRQ-enable setting and disables IRQs before these updates. After a paused call resumes, restore_irqs() restores its previous setting. New tasks inherit the setting from the caller of run_until_finished().

The timer handler already runs with IRQs disabled. When it resumes after a switch, it keeps them disabled until the assembly exception return restores the interrupted task’s status.

5. A test that needs preemption to finish

Two kernel tasks each publish a round number and wait until the other task has reached that round. They repeat this eight times. Neither calls yield_now().

for round in 1..=8 {
    publish_my_progress(round);
    while other_task_progress() < round {
        // Keep waiting. The timer must give the other task CPU time.
    }
}

This is a simplified version of wait_for_other_task() in scheduler.rs. The implementation uses atomic values so the tasks can observe each other’s progress.

Before reading the answer: A publishes round 1 and starts waiting. What lets B publish round 1?

Show the sequence

The timer interrupts A. Its handler yields to the dispatcher, which starts B. B publishes round 1 and can proceed to round 2, where it waits for A. A later timer interrupt switches back to A. Repeated timer interrupts let both tasks finish all eight rounds.

The test checks both final progress values, both Finished states, and at least eight timer preemptions. If the timer never switches tasks, the first task waits indefinitely. QEMU has a timeout; the physical Pi has a watchdog around this boot test to return a stalled kernel to the UART loader.

6. Current scope

Preemption applies to the registered kernel tasks on one core. The UART/Ethernet server still uses its existing polling loop after the boot tests. ARM userspace processes, per-process memory isolation, and floating-point/SIMD register switching remain separate work.
