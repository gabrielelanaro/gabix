Lesson 21 · Phase 2 · networking · first RX bytes

First Frames on the Wire

Build an Ethernet frame, push it down the TX queue, then poll the RX queue for a reply. Strip the virtio-net header, parse the Ethernet header, print it, recycle the buffer. End with a NetDevice abstraction that hides the queues — the network parallel of Lesson 9's read_sector.

Read time ~25 min Build time ~45–60 min Prereq Lesson 20

Lesson 8 was the disk path's keystone — the first sector read, bytes flowing from disk for the first time. This lesson is the network path's equivalent, with one structural twist. The disk never spoke until spoken to: every byte the kernel ever saw came in response to a request it issued. The wire is busier than that. Frames arrive on their own clock, provided some other machine has a reason to send them. In our isolated QEMU playground, the only other machine is slirp, and slirp stays quiet until prompted. So to see our first RX byte, we have to TX something first.

The shape of the lesson

Five steps, two milestones. The first milestone is the TX path working: a frame leaves the kernel, the device consumes it, the TX used ring reports completion. The second milestone is the RX path working: a frame arrives in one of the buffers we posted in Lesson 20, the kernel parses it, the Ethernet header prints on serial. The fifth step wraps both into a single NetDevice struct with two methods — the parallel of Lesson 9's read_sector closing the block layer.

The trigger for the RX milestone is a broadcast ARP (Address Resolution Protocol) request. Slirp answers ARP for the gateway address 10.0.2.2, so a request that asks "who has 10.0.2.2?" guarantees a reply within milliseconds. We don't need the full ARP parser from Lesson 22 — we'll hand-craft the 28 bytes of ARP request inline, treating it as opaque payload, and look only at the Ethernet header wrapping it. Lesson 22 will revisit those 28 bytes with a parser.

The Ethernet frame layout

An Ethernet frame on the wire is three fields: a 6-byte destination MAC (Media Access Control), a 6-byte source MAC, and a 2-byte EtherType. Fourteen bytes total, no checksum on our virtual wire — slirp strips the CRC (Cyclic Redundancy Check) that real Ethernet appends. The EtherType field tells the parser on the receiving end which protocol owns the bytes that follow.

Ethernet header — 14 bytes prepended to every frame
dst MAC [u8; 6] 0x00–0x05
src MAC [u8; 6] 0x06–0x0B
EtherType u16 BE 0x0C–0x0D
dst MAC [u8; 6]

The card on this wire the frame is addressed to. Six bytes, no structure — just an identifier. The broadcast address ff:ff:ff:ff:ff:ff means everyone, and that is what we'll send for an ARP request. Real switches forward broadcast to every port.

ff ff ff ff ff ff (broadcast)
src MAC [u8; 6]

The card that sent the frame. We read this from device config in Lesson 20 (52:54:00:12:34:56) and stash it in the driver struct. Every TX frame carries it here.

52 54 00 12 34 56 (our MAC)
EtherType u16 · big-endian

The demux key for the link layer. The receiving kernel reads this 2-byte value to decide which parser owns the payload. Two values matter for us: 0x0806 = ARP (Lesson 22), 0x0800 = IPv4 (Internet Protocol version 4, Lesson 23). The bytes on the wire are 08 06 — most significant byte first.

08 06 → 0x0806 → ARP parser

After the 14-byte Ethernet header comes the payload — for ARP, 28 bytes; for IPv4, 20+ bytes of IP header plus everything above. The receiver knows where the payload ends because the Ethernet frame as a whole has a known length. The device tells us that length in the used ring entry's len field. Ethernet has no end-marker in the header.

Big-endian on the wire

Every multi-byte integer in those headers is stored most significant byte first. The convention is older than the chips we're running on — fixed in RFC 791 (1981) by people who were thinking about IBM mainframes and PDP-11s, neither of which won the desktop. Little-endian x86-64 won the desktop. So the parser reflex you built doing ext2 — u16::from_le_bytes — has to flip.

ext2 (Lesson 13) — little-endian
// magic at offset 56 of the superblock
let magic = u16::from_le_bytes(
    [buf[56], buf[57]]
);
// bytes on disk: 53 EF
// → 0xEF53 = 61267
✓ matches superblock magic 0xEF53
Ethernet / IP — big-endian
// EtherType at offset 12 of the frame
let ethertype = u16::from_be_bytes(
    [frame[12], frame[13]]
);
// bytes on wire: 08 06
// → 0x0806 = ARP
✓ correct parser dispatches

The two functions are spelled one letter apart. The bug they make — silently swapped byte order — is the most common from-scratch networking bug there is, because nothing crashes. The frame just goes to the wrong parser, or to the wrong port, or to a port that doesn't exist. Lesson 19's first implementer rule was this, in one line; here is where it costs you an afternoon if you forget.

The MAC addresses dodge the issue entirely — they're six individual bytes, no integer interpretation needed. Read them straight into a [u8; 6]. Only the EtherType and every multi-byte field above it (IP lengths, port numbers, checksums) care about endianness.

The TX path — your turn to talk

Transmit is five moves. The frame exists in kernel memory as a byte array. The device needs two things from you: the 12-byte virtio-net header (all zero, from Lesson 20) prepended to the frame, and a descriptor chain pointing at both. The device reads the header, reads the frame, ships it onto the wire, writes a completion entry to the TX used ring.

segmentaddrlenflagsnextnote
seg 0 hdr_phys 12 F_NEXT → 1 virtio_net_hdr · all zero · device reads
seg 1 frame_phys 42 (none) — 14 B Ethernet + 28 B ARP · device reads

Two segments, both device-readable (no F_WRITE). Compare to virtio-blk's three-segment read chain from Lesson 8 — header / data / status — where the middle was writable. virtio-blk needed a writable segment because the device writes the read data and the status byte back. virtio-net TX has nothing for the device to write; the device just consumes both segments and reports completion.

Five moves, in order:

TX path — kernel drives
1build the 42-byte frame in RAM: 14-byte Ethernet header (broadcast dst, our src, EtherType 0x0806) + 28-byte ARP request payload
2prepend 12 zero bytes — the virtio_net_hdr — to make one 54-byte buffer
3build a 2-segment descriptor chain: seg 0 = hdr (12 B, F_NEXT), seg 1 = frame (42 B, no flags)
4submit the chain head to TX avail ring with Release ordering, bump idx
5kick the TX queue — write 1 (queue index) to the notify register
The device wakes on the kick, walks the avail ring, DMAs both segments, ships the 14+28 = 42 bytes onto the wire, writes (head_id, 0) to the TX used ring. Poll the used ring to confirm completion before reusing the buffers.
RX path — device drives
1device reads RX avail slot 0, sees a posted buffer
2frame arrives from the wire (slirp's ARP reply, ~60 bytes)
3device DMAs the bytes into the posted buffer's address: 12 B virtio_net_hdr + 14 B Ethernet + 28 B ARP + padding
4device writes (descriptor_id, len=60) to RX used ring, bumps used idx
5kernel's poll loop sees the new idx, reads the entry, follows descriptor_id to the buffer
The 60 bytes are now in kernel RAM. The first 12 are the virtio-net header — strip them. The next 14 are the Ethernet header — parse them. The remaining 34 are payload (the ARP reply) plus padding — Lesson 22 owns those bytes.

Two descriptor shapes, two rings, opposite initiators. Same Lesson 7 virtqueue primitives underneath — build_read_chain from L8 has its TX sibling in a build_tx_chain helper; the avail-ring publication and used-ring poll are identical code paths.

The RX path — listening for the reply

Within a millisecond of your TX kick, slirp processes the ARP request, decides it owns 10.0.2.2, and ships an ARP reply back onto the virtual wire. The reply lands in one of the eight RX buffers you posted in Lesson 20. The device writes a used-ring entry. The kernel's poll loop catches the idx advance.

What the kernel pulls out of the buffer is 60 bytes laid out as three nested layers. Each layer has its own parser:

RX buffer contents — what slirp's reply looks like 60 bytes total
virtio_net_hdr 12 B · zero 0x00–0x0B
dst MAC 6 B 0x0C–0x11
src MAC 6 B 0x12–0x17
EtherType u16 BE 0x18–0x19
ARP payload 28 B 0x1A–0x35
padding 4 B 0x36–0x39
virtio_net_hdr 12 B · zero

Lesson 20 covered this in detail. The device prepended it on RX. Our negotiated features make every field zero — strip the 12 bytes and continue parsing at offset 12.

Ethernet header 14 B

Offsets 0x0C through 0x19 of the buffer. Parse with the same code path used on the TX side — bytes 0–5 are dst MAC, 6–11 are src MAC, 12–13 are big-endian EtherType. The interesting field here is src MAC — that is the gateway's hardware address, the answer to the question our ARP request asked.

src: 52 55 0a 00 02 02 (gateway MAC)
ARP payload 28 B · opaque for now

The actual ARP reply's content — sender IP, sender MAC, target IP, target MAC. Lesson 22 builds the parser. For this lesson, hexdump the 28 bytes and move on; the Ethernet header is enough to prove the RX path works.

One print line closes the milestone: [net] RX ethertype=0x0806 src=52:55:0a:00:02:02 dst=52:54:00:12:34:56. When that line appears on serial, the full RX path works: device filled a posted buffer, kernel polled, parsed, dispatched by EtherType. Every byte that came in was a byte the kernel did not ask for. The unsolicited-receive model from Lesson 19 is now running code.

Recycling — close the loop

The buffer the device filled is one of the eight from Lesson 20. Right now, it's "in the used ring" — neither posted nor free, the third state from the Lesson 20 snapshots. If we leave it there, supply drops by one. After eight RX frames, supply hits zero and the next frame is dropped silently. Recycling is the move that keeps the supply alive.

The mechanic is exactly the T6 snapshot from Lesson 20: read the used-ring entry to get the descriptor index, parse the buffer the descriptor points at, then re-submit that descriptor index to the avail ring. The descriptor's addr, len, and flags fields never changed — same buffer, same 2048-byte capacity, same F_WRITE. Only the avail ring's idx advances.

The recycling happens inside the RX poll routine, immediately after the kernel finishes parsing. One frame in, one buffer back out. Supply stays at 8 forever — at least until traffic exceeds what the poll loop can drain, which on this stack would mean thousands of frames per second. We are a long way from that.

The NetDevice abstraction

Lesson 9 closed the block layer with read_sector(n) -> [u8; 512] — one synchronous call hiding the descriptor chain, the kick, the poll, the validation, the cleanup. Everything above the block layer (ext2, the ELF loader, the filesystem trait) could call that one method without knowing how virtio worked.

The network layer wants the same shape. Above this lesson, ARP and IPv4 and ICMP and UDP all need to send and receive raw Ethernet frames. None of them should know that virtio-net has two queues, or that a 12-byte header gets prepended, or that descriptors have flags. They should see this:

— the NetDevice surface 
pub struct NetDevice { /* virtio-net, RX queue, TX queue, MAC */ }

impl NetDevice {
    pub fn send_frame(&mut self, eth_frame: &[u8]) {
        // prepend virtio_net_hdr, build chain, submit, kick, poll for completion
    }
    pub fn recv_frame(&mut self) -> Option<Frame> {
        // poll RX used ring, strip virtio_net_hdr, parse Ethernet, recycle buffer
    }
    pub fn mac(&self) -> [u8; 6] { self.mac }
}

pub struct Frame {
    pub dst: [u8; 6],
    pub src: [u8; 6],
    pub ethertype: u16,
    pub payload: [u8; 1500],   // MTU-sized
    pub payload_len: usize,
}

recv_frame returns Option<Frame> because the poll may find nothing — the ring may be empty this tick. Lesson 22's ARP code will call recv_frame in a loop, classify by ethertype, and dispatch. Lesson 26's socket layer will sit on top of the same abstraction. The two methods carry the full virtio-net complexity underneath them.

Two abstractions now define the bottom of the kernel: read_sector for storage, send_frame / recv_frame for networking. Everything you build in the rest of this phase sits on top of these three calls.

The build — five steps

Steps 21.2 and 21.3 are the two milestones. The rest is plumbing and polish.

1
EthernetHeader parse and build. New src/net/ethernet.rs module. A struct EthernetHeader { dst: [u8; 6], src: [u8; 6], ethertype: u16 } with two methods: parse(buf: &[u8]) -> Option<Self> using u16::from_be_bytes, and to_bytes(&self) -> [u8; 14] using ethertype.to_be_bytes(). Unit test: round-trip a broadcast ARP header through both, verify the EtherType bytes are [0x08, 0x06]. Commit.
2
TX: send a broadcast frame. Hand-craft a 28-byte ARP request payload (the exact bytes are in RFC 826 — sender MAC = our MAC, sender IP = 10.0.2.15, target MAC = 00:00:00:00:00:00, target IP = 10.0.2.2). Wrap with an EthernetHeader (broadcast dst, our src, EtherType 0x0806). Prepend 12 zero bytes for the virtio_net_hdr. Build the 2-seg chain, submit, kick, poll the TX used ring for completion. Print [net] TX broadcast frame sent, 54 bytes. Commit. This is milestone 1.
3
RX: poll, strip, hexdump. Loop on recv_frame's poll primitive. When a frame arrives, strip the 12-byte virtio_net_hdr, parse the EthernetHeader, print the dst/src/ethertype, hexdump the next 28 bytes (the ARP reply). If you sent the ARP request in step 2 a millisecond ago, slirp's reply should land within thousands of poll iterations. Print [net] RX ethertype=0x0806 src=52:55:0a:00:02:02. Commit. This is milestone 2 — first RX bytes.
4
Recycle RX buffers. After parsing the frame, re-submit the descriptor index to the RX avail ring (bump avail idx). The buffer is back in service without any new allocation. Verify by sending four ARP requests in a row and confirming four replies arrive — supply of 8 should never drop below 7. Commit.
5
Wrap as NetDevice. Pull everything into a NetDevice struct with send_frame(&[u8]), recv_frame() -> Option<Frame>, and mac() -> [u8; 6]. The two queue internals, the buffer pool, the virtio_net_hdr handling — all private. Replace inline calls in main.rs with method calls. Re-run the test from step 3 to confirm behavior is unchanged. Commit.
Lesson 21 scope

The ARP request is hand-crafted byte-by-byte with no struct, parser, or cache. Lesson 22 turns those 28 bytes into a proper ArpPacket with parse/build and a real ARP cache that future protocols can query. The hexdump you print here is the proof the wire works; the structured ARP knowledge comes next.

Primary source

The Ethernet frame format is specified in IEEE 802.3, but the version you'll actually want to read is RFC 894 — "A Standard for the Transmission of IP Datagrams over Ethernet Networks" (1984, still current). It's three pages. The EtherType registry is owned by IEEE; the live list is at standards-oui.ieee.org/ethertype/eth.txt. For Linux's parallels: drivers/net/virtio_net.c — start_xmit (TX path, including the 12-byte header prepend) and receive_buf (RX path, including the header strip); net/ethernet/eth.c — eth_type_trans, the kernel's Ethernet parser that your EthernetHeader::parse is a stripped version of.

Probe — check the model before you build

You send the broadcast ARP request at T = 0. At T = 1 ms, slirp's reply lands in RX buffer D0. The kernel polls at T = 2 ms, parses the frame, prints it, recycles D0. Suppose slirp sends a second, identical reply at T = 3 ms (a duplicate, say) before the kernel polls again. Where does that second frame go, what's the state of D0 at T = 3 ms, and what happens to the second frame when the kernel polls at T = 4 ms?

Say your answer back to me, or push on whatever didn't land — the TX descriptor chain shape, the 12-byte header's role in both directions, the recycle mechanic. I'm your teacher for this phase; the probe is where the conversation starts.
