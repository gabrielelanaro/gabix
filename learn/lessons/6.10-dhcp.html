DHCP

Replace the hardcoded 10.0.2.15 with a four-packet conversation that obtains an address lease.

User program /dhcp.elf Endpoint 0.0.0.0:68 → 255.255.255.255:67 Primary source RFC 2131

Every packet mini-os has sent since Lesson 22 used a hardcoded source address. A real machine boots with no IP address, no subnet mask, no gateway address, and no DNS server addresses. DHCP (Dynamic Host Configuration Protocol) obtains these values through a UDP conversation. This lesson replaces the hardcoded address with the DHCP exchange. QEMU's built-in server assigns 10.0.2.15, so the leased value equals the constant it replaces.

The problem: sending IP packets requires an IP address

IP packets require source and destination addresses. Sending a packet requires a source address. Receiving a packet requires the destination address to match one of the host's addresses. Requesting an address from a server requires knowing the server's address. A newly booted machine has none of these values.

the circular dependency

send an IP packet → needs a source address
receive the reply → needs a destination address
request an address from a server → needs the server's address

the solution: reserved addresses

Use 0.0.0.0 as the source address. This value means the host has no assigned address.

Use 255.255.255.255 as the destination address. This value means deliver to all hosts on the local link layer.

On Ethernet, the broadcast IP address maps to the Ethernet broadcast address ff:ff:ff:ff:ff:ff by definition. No ARP lookup is needed.

Two reserved addresses break the circular dependency. Using broadcast means every host on the link receives the frame. The client sends two broadcast messages (DISCOVER and REQUEST), then uses unicast for the remainder of the lease.

Lesson 22 comparison. ARP sent a broadcast to learn one MAC address. DHCP sends broadcasts to obtain network configuration parameters.

All messages use broadcast because the client has no assigned IP address. The BROADCAST flag (0x8000 in flags) requests broadcast replies.

1 · DISCOVER. The client sends a broadcast UDP datagram containing its MAC address in the chaddr field and a randomly generated transaction identifier in the xid field. Any server that receives the datagram may respond.

2 · OFFER. A server sends a reply containing an IP address in the yiaddr field and lease parameters in options. The server copies the xid field unchanged. The client matches replies to its request by comparing the xid value, the same method used to match ICMP ping replies by identifier (Lesson 24).

3 · REQUEST. The client selects one offer and sends a broadcast message containing option 50 (requested IP address) and option 54 (server identifier). All servers that sent an offer receive this broadcast. Servers whose offers were not selected free the addresses they had reserved (RFC 2131 §3.1).

4 · ACK. The selected server sends a confirmation containing the lease parameters. The client records the lease, starts the T1 and T2 timers, and applies the IP address, subnet mask, gateway, and DNS server addresses to its network stack.

Why four messages

DISCOVER and OFFER locate servers and reserve an address. REQUEST and ACK commit to one lease. Splitting the exchange allows multiple servers to share one link without assigning the same address to multiple clients. If the selected server has already assigned the address to another client, it sends DHCPNAK and the client restarts at DISCOVER.

Retrieval check. RFC 2131 specifies that the client broadcasts DHCPREQUEST instead of unicasting it to the selected server. What does the broadcast accomplish?

The packet format

DHCP uses the packet layout defined by BOOTP (Bootstrap Protocol, RFC 951) in 1985. The first 236 bytes contain the BOOTP header. Most fields supported diskless boot stations: sname and file specified a server address and boot image filename; hops and giaddr routed packets through relay agents. A DHCP client sets these fields to zero. The DHCP conversation uses a few header fields and the options area following the magic cookie.

op u8
1 = request (client → server), 2 = reply. htype 1 + hlen 6 indicate Ethernet hardware address; hops remains 0.
xid u32
Transaction identifier. The client generates this value in DISCOVER, includes it in REQUEST, and accepts only replies that echo the same value.
flags u16
Bit 0x8000 is the BROADCAST flag: request the server to send the reply as a layer-2 broadcast because the client cannot receive IP unicast yet. All other bits are zero.
chaddr 16 B
Client hardware address. The virtio network card MAC address occupies the first 6 bytes. The server uses this address to address replies and to identify the lease.
yiaddr addr
“Your IP address” — the address the server offers. The server sets this field in OFFER and ACK; the client sets this field to zero.
magic cookie u32
0x63825363 (RFC 2132 §3). This value marks the start of the options area. A parser verifies this value before parsing any option.

The options area uses TLV (type-length-value) encoding: one byte of option code, one byte of length, that many bytes of value, repeated until code 255 (end). The option codes used in this lesson, from RFC 2132:

Lease lifecycle

The address in an ACK is a lease that expires after a duration. Option 51 specifies the lease duration in seconds. Two timers determine when the client sends renewal requests (RFC 2131 §4.4.5):

BOUND0 → T1
RENEWINGT1 → T2
REBINDINGT2 → end
T1 = 0.5 × lease
client unicasts REQUEST to the granting server T2 = 0.875 × lease
client broadcasts REQUEST to any server expiry
address returns to server pool

When T1 expires, the client unicasts a REQUEST to the server that granted the lease. If the server responds with ACK, the lease timer resets. If T2 expires before renewal succeeds, the client broadcasts a REQUEST to any server. If the lease expires, the client returns to INIT and restarts at DISCOVER. Servers can override the default T1 and T2 values with options 58 and 59. Slirp's lease duration exceeds any test run, so mini-os will not perform renewal in practice. The timers still matter for understanding real network traffic: a laptop that reboots while its lease is valid can continue using the address.

The lab server assigns 10.0.2.15

QEMU's user-mode networking stack (slirp) runs a DHCP server at 10.0.2.2 and assigns addresses starting from 10.0.2.15 (QEMU network emulation docs). mini-os is the only guest on the virtual link, so the server assigns 10.0.2.15 — the same value that the kernel has hardcoded since Lesson 22.

The test procedure: boot without the hardcoded address, execute the DHCP conversation, and verify the leased address equals the previous constant. Then re-run the Lesson 24 ping test and the Lesson 25 UDP test using the acquired address. Network behavior should be identical with the hardcoded address removed.

What to build in mini-os

The DHCP client is a user-mode program. UDP sockets transmit and receive the packets. The kernel requires three modifications and one new system call.

30.1
Transmit and receive while unconfigured. Transmit: allow 0.0.0.0 as a source address; map destination 255.255.255.255 to Ethernet broadcast ff:ff:ff:ff:ff:ff without ARP. Receive: while the host has no assigned IP address, accept broadcast frames containing UDP datagrams for port 68.
30.2
DHCP packet module. Construct DISCOVER and REQUEST packets. Parse OFFER and ACK replies. Verify the magic cookie value and echoed xid. Parse TLV options for codes 53, 51, 54, 1, 3, 6.
30.3
Execute /dhcp.elf from user mode. Call socket(), bind() to port 68, send DISCOVER. Call recvfrom() which blocks until Lesson 29's interrupt-driven RX delivers the OFFER. Send REQUEST, receive ACK. Call the new net_configure(addr, mask, gateway, dns, lease_secs) system call to write the runtime network configuration into the kernel.
30.4
Remove hardcoded address. The kernel boots with empty network configuration. Init executes dhcp.elf before any other network program. The test suite runs against the leased address.
Dependencies

All prerequisites exist: blocking sockets (Lesson 26), readiness (Lesson 27), and interrupt-driven RX that wakes the blocked recvfrom() call (Lesson 29). The new code is the DHCP packet format and the configuration system call.

Minigame — run the Lease Office

Implement the server side. You are the server at 10.0.2.2 with three addresses in the pool. Clients send messages; send the correct reply before each patience bar reaches zero.

  • Send OFFER in response to DISCOVER — the server reserves the address for a few seconds while the client decides.
  • Send ACK in response to REQUEST for the address you offered that client — the server records the lease and starts the lease timer.
  • Send NAK in response to REQUEST for any other address — the client restarts at DISCOVER.
  • Send no response to DISCOVER when the pool is empty — a lease expiry frees an address.
