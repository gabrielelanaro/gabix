The Pi's two mailboxes

Why the ARM cannot power on USB by itself — and the request it sends to the GPU.

The Pi's USB controller will not run until it is powered on. On most boards the CPU would just flip a bit in a register to power a peripheral. On the Pi it cannot: the USB controller's power is owned by the Pi's other processor, the GPU (the graphics chip that actually booted the board before the ARM started). To get the GPU to power on USB, the ARM must send it a request. The channel for that request is a mailbox.

This lesson explains that mailbox: why two processors that share memory still need a way to signal each other, the Pi's property mailbox (the one gabix uses to power on USB and to read the Ethernet card's hardware address (its MAC)), and the second mailbox the Pi has for its four CPU cores to signal each other (which gabix does not use).

1. Why a mailbox: the shared-memory problem

The ARM and the GPU can both read and write the same physical memory. So why can the ARM not just write a request into memory and let the GPU read it? Because the GPU may be running other code — nothing notifies it that a request is waiting. Writing the data is not enough; the ARM has to alert the GPU that there is something to read.

A mailbox solves that. The ARM writes the message into shared memory, then performs one special write — to a register that signals the other processor. That write is the doorbell: it points the GPU at the message and signals it to read. The GPU reads the message, carries out the operation requested, writes the answer back into the same memory, and rings its own doorbell to signal completion. The memory carries the data; the doorbell carries the alert. That is the idea.

2. The Pi has two of them

The Pi has two processors and four CPU cores, so it has two different mailboxes for two different message exchanges:

  • The property mailbox — ARM to GPU. The ARM uses it to request GPU actions: power on the USB controller, report the Ethernet MAC address, set up the display. Anything that needs the GPU's control of power or clocks goes through here. gabix uses this one.
  • The inter-core mailboxes — one ARM core to another, in the ARM-local region (the per-core registers from lesson 7.01). One core writes to another core's mailbox register, which raises an interrupt on that core to wake it or pass it a task. gabix parks three of the four cores and runs only core 0, so it never sends or receives one.

Both are called "mailboxes," which is the source of the confusion you hit in lesson 7.01. This lesson covers the property mailbox in detail, because that is the one gabix uses to power on USB; the inter-core mailbox is section 6.

3. The property mailbox, concretely

The property mailbox is a set of registers at address 0x3f00_b880. Three matter: a WRITE register, a READ register, and a STATUS register. The exchange runs in four steps:

  1. The ARM builds a message in memory — a small array of words describing the request ("power on device 3, the USB controller").
  2. The ARM waits until the STATUS register reports the mailbox is not full, then writes the message's address into the WRITE register, combined with a channel number. That single write is the doorbell: it both points the GPU at the message and alerts it.
  3. The GPU reads the message, carries out the operation, writes the answer back into the same memory buffer, and signals completion by placing the reply on the READ register.
  4. The ARM polls the READ register until the reply appears, then reads the answer out of the buffer it wrote in step 1.

4. The message, and the address trick

gabix's real call requests that the GPU power on the USB controller:

targets/armv7/src/raspi2b/mailbox.rs · power_on_usb · mailbox.rs:43–50
pub unsafe fn power_on_usb() -> Option<()> {
    let returned_state = exchange_id_value(
        SET_POWER_STATE,
        USB_HCD_DEVICE,
        POWER_ON | WAIT_FOR_STABLE_POWER,
    )?;
    (returned_state & POWER_ON != 0).then_some(())
}

POWER_ON requests power; WAIT_FOR_STABLE_POWER asks firmware to wait for the change. The helper returns the firmware's state value, and the final expression checks its power bit. Source: mailbox.rs:17–20, 43–50.

exchange_id_value builds the aligned message array, converts its address to a bus address and combines it with property channel 8. It handles cache visibility, bounded polling and response checks before returning the value. Both USB power and SD clock queries share this buffer, so callers must serialize them. Source: mailbox.rs:64–117.

5. Why it polls, again

This driver polls mailbox status synchronously, with a bounded wait in mailbox.rs::wait_until (line 119). It installs no mailbox reply handler. The Pi timer uses interrupts for scheduling through raspi2b/timer.rs::handle_interrupt; its mechanism is separate from this mailbox polling loop.

6. The inter-core mailbox (the one gabix ignores)

The ARM-local region (0x4000_0000, from lesson 7.01) holds a second set of mailboxes, one per core. Core A writes into core B's mailbox register; that write both leaves a tiny message and raises an interrupt on core B. That is how a multi-core kernel wakes a parked core or dispatches tasks between cores. gabix is single-core — it parked cores 1, 2, and 3 back in lesson 0.01 — so it never sends or receives one. The "mailboxes the four cores use to exchange messages" you saw in 7.01 referred to this hardware: it exists, gabix does not use it.
