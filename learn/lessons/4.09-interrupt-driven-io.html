Lesson 28 · Interrupt-driven I/O

Interrupt-Driven I/O

Replace virtio-blk's 200,000-iteration busy-wait with a Local APIC, an MSI-X vector, and an ISR that fires when the hardware finishes the read.

Prereq Lesson 9 (block layer), Lesson 27 (poll) Focus APIC + MSI-X + ISR Build status implemented and tested

Every disk read in mini-os costs the CPU 200,000 busy-wait iterations. Every network frame costs a cooperative task that polls forever. The device finishes its work in microseconds; the kernel discovers this by spinning. This lesson replaces that spin with a hardware interrupt — the device signals completion, the CPU sleeps until it arrives.

The cost of polling

Here is read_sector today, from src/virtio.rs:331:

// Submit the read request, kick the device, then ... spin. let completion = (0..200_000u32) .find_map(|_| self.queue.as_mut().unwrap().poll_completion()) .expect("read_sector: no completion arrived");

Each iteration reads used->idx from memory — a volatile load — compares it against last_used_idx, finds them equal, returns None, loops back. The CPU executes this at full clock speed. For the few microseconds a virtio-blk read takes inside QEMU, the core spins through hundreds of iterations, each one a wasted memory read discovering nothing.

Multiply across one boot. ext2 mount reads the superblock (2 sectors), the block group descriptor table (1 sector), the root inode (1 sector), the root directory block (1 sector). Each read_sector call spins the same loop. Then the ELF loader reads the binary's blocks. The poll loop runs thousands of times to discover completions that were ready almost instantly.

The network path is the same shape but runs continuously. The polling worker from src/virtio.rs:808:

pub unsafe extern "C" fn network_worker() { loop { let _ = with_net_device(|device| device.poll_rx()); crate::task::yield_now(); } }

This task yields (so it doesn't starve others), but it wakes every schedule cycle and polls the RX virtqueue. When no frames arrive — the common case — the poll is pure waste. The CPU runs this task thousands of times per second, each time reading the used ring and finding it empty.

The delivery path you already own

The timer interrupt is a working device interrupt. The kernel already has every piece of the delivery path — for the timer. Extending it to virtio means reusing the same machinery with a different trigger.

Trace the timer's path end to end:

1 PIT (Programmable Interval Timer) fires at 100 Hz
↓
2 8259 PIC maps IRQ 0 → raises vector 0x20 to the CPU
↓
3 CPU pushes interrupt frame (RIP, CS, RFLAGS, RSP, SS) onto the kernel stack
↓
4 CPU consults IDT[0x20] → jumps to timer_wrapper
↓
5 Wrapper pushes all 15 GP registers, calls timer_inner
↓
6 timer_inner: increment tick counter, send EOI to PIC and Local APIC, call yield_now()
↓
7 Wrapper restores registers, iretq pops the frame

Every device interrupt follows this shape: device signals → controller delivers → CPU pushes frame → IDT dispatches → ISR runs → EOI → iretq. Steps 3, 4, 5, and 7 are identical regardless of source. What changes is step 1 (how the device signals), step 2 (which controller delivers), and step 6 (what the ISR does).

The timer goes through the 8259 PIC. virtio-blk will go through the Local APIC via MSI-X. The ISRs differ in content but share the same wrapper, the same IDT registration, and the same iretq return.

Why the PIC is the wrong tool for virtio

Think of the PIC's IRQ lines as phone lines. The PIC has 15 of them. A real computer has far more than 15 devices, so devices share phone lines.

When a shared line rings, the CPU picks up and runs the handler for that line. But it doesn't know which device on that line is calling. So it has to ask each device: "was that you?" The virtio ISR status register — a one-byte register inside the virtio PCI capability list (cfg_type 3, defined at src/virtio.rs:42 but never mapped or read today) — exists for exactly this. Reading its bit 0 answers "yes, that was me."

That round-trip — "was that you?" — is the first cost. Two more follow from the way shared lines work electrically:

  • The line stays ringing until you explicitly hang up. The device holds the line active until the driver reads that ISR register, which clears it. Forget to read ISR and the line stays stuck ringing forever — no further interrupts get through.
  • Every device on the line wakes up for every interrupt. Two devices sharing IRQ 11 means both get asked "was that you?" every time either one fires. Most of the time the answer is "no" — wasted work.

QEMU gives each PCI device its own virtual pin, so sharing isn't a real problem in our environment. But using the PIC path means building the "was that you?" and "hang up the line" machinery that real hardware is leaving behind. Linux's virtio driver prefers MSI-X and falls back to the PIC path only when MSI-X is unavailable. We'll do the same.

MSI-X — each device gets a private line

MSI-X (Message Signaled Interrupts, Extended) gives each device its own private line. Instead of asserting a physical pin that might be shared, the device writes a few bytes to a specific memory address — the Local APIC's address at 0xFEE00000. The APIC reads the write, sees the vector number encoded in it, and delivers the interrupt to the CPU core. No shared line, no "was that you?", no "hang up."

Four consequences follow:

  1. No shared lines. Each virtqueue gets its own private vector. When the ISR fires, the vector number alone tells it exactly which queue completed. No asking "was that you?" — the answer is built into the delivery.
  2. One write, one event. The shared-line approach holds the line ringing until the driver explicitly clears it. MSI-X is a single memory write: the interrupt fires once, done. Nothing to clear at the device, no stuck lines if the driver forgets a step. The ISR processes completions and sends EOI to the APIC — that's the whole acknowledgment.
  3. No ISR status register needed. The old "was that you?" register (cfg_type 3) exists in the capability list but drivers using MSI-X never read it. The memory write itself is the complete signal. The driver processes the used ring and moves on.
  4. Scalable. The PIC tops out at 15 lines. MSI-X supports 2048 vectors. A modern NVMe drive uses dozens — one per queue per CPU core. The PIC cannot reach this.

The Local APIC

The Local APIC (Advanced Programmable Interrupt Controller) is a per-CPU interrupt controller built into the processor die. On x86-64 every core has its own, memory-mapped at physical address 0xFEE00000. The kernel reads and writes APIC registers by loading from and storing to addresses in that 4 KB page.

mini-os currently uses the 8259 PIC exclusively. Enabling the Local APIC does not break the PIC. QEMU boots in "virtual wire" compatibility mode where PIC interrupts (including our timer on IRQ 0) continue to be delivered through the APIC transparently. The APIC adds the ability to receive MSI-X writes on top of the existing timer path.

Three registers matter for this lesson:

RegisterAPIC offset from 0xFEE00000Purpose
SPURIOUS_VECTOR 0xF0 Bit 8 is the APIC global enable switch. Bits 0–7 set the spurious vector (a catchall for interrupts with no handler — we'll use 0xFF).
EOI 0xB0 Writing 0 signals end-of-interrupt for the current APIC-delivered interrupt. Replaces PICS.notify_end_of_interrupt() for MSI-X sources.
IA32_APIC_BASE MSR 0x1B Contains the APIC's physical base address (bits 12–35) and the global enable bit (bit 11). Must be set before any APIC register access works.

To enable: set bit 11 of the IA32_APIC_BASE MSR, map the 4 KB page at 0xFEE00000 via map_mmio (the same function used for virtio's PCI capabilities in Lesson 6), then write the spurious vector register with bit 8 set and a vector like 0xFF. The PIC keeps working. MSI-X starts landing.

EOI: two controllers, two destinations

The timer interrupt arrives through the PIC, so timer_inner sends EOI to the PIC and to the Local APIC because QEMU routes the legacy PIC through its ExtINT virtual-wire input after xAPIC is enabled. The virtio-blk interrupt will arrive through the APIC via MSI-X, so its ISR must send EOI to the APIC — write 0 to 0xFEE000B0. Sending EOI to the wrong controller leaves the source stuck and no further interrupts arrive from it.

Configuring MSI-X for a virtqueue

The virtio PCI capability walker (src/virtio.rs:148) currently collects only vendor-specific capabilities (cap ID 0x09). The MSI-X capability (cap ID 0x11) is silently skipped — the if cap_id == CAP_VENDOR_SPECIFIC check filters it out.

MSI-X lives in a PCI capability with this structure:

FieldOffset in capWhat it tells the driver
Capability ID+0 (byte)0x11 = MSI-X
Next cap pointer+1 (byte)Linked-list continuation
Message Control+2 (u16)Bits 0–10: table size (N+1 vectors). Bit 15: MSI-X enable.
Table Offset / BIR+4 (u32)Bits 0–2: which BAR holds the table. Bits 3+: offset within that BAR.
PBA Offset / BIR+8 (u32)Same format — Pending Bit Array location (we won't use it).

The MSI-X table itself is an array of entries, each 16 bytes:

Entry fieldSizeDriver writes
Message Addressu320xFEE00000 (the APIC base — where the device sends its DMA write)
Message Upper Addressu320 (32-bit address mode)
Message Datau32Vector number (0x21 for our first device interrupt)
Vector Controlu32Bit 0 = mask. Write 0 to unmask.

After programming one table entry, the driver writes that entry's index into the virtqueue's msix_vector field at common-config offset 0x1A (VIRTIO 1.2 §4.1.4.3). This field currently sits at its default 0xFFFF (NO_VECTOR), meaning "no MSI-X assigned." Writing 0 (entry index zero) tells the device: when this queue's used ring advances, perform the MSI-X write defined in table entry zero.

hlt (halt) is the x86 instruction that stops the CPU core until the next interrupt. Combined with interrupts enabled (sti, which is the normal kernel state), it is a one-instruction sleep. The core draws near-zero power. When an interrupt arrives — the timer every 10 ms, or the virtio-blk MSI-X write the moment the device finishes — the CPU wakes, the ISR runs, and execution resumes after hlt.

The replacement loop:

let completion = loop { interrupts::disable(); if let Some(c) = self.queue.as_mut().unwrap().poll_completion() { interrupts::enable(); break c; } // Atomic sti; hlt closes the check-to-sleep race. interrupts::enable_and_hlt(); };

The timer interrupt still fires every 10 ms — hlt wakes, poll_completion returns None, the loop goes back to hlt. A brief check, then back to sleep. When the device finishes, its MSI-X write hits the APIC, the ISR sends EOI and returns, and the next poll_completion call returns the result.

hlt and the scheduler

hlt does not freeze the scheduler. When the timer fires during hlt, the timer ISR runs yield_now() as usual — the scheduler switches to another task. That task gets CPU time. Eventually we come back, resume after hlt, and check the used ring. hlt just prevents the CPU from burning cycles between timer ticks; it does not prevent other processes from running.

This means two processes could both call read_sector while each other's requests are in flight. The current virtqueue is single-outstanding (one request at a time) and has no lock. For Lesson 28 this is safe — boot is single-user, and user programs that read from disk don't run concurrently in the test scenarios. Lesson 29 replaces the hlt loop with proper blocking states (task marked Blocked, ISR wakes it) and adds the locking that concurrent access requires.

This is still synchronous I/O — read_sector blocks until the data arrives. But the CPU is no longer burning cycles during the wait. It sleeps between timer ticks. That is the difference between polling and interrupt-driven I/O.

Build steps

Five steps. The first three set up hardware infrastructure; the last two replace the poll loop and verify.

28.1
Enable the Local APIC. Create a new module src/apic.rs. Read the IA32_APIC_BASE MSR (0x1B), set bit 11 (APIC global enable), write it back. Map the 4 KB page at physical 0xFEE00000 via crate::memory::map_mmio. Write the spurious vector register (offset 0xF0): set bit 8 and vector 0xFF. Call apic::init() from the boot sequence after pic::init(). Verify: boot still works, timer still fires, tick counter still increments.
28.2
Parse and map the MSI-X capability. In parse_virtio_capabilities (src/virtio.rs:130), add a branch for cap_id == 0x11 (MSI-X). Read the Message Control field (cap offset +2, u16): table size is (ctrl & 0x7FF) + 1. Read the Table Offset/BIR field (cap offset +4, u32): BAR index is bir & 0x7, table offset is bir & !0x7. Compute the table's physical address from the BAR base, map it via map_mmio. Store the virtual address and entry count in the VirtioBlk struct. Enable MSI-X by writing bit 15 to the Message Control field.
28.3
Program the MSI-X vector for virtio-blk's queue. Pick vector 0x21 (one past the timer's 0x20). In MSI-X table entry 0: write Message Address = 0xFEE00000, Message Upper Address = 0, Message Data = 0x21, Vector Control = 0 (unmasked). Then in the common config region: select queue 0 (write COMMON_QUEUE_SELECT), write 0 to COMMON_QUEUE_MSIX_VECTOR (offset 0x1A) to bind entry 0 to queue 0. Verify: serial print confirming vector assignment.
28.4
IDT entry and ISR handler. Write a naked wrapper for vector 0x21 — identical shape to timer_wrapper (push 15 registers, call inner, pop 15 registers, iretq). The inner handler does one thing: send EOI to the Local APIC (write 0 to APIC offset 0xB0). Do not call poll_completion from the ISR — read_sector checks the used ring itself after hlt wakes. If the ISR drained the ring, read_sector's poll_completion would find nothing. The ISR's only job is to acknowledge the interrupt so the APIC can deliver the next one, and to cause hlt to return. Register in IDT[0x21] and reload the IDT. Verify: boot reaches the same point without triple-faulting.
28.5
Replace the poll loop in read_sector. Replace the (0..200_000).find_map(...) expression at src/virtio.rs:331 with the hlt-based wait loop shown above. Verify: read sector 0, confirm the boot signature bytes match (MINIOS_DISK_v0\n), confirm ext2 mount still works, confirm the ELF loader still reaches ring 3.
Current mini-os boundary after Lesson 28

virtio-blk reads are interrupt-driven — the CPU sleeps between submit and completion. The timer still wakes it every 10 ms for a brief check. virtio-net TX, RX, and ARP resolution still poll. Blocking recvfrom and poll still rely on the cooperative polling worker. Lesson 29 generalizes: interrupt-driven networking, proper sleep/wake for blocking calls, and the network worker task is deleted.

Probe — check the model before you build

The timer ISR sends EOI to the PIC (PICS.lock().notify_end_of_interrupt(0x20)) and the Local APIC virtual-wire path. The virtio-blk ISR will send EOI to the Local APIC (write 0 to APIC offset 0xB0). Two questions: what happens to future virtio-blk interrupts if the ISR forgets to send EOI to the APIC? And what happens if the ISR sends EOI to the PIC instead of the APIC — does the APIC care, does the PIC care, and does either un-stick the virtio-blk interrupt source?

Say your answer back to me, or push on anything that didn't land — the difference between edge-triggered and level-triggered interrupts, why hlt is safe inside a kernel function, or how the APIC and PIC coexist. The probe is where the conversation starts.
