Lesson 20 · Phase 2 · networking

virtio-net Initialization

Wake the network card with the same handshake virtio-blk used, then do three things virtio-blk never needed: read its MAC address, set up a second virtqueue, and stock the receive queue with empty buffers before any traffic can arrive.

Read time ~20 min Build time ~30–45 min Prereq Lesson 6, Lesson 7, Lesson 19

Lesson 19 ended with virtio-net visible on the PCI (Peripheral Component Interconnect) bus, silent and unclaimed. This lesson wakes it. The work splits cleanly: most of it is reuse, three pieces are genuinely new, and the new pieces exist for one reason — networks deliver bytes the kernel did not ask for. Every addition in this lesson answers the same question: what does a device need from its driver before the driver has anything to say?

The handshake you already know

The virtio modern-transport handshake is device-agnostic by design. Reset, ACKNOWLEDGE, DRIVER, feature negotiation, FEATURES_OK, DRIVER_OK — the same six steps, in the same order, on the same common-config registers, for every virtio device in the spec (VIRTIO 1.2 §4 — Virtio Transport Options). Lesson 6 walked it for virtio-blk. The card on the other end is virtio-net now; the dance is unchanged.

The capability list walk, the MMIO (Memory-Mapped I/O) mapping of the common-config region, the status-byte transitions, the feature-select register dance — all of Lesson 6 transfers line for line. The driver code you already wrote for virtio-blk, point for point, also drives virtio-net once the queue and feature pieces change. That is the spec paying back the work you put into Lesson 6.

Three places need virtio-net-specific knowledge: which feature bits to claim, where the MAC address lives, and what the device expects of its two virtqueues before it will start moving frames. The rest of the lesson is those three.

Feature negotiation — claim MAC, refuse merge-RX

virtio-net advertises its own device-specific feature bits in the low 32 of the 64-bit feature space. The spec defines about thirty of them (VIRTIO 1.2 §5.1.3); mini-os needs two and explicitly avoids a third.

  • VIRTIO_F_VERSION_1 (bit 32, transport layer) — the modern-transport compliance bit. Same claim as virtio-blk. Without it the device falls back to legacy mode, which we have never driven and will not start now.
  • VIRTIO_NET_F_MAC (bit 5, device-specific) — the device exposes its MAC (Media Access Control) address in the device-config region. Claiming this bit is what makes the MAC field at offset 0 of device config valid to read. Without it, the driver would have to fabricate or guess a MAC.
Refused: VIRTIO_NET_F_MRG_RXBUF (bit 15). The device offers to spread one incoming frame across multiple RX buffers when the frame is larger than one buffer's worth. Useful for jumbo frames and high throughput. We refuse it: one frame per buffer keeps the RX descriptor chain a single F_WRITE entry and the receive parser one buffer ahead in memory. Simplicity wins at our packet sizes; we'll revisit if we ever approach the 1500-byte Ethernet MTU (Maximum Transmission Unit).

Every other offered feature — checksum offload, TCP segmentation, multiqueue, MTU negotiation — is left untouched. The driver-feature write is 0x20 in the low half (bit 5) and 0x1 in the high half (bit 0 of high = bit 32). The device accepts; FEATURES_OK stays set.

Reading the MAC from device config

The common-config region is where the handshake lives, but it carries nothing device-specific. The MAC lives in a second region: the device-config capability (cfg_type = 4), the same cap virtio-blk uses for its disk-capacity field. Different cap, different region, mapped to its own virtual address the same way common-config was in Lesson 6.

The device-config region for virtio-net starts with the 6 bytes of MAC, followed by fields valid only if other feature bits were negotiated. Layout when only NET_F_MAC is claimed (VIRTIO 1.2 §5.1.4):

0x00–0x05mac[6]6 bytes — the card's hardware address, exposed because we negotiated NET_F_MAC
0x06–0x07statusu16 — link up/down; valid only with NET_F_STATUS (we didn't claim; reads as zero)
0x08–0x09max_pairsu16 — multiqueue depth; valid only with NET_F_MQ (we didn't claim; reads as zero)
0x0A–0x0Bmtuu16 — MTU in bytes; valid only with NET_F_MTU (we didn't claim; reads as zero)

Six bytes, six read_volatile calls at offsets 0 through 5. QEMU's virtio-net-pci without explicit configuration supplies 52:54:00:12:34:56 — the locally-administered range (the 52:54 prefix is QEMU's signature on the wire). Printing it after FEATURES_OK confirms the device-specific config cap mapped correctly and the device accepted our feature subset.

Why we read the MAC instead of inventing one

The MAC is the card's identity on the wire. ARP (Address Resolution Protocol, Lesson 22) and every Ethernet frame the kernel transmits carry it as the source. QEMU's slirp backend uses the MAC to identify the guest in its internal state. A fabricated MAC that doesn't match what QEMU thinks the card has would still let us transmit, but ARP replies we send would be ignored by the gateway. The MAC is part of the device; reading it is the right move.

Two queues, opposite directions

virtio-blk had one virtqueue. Every request the kernel submitted to it was a request that needed a response — read this sector, here is the data. The kernel drove the queue; the device answered. Network traffic has no such symmetry. Frames come in without being asked for, and frames go out without any reply expected on the same path. One queue cannot serve both roles cleanly, so virtio-net splits them:

Both queues use the same descriptor table, available ring, used ring layout from Lesson 7. The VirtQueue struct mini-os already has works for both. The differences live entirely in descriptor flags and in who initiates work: TX work is always kernel-initiated (the kernel builds a frame, submits, kicks); RX work is device-initiated (the device fills a buffer whenever a frame arrives, on its own schedule, with no kick from us).

virtio-blk's queue was its own thing — a single channel for paired request/response. virtio-net's two queues are siblings of each other under the virtqueue abstraction, with opposite purposes. Comparing side by side:

Lesson 7's mechanics — descriptor allocation, the available-ring publication with Release ordering, the used-ring poll with Acquire — all carry over unchanged. The shape of a chain and the rhythm of the dance vary; the rings themselves are identical.

The RX supply problem

Lesson 19's two implementer rules — network byte order is big-endian, and receive is unsolicited — were a preview of where the difficulty lives. Here is the unsolicited rule made concrete. When a frame arrives, the device must have a place to put it already queued and waiting. There is no request the kernel can issue to "fetch the next frame" — the device just lands one in whatever empty buffer the kernel has posted, on the device's own clock. If no buffer is posted, the frame is dropped silently. The wire does not wait.

The kernel is therefore a buffer producer, and the device is a buffer consumer. The dance between them, for the receive path:

at initallocate N × 2048-byte frames, write a F_WRITE descriptor per buffer, publish to RX avail ring
at initset DRIVER_OK — device is now permitted to read the RX queue
on frame arrivalpick the next posted buffer, DMA the frame into it, write an entry in the RX used ring
when kernel pollssee the new used entry, read the buffer, recycle it back into the avail ring
if supply runs lowpost more empty buffers before the device runs out — kick optional, device usually polls

Each posted RX buffer is one descriptor with F_WRITE set and a length large enough for the worst case. We use 2048 bytes: an Ethernet frame can be up to 1518 bytes (destination MAC + source MAC + EtherType + 1500 MTU + 4-byte CRC, which QEMU does not pass through), plus the 12-byte virtio-net header the device prepends, plus a margin. A 4 KiB frame would also work; 2048 keeps two buffers per frame.

Initial supply size: eight buffers. Enough to absorb a short burst of incoming ARP and ICMP (Internet Control Message Protocol) traffic in Lesson 22–24 before the kernel gets around to polling. Linux uses 256 and refills on a softirq; we use eight and refill in the polling loop. Lesson 21 will recycle a buffer back into the avail ring the moment it has been consumed.

The kernel didn't poll fast enough. Three more frames arrived; device filled D0, D1, D2 in sequence (the same D0 we just recycled, then D1, D2) and stacked three new entries in the used ring. The supply of 8 buffers absorbed the burst with no drops. If a sixth frame arrives before the kernel polls, it lands in D3. If the supply ever empties out entirely (all 8 filled, none recycled), the next frame is dropped silently — the wire does not wait. This is the entire reason the supply exists.

Two things to notice across the seven snapshots. The buffer memory itself is reused, never freed — once allocated, those 16 KiB of RX buffers stay live for the kernel's whole lifetime. And the descriptor's addr, len, and flags fields, once written at T2, are never rewritten — recycling just re-publishes the descriptor's index to the avail ring. The whole dance is ring arithmetic; the data structures underneath are static.

virtio_net_hdr — the device's own envelope

Every frame the device hands the kernel — in either direction — comes prefixed by a 12-byte header that is purely between driver and device. Ethernet, IP, and the rest never see it. Lesson 19 showed it as the outermost bar on the dissected UDP (User Datagram Protocol) packet; here is what those 12 bytes actually carry (VIRTIO 1.2 §5.1.6):

virtio_net_hdr — the device's own envelope 12 bytes · all zero for us
flags u8 · 1 B 0x00
gso_type u8 · 1 B 0x01
hdr_len u16 · 2 B 0x02–0x03
gso_size u16 · 2 B 0x04–0x05
csum_start u16 · 2 B 0x06–0x07
csum_offset u16 · 2 B 0x08–0x09
num_buffers u16 · 2 B 0x0A–0x0B
flags u8

Checksum-offload hints. With NET_F_CSUM or GUEST_CSUM negotiated, the kernel can ask the device to compute and insert a checksum at transmit, or signal that one was validated at receive. We refused both, so the field stays zero in both directions and the kernel computes checksums in software (Lesson 23, RFC 1071).

00
gso_type, hdr_len, gso_size u16 ×3

Segmentation offload — letting the device split one large TCP send into multiple Ethernet frames. We did not negotiate GSO. All three fields are zero.

00 00 00 00 00 00
num_buffers u16

The only field that has meaning on receive without any feature negotiated — when MRG_RXBUF is on, it tells the kernel how many RX buffers were consumed by this one frame. We refused MRG_RXBUF, so each received frame uses exactly one buffer, and the field reads as 1 (device still writes it). We can ignore it.

The pattern across all 12 bytes: every field is a hook for a feature we refused to negotiate. Saying "no" to offloads at feature negotiation time is what lets the entire header be zero on transmit and ignored on receive. Lesson 21's TX path will build a 12-byte zero header and prepend it to every Ethernet frame; Lesson 21's RX path will skip 12 bytes and start parsing at offset 12. No parsing logic, no feature branches — the simplest possible header is the one you negotiated away to zero.

Why the header exists at all

virtio could have made the header optional. It didn't, because making every device offload-capable by default lets a guest enable offloads later without renegotiating the queue layout. The 12 bytes are dead weight we pay for the option of features we didn't claim. Linux, which claims most of them, treats the header as load-bearing metadata.

The build — four steps

All four steps reuse Lesson 6 and Lesson 7 code. The genuinely new code is the device-config mapping in step 2 and the RX buffer poster in step 4.

1
Probe virtio-net and run the handshake through FEATURES_OK. Reuse Lesson 6's VirtioBlk::probe shape — PCI find, capability walk, map common-config region — but for the network device (vendor 0x1AF4, device 0x1041). Drive reset_and_acknowledge and negotiate_features. The feature bits change — low half 0x20 for NET_F_MAC, high half 0x1 for VERSION_1 — but the register dance is identical to virtio-blk. Stop after FEATURES_OK sticks. Commit.
2
Map the device-config cap and read the MAC. Find the cap with cfg_type == 4 in the capability list, map it via map_mmio. Six read_volatile calls at offsets 0–5 read the MAC bytes. Print as 52:54:00:12:34:56. Stash the MAC in the driver struct for later ARP and TX use. Commit.
3
Set up virtqueue 0 (RX) and virtqueue 1 (TX). Two VirtQueue::new(64) calls, two configure_queue calls — one with queue_select = 0, one with queue_select = 1. The Lesson 7 code already handles any queue index; pass it. Verify both queue_enable readbacks are 1. Commit.
4
Post 8 empty RX buffers, then set DRIVER_OK. Allocate eight 2048-byte frames (two 4 KiB allocations each, or one frame split in half). For each: allocate a descriptor with F_WRITE, point it at the buffer's physical address, length 2048, and submit it to RX's avail ring with Release ordering. Do not kick — the device reads RX at DRIVER_OK time. Then write DRIVER_OK. The device is now live and any broadcast ARP from slirp will land in one of the posted buffers within milliseconds. Commit.
Deferred work

No frames are sent or received yet. DRIVER_OK is set, RX is stocked, TX is empty, and the device is waiting. The first byte to cross the wire is Lesson 21. This lesson's job is to leave the card in a state where the next lesson has something to parse.

Primary source

The virtio 1.2 spec is the authoritative reference for everything in this lesson: §5.1 Network Device covers feature bits, device config, the header, and the queue semantics. For Linux's implementation of the same ideas, drivers/net/virtio_net.c's virtnet_probe walks the same handshake and reads the same MAC field — though it claims more features, posts more buffers, and runs the whole thing under a softirq. The mini-os version is a stripped-down outline of the same shape.
