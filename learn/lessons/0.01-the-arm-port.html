The ARM port, read beside x86

What actually changes when you move a kernel to a second CPU — walked one job at a time, against the x86 you already know.

Gabix ran on one CPU: x86_64, inside an emulator. You wanted it on a second CPU, ARM, so it could run on the Raspberry Pi 2B on your desk. Moving a kernel to a new CPU sounds like rewriting it. The first thing this lesson shows is how little of the kernel actually depends on the CPU. What follows is a walk through the parts that do — each read against the x86 version you already have, so you can see exactly what changed, and which lesson to open when you want the detail.

Most of the kernel does not care which CPU runs it

Consider what the kernel does to read a file. It asks the disk for some bytes, walks the ext2 on-disk format to find which bytes belong to the file, and hands them to the program. Not one step in that chain depends on x86 or ARM — the ext2 layout is the same bytes whoever reads it. The same is true of the network: the bytes of a TCP segment mean the same thing on every CPU.

Gabix pulled all of this CPU-independent code into one library that both kernels share, and left only the genuinely CPU-specific code in per-CPU directories:

Where the code lives, after the port.
crates/kernel-core — shared by both kernels: ext2, the ELF loader's logic, the network protocol codecs, the file-descriptor machinery.
src/arch/x86_64/ — the x86 side: paging, the interrupt table, the syscall entry, context switching.
targets/armv7/ — the ARM side: the same jobs, written for the ARM CPU and the Raspberry Pi's chips.

This is how Linux is built too. Linux's fs/, net/, and mm/ directories are shared by every architecture; arch/x86/ and arch/arm/ hold only the parts that genuinely differ. So when you ask what did it take to port gabix to ARM, the short answer is: less than you would think.

Five jobs where the CPU matters

There are five things a kernel does where the choice of CPU changes the code. We take them in the order the hardware makes you care about them: starting up, protecting user programs, translating memory, getting interrupted, and finding devices.

1. Starting up

When you apply power, the CPU starts running instructions at some fixed address, fully privileged, with no setup at all. The kernel's first few instructions have to build enough of a world — a stack, a way to print to the console, eventually memory — to hand control to ordinary Rust code.

On x86, a separate program called a bootloader does a lot of this for you: it loads the kernel into memory and jumps in with the CPU in a known state. On ARM there is usually no such helper. The board's firmware loads the kernel image (on the Pi, a file named kernel7.img) into memory and jumps to its first instruction; the kernel does the rest itself.

One wrinkle is pure Raspberry Pi. The Pi 2B has four CPU cores, and the firmware starts all four at the same first instruction at the same instant. Gabix is not ready to use four cores, so its first instruction asks the CPU "which core am I?" and everything but core 0 immediately parks itself in a low-power wait. You can read this in the first lines of src/arch/armv7/boot.S.

2. Letting a program run with fewer rights — and giving it a way back to the kernel

This is the job that defines a kernel. A user program must not be free to read kernel memory or run the CPU's most dangerous instructions. But it must be able to ask the kernel to do those things on its behalf — read a file, send a packet, get the time of day. So the CPU needs two things built in: a way to run a program with reduced rights, and a controlled door that program can knock on to re-enter the kernel.

x86 calls the privilege levels rings. The kernel runs in ring 0 (full rights); a user program runs in ring 3 (restricted). The current ring is a small field the CPU keeps about the program it is running. To call the kernel, the program runs a single instruction, syscall. The CPU treats that instruction specially: it raises the privilege to ring 0 and jumps to a kernel address the kernel registered in advance. Returning to the program is the reverse instruction, sysret, which drops back to ring 3.

ARM does the same job with a different vocabulary. Instead of rings it has modes: User mode for programs, Supervisor mode for the kernel, and a few others for handling errors and interrupts. The current mode lives in a field in a CPU status register. To call the kernel, the program runs an instruction called svc. The CPU switches to Supervisor mode and jumps to a fixed entry point the kernel set up. Returning drops the mode back to User.

Same two problems — restrict the program, then give it a door — solved two ways. This is the single biggest conceptual difference between the two kernels, and Module 1 takes it apart instruction by instruction.

Go deeper: Module 1.

3. Translating memory

Every program must see its own memory, and it must not see another program's memory or the kernel's. The CPU enforces this with a table. On every memory access a program makes, the CPU consults the table, which says — for each range of addresses — where the bytes physically live and whether this program is allowed to reach them.

On x86 the kernel gives each process its own table and swaps it in when that process runs; the blocks are small (4 KB). Gabix on x86 builds a fresh table for every process, which is how two programs can both believe they live at the same address.

The ARM port so far does the simpler thing: one shared table for everything, with large 1 MB blocks, mapping every address to itself. To isolate a user program, it flips the permission bits on the single 1 MB block the program occupies, so the program can reach its own code and nothing else. That is enough to run a user program. The port does not yet give each process its own table; that is a later step.

Go deeper: Module 2.

4. Getting interrupted

Left to itself, the CPU runs a program's instructions one after another. The kernel needs the CPU's attention pulled away on two occasions: when a timer fires (so the kernel can switch to another program), and when a device finishes a job (a disk read completes, a network packet arrives). The running program cannot be trusted to yield; the hardware has to force the issue.

The mechanism has two halves: a chip that raises the signal, and a table that tells the CPU where to jump. On x86 the chip is the Local APIC and the table is the IDT — 256 numbered slots, each holding the address of one handler. When the signal arrives, the CPU reads the slot's address and jumps there, into the kernel, at full privilege.

ARM has the same two halves, with different names and, on the Pi, a different chip. On the ARM emulator the chip is called the GIC; on the Raspberry Pi it is a controller Broadcom built into the board. The table is tiny — eight slots — and sits at an address the kernel wrote into a CPU register. When the signal arrives, the CPU jumps to one of those eight. Which of the eight it is, and how you then ask the controller "which device interrupted?", differs between the emulator and the real Pi — and matters when you debug on Monday.

Go deeper: Module 1 for the mechanism; Module 7 for the Pi's controller.

5. Finding devices

Before the kernel can read a disk or send a packet, it has to find the device. The two architectures make the kernel look in completely different places.

On x86, devices sit on a shared bus called PCI. The kernel walks the bus — "who is at slot 0? slot 1? slot 2?" — and reads a little identifying information each device reports.

The ARM emulator has no such bus. It places up to 32 virtual devices at 32 fixed addresses in memory, and the kernel reads each address looking for a magic value that means "I am a virtio device." There is no discovery protocol; the locations are agreed in advance.

The Raspberry Pi is different again, and harder. There are no virtio devices and no PCI bus. The "disk" is the SD card, reached through a controller Broadcom made. The "network card" is a chip that hangs off the Pi's USB port. Each is a separate piece of hardware with its own rulebook, and the kernel drives each one by its own rules. This is the module that matters most for getting gabix running on the actual board.

Go deeper: Module 4 for the mechanism; Module 7 for the Pi's real chips.
