Block Layer Abstraction

Wrap "submit a read for sector N" into a clean read_sector(n) -> [u8; 512]. Everything below this point speaks sectors; everything above speaks files.

Read time ~15 min Build time ~20–30 min Prereq Lesson 8

Lesson 8 reads one sector: build descriptor chain, submit, kick, poll, verify. The code is inline in main.rs. That works for a one-off test, but the ext2 parser (Lesson 11) needs to read hundreds of sectors — superblocks, block group descriptors, inode tables, directory entries. Each read goes through the same dance. Lesson 9 wraps the dance into a function.

Why a block layer at all

"Block layer" sounds like jargon, but the concept is simple: a single function the filesystem calls, read_sector(n) -> [u8; 512]. Filesystem code asks for bytes by sector number. Driver code below the function does the actual I/O.

This separation lets the filesystem code ignore the device. ext2 doesn't care whether the storage is virtio-blk, NVMe, SATA, or a RAM disk — it just calls read_sector(N). The device driver doesn't care whether the bytes are an inode, a directory entry, or file data — it just reads sector N and hands back bytes.

ext2 / VFS "give me inode 2" / "list this directory"
block layer ← Lesson 9 read_sector(n) -> [u8; 512]
virtio-blk driver build chain, submit, kick, poll
virtqueue descriptors, available ring, used ring
PCI + MMIO device discovery, register access

Linux's analog is submit_bio(bio) — filesystems construct a bio (block I/O) describing what bytes they want, submit it through the block layer, and the block layer routes it to the right device's driver. Ours is much simpler (synchronous, single device, no merging or scheduling) but the boundary is in the same place.

The API contract

The function we're building: 

impl VirtioBlk {
    pub fn read_sector(&mut self, sector: u64) -> [u8; 512] {
        // ...
    }
}

The contract:

  • Input: a sector number (always 512-byte units for virtio-blk).
  • Output: a fixed [u8; 512] array, by value. Caller owns it; can read, copy, or drop it freely.
  • Synchronous: returns when the read completes. No callbacks, no futures.
  • Side effects: internally submits a virtio-blk request, kicks the device, polls for completion. Allocates and leaks DMA buffers (~12 KB per call).

The leak is a known wart. Each call allocates three frames (header, data, status) and never frees them. Real Linux has a slab pool for request structures. We'll do the same in a later lesson; for now, "leak per call" is fine because we won't read that many blocks during boot.

Returning [u8; 512] by value

512 bytes on the stack sounds big, but it's fine. The array gets returned via Rust's "return value optimization" — the caller's stack slot is the destination, no intermediate copy. Even if there were a copy, 512 bytes is 8 cache lines, sub-100ns on modern CPUs. The alternative (Vec<u8>) would heap-allocate per call, which is worse.

Refactor: VirtioBlk owns the queue

Currently virtio_dev and queue are separate locals in main.rs. For read_sector to work, it needs both — the device for kicking, the queue for descriptor allocation and ring access.

The cleanest fix: VirtioBlk owns the VirtQueue. The boot sequence becomes: 

let mut virtio_dev = VirtioBlk::probe()?;
virtio_dev.reset_and_acknowledge();
virtio_dev.negotiate_features();
virtio_dev.set_driver_ok();
virtio_dev.setup_queue(64);  // ← was: VirtQueue::new + configure_queue

let block0 = virtio_dev.read_sector(0);  // clean API, no queue argument

The queue sits in a Option<VirtQueue> field, populated by setup_queue. read_sector unwraps it. This hides the descriptor chain from callers entirely — they don't even know there is a queue.

pub fn setup_queue(&mut self, queue_size: u16) {
    let queue = VirtQueue::new(queue_size);
    self.configure_queue(&queue);
    self.queue = Some(queue);
}

Update main.rs: replace the local VirtQueue::new + configure_queue + inline Lesson 7/8 tests with a single virtio_dev.setup_queue(64) call. The Lesson 7/8 tests can stay (they verify the underlying methods work) but they need to reach the queue via virtio_dev.queue.as_mut().unwrap() or a similar accessor.

Verify: boot still completes the Lesson 8 read end-to-end. No behavior change, just ownership moved.

9.2Add read_sector

New method on VirtioBlk: 

pub fn read_sector(&mut self, sector: u64) -> [u8; 512] {
    let buffers = BlkBuffers::new();
    let req = VirtioBlkReq::new_read(sector);
    buffers.write_header(&req);

    let queue = self.queue.as_mut().expect("queue not set up");
    let head = queue.build_read_chain(
        buffers.header_phys, buffers.data_phys, buffers.status_phys);

    queue.submit_chain(head);
    self.kick();

    // Poll for completion (sync — block until done)
    let completion = (0..200_000)
        .find_map(|_| queue.poll_completion())
        .expect("read_sector: no completion");

    let status = buffers.read_status();
    assert_eq!(status, VIRTIO_BLK_S_OK, "read failed");

    // Copy the 512 bytes out of the DMA buffer into a stack array
    let mut block = [0u8; 512];
    let data_view = buffers.read_data_prefix(512);
    block.copy_from_slice(&data_view);

    // Free the descriptors (buffers leak — future optimization)
    queue.free_descriptor(head);
    // ... also free mid and tail (need to track them or follow chain)

    block
}

Note: to free all three descriptors, build_read_chain needs to return all three indices (or we walk the next pointers from head to find them). The simplest change: have build_read_chain return (head, mid, tail) instead of just head. Callers that only need the head can use let (head, _, _).

9.3Verify: read multiple sectors

Call read_sector on sectors 0, 1, and 2:

  • Sector 0: first 15 bytes should be b"MINIOS_DISK_v0\n", rest zero (already verified in Lesson 8 but re-check via the new API).
  • Sector 1: should be all zero (the signature is only 15 bytes, fits in sector 0).
  • Sector 2: should be all zero (we'll learn in Lesson 11 that ext2 puts the superblock here, but our raw disk has no filesystem yet).

Three calls, three arrays. Verify all three match expectations. This confirms read_sector works for arbitrary sector numbers, not just sector 0.

What this enables

After Lesson 9, the kernel has a primitive that the ext2 parser can call. When Lesson 11 wants to read the superblock, it calls read_sector(2) — because the ext2 superblock lives at byte offset 1024, which is sector 2 (1024 / 512). When Lesson 12 wants to read inode 2 (the root inode), it computes which block holds that inode, calls read_sector(block_num), and parses the inode structure out of the returned bytes.

None of the ext2 code will know about virtio, descriptors, DMA buffers, or the kick/poll dance. That's the win.

Primary source

Linux's block layer is documented in the kernel's block documentation. The function submit_bio in block/bdev.c is the entry point — filesystems call it, the block layer routes to the device driver.

For our reference design: drivers/block/virtio_blk.c shows how a driver registers with the block layer (blk_mq_alloc_tag_set + blk_mq_init_queue). Our read_sector folds both halves — submission and driver-specific execution — into one synchronous call. Linux keeps them separate for async performance.

Pause and think

read_sector is synchronous: it spins in a poll loop until the device responds, blocking the whole kernel. For single-process mini-os that's tolerable. Why is this design unacceptable for a real OS? What's the smallest change that would let other code run while waiting for a disk read?
