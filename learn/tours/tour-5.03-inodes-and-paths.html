3.1Inode shape: ino, kind, and the REGISTRY

Files touched: src/fs.rs

Before this step, Inode was just a wrapper around Mutex<Vec<u8>> — pure bytes, no identity, no kind. The hardcoded inode from Lesson 2 worked because there was exactly one of it. Step 3.1 grows Inode into something that can be named and looked up.

The kind discriminant

A clean Rust enum replaces Linux's type-bitmask-in-i_mode. Two variants for now; symlink/device/pipe/socket come in later lessons.

src/fs.rs — InodeKind enum 
pub enum InodeKind {
    File,  // bytes are file contents
    Dir,   // bytes are dirent records
}

Derived traits: Debug for println!, Clone + Copy because it's a 1-byte value, PartialEq + Eq for == in path walk ("is this a directory?").

The grown Inode struct

src/fs.rs — Inode struct (with new ino and kind fields) 
pub struct Inode {
    pub ino: u64,
    pub kind: InodeKind,
    pub data: Mutex<Vec<u8>>,
}

ino is the stable identifier — what directory entries store, what stat() returns. kind tells the kernel how to interpret data. The Mutex<Vec<u8>>> payload is unchanged from Lesson 2.

Inode number allocation

src/fs.rs — NEXT_INO counter (module-level static) 
/// Monotonic counter. Starts at 1 — Linux reserves inode 0 as "no inode".
static NEXT_INO: AtomicU64 = AtomicU64::new(1);

AtomicU64 is overkill on single-CPU QEMU but correct under any future SMP configuration. fetch_add(1, SeqCst) returns the value before the add, so the first allocated inode gets number 1.

Constructors that allocate + register

src/fs.rs — impl Inode (new_file, new_dir, alloc, lookup) 
impl Inode {
    pub fn new_file(initial: &[u8]) -> Arc<Inode> {
        Self::alloc(InodeKind::File, Vec::from(initial))
    }

    pub fn new_dir() -> Arc<Inode> {
        Self::alloc(InodeKind::Dir, Vec::new())
    }

    fn alloc(kind: InodeKind, data: Vec<u8>) -> Arc<Inode> {
        let ino = NEXT_INO.fetch_add(1, Ordering::SeqCst);
        let inode = Arc::new(Inode { ino, kind, data: Mutex::new(data) });
        REGISTRY.lock().insert(ino, inode.clone());
        inode
    }

    pub fn lookup(ino: u64) -> Option<Arc<Inode>> {
        REGISTRY.lock().get(&ino).cloned()
    }
}

The constructor returns Arc<Inode> rather than Self because it has to register a clone in the REGISTRY anyway. Callers get the same Arc back; future Inode::lookup(ino) calls return clones of the same shared struct.

The registry itself

src/fs.rs — REGISTRY lazy_static 
use alloc::collections::BTreeMap;

lazy_static! {
    pub static ref REGISTRY: Mutex<BTreeMap<u64, Arc<Inode>>> =
        Mutex::new(BTreeMap::new());
}

BTreeMap over HashMap because we don't have a hashing crate bundled; BTreeMap lives in alloc::collections with no extra deps. Linux's analog is xarray-indexed; same shape, different data structure.

HARDCODED_INODE migrated

src/fs.rs — HARDCODED_INODE before/after 
// Before (Lesson 2):

// After (3.1):
pub static ref HARDCODED_INODE: Arc<Inode> =
    Inode::new_file(b"hello vfs\n");

Same observable bytes, but the inode now lives in the registry under whatever ino the counter handed it (1, since this is the first allocation). Step 3.3 will replace this static entirely with a real root directory.

3.2Dirent byte format: encode and decode helpers

Files touched: src/fs.rs, src/main.rs (test)

Step 3.1 made inodes addressable by number; step 3.2 makes the directory format real. The format we landed on in the design chat:

— Directory entry byte layout (conceptual diagram) 
+-----------+-----------------+----------------+
| name_len  | name [N bytes]  | ino [u64 LE]   |
+-----------+-----------------+----------------+
   1 byte        name_len           8 bytes

Length-prefix lets the parser skip an entry without reading the name or the ino field. Linux's struct linux_dirent64 uses the same trick via d_reclen.

encode_dirent

src/fs.rs — encode_dirent function 
pub fn encode_dirent(name: &str, ino: u64) -> Vec<u8> {
    let name_bytes = name.as_bytes();
    assert!(name_bytes.len() <= u8::MAX as usize, "dirent name too long");
    let mut out = Vec::with_capacity(1 + name_bytes.len() + 8);
    out.push(name_bytes.len() as u8);
    out.extend_from_slice(name_bytes);
    out.extend_from_slice(&ino.to_le_bytes());
    out
}

u8::MAX = 255, matching Linux's NAME_MAX. The assert! panics rather than returning a Result because a kernel-internal encode_dirent calling itself with a 256-byte name is a programmer bug, not a runtime error.

lookup_in_dir

src/fs.rs — lookup_in_dir function (linear scan) 
pub fn lookup_in_dir(dir_bytes: &[u8], name: &str) -> Option<u64> {
    let name_bytes = name.as_bytes();
    let mut i = 0;
    while i < dir_bytes.len() {
        let name_len = dir_bytes[i] as usize;
        let entry_size = 1 + name_len + 8;
        if i + entry_size > dir_bytes.len() {
            return None; // truncated final entry — corrupted directory
        }
        let entry_name = &dir_bytes[i + 1 .. i + 1 + name_len];
        if entry_name == name_bytes {
            let ino_start = i + 1 + name_len;
            let ino_bytes: [u8; 8] = dir_bytes[ino_start .. ino_start + 8].try_into().ok()?;
            return Some(u64::from_le_bytes(ino_bytes));
        }
        i += entry_size;
    }
    None
}

The while loop walks entries. The "skip to next" operation is just i += entry_size — that's the O(1) advance we talked about in the design chat. On a hit we try_into the 8 ino bytes into a fixed array, parse little-endian, and return. On a miss or on truncation we return None.

Why ? on try_into. The slice is exactly 8 bytes when we reach that line (we just bounds-checked i + entry_size), so try_into can only fail if our arithmetic is wrong. ? propagates the impossible case as None.

3.3Root directory inode with one entry

Files touched: src/fs.rs, src/main.rs (test)

Steps 3.1 and 3.2 gave us the type system and the dirent byte format. Step 3.3 uses both to actually build a filesystem — a root directory containing one file.

Reserved inode numbers

src/fs.rs — Reserved inode number constants (module-level) 
pub const ROOT_INO: u64 = 1;
const HELLO_INO: u64 = 2;

Hardcoded constants so the boot test can assert them specifically. Linux's ext4 reserves inode 1 for a "bad blocks" list and uses inode 2 for the root; we don't have bad blocks, so root is inode 1. HELLO_INO is private — only the root initializer needs it.

The root initializer

src/fs.rs — ROOT_INODE lazy_static initializer 
lazy_static! {
    pub static ref ROOT_INODE: Arc<Inode> = {
        let root = Inode::new_dir();
        debug_assert_eq!(root.ino, ROOT_INO,
            "root must be the first inode allocated; something allocated first");

        let hello = Inode::new_file(b"hello vfs\n");
        debug_assert_eq!(hello.ino, HELLO_INO,
            "hello.txt must be the second inode allocated");

        // Append the directory entry: name="hello.txt", ino=hello.ino
        let entry = encode_dirent("hello.txt", hello.ino);
        root.data.lock().extend_from_slice(&entry);

        root
    };
}

Three things happen in this initializer, in order:

  1. Inode::new_dir() allocates an inode from NEXT_INO (which is 1, since this is the first allocation), registers it, returns the Arc.
  2. Inode::new_file(b"hello vfs\n") allocates again — gets ino=2 this time.
  3. encode_dirent("hello.txt", 2) builds the dirent bytes [9][h,e,l,l,o,.,t,x,t][02 00 00 00 00 00 00 00], which get appended to the root's data via the Mutex.

The debug_assert_eq!s catch the case where some other code allocates an inode before ROOT_INODE initializes — for example, if HARDCODED_INODE's old Inode::new_file(b"...") initializer were still in place. They're cheap assertions: fire only in debug builds, no runtime cost in release.

HARDCODED_INODE becomes an alias

src/fs.rs — HARDCODED_INODE repurposed as registry lookup 
pub static ref HARDCODED_INODE: Arc<Inode> = {
    // Force ROOT_INODE init first, so hello.txt (ino=2) is registered.
    let _ = &*ROOT_INODE;
    Inode::lookup(HELLO_INO).expect(
        "hello.txt inode should be registered after ROOT_INODE init")
};

Two design options existed here: (a) remove HARDCODED_INODE entirely and rewrite sys_open's call site, or (b) keep it as an alias that looks up the same inode by number. Option (b) keeps step 3.3 scoped — no syscall.rs changes, the existing USER_PROGRAM still works. Step 3.4 will eliminate the alias when sys_open gets real path resolution.

The let _ = &*ROOT_INODE; line is the load-bearing trick: lazy_static initializers run on first access, and &*STATIC is what counts as "access." This forces ROOT_INODE to initialize first, which guarantees the hello inode is in the registry before we try to look it up.

3.4Path resolution in sys_open

Files touched: src/fs.rs, src/syscall.rs, src/main.rs (test)

The Lesson 2 sys_open ignored its path argument and returned the hardcoded inode. Step 3.4 replaces that stub with real path resolution — read the path string from user memory, walk the directory tree, return the resolved inode wrapped in a File.

The path walker

src/fs.rs — resolve_path function 
pub fn resolve_path(path: &str) -> Option<Arc<Inode>> {
    if !path.starts_with('/') {
        return None;
    }

    let mut current = ROOT_INODE.clone();

    for component in path.split('/').filter(|c| !c.is_empty()) {
        if current.kind != InodeKind::Dir {
            return None; // ENOTDIR
        }

        let dir_data = current.data.lock();
        let next_ino = lookup_in_dir(&dir_data, component)?;
        drop(dir_data);

        current = Inode::lookup(next_ino)?;
    }

    Some(current)
}

Six-step walk, exactly as designed in the lesson:

  1. Reject relative paths (must start with /).
  2. Start at ROOT_INODE.
  3. Split on /, drop empty components — this handles leading /, double //, and trailing / uniformly.
  4. For each component: require current to be a directory (ENOTDIR otherwise), look up the name in current's bytes via lookup_in_dir, fetch the inode from the registry.
  5. Descend: current = looked_up_inode.
  6. Return whatever current ends up being. The final inode's kind isn't checked — that's the caller's responsibility (in Linux, open() on a directory has different semantics than on a file, but we don't model that yet).

Lock discipline. Each iteration locks the current directory's data only long enough to read its entries, then drops the guard before locking the REGISTRY. No nested locks, no deadlock potential.

Reading the path from user memory

src/syscall/user.rs:24 — read_user_path helper 
pub(super) fn read_user_path(ptr: u64) -> Option<alloc::string::String> {
    const PATH_SCAN_BYTES: usize = 256;

    if ptr == 0 || !is_low_half_range(ptr, PATH_SCAN_BYTES as u64) {
        return None;
    }

    let bytes = unsafe { core::slice::from_raw_parts(ptr as *const u8, PATH_SCAN_BYTES) };
    let end = bytes.iter().position(|&byte| byte == 0)?;
    if end == 0 {
        return None;
    }

    let path = core::str::from_utf8(&bytes[..end]).ok()?;
    Some(alloc::string::String::from(path))
}

The helper rejects a zero pointer, a numerically out-of-range window, a missing terminator, an empty path or invalid UTF-8. It still assumes the entire 256-byte window is readable. The range check does not establish page presence or user permissions, so constructing and reading this slice remains an unchecked requirement that can fault in the kernel. Source: src/syscall/user.rs:20–41.

The in-range-but-unmapped case (e.g., user passes 0x1000 but never mapped that page) still page-faults. Same limitation as sys_read/sys_write — see learning-record 0005. Fixing it requires a page-fault handler, which is its own future milestone.

The new sys_open

src/syscall.rs — sys_open (replaces Lesson 2 stub) 
fn sys_open(name_ptr: u64) -> u64 {
    let path = match read_user_path(name_ptr) {
        Some(p) => p,
        None => {
            println!("[syscall] sys_open: bad path pointer 0x{:x}", name_ptr);
            return u64::MAX;
        }
    };

    let inode = match fs::resolve_path(&path) {
        Some(i) => i,
        None => {
            println!("[syscall] sys_open: no such file: {:?}", path);
            return u64::MAX;
        }
    };

    let file = Arc::new(fs::File::new(inode));
    let fd = crate::task::with_current_fd_table(|fdt| fdt.open(file));
    println!("[syscall] sys_open(path={:?}) -> fd={}", path, fd);
    fd
}

Two distinct error returns: bad pointer (read failed) and no-such-file (resolution failed). Linux would distinguish these as EFAULT versus ENOENT; we collapse both to u64::MAX (our generic -1 sentinel). When USER_PROGRAM passes a real path in step 3.5, both branches become unreachable for the success case.

3.5USER_PROGRAM calls open("/hello.txt")

Files touched: src/user.rs

Step 3.4 left USER_PROGRAM passing NULL — sys_open returned u64::MAX and the chain failed with "bad fd". Step 3.5 changes the test program to pass a real absolute path so the whole flow exercises.

The instruction change

src/user.rs — USER_PROGRAM opening instruction (was xor, now mov) 
// Before (Lesson 2):
// 0x0A: xor rdi, rdi (path = NULL, 3 bytes)
0x48, 0x31, 0xFF,

// After (3.5):
// 0x0A: mov rdi, 0x4000008C (path = "/hello.txt", 10 bytes)
0x48, 0xBF, 0x8C, 0x00, 0x00, 0x40, 0x00, 0x00, 0x00, 0x00,

Replacing a 3-byte instruction with a 10-byte one shifts every offset after it by 7. BUF_OUT moved from 0x40000075 to 0x4000007C; both mov rsi references updated. The path string itself is appended at the end of the program at 0x4000008C, 11 bytes including the null terminator. Total program size: 133 → 151 bytes.

0x2F = /, then ASCII for hello.txt, then 0x00 null terminator. This is what the kernel's read_user_path reads out of user memory.

3.6Second file secret.txt proves resolution distinguishes files

Files touched: src/fs.rs, src/main.rs (test), src/user.rs

The load-bearing test for Lesson 3. Without a second file, the whole path resolution machinery could silently always return the same inode and every test would still pass. Adding a second file with different contents is the only way to prove the walker actually looks at the path argument.

The new file in the root initializer

src/fs.rs — ROOT_INODE initializer now creates two files 
pub static ref ROOT_INODE: Arc<Inode> = {
    let root = Inode::new_dir();
    debug_assert_eq!(root.ino, ROOT_INO, ...);

    let hello = Inode::new_file(b"hello vfs\n");
    debug_assert_eq!(hello.ino, HELLO_INO, ...);

    let secret = Inode::new_file(b"top secret\n");   // new
    debug_assert_eq!(secret.ino, SECRET_INO, ...); // new

    let mut root_data = root.data.lock();
    root_data.extend_from_slice(&encode_dirent("hello.txt", hello.ino));
    root_data.extend_from_slice(&encode_dirent("secret.txt", secret.ino)); // new
    drop(root_data);

    root
};

Same pattern as the hello file: allocate inode (gets number 3), append a dirent to root's bytes. The directory's data is now two records concatenated: (hello.txt, 2) then (secret.txt, 3). The linear scan in lookup_in_dir returns the first name match.

The kernel-internal proof

src/main.rs — Multiple-files boot test 
let hello = resolve_path("/hello.txt").expect("hello.txt should resolve");
let secret = resolve_path("/secret.txt").expect("secret.txt should resolve");

assert_ne!(hello.ino, secret.ino);

let hello_data = hello.data.lock();
let secret_data = secret.data.lock();
assert_eq!(&*hello_data, b"hello vfs\n");
assert_eq!(&*secret_data, b"top secret\n");

Doesn't depend on USER_PROGRAM — directly resolves both paths and checks both bytes. If the path resolver ever started ignoring the argument and returning the same inode, both expects would still succeed but assert_ne! would fail (inos equal) and assert_eq! on bytes would fail (one of them would be wrong).

The doubled USER_PROGRAM

src/user.rs — USER_PROGRAM now has two open/read/write/close cycles 
// Cycle 1: hello.txt (10 bytes)
0x00: mov rax, 2; mov rdi, "/hello.txt"; syscall       // open
0x16: xor rdi, rdi; mov rsi, BUF_OUT; mov rdx, 10; xor rax, rax; syscall // read
0x32: mov rdi, 1; mov rsi, BUF_OUT; mov rdx, 10; mov rax, 1; syscall // write
0x5C: xor rdi, rdi; mov rax, 3; syscall                       // close

// Cycle 2: secret.txt (11 bytes)
0x6B: mov rax, 2; mov rdi, "/secret.txt"; syscall       // open
0x81: xor rdi, rdi; mov rsi, BUF_OUT; mov rdx, 11; xor rax, rax; syscall // read
0x9D: mov rdi, 1; mov rsi, BUF_OUT; mov rdx, 11; mov rax, 1; syscall // write
0xC7: xor rdi, rdi; mov rax, 3; syscall                       // close

Both cycles share BUF_OUT since operations are sequential. Two path strings live at the end of the program: "/hello.txt\0" (11 bytes) and "/secret.txt\0" (12 bytes). Total program size: 151 → 270 bytes.

[test] multiple files (3.6)
[test]   hello.txt ino=2, secret.txt ino=3 (must differ)
[test]   hello.txt bytes = [104, 101, 108, 108, 111, 32, 118, 102, 115, 10]
[test]   secret.txt bytes = [116, 111, 112, 32, 115, 101, 99, 114, 101, 116, 10]
...
[syscall] sys_open(path="/hello.txt") -> fd=0
[syscall] sys_read fd=0 buf=0x400000e7 len=10 -> read 10 bytes (inode 10 bytes, cursor 0->10)
hello vfs
[syscall] sys_write fd=1 -> serial, 10 bytes
[syscall] sys_close fd=0 -> ok
[syscall] sys_open(path="/secret.txt") -> fd=0  (fd=0 reused after close)
[syscall] sys_read fd=0 buf=0x400000e7 len=11 -> read 11 bytes (inode 11 bytes, cursor 0->11)
top secret
[syscall] sys_write fd=1 -> serial, 11 bytes
[syscall] sys_close fd=0 -> ok
[syscall] sys_exit(0)

Two things worth noticing:

  1. fd=0 is reused for secret.txt after hello.txt is closed. That's POSIX "lowest free fd" semantics — the freed slot from close(0) is the first one FdTable::open finds on the next open.
  2. Cursor 0→11 on the secret.txt read shows the inode's data is exactly 11 bytes ("top secret\n"). The cursor moved the right amount for the right file — silent proof that path resolution didn't return the hello inode.

Commit c4f6101. Wall-clock time: ~220 seconds. Lesson 3 complete — the kernel now has a real (two-file) filesystem with real path resolution.
