5.1Raw disk image + QEMU virtio-blk-pci attach

Files touched: scripts/make-disk.sh (new), scripts/run.sh (new), .gitignore

Pure infrastructure — no kernel code. The disk needs to exist before the kernel can find it on the PCI bus in step 5.3, so this step makes it exist and attaches it to QEMU.

Disk image creation script

scripts/make-disk.sh — Full script 
#!/bin/sh
# Create or reset the test disk image used by mini-os for the virtio-blk path.

set -e

DISK_IMG=disk.img
SIZE_MB=1
SIGNATURE='MINIOS_DISK_v0'

# Create the file (sparse, all zeros)
truncate -s "${SIZE_MB}M" "$DISK_IMG"

# Write the signature at offset 0 followed by a newline
printf '%s\n' "$SIGNATURE" | dd of="$DISK_IMG" conv=notrunc bs=1 count=$(( ${#SIGNATURE} + 1 )) 2>/dev/null

# Verify
echo "Created $DISK_IMG ($SIZE_MB MB)"
echo "First 16 bytes:"
hexdump -C "$DISK_IMG" | head -1

Two commands do the real work: truncate -s 1M disk.img creates a 1 MB sparse file (no actual disk space used until written), and dd conv=notrunc writes the signature without truncating the file. The bs=1 count=15 writes exactly the signature length, leaving the rest of the file as zeros.

The signature "MINIOS_DISK_v0\n" is 15 bytes — a readable marker that Lesson 8 will verify after the first disk read. Any recognizable pattern works; the point is having known bytes at sector 0 to compare against.

QEMU launch script

scripts/run.sh — Full script (boots kernel + attaches virtio-blk) 
#!/bin/sh
set -e

DISK_IMG=disk.img
KERNEL=target/x86_64-mini-os/debug/bootimage-mini-os.bin

if [ ! -f "$DISK_IMG" ]; then
    echo "Run ./scripts/make-disk.sh first to create $DISK_IMG" >&2
    exit 1
fi

cargo bootimage 2>&1 | tail -3

exec qemu-system-x86_64 \
    -drive format=raw,file="$KERNEL" \
    -drive file="$DISK_IMG",format=raw,if=none,id=drv0 \
    -device virtio-blk-pci,drive=drv0 \
    -display none \
    -serial stdio \
    -no-reboot

Two -drive flags + one -device flag attach the virtio-blk disk:

  1. First -drive — the kernel bootimage. QEMU's bootloader (SeaBIOS) sees this as the boot disk and loads our kernel from it.
  2. Second -drive — our raw disk.img. The if=none means "don't auto-attach it to a built-in controller" — we're going to wire it up explicitly via the next flag. The id=drv0 gives it a name we can reference.
  3. -device virtio-blk-pci,drive=drv0 — instantiates a virtio-blk PCI device and connects it to the drive we just defined. From QEMU's perspective: this is the moment the PCI bus gets a virtio-blk device attached. From the guest kernel's perspective (once we look): there's now a device at some PCI slot waiting to be found.

The -no-reboot flag tells QEMU to halt on triple fault instead of rebooting. Useful for catching kernel bugs that would otherwise cause an infinite reboot loop.

5.2PCI config space access — src/pci.rs

Files touched: src/pci.rs (new), src/main.rs

New module pci.rs with two functions — config_read and config_write — that translate bus/device/function/offset into a 32-bit I/O port transaction. The full PCI bus walk comes in 5.3; this step is the primitive they're built on.

The address-word helper

src/pci.rs — make_address: build the 32-bit config address word 
fn make_address(bus: u8, device: u8, func: u8, offset: u8) -> u32 {
    (1u32 << 31)
        | ((bus as u32) << 16)
        | ((device as u32) << 11)
        | ((func as u32) << 8)
        | ((offset as u32) & 0xFC)
}

Direct translation of the bitfield from the lesson. Enable bit at position 31, bus at 23-16, device at 15-11, function at 10-8, offset at 7-2 (the & 0xFC mask clears the low 2 bits — config space accesses are always 32-bit-aligned).

Config read

src/pci.rs — config_read function 
pub fn config_read(bus: u8, device: u8, func: u8, offset: u8) -> u32 {
    let address = make_address(bus, device, func, offset);
    unsafe {
        let mut addr_port: Port<u32> = Port::new(CONFIG_ADDRESS);
        let mut data_port: Port<u32> = Port::new(CONFIG_DATA);
        addr_port.write(address);
        data_port.read()
    }
}

Two-step protocol: write the address word to port 0xCF8, then read 32 bits from port 0xCFC. The x86_64 crate's Port::new + read/write wraps the in/out instructions — same pattern as src/pit.rs and src/serial.rs.

The unsafe block is required because port I/O touches hardware. The safety argument: 0xCF8 and 0xCFC are well-defined PCI configuration access ports, stable across all x86 platforms. Reading a non-existent device returns 0xFFFFFFFF, doesn't crash.

Config write

Identical shape to config_read but writes value to 0xCFC after setting the address. Not used in step 5.2's smoke test — comes into play in Lesson 6 when we write the virtio status register to set DRIVER_OK.

Smoke test

Reads the host bridge at 00:00.0 and asserts its vendor ID is Intel (0x8086). QEMU's pc machine always has an Intel i440FX host bridge at slot 00:00.0, so this is a reliable sanity check that the port I/O actually works.

src/main.rs — PCI config access smoke test 
println!("[test] PCI config space access (5.2)");
{
    let word0 = pci::config_read(0, 0, 0, 0x00);
    let vendor_id = (word0 & 0xFFFF) as u16;
    let device_id = (word0 >> 16) as u16;
    println!("[test]   00:00.0 vendor={:04x} device={:04x}", vendor_id, device_id);
    assert_eq!(vendor_id, 0x8086,
        "host bridge at 00:00.0 should be Intel (0x8086); got 0x{:04x}",
        vendor_id);
}

The 32-bit word at offset 0 holds both IDs packed: vendor in the low 16 bits, device in the high 16. So one read gets both.

5.3Walk bus 0, list every device

Files touched: src/pci.rs, src/main.rs

The kernel can now see the PCI bus. This step builds the walk on top of the step 5.2 primitives: nested loops over device and function, read vendor ID, skip absent slots, print everything present.

Human-readable class names

src/pci.rs — class_name lookup 
fn class_name(base_class: u8) -> &'static str {
    match base_class {
        0x00 => "unclassified",
        0x01 => "mass storage",
        0x02 => "network",
        0x03 => "display",
        0x04 => "multimedia",
        0x05 => "memory controller",
        0x06 => "bridge",
        0x07 => "comm controller",
        0x08 => "generic peripheral",
        0x09 => "input device",
        0x0B => "processor",
        0x0C => "serial bus (USB etc.)",
        0x0D => "wireless",
        _ => "other",
    }
}

Not exhaustive — the full table lives at pci-ids.ucw.cz. Just the common ones we'll see in QEMU.

The enumeration loop

src/pci.rs — enumerate function 
pub fn enumerate() {
    println!("[pci] scanning bus 0");
    for device in 0..32u8 {
        for func in 0..8u8 {
            let vendor_word = config_read(0, device, func, 0x00);
            let vendor_id = (vendor_word & 0xFFFF) as u16;
            if vendor_id == 0xFFFF {
                continue; // absent slot
            }
            let device_id = (vendor_word >> 16) as u16;

            let class_word = config_read(0, device, func, 0x08);
            let base_class = ((class_word >> 24) & 0xFF) as u8;
            let subclass = ((class_word >> 16) & 0xFF) as u8;

            println!(
                "[pci] {:02x}:{:02x}.{} vendor={:04x} device={:04x} class={:02x}{:02x} ({})",
                0u8, device, func,
                vendor_id, device_id,
                base_class, subclass,
                class_name(base_class)
            );
        }
    }
}

Two config reads per slot: offset 0x00 for vendor+device (both 16-bit, packed in one 32-bit word), offset 0x08 for revision+class (revision is byte 0, programming interface is byte 1, subclass is byte 2, base class is byte 3). The class is what tells us "this is a storage device, this is a display, this is a bridge."

Scanning all 8 functions for every device is wasteful for single-function devices — strictly speaking, the PCI spec says you should check the header type's multifunction bit (offset 0x0E bit 7) and only scan functions 1-7 if it's set. In practice, all PCI host bridges return 0xFFFF for absent functions, so the filter does the right thing. Linux does the proper check; we don't bother.

Seven devices on bus 0. The first six are QEMU's default chipset-and-peripherals inventory — the i440FX host bridge and PIIX ISA bridge are the chipset, IDE and PM are part of PIIX, Bochs VGA is the display, E1000 is networking (QEMU adds a NIC by default).

5.4Find virtio-blk specifically, decode its BARs

Files touched: src/pci.rs, src/main.rs

Step 5.3 walked every device. Step 5.4 picks out the virtio-blk specifically and reads its BAR layout — the memory regions where the device's registers live. This is the last kernel-side output we need before Lesson 6's virtio handshake.

Identifying constants

src/pci.rs — virtio vendor and device IDs 
const VIRTIO_VENDOR_ID: u16 = 0x1AF4;
const VIRTIO_BLK_TRANSITIONAL: u16 = 0x1001;
const VIRTIO_BLK_NON_TRANSITIONAL: u16 = 0x1042;

The lesson text mentioned only the non-transitional ID (0x1042), but QEMU exposes the transitional one (0x1001) by default. Both are virtio-blk; transitional means the device also supports the legacy transport for backward compatibility. Modern Linux works with either. We accept both — never trust a single canonical device ID where the spec allows multiple.

Finding the device

src/pci.rs — find_virtio_blk function 
pub fn find_virtio_blk() -> Option<(u8, u8, u8)> {
    for device in 0..32u8 {
        for func in 0..8u8 {
            let vendor_word = config_read(0, device, func, 0x00);
            let vendor_id = (vendor_word & 0xFFFF) as u16;
            if vendor_id != VIRTIO_VENDOR_ID {
                continue;
            }
            let device_id = (vendor_word >> 16) as u16;
            if device_id == VIRTIO_BLK_TRANSITIONAL
                || device_id == VIRTIO_BLK_NON_TRANSITIONAL
            {
                return Some((0, device, func));
            }
        }
    }
    None
}

Same nested-loop shape as enumerate(), but stops on the first match. Returns the bus/device/function tuple so callers can address the device in subsequent config reads. Returns None if no virtio-blk is attached — QEMU without -device virtio-blk-pci would hit this path.

BAR decoding

Each BAR encodes both the type and the address. The low bits are type flags; the rest is the address. Different masks depending on what the type bits say:

src/pci.rs — print_bars: the type/decode logic 
if bar & 0x1 == 1 {
    // I/O BAR — bit 0 is 1, bits 2-31 are the address
    let base = bar & !0x3;
    // ...
} else {
    // Memory BAR — bits 1-2 type, bit 3 prefetch, bits 4-31 address
    let type_bits = (bar >> 1) & 0x3;
    let prefetchable = (bar & 0x8) != 0;
    let base_low = bar & !0xF;

    if type_bits == 0b10 {
        // 64-bit memory BAR — consume THIS slot AND the next.
        // Next BAR holds the high 32 bits of the address.
        let bar_high = config_read(bus, device, func, offset + 4);
        let base64 = (base_low as u64) | ((bar_high as u64) << 32);
        // ... advance i by 2 (skip the consumed next slot)
    } else if type_bits == 0b00 {
        // 32-bit memory BAR — this slot alone
    } else {
        // Reserved type (01 or 11) — shouldn't happen
    }
}

The 64-bit BAR case is the easy-to-miss detail: a 64-bit memory BAR consumes two adjacent BAR slots. The first slot holds the type bits + low 32 bits of address; the next slot holds the high 32 bits. If you naively iterated one slot at a time, you'd misinterpret the high half as a separate BAR.

The full loop tracks the slot index with i += 1 or i += 2 accordingly, so 64-bit BARs are decoded as one entry, not two.

— Boot serial output (virtio-blk BAR dump) 
[test] find virtio-blk and decode BARs (5.4)
[pci] virtio-blk found at 00:04.0
[pci]   BAR0 = 0x0000C001 (I/O space, base 0x0000C000)
[pci]   BAR1 = 0xFEBF1000 (memory, 32-bit, base 0xFEBF1000)
[pci]   BAR2 = 0x00000000 (unused)
[pci]   BAR3 = 0x00000000 (unused)
[pci]   BAR4-BAR5 = 0x00000000FE00000C (memory, 64-bit prefetchable, base 0x00000000FE000000)

Decoding this output by what each BAR holds for the transitional virtio-blk device:

  • BAR0 (I/O at 0xC000) — the legacy virtio transport interface. Old-style I/O port access. We won't use this; we're going modern.
  • BAR1 (32-bit memory at 0xFEBF1000) — likely the MSI-X (Message Signaled Interrupts, Extended) table region. Used for interrupt delivery. We'll defer interrupts and poll for completions initially.
  • BAR4-BAR5 (64-bit prefetchable memory at 0xFE000000) — the modern virtio transport region. This is what Lesson 6 reads from. The 64-bit form means it spans two BAR slots (the loop's i += 2 advance handled that).

The high 32 bits being zero (the 0x00000000FE000000 padding) is just the formatter showing the full 64-bit value. virtio's MMIO regions comfortably fit in 32-bit address space; QEMU places them around 0xFE000000, the standard MMIO window.

Lesson 6 doesn't use the BAR addresses directly. Modern virtio hides the actual regions behind a capability list in the config space's upper bytes (0x40–0xFF). Each capability points at an offset within a BAR where a specific structure lives (common config, ISR, notifications, device config). The capability list is how the device tells the OS "the common config is at BAR4 + 0x1000" rather than the OS having to guess.
