One UDP echo, from Mac to kernel and back

Follow one datagram through QEMU’s hostfwd rule, IPv4 protocol 17, port 5555, and the virtio TX/RX boundary.

Keep one datagram in view: a Mac UDP socket sends hello from lesson 25 to 127.0.0.1:5555. QEMU forwards that host port into the guest. The guest sees an IPv4 packet for 10.0.2.15, parses UDP protocol 17, selects destination port 5555, and echoes the same payload to the original source endpoint.

Use the forward and backward controls after each stage. The implementation sections below point to the code that owns each boundary.

      │  UDP payload: "hello from lesson 25"

      ▼

IPv4 → UDP

IPv4 header byte 9 carries protocol 17. The IPv4 total length bounds the bytes available to UDP.

UDP → endpoint

The destination port 5555 selects the Lesson 25 handler. The source port identifies where the reply goes.

UDP → payload

The UDP length includes its 8-byte header, so the payload is the slice 8..length.

driver → protocol

recv_frame consumes a virtio RX completion and recycles the DMA buffer. poll_rx hands stable parsed data upward.

Packet walk · stage 1 of 7

1 · The Mac sends one datagram

tests/test_udp.sh waits for the guest’s UDP syscall marker, then sends b"hello from lesson 25" to 127.0.0.1:5555. The host socket owns an ephemeral source port.

2 · QEMU moves the host port into the guest

The QEMU argument hostfwd=udp::5555-:5555 maps the Mac’s port 5555 to the guest’s port 5555. The guest’s network stack receives an Ethernet frame through virtio-net.

3 · IPv4 selects UDP

Ipv4Header::parse validates the 20-byte header and its total length. The protocol field is 17, so NetDevice::dispatch_frame sends the bounded IPv4 payload to UDP parsing.

4 · UDP validates the datagram

The declared UDP length is 28. It fits inside the IPv4 payload and leaves 28 − 8 = 20 payload bytes. The pseudo-header checksum binds the datagram to both IPv4 endpoints and protocol 17.

5 · Port 5555 selects the handler

handle_udp_packet compares the destination port with ECHO_PORT. A match enters the Lesson 25 echo path. Lesson 26 will introduce a socket table for this decision.

6 · The reply reverses endpoints

The reply uses guest source 10.0.2.15:5555, the received source IP and source port as its destination, and the same 20 payload bytes. send_udp rebuilds the checksum and passes protocol 17 to IPv4 TX.

7 · The Mac receives the echo

IPv4 and Ethernet travel through the virtio TX queue. QEMU reverses the hostfwd mapping, and the Python socket receives exactly the bytes it sent. The fixture returns to ring 3 and exits successfully.

Why does protocol 17 come before the port?

IPv4 and UDP own different headers. IPv4 can select the transport protocol from byte 9; only the UDP parser can read bytes 0–3 as source and destination ports.

25.5Port 5555 is a hardcoded Lesson 25 receiver

File: src/virtio.rs · handle_udp_packet around lines 1291–1326

After checksum validation, the dispatcher stores the datagram as UdpPacket and calls the kernel handler. The handler compares one constant: udp::ECHO_PORT, whose value is 5555.

src/virtio.rs:1291–1307destination-port demultiplexing and echo call
fn handle_udp_packet(&mut self, packet: &UdpPacket) {
    if packet.header.dst_port != udp::ECHO_PORT {
        println!("[udp] no receiver for destination port {}",
            packet.header.dst_port);
        return;
    }

    self.send_udp(
        packet.ip_header.src_ip,
        packet.header.src_port,
        udp::ECHO_PORT,
        packet.payload(),
    );
}

25.6The reply reverses both endpoint pairs

File: src/virtio.rs · send_udp around lines 1118–1140

For the received datagram, the guest sees source 10.0.2.2:ephemeral and destination 10.0.2.15:5555. The reply uses source 10.0.2.15:5555 and destination 10.0.2.2:ephemeral. QEMU maps that guest destination back to the Mac socket.

src/virtio.rs:1118–1140build UDP, select IPv4 protocol 17, hand off to existing TX
pub fn send_udp(
    &mut self,
    dst_ip: [u8; 4], dst_port: u16,
    src_port: u16, payload: &[u8],
) -> Option<()> {
    let mut datagram = [0u8; ETHERNET_MTU - IPV4_HEADER_LEN];
    let datagram_len = udp::write_datagram(
        &mut datagram, net::OUR_IP, dst_ip,
        src_port, dst_port, payload,
    )?;
    self.send_ipv4_packet(
        net::ipv4::PROTOCOL_UDP, dst_ip,
        &datagram[..datagram_len],
    )
}

send_ipv4_packet builds the IPv4 header, resolves the next-hop MAC through ARP, wraps the bytes in Ethernet, and calls send_frame. UDP stops at that IPv4 handoff.

25.7RX and TX cross the virtio driver boundary

File: src/virtio.rs · recv_frame, poll_rx, and send_frame around lines 817–995

RX starts with a completed descriptor. recv_frame reads the virtio header and Ethernet bytes from the DMA buffer, creates an owned Frame, and recycles the descriptor. The protocol dispatcher then copies the UDP payload into UdpPacket. TX takes the opposite route: protocol bytes become an Ethernet frame, a TX descriptor chain is submitted, and the queue is kicked.

pub fn poll_rx(&mut self) -> Option<NetRxEvent> {
    let frame = self.recv_frame()?;
    Some(self.dispatch_frame(&frame))
}
Why does the handler receive an owned payload array?

The virtio RX buffer is immediately recyclable. Copying the bounded UDP payload gives the echo handler bytes that remain valid while it builds the reply.
