6.1Parse the PCI capability list

Files touched: src/virtio.rs (new), src/main.rs

New src/virtio.rs module. The PCI capability list is a linked list of vendor-defined feature records living in the upper half of PCI config space (offsets 0x40–0xFF). virtio uses vendor-specific caps (cap_id=0x09) with a sub-header pointing at regions inside the device's BARs.

src/virtio.rs — VirtioCap struct and parse function (key part) 
pub struct VirtioCap {
    pub cfg_type: u8,   // 1=common, 2=notify, 3=ISR, 4=device, 5=PCI
    pub bar: u8,       // which BAR (0-5)
    pub offset: u32,    // offset within that BAR (bytes)
    pub length: u32,    // size of the region (bytes)
}

pub fn parse_virtio_capabilities(bus, device, func) -> Vec<VirtioCap> {
    // Read capabilities pointer at offset 0x34
    let mut cap_offset = pci::config_read(..., 0x34) & 0xFF as u8;

    while cap_offset != 0 {
        let word0 = pci::config_read(..., cap_offset);
        let cap_id = (word0 & 0xFF) as u8;
        let next_ptr = ((word0 >> 8) & 0xFF) as u8;

        if cap_id == 0x09 {  // vendor-specific
            let cfg_type = ((word0 >> 24) & 0xFF) as u8;
            let bar = pci::config_read(..., cap_offset + 4) & 0xFF;
            let offset = pci::config_read(..., cap_offset + 8);
            let length = pci::config_read(..., cap_offset + 12);
            // ...push VirtioCap...
        }
        cap_offset = next_ptr;  // follow linked list
    }
}

The linked-list walk: read the pointer at offset 0x34, follow next_ptr from each cap to the next, stop when next_ptr == 0. For vendor-specific caps (cap_id == 0x09), the sub-header at bytes 3-15 holds the virtio sub-type and the (BAR, offset, length) of the region.

The other three (ISR, device config, notifications) come into play later: ISR for interrupts (we'll poll instead), device config for sector size info, notifications for virtqueue kicks in Lesson 7.

6.2Map MMIO + reset/ACK/DRIVER

Files touched: src/memory.rs, src/pci.rs, src/virtio.rs, src/main.rs

Three new pieces: a way to map MMIO regions into kernel memory, a way to read BAR base addresses programmatically, and a VirtioBlk struct with the first phase of the handshake.

MMIO mapping helper

src/memory.rs — map_mmio: ensure an MMIO region is reachable 
pub fn map_mmio(phys_start: u64, size: u64) -> u64 {
    let offset = phys_offset();
    let virt_start = phys_start + offset;

    let aspace = AddressSpace::from_current();
    let flags = PageTableFlags::PRESENT
        | PageTableFlags::WRITABLE
        | PageTableFlags::NO_CACHE      // load-bearing for MMIO
        | PageTableFlags::NO_EXECUTE;

    // For each page in the range, map it if not already mapped
    for page in Page::range_inclusive(start_page, end_page) {
        if translate(page.start_address()).is_none() {
            unsafe { aspace.map_to(page.start_address(), current_phys, flags).unwrap(); }
        }
        current_phys += 4096;
    }
    virt_start
}

NO_CACHE is the load-bearing detail. Without it, the CPU might cache device register reads/writes — a stored read could return a stale value, a buffered write might not reach the device for microseconds. Device protocols assume every load/store hits the hardware immediately.

BAR base extraction

src/pci.rs — bar_base: decode a BAR's physical address 
pub fn bar_base(bus, device, func, bar_index) -> u64 {
    let bar = config_read(..., 0x10 + bar_index * 4);
    if bar & 0x1 == 1 {                       // I/O BAR
        (bar & !0x3) as u64
    } else {
        let type_bits = (bar >> 1) & 0x3;
        let base_low = (bar & !0xF) as u64;
        if type_bits == 0b10 {               // 64-bit memory BAR
            let bar_high = config_read(..., 0x10 + (bar_index + 1) * 4);
            base_low | ((bar_high as u64) << 32)
        } else {                                // 32-bit memory BAR
            base_low
        }
    }
}

Same decode logic as print_bars() from step 5.4, but returning the address as a number instead of printing it. The 64-bit case reads the next BAR slot for the high 32 bits.

The VirtioBlk struct and probe()

src/virtio.rs — VirtioBlk with common config mapped 
pub struct VirtioBlk {
    bus: u8, device: u8, func: u8,
    common_virt: u64,   // virtual address of common config region
}

impl VirtioBlk {
    pub fn probe() -> Option<Self> {
        let (bus, device, func) = pci::find_virtio_blk()?;
        let caps = parse_virtio_capabilities(bus, device, func);
        let common_cap = caps.iter().find(|c| c.cfg_type == 1)?;
        let common_bar_base = pci::bar_base(bus, device, func, common_cap.bar);
        let common_phys = common_bar_base + common_cap.offset as u64;
        let common_virt = crate::memory::map_mmio(common_phys, common_cap.length as u64);
        Some(Self { bus, device, func, common_virt })
    }

    // Volatile MMIO access
    fn read_common_u8(&self, offset: u8) -> u8 {
        unsafe { read_volatile((self.common_virt + offset as u64) as *const u8) }
    }
    // ...similar write_common_u8, read_common_u32, write_common_u32...
}

Volatile reads/writes are required for MMIO. Without read_volatile, the compiler might elide the load ("we read this byte two lines ago, return the cached value") or reorder it. Device registers have side effects; the access has to happen exactly when we say so.

The first handshake phase

src/virtio.rs — reset_and_acknowledge: reset, ACK, DRIVER 
pub fn reset_and_acknowledge(&self) {
    println!("[virtio]   device_status before reset: 0x{:02X}", self.read_status());

    self.write_status(0);                          // reset
    assert_eq!(self.read_status(), 0);

    self.write_status(STATUS_ACKNOWLEDGE);        // 0x01
    self.write_status(STATUS_ACKNOWLEDGE | STATUS_DRIVER);  // 0x03
}

Verification

— Boot serial output 
[virtio] common config: BAR4+0x0 = phys 0xFE000000 = virt 0x180FE000000

[virtio]   device_status after reset:  0x00
[virtio]   device_status after ACK:    0x01

The "before reset: 0x0F" is normal — SeaBIOS (QEMU's firmware) initialized the device to DRIVER_OK state during boot. The reset clears it; we then walk through the handshake cleanly.

6.3Feature negotiation — FEATURES_OK

Files touched: src/virtio.rs, src/main.rs

The most interesting phase. Device advertises what it can do; driver picks a subset it can use; both verify they agree.

src/virtio.rs — negotiate_features 
pub fn negotiate_features(&self) {
    // Read both halves of device features
    self.write_common_u32(COMMON_DEVICE_FEATURE_SELECT, 0);
    let device_features_low = self.read_common_u32(COMMON_DEVICE_FEATURE);
    self.write_common_u32(COMMON_DEVICE_FEATURE_SELECT, 1);
    let device_features_high = self.read_common_u32(COMMON_DEVICE_FEATURE);

    // Pick what we support: just VIRTIO_F_VERSION_1 (bit 32)
    let supported_low: u32 = 0;
    let supported_high: u32 = if device_features_high & 0x1 != 0 { 0x1 } else { 0 };

    // Write our subset
    self.write_common_u32(COMMON_DRIVER_FEATURE_SELECT, 0);
    self.write_common_u32(COMMON_DRIVER_FEATURE, supported_low);
    self.write_common_u32(COMMON_DRIVER_FEATURE_SELECT, 1);
    self.write_common_u32(COMMON_DRIVER_FEATURE, supported_high);

    // Set FEATURES_OK, then re-read to verify the device accepted
    self.write_status(STATUS_ACK | STATUS_DRIVER | STATUS_FEATURES_OK);
    let status = self.read_status();
    assert!(status & STATUS_FEATURES_OK != 0,
        "device rejected our features — FEATURES_OK was cleared");
}

The two-step "write FEATURES_OK then re-read to verify" is the most spec-mandated subtlety. If the device doesn't accept the proposed subset, it silently clears FEATURES_OK. Without the re-read, you'd proceed assuming features are agreed when they aren't.

Verification

— Boot serial output 
[virtio]   device features low:  0x30006E54  (full virtio-blk suite)
[virtio]   device features high: 0x00000101  (VIRTIO_F_VERSION_1 + 1 other)
[virtio]   driver features low:  0x00000000
[virtio]   driver features high: 0x00000001 (VIRTIO_F_VERSION_1)
[virtio]   device_status after FEATURES_OK: 0x0B

Device advertised a rich feature set (SEG_MAX, GEOMETRY, BLK_SIZE, FLUSH, DISCARD, WRITE_ZEROES, etc.). We accepted only VIRTIO_F_VERSION_1 (the modern-transport-required bit). The device accepted our minimal subset — 0x0B includes FEATURES_OK. Real Linux would claim more (flush for write persistence, discard for SSD TRIM) but for first read we keep it minimal.

Commit ab8ff4b. Wall-clock time: ~2 minutes.

6.4DRIVER_OK — device is live

Files touched: src/virtio.rs, src/main.rs

The final "go" bit. After DRIVER_OK, the device is in operational state and ready for virtqueue setup.

src/virtio.rs — set_driver_ok 
pub fn set_driver_ok(&self) {
    self.write_status(
        STATUS_ACKNOWLEDGE | STATUS_DRIVER |
        STATUS_FEATURES_OK | STATUS_DRIVER_OK
    );  // 0x0F

    let status = self.read_status();
    assert!(status & STATUS_FAILED == 0, "device FAILED");
    assert!(status & STATUS_DEVICE_NEEDS_RESET == 0, "device needs reset");
    assert!(status & STATUS_DRIVER_OK != 0, "DRIVER_OK didn't stick");
    println!("[virtio] device is live — ready for virtqueue setup");
}

Three assertions catch the failure modes: FAILED (guest gave up somewhere), DEVICE_NEEDS_RESET (device hit an internal error), DRIVER_OK didn't stick (device rejected operational state for some reason).

Verification

— Boot serial output 
[test] virtio handshake phase 3 — DRIVER_OK (6.4)
[virtio]   device_status after DRIVER_OK: 0x0F
[virtio] device is live — ready for virtqueue setup

0x0F = ACKNOWLEDGE (0x01) | DRIVER (0x02) | FEATURES_OK (0x08) | DRIVER_OK (0x04). All four handshake bits set, no FAILED. Device is in operational state.

At this point the device accepts virtqueue configuration (Lesson 7). Doing actual I/O (Lesson 8) requires queues to be set up first — the device won't accept work requests from an unconfigured queue.

Commit d5f03d3. Wall-clock time: ~1 minute. Lesson 6 complete — the device is initialized, ready for virtqueues.
