Code Tour — ELF Header Parser

The bridge from "file of bytes" to "loadable program." A new src/elf.rs module parses the 64-byte ELF header and 56-byte program headers, validates them, and confirms the entry point sits inside an executable segment.

Steps done 15.1 – 15.4 (complete) Commits fb36235 → f480577

Lesson 15 is the second-to-last step of the mission. Lessons 1–14 built the path from "block on disk" to "file in VFS." Lesson 15 turns that file into a structured description the kernel can actually execute — and Lesson 16 maps its segments and jumps to entry, completing exec().

The conceptual unlock: code can't be relocated because addresses are baked into the instruction bytes themselves. ELF exists to carry the map saying "these bytes go to this virtual address, with these permissions." Once that lands, the parser itself is mechanical — same shape as the ext2 superblock parser.

15.1Cross-compile a tiny ELF onto the disk

File: scripts/make-disk.sh

The disk image needed a real ELF on it. rustc compiles a 4-line freestanding program for the bare-metal x86-64 target, then debugfs writes it into the ext2 filesystem alongside hello.txt.

scripts/make-disk.sh— the 4-line Rust source compiled into /hello.elf
#![no_std]
#![no_main]
#[no_mangle]
pub extern "C" fn _start() -> ! { loop {} }
#[panic_handler]
fn panic(_: &core::panic::PanicInfo) -> ! { loop {} }

Two rustc flags matter. --target x86_64-unknown-none produces a bare-metal ELF (no host OS ABI). -C relocation-model=static forces ET_EXEC (fixed addresses) instead of the default ET_DYN (position-independent). Lesson 16 won't handle dynamic relocations; ET_EXEC lets us skip that.

The script sanity-checks via file before writing, so a future toolchain regression fails loudly at make-disk time rather than mysteriously at boot time.

15.2ElfHeader struct + 64-byte parser

File: src/elf.rs (new, 165 lines)

A new kernel module. Constants for every value we validate against, then a struct modeling every load-bearing field of Elf64_Ehdr at its spec-mandated offset.

src/elf.rs— the constants and the header struct
pub const ELF_MAGIC: [u8; 4] = [0x7F, 0x45, 0x4C, 0x46]; // 0x7F 'E' 'L' 'F'
pub const ELFCLASS64:   u8  = 2;
pub const ELFDATA2LSB:  u8  = 1;
pub const ET_EXEC:      u16 = 2;
pub const ET_DYN:       u16 = 3;
pub const EM_X86_64:    u16 = 0x3E;

pub struct ElfHeader {
    pub class: u8,           // 2 = 64-bit
    pub data:  u8,          // 1 = little-endian
    pub version: u8,
    pub osabi: u8,
    pub e_type: u16,         // 2 = ET_EXEC
    pub machine: u16,        // 0x3E = x86-64
    pub entry: u64,           // jump target after loading
    pub phoff: u64,           // file offset of program header table
    pub shoff: u64,           // ignored — sections are a linker concern
    pub flags: u32,
    pub ehsize: u16,
    pub phentsize: u16,      // 56 for ELF64
    pub phnum: u16,
    pub shentsize: u16,
    pub shnum: u16,
    pub shstrndx: u16,
}

The parser mirrors Superblock::parse from Lesson 10: closure-based u16_at / u32_at / u64_at helpers reading via from_le_bytes, with magic check up front and Option-typed failure.

src/elf.rs— the one-line validation helper Lesson 16 will lean on
pub fn is_x86_64_exec(&self) -> bool {
    self.class    == ELFCLASS64
        && self.data     == ELFDATA2LSB
        && self.e_type   == ET_EXEC
        && self.machine  == EM_X86_64
}

Wired in via mod elf; in src/main.rs.

15.3ProgramHeader struct + 56-byte parser

File: src/elf.rs (+114 lines)

Same file, second struct. Constants for the p_type values we recognize and the p_flags permission bits.

src/elf.rs— the PT_* / PF_* constants
// p_type — only PT_LOAD causes memory mapping
pub const PT_LOAD:      u32 = 1;
pub const PT_DYNAMIC:   u32 = 2;  // dynamic-link table (for ld.so)
pub const PT_INTERP:    u32 = 3;  // path to dynamic linker
pub const PT_NOTE:      u32 = 4;  // build-id, ABI hints
pub const PT_PHDR:      u32 = 6;  // the PHT itself, as a segment
pub const PT_GNU_STACK: u32 = 0x6474E551;  // stack-permission hint

// p_flags — permission bits
pub const PF_R: u32 = 0x4;
pub const PF_W: u32 = 0x2;
pub const PF_X: u32 = 0x1;

The struct models all 8 fields of Elf64_Phdr. Parser uses the same closure pattern as ElfHeader::parse.

src/elf.rs— three helpers for the Lesson 16 loader and for printing
pub fn is_load(&self) -> bool { self.p_type == PT_LOAD }

pub fn perms_str(&self) -> &'static str {
    let (r, w, x) = (
        self.p_flags & PF_R != 0,
        self.p_flags & PF_W != 0,
        self.p_flags & PF_X != 0,
    );
    match (r, w, x) {
        (true,  false, true ) => "r-x",
        (true,  true,  false) => "rw-",
        // ... 6 more arms
        _ => "???",
    }
}

pub fn type_str(&self) -> &'static str { /* LOAD / DYN / INTRP / NOTE / PHDR / GSTK / OTHER */ }

15.4Parse /hello.elf via VFS + verify structure

File: src/main.rs (+65 lines)

The test block sits after Lesson 14's mount. It uses the existing VFS path — no special ELF I/O — so the bytes flow resolve_path → read_file → ext2 → virtio-blk → disk. The ELF parser sees an opaque Vec<u8>.

src/main.rs— the dispatch: VFS hands bytes to the ELF parser
let elf_inode = fs::resolve_path("/hello.elf").expect("should resolve");
let bytes = elf_inode.data.lock();
let header = elf::ElfHeader::parse(&bytes).expect("magic check");
assert!(header.is_x86_64_exec());

for i in 0..header.phnum {
    let off = header.phoff as usize + i as usize * header.phentsize as usize;
    let ph = elf::ProgramHeader::parse(&bytes[off..]).expect("ph parse");
    // ... print + count PT_LOADs
}

// Entry-point sanity check
let entry_in_r_x = (0..header.phnum).map(|i| { /* ... */ })
    .any(|ph| ph.is_load() && ph.p_flags & elf::PF_X != 0
              && header.entry >= ph.p_vaddr
              && header.entry <  ph.p_vaddr + ph.p_memsz);
assert!(entry_in_r_x, "entry not inside any r-x PT_LOAD");

Two assertions deserve explanation. The directory-walk assertion bumped from 5 to 6 entries (hello.elf joined the root). The entry-point assertion checks something subtle: the address in e_entry must actually fall inside a mapped executable segment. If the linker produced a binary where the entry pointed at non-code, jumping there would crash. Catching it at load time beats a page-fault in user mode.

The two ★ rows are what Lesson 16 maps. [1] is the rodata segment — 388 bytes starting at file offset 0, landing at 0x200000 with read-only permission. Note this segment includes the ELF header and PHT themselves — common for static binaries, since the linker lays them out together. [2] is the code segment — 4 bytes (just _start: jmp .) at 0x201190 with read+execute permission, and that address matches e_entry.

What was removed / changed

  • Directory-walk assertion in main.rs bumped from 5 to 6 entries (hello.elf joined the ext2 root).
  • scripts/make-disk.sh now requires rustup target add x86_64-unknown-none; the script checks and errors out clearly if missing.

Nothing in the existing kernel was rewritten. The Lesson 14 VFS / mount design paid off here: the ELF parser doesn't know about ext2 or virtio-blk — it consumes a Vec<u8>, which is what resolve_path already returned. Clean layering.
