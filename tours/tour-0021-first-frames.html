Code Tour - First Frames on the Wire

Build one ARP request, send it through TX queue 1, read slirp's ARP reply from RX queue 0, and put the filled RX buffer back into service.

Files src/net/ethernet.rs, src/virtio.rs, src/main.rs Test tests/test_virtio_net_frames.sh

Lesson 21 turns the initialized network card into a tiny raw-frame device. The kernel can hand it Ethernet bytes to send and can ask whether a received Ethernet frame is waiting. 

EthernetHeader builds 14 bytes
NetDevice builds a 42-byte ARP request
virtio-net prepends a 12-byte zero header
TX queue 1 sends the frame
RX queue 0 returns slirp's ARP reply
recv_frame strips the 12-byte header
the RX descriptor goes back into the avail ring

21.1Add the Ethernet header helper

File: src/net/ethernet.rs

Ethernet starts with 14 bytes: destination MAC, source MAC, and EtherType. The helper keeps byte order in one place. EtherType uses big-endian bytes on the wire, so ARP appears as 08 06.

src/net/ethernet.rsparse and build
let ethertype = u16::from_be_bytes([buf[12], buf[13]]);

out[0..6].copy_from_slice(&self.dst);
out[6..12].copy_from_slice(&self.src);
out[12..14].copy_from_slice(&self.ethertype.to_be_bytes());

Later ARP, IPv4, ICMP, and UDP code can use this same header helper.

21.2Build a small NetDevice surface

File: src/virtio.rs

NetDevice owns the initialized VirtioNet. Callers see three useful methods: read the MAC, send a raw frame, and receive one raw frame if the RX ring has a completion.

src/virtio.rspublic shape
pub struct NetDevice {
    inner: VirtioNet,
}

pub fn mac(&self) -> [u8; 6]
pub fn send_frame(&mut self, eth_frame: &[u8])
pub fn recv_frame(&mut self) -> Option<Frame>

The queues, descriptor indices, and 12-byte virtio header stay inside this layer.

21.3Send the ARP request

Files: src/virtio.rs, src/main.rs

The request asks the virtual gateway, 10.0.2.2, for its MAC address. The destination MAC is broadcast because the kernel begins without knowing the gateway's hardware address.

src/virtio.rsARP request bytes
dst MAC      ff:ff:ff:ff:ff:ff
src MAC      52:54:00:12:34:56
EtherType    0x0806
sender IP    10.0.2.15
target IP    10.0.2.2

send_frame allocates two DMA buffers. The first holds the 12 zero bytes required by virtio-net. The second holds the 42-byte Ethernet frame.

src/virtio.rsTX descriptor chain
desc[head] = virtio_net_hdr, len 12, F_NEXT
desc[tail] = Ethernet frame, len 42

submit head to TX queue 1
kick queue 1
poll TX used ring for completion

21.4Receive and parse the reply

File: src/virtio.rs

The RX queue was stocked in Lesson 20. When slirp answers, the device fills one posted buffer and writes its descriptor id to the used ring. recv_frame maps that id back to the saved buffer.

src/virtio.rsRX buffer layout
bytes 0..12      virtio_net_hdr
bytes 12..26     Ethernet header
bytes 26..       payload

The parser skips the first 12 bytes, parses the 14-byte Ethernet header, copies up to 1500 payload bytes into a Frame, and prints the line that proves the reply came from slirp.

serial outputfirst RX proof
[net] RX ethertype=0x0806 src=52:55:0a:00:02:02 dst=52:54:00:12:34:56 payload_len=50

21.5Recycle the RX buffer

File: src/virtio.rs

The used descriptor goes straight back to the RX avail ring after parsing. The buffer keeps its address, length, and F_WRITE flag. Re-posting the descriptor restores the receive supply.

src/virtio.rsrecycle path
zero the filled buffer
submit the same descriptor id to RX avail
kick RX queue 0

The serial line includes the ring counters so you can see the supply move forward after the first frame.

Where to Ask Questions

Good follow-ups: why TX uses two descriptors, why RX skips exactly 12 bytes, why the gateway MAC is 52:55:0a:00:02:02, or how Lesson 22 will turn the ARP bytes into fields.

Practice

Say the path out loud: build Ethernet, prepend virtio header, submit TX, poll RX, strip virtio header, recycle descriptor.
