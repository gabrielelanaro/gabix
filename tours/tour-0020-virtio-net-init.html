Code Tour - Wake the Network Card

The card moves from PCI-visible to driver-owned: features accepted, MAC read, queues enabled, RX buffers posted.

Files src/virtio.rs, src/main.rs Test tests/test_virtio_net_init.sh

Lesson 20 is the setup step before packets. The kernel gives the device two queues and a small pile of empty receive buffers, then sets DRIVER_OK. 

probe virtio-net
map common config, notifications, device config
negotiate VERSION_1 + NET_F_MAC
read MAC from device config
configure RX queue 0 and TX queue 1
post 8 empty RX buffers
set DRIVER_OK

20.1Add a network-device driver shell

File: src/virtio.rs

VirtioNet stores the same common pieces as the block driver: PCI location, common config, notification registers, and queues. It also stores the device-config region, the MAC address, and the RX buffers.

src/virtio.rsdriver state
pub struct VirtioNet {
    common_virt: u64,
    notify_virt: u64,
    device_config_virt: u64,
    mac: [u8; 6],
    rx_queue: Option<VirtQueue>,
    tx_queue: Option<VirtQueue>,
    rx_buffers: Vec<RxBuffer>,
}

The device-config region is the new mapped region. That is where the MAC address lives.

20.2Negotiate the small feature set

File: src/virtio.rs

The network driver asks for two bits: modern virtio transport and a valid MAC address in device config. Every offload stays disabled.

src/virtio.rsfeature subset
let supported_low = VIRTIO_NET_F_MAC;
let supported_high = 0x1; // VIRTIO_F_VERSION_1

write_driver_features(low = 0x00000020, high = 0x00000001);
set_status(ACKNOWLEDGE | DRIVER | FEATURES_OK);

The test checks that FEATURES_OK sticks before the driver touches queues.

20.3Read the MAC

File: src/virtio.rs

Once NET_F_MAC is accepted, the first six bytes of device config are the card address. QEMU gives this guest 52:54:00:12:34:56.

src/virtio.rsdevice config read
for (i, byte) in mac.iter_mut().enumerate() {
    *byte = read_volatile((device_config_virt + i as u64) as *const u8);
}

20.4Enable RX and TX queues

File: src/virtio.rs

The block driver needed one queue. The network driver configures queue 0 for receive and queue 1 for transmit. Both use the existing VirtQueue memory layout from Lesson 7.

src/virtio.rsqueue setup
let rx_queue = VirtQueue::new(64);
configure_queue_at(0, &rx_queue, "RX");

let tx_queue = VirtQueue::new(64);
configure_queue_at(1, &tx_queue, "TX");

20.5Post eight empty RX buffers

File: src/virtio.rs

Each RX buffer gets one descriptor with F_WRITE, because the device writes received bytes into memory owned by the kernel. The driver publishes all eight descriptors before DRIVER_OK.

src/virtio.rsreceive supply
desc.addr = buffer_phys;
desc.len = 2048;
desc.flags = VIRTQ_DESC_F_WRITE;

rx_queue.submit_chain(desc_idx);

The current implementation allocates one 4 KiB frame per 2048-byte RX buffer. That wastes half a page per buffer and keeps the bookkeeping simple for the first receive path.

Where to Ask Questions

Good follow-ups: why RX buffers must exist before DRIVER_OK, why queue 0 and queue 1 have opposite directions, or why the MAC is read from device config instead of hardcoded.
