2ICMP owns eight header bytes

File: src/net/icmp.rs

This module writes and reads the ICMP format. It receives a byte slice whose end is already known from IPv4. The checksum covers the complete slice.

src/net/icmp.rswrite the request, then checksum the whole ICMP message
fn write_echo(/* ... */) -> Option<usize> {
    let message_len = ECHO_HEADER_LEN.checked_add(payload.len())?;
    out[0] = message_type;       // 8 for request, 0 for reply
    out[1] = ECHO_CODE;          // 0 for echo
    out[4..6].copy_from_slice(&identifier.to_be_bytes());
    out[6..8].copy_from_slice(&sequence.to_be_bytes());
    out[ECHO_HEADER_LEN..message_len].copy_from_slice(payload);
    let checksum = checksum::internet_checksum(&out[..message_len]);
    out[2..4].copy_from_slice(&checksum.to_be_bytes());
    Some(message_len)
}

For this request, the helper returns 15: eight ICMP header bytes plus seven payload bytes. Binary data has no terminator.

Where does the receiver learn that the ICMP message is 15 bytes long?

IPv4 says the complete packet is 35 bytes. Its 20-byte header leaves a 15-byte IPv4 payload, which is the complete ICMP message.

3The syscall gives ICMP bytes to the existing IPv4 path

File: src/syscall.rs

The syscall selects IPv4 protocol 1, the QEMU gateway, and the exact ICMP byte slice. Lesson 23 then builds IPv4, resolves ARP, creates Ethernet, and submits to virtio.

src/syscall.rsrequest values and handoff to IPv4
const IDENTIFIER: u16 = 0x2400;
const FIRST_SEQUENCE: u16 = 7;
const REQUEST_COUNT: u16 = 4;
const PAYLOAD: &[u8] = b"mini-os";

for sequence in FIRST_SEQUENCE..FIRST_SEQUENCE + REQUEST_COUNT {
    let ttl = ping_gateway_once(device, IDENTIFIER, sequence, PAYLOAD)?;
    println!("[icmp] reply id=0x{:04x} seq={} ttl={}",
        IDENTIFIER, sequence, ttl);
}
What makes this an ICMP packet to IPv4?

PROTOCOL_ICMP is 1. IPv4 writes it into header byte 9. The receive path reads that same byte before it gives payload bytes to ICMP.

4RX preserves the IPv4 boundary

File: src/virtio.rs

Virtio RX buffers are recycled after dispatch. The event carries a parsed IPv4 header plus an owned copy of exactly the IPv4 payload, giving ICMP stable bytes after the device buffer is returned.

src/virtio.rspacket supplied to upper protocols
pub struct Ipv4Packet {
    pub header: Ipv4Header,
    payload: [u8; ETHERNET_MTU - IPV4_HEADER_LEN],
    payload_len: usize,
}

impl Ipv4Packet {
    pub fn payload(&self) -> &[u8] {
        &self.payload[..self.payload_len]
    }
}
src/virtio.rscopy exactly the bytes defined by IPv4 total length
let payload_len = header.payload_len();
let ip_payload = &frame.payload[
    IPV4_HEADER_LEN..IPV4_HEADER_LEN + payload_len
];
let mut payload = [0u8; ETHERNET_MTU - IPV4_HEADER_LEN];
payload[..payload_len].copy_from_slice(ip_payload);
Why does ICMP use the IPv4 length instead of the Ethernet-frame length?

Ethernet can include padding. IPv4’s total length defines the end of the IP packet, so it is the authoritative boundary for the ICMP message.

5A reply earns success through matching

Files: src/net/icmp.rs, src/syscall.rs

Parsing rejects a short message or a bad checksum. The matching rule then checks reply type, code, identifier, sequence, and payload. The syscall separately requires IPv4 protocol 1 and source address 10.0.2.2. It completes each sequence before sending the next.

src/net/icmp.rsparse and match the pending request
pub fn parse(bytes: &[u8]) -> Option<EchoMessage> {
    if bytes.len() < ECHO_HEADER_LEN { return None; }
    if checksum::internet_checksum(bytes) != 0 { return None; }
    Some(EchoMessage {
        message_type: bytes[0], code: bytes[1],
        identifier: u16::from_be_bytes([bytes[4], bytes[5]]),
        sequence: u16::from_be_bytes([bytes[6], bytes[7]]),
        payload: &bytes[ECHO_HEADER_LEN..],
    })
}

pub fn is_reply_to(&self, id: u16, seq: u16, payload: &[u8]) -> bool {
    self.message_type == ECHO_REPLY && self.code == ECHO_CODE
        && self.identifier == id && self.sequence == seq
        && self.payload == payload
}
Which check rejects a reply with sequence 8 when the request used sequence 7?

The conversation match. Identifier groups a ping owner; the sequence distinguishes that owner’s individual requests.

6The receive path can answer an echo request too

Files: src/virtio.rs, src/net/icmp.rs

When an ICMP type-8 request arrives for mini-os, the IPv4 handler rebuilds a type-0 reply with the same conversation fields and sends it to the original IPv4 source.

src/virtio.rsinbound echo-request branch
if request.message_type == net::icmp::ECHO_REQUEST
    && request.code == net::icmp::ECHO_CODE
{
    let reply_len = net::icmp::write_echo_reply(
        &mut reply, request.identifier,
        request.sequence, request.payload,
    ).expect("maximum IPv4 payload fits in an Ethernet frame");
    self.send_ipv4_packet(
        net::ipv4::PROTOCOL_ICMP, header.src_ip, &reply[..reply_len],
    );
}

QEMU slirp makes the guest-initiated ping the reliable end-to-end proof. The boot-level wire test verifies the request-to-reply transformation directly.
